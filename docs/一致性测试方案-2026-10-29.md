## 一、链路分解与覆盖判定

### 1.1 链路的八个段落

一段代码从实体声明走到用户拿到的对象，经过八段。每一段的失败方式不同，可观测点也不同。

| 段 | 内容 | 失败表现 | 可观测点 |
|----|------|----------|----------|
| P1 | 实体注解 → 元数据 | 形状识别错、列名映射错 | 生成物、`PalORM_Runtime` |
| P2 | 元数据 → DDL 与固定 CRUD SQL | SQL 文本形态错、约束未建立 | 生成物字符串、库内约束行为 |
| P3 | 查询 API → 运行期 SQL 拼装 | 条件丢失、优先级错 | `AsDryRun()`、`ToSql()` |
| P4 | SQL → 驱动参数绑定 | 参数序错位、类型不匹配 | 驱动异常、写入后的行内容 |
| P5 | 驱动 → 数据库解析与执行 | 方言语法错、计划退化 | 执行异常、`EXPLAIN` |
| P6 | 结果集 → 物化 | 列序错位、类型截断 | 返回对象的属性值 |
| P7 | 物化 → 应用语义（过滤、租户、软删、分页） | 过滤被绕过、划分不完整 | 结果集与集合关系 |
| P8 | 会话、事务、池、缓存、路由、取消 | 状态泄漏、串租、缓存脏读 | 归还后的会话行为、池计数 |

前七段由数据本身的可观测差异判定，第八段没有"正确的数据"可比，只能靠状态不变量判定。这个区别决定了后面的分层。

### 1.2 既有防线（六条）

| 防线 | 位置 | 锁住什么 | 锁不住什么 |
|------|------|----------|-----------|
| 编译期诊断（46 条 `PALORMxxx`，口径 = 43 条分析器 + 3 条生成器 PALORM041/045/046） | `src/PalORM.SourceGen/` | 实体形状非法、注解冲突、标识符含控制字符 | 运行期拼装出的条件语义 |
| 生成物快照（22 份，2026-10-29） | `test/PalORM.SourceGen.Tests/Snapshots/` | 生成物字节级形态 | 绑定代码与 SQL 占位符是否真的对齐。唯一的产物级列序断言只覆盖 UPDATE（`BindUpdateColumnOrderTests`，1 条），INSERT、DELETE 与批量族没有同类检查 |
| 三方言对称性 | `test/PalORM.SourceGen.Tests/DialectSymmetryTests.cs` | 未登记的方言差异（生成物文本层） | 值与边界行为、执行后的结果 |

### 1.3 五条结构性限制

这五条决定了任何单一套件都做不到"保持正确"，也是四层防线的存在理由。

| 编号 | 限制 | 后果 | 哪层缓解 | 能否消除 |
|------|------|------|----------|----------|
| X1 | 采样不完备：输入空间无限，用例有限 | 零缺陷只说明样本内没有 | A 层固定网格加 D 层随机扩展 | 不能，只能声明边界 |
| X2 | oracle 可能错：手写 SQL 也是人写的 | 两侧同错时判通过 | A 层模板全量评审、L6 跨方言互比、变形关系交叉 | 压低概率，不能归零 |
| X3 | 共享层缺陷不可见：两侧共用驱动、注解、物化器 | 对照失焦 | B 层按契约断言；A 层强制手写侧走裸 ADO 读字典 | 换判据后可见 |
| X4 | 规格缺失：契约没写死就没有"歧义"可测 | 测出来的只是与某个参照实现一致 | B 层把契约写下来并逐条断言 | 可以，这是 B 层的全部目的 |
| X5 | 静态缓存跨用例泄漏：`CapabilityProbeCache`、`UpsertShapeCache`、`CacheStore.Default` 是进程级状态 | 前一个用例的能力探测结果或缓存条目污染后一个用例，且不出现在断言里 | A 层每场景新会话；C 层 I1/I5 显式测；关键静态缓存用例前置重置 | 可以，但必须在用例编排里显式处理 |

X5 来自本项目已发生过的两类事故：MySQL `local_infile` 探测缓存被某个用例置 OFF 后，同一进程内其余批量写全部静默降级且测试仍绿；`UpsertShapeCache` 的键漏了会话态，导致结果依赖预热顺序。任何"进程内共享的可变量"都是这一类。

### 1.4 需求到判据的映射

| 需求原话 | 落成什么 | 由哪层判定 |
|----------|----------|-----------|
| 从 C# 到生成的 SQL | P1 到 P3 的正确性 | 既有快照与对称性，A 层 L1/L2 |
| 到执行完返回的数据 | P4 到 P7 的正确性 | A 层 L2/L3/L4/L6 |
| 不会有歧义 | 每个操作的语义有书面条目且可执行 | B 层 |
| 整个链条可预期 | 同一输入在任意会话状态下得到同一结果 | C 层 |
| 可判断 | 判据自身可被证伪，覆盖边界可量化 | L0 六探针加 §4.8 产品侧变异回放 |

交付判据用三句话表述：已定义行为有清单；每次改动对清单全绿；新增行为必须同时新增清单项。这是可交付的目标，"保持正确"不可证，不作为目标。

## 二、设计原则

1. **期望值必须独立**。手写 SQL 侧与裸 ADO 侧硬编码表名与列名，不复用 `PalORM_Runtime`、`AsDryRun()`、`ToSql()`、`[Column]` 注解的任何值。允许的期望来源只有三种：手写 SQL、裸 ADO 读出的行、集合论不变量。用被测实现自己的输出当期望值等于自证。
2. **判定看行为不看文本**。两侧在真库执行后比较结果集与受影响行数。SQL 文本只用于失败时定位原因，不参与判定。
3. **判据必须能被证伪**。证伪分两侧：oracle 侧（改手写 SQL、改比较器、改断言）证明判据会响；产品侧（回退历史修复、打乱绑定列序）证明判据对真实缺陷敏感。两侧都红，判据才算可用。
4. **期望值按成本分层**。手写 SQL 是最贵的 oracle，用集合关系、路径等价关系与跨方言互比承担体量，手写 SQL 只做锚点。
5. **契约先于断言**。B 层每条断言必须指向一条已登记的契约条目，断言消息带条目 ID。没有契约条目的断言属于个人偏好，不进套件。
6. **每层独立记账**。四层各有自己的覆盖率与缺陷分类，不合并成一个总分。总分掩盖空白，分层记账暴露空白。
7. **判据对产品侧敏感**。每条判据配一个产品侧变异（回退历史修复或打乱绑定）。产品侧变异杀不掉的判据，与不报红的判据同等无效。

## 三、四层防线总览

### 3.1 分层对照

| 层 | 名称 | 测什么 | 主判据 | oracle 成本 | 执行频率 |
|----|------|--------|--------|-------------|----------|
| A | 一致性 | P2 到 P7 的等价性：生成的 SQL 执行后与手写 SQL 一致 | 结果集、影响行数、跨方言结果 | 81 个手写 SQL 骨架加零成本的关系判据 | 每轮 |
| B | 契约 | P1 到 P8 的语义符合性：返回值、错误、边界与文档承诺一致 | 契约条目断言 | 文档即规格，无额外 oracle | 每轮 |
| C | 状态 | P8 的状态不变量：会话、事务、池、缓存、路由、取消、熔断 | 状态机转移断言与不变量 | 不变量，无需数据对照 | 每轮（短程） |
| D | 随机化 | A 层网格之外的输入空间 | 复用 A 层判据 | 零额外 oracle | 夜间 |

| 段 | A 一致性 | B 契约 | C 状态 | D 随机化 |
|----|:---:|:---:|:---:|:---:|
| P1 注解到元数据 | 间接 | 直接 | | |
| P2 元数据到固定 SQL | 直接 | | | |
| P3 查询到拼装 SQL | 直接 | 直接 | | 直接 |
| P4 SQL 到绑定 | 直接 | | | 直接 |
| P5 驱动到执行 | 直接 | 直接 | | 直接 |
| P6 结果到物化 | 直接 | 直接 | | 直接 |
| P7 物化到应用语义 | 直接 | 直接 | | 直接 |
| P8 会话到状态 | | 直接 | 直接 | |

八段全部有归属，没有空白段。P2 段在 v5 之前只是"间接"（靠场景能否跑通），v5 补 DDL 语义断言族后变为直接。

### 3.3 四层各自回答什么

A 层回答"生成的 SQL 执行后是否与一条直白的等价 SQL 得到同样的数据"。它最贴近用户直觉，也最容易扩展规模。

B 层回答"这个操作承诺了什么，实际做到了没有"。它管的是语义与错误，A 层看不到。文档里写着的方法在源码里不存在（历史上出现过 `OrderByDescending` 长期只存在于文档），A 层一条都测不到。

C 层回答"同一段代码在不同的会话状态下会不会给出不同结果"。它管的是可重复性，前两层都在干净会话上跑，天然测不到状态污染。

D 层回答"网格外的输入会不会翻车"。它管的是覆盖面，用随机化把 A 层的判据放大到网格之外。

## 四、A 层：一致性防线

### 4.1 判据分级

| 层 | 判据 | 由谁判定 | 能发现 | 盲区 | 每轮 |
|----|------|----------|--------|------|------|
| L0 变异探针 | 故意注入的错误必须被抓到（oracle 侧四个 + 产品侧两个） | 套件自检 | 判据失效 | 元判据自身失效只能人工复核 | 是 |
| L1 语法 | SQL 在目标库执行不报错 | 数据库 | 方言语法、引用符、类型错误 | 一切静默错误 | 是（随 L2 附带） |
| L2 行为对照 | 两侧结果集与受影响行数相等 | 规范化比较器 | 参数错位、过滤缺失、列序错乱、类型映射错误 | 两侧同时写错 | 是 |
| L3 业务语义 | 显式断言（幂等、二次执行、跨租户不覆盖） | 手写断言 | 业务语义违背 | 未被断言覆盖的语义 | 是 |
| L4 默认过滤不变式 | 有效集与已删集各自等于裸 ADO 期望集 | 集合运算 | 隐式过滤被绕过或漏加 | 单条 SQL 内部的条件写错 | 是 |
| L5 执行计划 | 索引命中布尔断言（SQLite `USING INDEX` 或 `USING COVERING INDEX` 出现；PG 存在 `Index Scan` 节点；MySQL `key` 列非 NULL） | 计划字段匹配 | 全表扫描、隐式类型转换 | 命中错误索引或回表过多 | 否，抽样 5% |
| L6 跨方言等价 | 同一场景在三方言的主键集合与列值相等 | 规范化比较器（限可比类型） | 某方言生成语义偏离、手写模板在某方言写错 | 三方言同错；不可比类型 | 是（限可比类型） |

L2 是主判据；L1 随 L2 免费附带；L3 只用于 L2 表达不了的场景；L5 单独抽样，不进每轮；L6 是 v5 新增，见 §4.9。

L5 的 SQLite 形态要同时匹配 `USING INDEX` 与 `USING COVERING INDEX` 两种文本，后者在 3.x 后期版本才出现，只匹配前者会让覆盖索引场景全部报红。

**实施状态（2026-10-29）**：三方言各两条抽样（唯一索引查找、复合索引前缀查找），实测六项全绿。一个必须注意的前提：单行表上三个规划器都会选全表扫描，插 1000 行并 `ANALYZE` 之后索引命中断言才有意义；MySQL 的判据取 `EXPLAIN` 结果集的 `key` 列非空，SQLite 取 `EXPLAIN QUERY PLAN` 文本含 `USING`，PG 取 `EXPLAIN` 文本含 `Index`。

### 4.2 双侧对照

差分测试（differential testing）指同一功能用两套独立实现跑同一输入再比较结果。本方案的两侧是 PalORM API 与手写 SQL。

场景表只携带"做什么"和"用什么值"，不携带委托。原因是 `DataSession<TProvider>` 是 sealed 泛型类，没有非泛型基接口（`src/PalORM.Core/DataSession.Crud.cs:7`），把会话类型写进 `Func<...>` 会让场景锁死在单一方言。

```csharp
internal sealed record Scenario(
    string Id,                     // "bulk-update/tenant/string-key/batch-7"
    EntityShape Shape,             // 决定用哪个测试实体
    OperationKind Op,              // 27 个操作之一
    ValueSample Values,
    ConditionKind[] Conditions,
    ComparisonProfile Profile);    // 该场景允许的比较宽严

internal sealed record SideResult(
    IReadOnlyList<IReadOnlyDictionary<string, object?>> Rows,
    int AffectedRows,
    string Sql);                   // 仅在失败时打印

// 执行器一：泛型分派，同一份场景表跑三个 Provider
internal static ValueTask<SideResult> RunPalormAsync<TProvider>(
    DataSession<TProvider> db, Scenario s) where TProvider : IDbProvider;

// 执行器二：手写 SQL 侧按 (Op, 方言) 取 81 个骨架之一，绑定同一份 Scenario 的值
internal static ValueTask<SideResult> RunSqlAsync(DbConnection conn, Scenario s);
```

代价是执行器里有一个 27 分支的 switch，收益是场景表与方言解耦，不需要为三个 Provider 各写一遍场景体。

六条硬约束：

| 约束 | 理由 |
|------|------|
| 手写 SQL 用最直白的写法，不加优化 | 手写 SQL 自己写错是这类测试的头号风险 |
| 两侧各用独立会话与连接 | 共享会话会因事务、临时表、连接状态互相污染 |
| 手写侧必须用裸 ADO 读成字典，禁止 `From<T>()`、`RowFactory`、`AsDryRun()`、`PalORM_Runtime` | 手写侧若走 PalORM 的物化器，`RowFactory` 序号错会在两侧同错，L2 与 X3 同时失效。这是 v5 补的：原方案的 `SideResult` 类型暗示了字典，但没有把这条写成约束 |
| 写场景两侧各用一张同构表（后缀 `_p` / `_s`），只读场景共用一张 | 独立会话不等于数据隔离：同一张表上先跑的一侧会污染后跑的一侧，而执行顺序是随机的。同构表也是 DDL 一致性的一次顺带校验 |
| 两侧执行顺序随机 | 消除先执行者预置状态带来的偏置 |

### 4.3 默认过滤不变式

SQLancer 的 TLP（Ternary Logic Partitioning）把查询按谓词 P、`NOT P`、`P IS NULL` 三分，验证三份结果的并集等于原查询。PalORM 上有两个直接落点（软删、租户）。

v5 重写了 v4 的判据形式，原因是 v4 的三条查询都由 PalORM 生成，全量侧经 `IgnoreFilters()` 取数。这有两个后果：

- **假阴**：若 `IgnoreFilters()` 失效（该跳过滤却没跳），则全量等于有效集、已删集为空，四条断言全部成立。它恰好漏掉自己要抓的那个方向。
- **假红**：`IgnoreFilters()` 在当前会话内**没有公开复位 API**（`DataSession.cs:497-499` 明写）。同一会话先取全量再取有效集时，后一条查询仍跳过过滤并含已删行，计数断言必然失败。此时红的原因是实现正确。

修正后的判据如下。全量期望来自裸 ADO，三分支各用一个会话。

```csharp
// 三分支会话隔离：IgnoreFilters 无公开复位 API，同会话复用会让后一条分支继承前一条的过滤状态
// OpenSharedSession 为伪代码，表示按 Data Source=cf_<guid>;Mode=Memory;Cache=Shared 建会话并持 keeper（阶段 0a 第 2 项）
await using var sessAll  = await OpenSharedSession(SqlDialect.Sqlite, sharedDb);
await using var sessLive = await OpenSharedSession(SqlDialect.Sqlite, sharedDb);
await using var sessDead = await OpenSharedSession(SqlDialect.Sqlite, sharedDb);

// 全量期望不来自 PalORM：裸 ADO 读同一张表，按 deleted_at 自行划分
var (expectedAlive, expectedDead) = await ReadPartitionRawAsync(
    sessAll.GetRawConnection(), "cf_soft_delete");   // 连接未开则先 Open

var actualAlive = (await sessLive.From<SoftDeleteEntity>().ToListAsync())
    .Select(e => e.Id).ToHashSet();
var actualDead = (await sessDead.IgnoreFilters().From<SoftDeleteEntity>()
    .Where($"deleted_at IS NOT NULL").ToListAsync())
    .Select(e => e.Id).ToHashSet();

await Assert.That(actualAlive.SetEquals(expectedAlive)).IsTrue();   // 有效集相等
await Assert.That(actualDead.SetEquals(expectedDead)).IsTrue();     // 已删集相等
await Assert.That(actualAlive.Overlaps(actualDead)).IsFalse();      // 不交
await Assert.That(expectedDead.Count).IsGreaterThan(0);             // 期望非空：种子必须含已删行
```

四条判据的取舍理由：

- 用"两个集合各自相等"替代"并集等于全量加计数相等"。全量已被裸 ADO 拆成两个期望集，并集恒成立，没有判别力。
- 保留不交断言，它能抓"同一行既被当有效又被当已删"。
- 期望非空断言不可省。种子数据不含已删行时，前两条在空集上恒真，这正是 v4 的假阴来源。
- 裸 ADO 侧不写 `WHERE deleted_at IS NULL` 而是全读回来在内存划分，避免手写 SQL 与 PalORM 的过滤语义耦合。

四种查询形态各执行一遍：`OrWhere`（`QueryBuilder.cs:231`）、`WhereIn`（`:316`）、IN 超 500、`With(cteName, subquery)`（`:568`）。选这四种是因为 ITM-401 的根因正是 OR 优先级把默认过滤吞进分支。

租户划分同理，另外增加一条"每个租户的期望集非空"，否则单租户数据下"两两不交"恒成立。

### 4.4 变异探针（六个）

| 探针 | 侧 | 注入方式 | 期望结果 |
|------|----|----------|----------|
| P1 | oracle | 手写 SQL 的 WHERE 追加 `AND 1=0`，把结果集压成空集 | L2 必须报红 |
| P2 | oracle | 手写 SQL 写成 `SELECT b AS a, a AS b`，对调两个值来源 | L2 必须报红 |
| P3 | oracle | 比较器的行序规则改成忽略差异 | 至少一个用例变红 |
| P4 | oracle | 断言改成"带软删实体的查询结果包含已删行" | L3 必须报红 |
| P5 | 产品 | `git show <ITM-401 修复前> -- src/PalORM.Core/QueryBuilder.cs`，回退 OR 吞过滤的修复 | L4 与 L6 必须报红 |
| P6 | 产品 | 临时打乱源生成器的 `BindInsertBody` 列序（或回退 ITM-552 的修复） | L2 必须报红 |

v4 只有 P1 到 P4，四个全在 oracle 侧。它们证明的是"判据对错误期望敏感"，不证明"判据对产品缺陷敏感"。P4 尤其错配：把断言反过来写当然会红，它没有回答"过滤失效时 L4 会不会红"，而 §4.3 的分析说明 v4 的 L4 对这个方向是盲的。

两个方向都红之后，套件的通过结果才有意义。P5 与 P6 的注入物必须还原，运行前后各记一次 `git status`。

两个最容易被写坏的探针：

- P1 若写成"加一个恒真谓词"（`AND 1=1`），结果集与不加完全相同。必须让注入落进结果集，`AND 1=0`、改值、`OR 1=1` 三者任一都可。
- P2 若写成"SELECT 列表顺序对调"，在按列名比较下 name→value 映射没变，同样不报红。必须对调值来源。

按列名比较不会放过 PalORM 侧的序号错位：`RowFactory` 若把第 3 列填进属性 A，实体侧 A 就带着错值，与手写 SQL 侧 A 的真实值不等，照样报红。前提是手写侧走裸 ADO（§4.2 第三条约束）。

### 4.5 变形关系

手写 SQL 是 81 个骨架（27 操作 × 3 方言），而执行数是 1350 到 1650 次。让每条场景都配一段手写 SQL，等于把成本压在最贵的一档 oracle 上。

| 关系 | 表达 | 覆盖的缺陷族 |
|------|------|-------------|
| 批量对逐行 | `BulkInsert(rows)` 的结果集等于逐行 `InsertAsync` 的结果集 | 数组填充顺序、批量骨架列序 |
| 批量更新 | `BulkUpdate(rows)` 等于逐行 `UpdateAsync` | SET 谓词与绑定顺序漂移 |
| 合并 | `BulkMerge` 等于 `Insert` 与 `Update` 的并集 | 存在性判定与分支绑定 |
| 批量删除 | `BulkDelete` 等于逐行 `DeleteAsync` | 键集合填充与 IN 切批 |
| 幂等 | 同一 `SaveAsync` 执行两次等于执行一次 | 冲突分支的参数绑定 |
| 分页 | `ToPageAsync` 各页并集等于 `GetAllAsync`，页间无重复 | 键集锚点与续页条件 |
| 切批 | `WhereIn`（超 500 值）等于逐批 `WhereIn` 的并集 | IN 切批拼接与 OR 组合 |
| 流式 | `QueryAsyncEnumerable`（`DataSession.Query.cs:321`）的元素序列等于 `QueryAsync`（`:431`） | 复用命令分支的枚举器状态 |

这些关系不需要期望 SQL，由 `OperationKind` 驱动执行器成对调用即可，边际成本远低于写手写 SQL。

盲区是两条路径共享缺陷，典型是 `RowFactory` 的序号错。所以变形关系只承担体量，判定仍以手写 SQL 锚点为最终依据：每个操作族至少留一条锚点。

**实施状态（2026-10-29）**：八条关系全部落地（`MetamorphicRelationTests`），两条路径在同一语义上互证：批量对逐行、合并对插入加更新、批量删除对逐行删除、幂等（两次等于一次）、分页并集对全量、切批（501 值）对逐批、流式对批量读。

**DDL 语义族落地（2026-10-29）**：7 条断言在 SQLite 上验证约束真的成立（NOT NULL 拒绝空值、UNIQUE 拒绝重复、复合与唯一索引出现在目录、外键拒绝孤儿行、DEFAULT 在省略列时生效、计算列由数据库生成、自增主键连续）。外键一条必须先 `PRAGMA foreign_keys = ON`：SQLite 的 FK 默认关闭，不显式打开时约束静默不生效。

**三方言落地（2026-10-29）**：多结果集族已在 SQLite / PostgreSQL / MySQL 上各跑通 QueryMultiple、GetRawConnection 与 StoredProc。手写侧 SQL 由 `DialectSql` 按方言生成（PG/SQLite 双引号、MySQL 反引号；upsert 用 `ON CONFLICT` 与 `ON DUPLICATE KEY UPDATE` 两种形态）。三组远程用例共用一把串行锁 `ConformanceRemoteTables`：同一容器库上并行会互相清表，实测曾让 MySQL 存储过程用例在并发下失败。

**表管理（统一）。** 每（形状，方言）建一对 `_p` / `_s` 表一次，场景间 `DELETE` 加自增复位；SQLite 每场景新库。崩溃残留用 `CREATE TABLE IF NOT EXISTS` 加启动时清理 `cf_` 前缀表兜底。v4 的 §4.6 写"场景间复用表，执行前清空"，§9 写"每场景新表加 `try/finally` DROP"，两处矛盾；v5 取前者，理由是 1350 到 1650 次 CREATE 加 DROP 在 MySQL 上（DDL 隐式提交且每次数十毫秒）会吃掉 15 分钟预算的显著部分。

### 4.7 判定与假阳性治理

每条规范化规则必须配一个反例测试，证明它没有掩盖真实差异。

| 项 | 规则 | 反例（必须保持报红） |
|----|------|-------------------|
| 行序 | 按全列元组稳定排序 | 两侧行数不同 |
| 列序 | 查询侧按列名排序；写入侧不用结果集 | 实体列序与 DDL 列序不一致 |
| decimal | 声明了精度/标度的列，scale 差异判失败；仅 SQLite（无 decimal 类型）按数值比较，尾零不追究 | 值本身不等；声明 scale 的列丢了尾零 |
| 时间 | 按「方言 × 列类型 × DateTimeKind」期望表判定，见下 | 时区偏移导致实际时刻不同；Kind 被静默改写 |
| 浮点 | 往返比较要求 bit-exact（NaN 除外，NaN 与 NaN 判不等）；容差只用于 `Sum`/`Avg` 这类计算聚合，取相对 1e-9 | 往返丢精度；聚合超出容差 |
| `byte[]` | Base64 后比较 | 长度或内容不同 |
| null | 单独标记 | null 被当成空字符串 |
| 字符串 | 原样比较，不折叠大小写 | 大小写敏感列上的差异 |

时间判定必须按矩阵展开，不能统一转 UTC 后比较。下表为 2026-10-29 三方言实测（探针 `TimeKindMatrixTests`；原始数据由探针每次运行生成到 `artifacts/time-kind-matrix-*.csv`，该目录 gitignored，不入库）：

| 方言 | DateTime 列类型 | 输入 Utc | 输入 Local | 输入 Unspecified | DateTimeOffset |
|------|-----------------|----------|------------|------------------|----------------|
| SQLite | `TIMESTAMP`（NUMERIC 亲和） | 读回 Unspecified，刻度不变 | 读回 Unspecified，刻度不变 | 读回 Unspecified，刻度不变 | offset 保留 |
| PostgreSQL | `timestamptz`（D1 修复前为 `timestamp`，见下） | 读回 `Utc`，刻度不变 | **写入抛 `ArgumentException`** | **写入抛 `ArgumentException`** | 仅 Utc 行可写入 |
| MySQL | `TIMESTAMP` | 读回 Unspecified，刻度不变 | 读回 Unspecified，刻度不变 | 读回 Unspecified，刻度不变 | 归一为 UTC（时刻正确、offset 丢失） |

**D1 修复（2026-10-29）**：首轮实测时 PG 的 `DateTime` 列落的是 `timestamp`（无时区），而参数侧 `DbType.DateTime` 被 Npgsql 映射为 `timestamptz`。列与参数类型不匹配的后果是"读出、改字段、写回"抛 `ArgumentException`，即 PG 上带 DateTime 列的实体无法走完整的 CRUD 往返。修复方式是把 PG 的 DateTime 列类型改为 `timestamptz`（`MigrationEmitter.GetTemporalDbType` 一处），使列与参数对齐：读回 Kind=Utc、刻度不变、往返可用。回归测试 `PostgreSql_DateTimeRoundTrip_ReadThenWriteBackSucceeds`。已有库需手工 `ALTER COLUMN ... TYPE timestamptz`（`MigrateAsync` 只建不改）。

三条结论修正了 v5 修订前的推断：

1. 三方言读回的 Kind **都是 Unspecified**（当时推断 PG `timestamptz` 读回 `Utc`，实测证伪）。因此"Kind 被静默改写"不构成方言差异，而是 PalORM 与驱动的统一归一行为，不能当缺陷报。
2. PG 的 `timestamptz` 只接受 `Utc`，`Unspecified` 与 `Local` 在写入阶段就被 Npgsql 拒绝（`ArgumentException: only UTC is supported`）。这是错误契约，记入 B 层 E9，不属于映射缺陷。
3. A 层的时间判据改为"刻度相等 且 Kind 等于该方言实测值"；对 PG 另加一条"非 Utc 写入必须抛出"，反例是写入成功。

失败分四类：真缺陷（记入清单附最小复现）、规范化不足（补规则并补反例）、对照 SQL 写错（修 SQL 并登记）、环境态（容器重启、`local_infile` 重置、端口变化；重跑确认，不归因）。容器重启后的首批为 transition 态，至少 3 个完整批之后再判定。

零缺陷必须写成"在 1350 到 1650 次执行覆盖三方言的范围内未发现缺陷"，并注明检索范围。

### 4.9 跨方言等价性（L6）

v5 新增。SQLite、PostgreSQL、MySQL 是三个独立引擎，构成天然的第三 oracle。现有设计只做"每方言各自与手写 SQL 比"，三方言之间的差异不在判据内。

判据：同一 `Scenario.Id` 在三方言的结果集，主键集合相等，且每个主键行的列值在可比类型集合内相等。

**实施状态（2026-10-29）**：两个场景落地（`CrossDialectEquivalenceTests`）。简单列（long、string 与 long 极值、emoji、引号）三方言逐字相同；时间面按列语义归一后一致（dt、date_only、time_only），`DateTimeOffset` 因 MySQL 归一 UTC 而 SQLite 保留 offset 登记为列级不可比，跳过量按场景计仍为 0。

实测暴露三条表示差异：SQLite 无原生日期类型，裸 ADO 读回 string；MySQL 的 DATE 读回 DateTime、TIME 读回 TimeSpan；共享库的自增序列跨用例累积（PG 需 `TRUNCATE ... RESTART IDENTITY`、MySQL 需 `TRUNCATE`）。因此 L6 比较前必须按列语义投影并重置序列，否则差异来自表示而非语义。

限制域（不满足则跳过该场景并登记）：
- 可比类型：`bool`、整数族、`string`、`byte[]`、`Guid`（统一按字符串形态）、`decimal`（按声明 scale 规范化）、时间（按 §4.7 的矩阵换算到同一基准）。
- 排除：浮点（NaN 与精度差异）、排序顺序（只比集合）、`LIKE` 大小写敏感性（MySQL collation 与 PG 不同，登记白名单）、`GROUP_CONCAT` 类聚合的分隔符与顺序。
- 每次跳过必须记入报告，跳过量超过场景数 20% 时 L6 层不成立，需补可比类型的定义。

L6 的成本主要是规范化，不是执行；它与 L2 共用同一批执行结果，不额外跑库。

### 6.4 并发浸泡

N 个线程各做 M 次"租出、操作、归还"，跑 30 到 60 秒。断言四条：同一会话同一时刻只在一个线程手里；租期写入的状态不跨租期可见；`IdleCount` 回到基线；连接池计数无泄漏。

判定优先看不变式，不看耗时。这一层不做性能测试，时长取短是因为要抓的是串租与状态污染，长稳压测属于 PerfHub 的职责。

### 6.5 完成判据

转移表每格有断言或显式"不适用"注释；十条不变量全绿；并发浸泡连续 3 轮零不变式失败。

**实测完成（2026-10-29）**：80 格全覆盖分类（19 个断言方法，断言数下限 15 由用例自检）；I1 到 I10 全绿（I10 见上方实测结论）；并发浸泡按 §6.5 跑连续 3 轮、每轮窗口 30 秒（§6.4 的 30 到 60 秒下沿），每轮独立库与会话池，四条断言逐轮核对，三轮零违规、操作数均高于地板 100，单测耗时 1 分 30 秒。

## 七、D 层：随机化差分层

### 7.1 随机化对象

| 维度 | 生成策略 | 边界偏置 |
|------|----------|----------|
| 值 | 按 CLR 类型驱动生成器 | 每类必含 null、空、min、max、超长、Unicode、NaN 与无穷 |
| 条件 | 从 7 种形态随机组合，深度 1 到 3 | 必含 OR 与 AND 混合、IN 边界 |
| 批量大小 | 随机取值 | 偏置到 1、2、499、500、501、2000 |
| 操作序列 | 同一实体上随机排列读写 | 必含"写后读""读后写""删后读" |

### 7.2 种子与复现

固定基础种子加每轮打印实际种子。失败样本的三元组（种子、场景 ID、值）落盘到 `artifacts/`，可独立重放。CI 每晚跑两组：固定种子集合做回归，新种子集合做探索。

### 7.3 收缩

失败样本必须收缩到最小可读形式：值列表做长度减半，值替换为同类最简值，操作序列逐条删除。收缩后仍失败才算一条有效报告。不做收缩的随机化报告没人会看，等于没做。

**实施状态（2026-10-29）**：收缩器落为 `ScenarioShrinker`，五步贪心（批量大小减半、值列表减半、逐项删除、值替换为最简、条件与操作序列降级），每步只在「收缩后仍失败」时才接受，迭代上限 80 防退化路径打转。比原文多两步降级（条件降为 None、序列降为 InsertThenQuery），因为这两维也是随机化的自变量。收缩器不碰数据库，6 条单元测试用纯逻辑谓词验证，其中一条用恒真谓词确认能终止并压到最小形态。

### 7.4 预算与闭环

每方言 60 到 120 秒，不计入 pre-commit。D 层发现的缺陷必须固化成 A 层的固定用例，否则随机化只发现一次、无法防回归。固化率进 §11 度量。

**实施状态（2026-10-29）**：固定种子回归（6 个种子 × 8 场景 = 48）进 PR 门禁，实测约 0.4 秒；探索由 `PALORM_FUZZ_SEED` 环境变量启用（每种子 12 场景），未设置时该测试直接返回。失败样本按 `种子|场景ID|值|条件|批量大小|序列` 组成 ReplayKey，可直接重放。当前固定与探索种子均零差异，固化率暂无样本可计。

阶段 0a 可以前移一次 30 分钟的探索运行，用缺陷命中率作为"组合面是否有空白"的客观信号（替代 v4 用定向用例判定的做法，见 §10）。

### 7.5 与 A 层的关系

A 层是固定网格，可审计、可复现、进回归，但覆盖率由网格定义。D 层把同一套判据放大到网格之外，找到的是"没想到的输入"。两层共用判据与执行器，D 层不需要新的 oracle，成本主要是执行时间。

阶段 0b 的 60 条不是 27 个操作各一条。基线部分每个操作族一条（27），定向部分 33 条按事故家族分配：SET 谓词与绑定漂移（ITM-552/642）、OR 吞过滤（ITM-401）、链式 WHERE/OR 优先级（C16）、租户写作用域（ITM-599）、会话粘性，每族 5 到 8 条。

| 项目 | 理由 |
|------|------|

## 十三、风险与缓解

只列缓解措施尚未落到其他章节的风险；规范化过宽、场景同构、执行预算、表名冲突、判别力失效的处置分别见 §4.7、§11、§10、§4.6、§4.8。

| 风险 | 影响 | 缓解 |
|------|------|------|
| 手写 SQL 自己写错，两侧都不对却判通过 | 假阴性，A 层失去意义 | 81 个骨架全量逐条评审并登记记录；L6 跨方言互比作为第二道交叉 |
| 变形关系两侧共享缺陷 | 假阴性 | 每个操作族至少一条手写 SQL 锚点；L6 补充方言间交叉 |
| 场景定义与实体漂移 | 改了实体注解而手写 SQL 没跟上，套件静默失去判别力 | 手写 SQL 登记来源实体与 `[Column]` 值，实体变更由 `git diff` 触发人工确认 |
| 契约条目照抄实现 | B 层退化成自证 | 期望值只从文档取；文档与实现冲突时先判定谁错，不允许以实际为准改文档 |
| 新层先观察期被无视 | 假阳性长期挂着，没人看 | 观察期设两周上限与责任人，到期必须转阻断或删除 |
| 容器环境漂移 | 判定不可复现 | SQLite 作为主要判定面；环境变更记录在报告头部 |
| 产品侧变异污染工作树 | 回放后忘记还原，后续提交带缺陷 | 每次回放前后记 `git status` 与目标文件哈希；阶段 0a 用临时 checkout 隔离 |
| L6 跳过量过高 | 跨方言判据名存实亡 | 跳过量超过 20% 时该层不成立，需补可比类型定义；报告必须列出跳过原因分布 |
| 慢速类拖垮 CI | 15 分钟预算击穿 | E3/E4/I10 单列 Slow 类，随夜间跑 |

## 附录 A：外部数据集

结论是**不存在公开的"ORM 生成 SQL 正确性"数据集**，原因是原理性的：期望 SQL 依赖实现细节（列序、引用符、别名策略、参数编号），没有公共可标注的标签。

可用部分有三块。sqllogictest 提供结果期望值与值边界样本，但只覆盖物化层，接入前须按官方 statement/query 格式核对解析器。SQLancer 的 TLP 三分支方法论可直接移植，已落到 §4.3，零外部依赖。TPC-H 与 TPC-DS 的 schema 可裁剪借用，查询不可用（PalORM 不支持复合主键，TPC-DS 复合键更多）。sqlglot 只作离线归一化辅助，本机只有 `python` 无 `python3`，不进 CI。EF Core Relational Spec Tests 提供"一套抽象测试跑多 Provider"的架构形态，用例基于 LINQ 不可移植。Spider 与 BIRD 面向自然语言到 SQL，与映射正确性无关。

v5 补充：三方言互比（§4.9）不需要外部语料，但需要一份"方言差异白名单"，可从 sqllogictest 的类型边界用例中提取素材。

## 附录 C：已否定的定义（勿重开）

这一节替代变更日志。只记那些未来可能被重新提出、且已经证明不成立的定义。

| 已否定的定义 | 为什么不能重开 |
|------|---------------|
| P1 用恒真谓词（`AND 1=1`）验证 L2 | 不改变结果集，永远不报红。必须用 `AND 1=0` 或 `OR 1=1` |
| P2 用 SELECT 列序对调验证 L2 | 按列名比较下 name→value 映射不变，永远不报红。必须对调值来源 |
| SQLite 用 `TestDb.SqliteAsync()` 跑双侧对照 | `Data Source=:memory:` 每个连接一个私有空库，两侧不在同一数据库 |
| decimal 的 scale 差异记录但不判失败 | 声明了精度/标度的列丢尾零是真缺陷 |
| 时间统一转 UTC 后比较 | `Unspecified` 归一化会洗掉 Kind 丢失；必须按方言 × 列类型矩阵判 |
| 浮点统一给 1e-9 容差 | 三方言浮点都是 IEEE754，往返应 bit-exact，容差只给聚合 |
| 手写 SQL 抽 5% 样本交叉验证 | 只有 81 个骨架，抽取等于只查 4 个，与头号风险不匹配 |
| 每场景用事务回滚清理 | MySQL DDL 隐式提交，建表无法回滚 |
| 用单一"覆盖填充率百分比"度量 | （操作 × 形状）全覆盖使该指标恒为接近 100% |
| 阶段 0 取"27 个操作族各 1 条"共 60 条 | 27 × 1 等于 27 不是 60，缺的 33 条必须按事故家族定向分配 |
| 场景委托写成 `Func<DataSession<SqliteProvider>, ...>` | `DataSession<TProvider>` 是 sealed 泛型类且无非泛型基接口，该写法锁死单方言 |
| 靠单一一致性套件证明"保持正确" | 采样不完备、oracle 可能错、共享层不可见、规格缺失、静态缓存泄漏五条限制（1.3），只能声明覆盖边界 |
| 契约期望值以实际实现为准 | 那会让 B 层退化成自证，文档与实现冲突时必须先判定谁错 |
