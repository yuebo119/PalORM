# 性能探针结果：PERF-0.3 / 0.4 / PERF-9.1（2026-11-05）

> 对应方案：[性能优化方案-v2-最终版-2026-11-05.md](性能优化方案-v2-最终版-2026-11-05.md) §4 Phase 0 与独立立项
> 数据来源：`bench/perfhub/results/history-20261102-181157.json`（最近完整批，416 项）+ 本仓库源码静态统计
> 结论用途：决定 Phase 6（条件项）去留、是否启动「编译期查询特化」

## 1. PERF-0.4：构建成本占单次查询的比例

【事实】PerfHub 最近完整批（SQLite/MySQL/PostgreSQL × 2000 行档，PalORM 臂）实测：

| 操作对 | SQLite | MySQL | PostgreSQL |
|---|---:|---:|---:|
| `BuildGetByKeySql`（纯构建） | 800 ns | 500 ns | 400 ns |
| `GetByKey`（单键完整读） | 5,800 ns | 232,600 ns | 199,700 ns |
| **构建占比** | **13.8%** | **0.21%** | **0.20%** |
| `BuildComplexQuerySql`（纯构建） | 4,300 ns | 1,800 ns | 1,500 ns |
| `QueryAll`（2000 行全表物化） | 975,000 ns | 1,111,300 ns | 643,800 ns |
| **构建占比** | **0.44%** | **0.16%** | **0.23%** |

【判定】PERF-0.4 的判据是「构建路径占单次查询总成本是否 ≥5%」，决定 Phase 6.2（构建期免物化子句数组）去留。

- 目标场景（复杂查询，即 `QueryBuilder` 的免物化对象）构建占比 **0.16%~0.44%**，远低于 5% 行动线。
- 唯一 ≥5% 的格是 SQLite 单键读（13.8%），但那是 `GetByKey` 的固定 SQL（4 槽静态缓存命中路径，
  800 ns 中大部分是首次构建摊销），**不属于 Phase 6.2 的目标路径**（它针对 `QueryBuilder` 子句数组）。
- **结论：Phase 6.2 关闭**（低于行动线，不做）。

## 2. PERF-0.3：动态形状负载占比

【事实】对本仓库全部 PalORM 查询调用点（`src` / `test` / `bench` / `tools`，排除 obj/bin）
做静态分类，共 **694** 个 `.From<T>()` 调用点：

| 分类 | 数量 | 占比 | 判据 |
|---|---:|---:|---|
| 带字面量 `Where($"…")` | 189 | 27.2% | 子句格式串为字面量，插值孔走参数化 |
| 形状动态信号 | 7 | **1.0%** | `Where(变量)` / `Take(变量)` / `Skip(变量)` / `Tag(变量)` / `When(…)` / `FormattableStringFactory.Create(变量…)` |
| 无 `Where`（裸 `From<T>().ToListAsync()` 等） | 498 | 71.8% | 形状在编译期完全确定 |

动态信号 7 处分布：`FormattableDuplicateParamTests`、`SqlShapeCacheGrowthTests`、
`DialectRandomDiffTests`、`RandomDiffRunner`×2、`PerfHub/Implementations`×2——其中 4 处是
**为制造多形状而写的测试/模糊夹具**，不是业务负载。

【判定】PERF-0.3 的判据是「形状数 >1 的调用占比」，<10% 则关闭 Phase 6.1（动态形状多槽）。

- 多形状调用占比 **1.0%**（7/694），远低于 10% 关闭线。
- **结论：Phase 6.1 关闭**（不做）。

【样本边界（必读）】本统计的样本是**本仓库自身**（测试与基准占绝大多数），不是外部用户代码库。
真实业务负载的动态筛选（分页、动态排序、权限驱动的谓词拼接）占比可能显著更高；本结论只对本仓
样本成立。若要重开 Phase 6.1，需要的证据是真实业务调用点分布，而不是本表的数字。

## 3. PERF-9.1：编译期查询特化覆盖率实验

【事实】同一份 694 个调用点样本，按「编译期可特化」两个口径统计：

| 口径 | 数量 | 占比 | 门槛（≥30%） |
|---|---:|---:|---|
| 全部调用点中「字面量 `From<T>` + 字面量 `$"…"` Where」 | 189 / 694 | **27.2%** | **未过** |
| 带 Where 的调用点中「字面量 Where」 | 189 / 196 | **96.4%** | 通过 |
| 全部调用点中「形状在编译期可确定」（无动态信号） | 687 / 694 | **99.0%** | 通过 |

【判定】

- 按方案原文口径（「字面量 `From<T>` + 字面量 `FormattableString` + 固定 `Take/OrderBy`」占全部调用点），
  实测 **27.2% < 30%**，**未过门槛**。
- 若把「无 Where 的裸查询」也算作形状可特化（它们在编译期确实完全确定），则为 **99.0%**，远超门槛。
  两个口径结论相反，差别全在分母定义，故本表把两个数都列出而不择一。

【建议】**不在本轮立项**，理由三条：

1. 唯一严格按方案口径的读数（27.2%）未过 30% 门槛。
2. 99.0% 的读数来自本仓库样本——测试与基准的写法天然是静态形状，不能代表外部用户代码。
   以它立项等于用自家夹具证明产品方向。
3. 立项代价在方案里已标明是「仓库内唯一的架构级杠杆，也是唯一会显著增加生成器复杂度的项」
   （Roslyn 版本耦合、生成物体积、trimming 回归面）。用不具代表性的样本支撑这个代价，风险不对称。

若仍要做，前置条件应改为：拿到一份**真实业务代码库**的调用点分布（同样三口径统计），再判定。

## 4. 对 Phase 6 的最终裁决

| 项 | 判据 | 实测 | 裁决 |
|---|---|---|---|
| 6.1 动态形状多槽（−32%） | 多形状调用占比 <10% 关闭 | 1.0% | **关闭** |
| 6.2 构建期免物化子句数组（4.6%） | 构建占单次查询 <5% 关闭 | 0.16%~0.44% | **关闭** |
| 独立立项：编译期查询特化 | 字面量形态占比 ≥30% | 27.2%（严格口径） | **不立项**（样本不足，见 §3） |

两项条件项与独立立项均关闭后，本轮剩余工作量集中在 Phase 5（形态对照交付）与 Phase 4（收口）。
