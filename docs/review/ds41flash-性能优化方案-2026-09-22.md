# PalORM 性能与可靠性优化方案（ds41flash）

> 基线：`dev@8935d24`。来源：全仓只读源码审计，覆盖 `src/` 全部 70 个 C# 文件（约 1.65 万行），分两条路线：运行时核心与 Provider 直读，源生成器由独立 sub-agent 审计后并入。
> 方向：并发、延迟、内存、可靠性、事务完整可靠性（用户指定的五维）。
> 纪律：任务只有在实现、对应测试与验收命令均通过后才标记完成；涉及分配或耗时的任务按 `docs/性能基准规范.md` 走同会话交替配对 A/B，分配用 `GC.GetTotalAllocatedBytes(precise)` 确定性口径，耗时只作量级参考（同机漂移实测可达 43%）。
> 依据等级：`[事实]` 代码或参考程序集可查证；`[推断]` 逻辑推导未实测。
> 本方案为审计输出，未改动任何源码（仅执行过 `dotnet build` 与 5 条 `PgNotificationListenerHotPathTests` 用于验证假设）。

## 总体判断

PalORM 的优化水位已经很高：生成代码用 ordinal 常量映射、SQL 全编译期预构建、注册表是不可变快照、批量路径已做参数池化（PG COPY 每行 882 → 211 B）。剩余优化点集中在三类：

1. **默认配置把只读查询拉进弹性执行器**。`IsPassThrough` 要求 `MaxRetries == 0`，而默认值是 3，于是每次 `ToListAsync` 固定多付约 272 B 与一个定时器（`QueryBuilderExtensions.cs:160-179` 已实测记录该数字）。
2. **几条"逐行 N 次往返"的批量路径没有用上库内已有的 `DbBatch` 与参数池能力**。`SessionBatch` 已把 N 条语句压成一次往返并实测 PG 3.4×，但逐条 UPDATE、`BulkMerge` 的乐观锁分支、`BulkDeleteAsync` 的分批上限都没接上。
3. **默认值层面的资源上限偏大**。SQLite 每连接 64 MB 页缓存（乘以池连接数）、参数名缓存 1.3 MB 常驻，都属"默认即付"。

另发现 2 处**代码与文档/注释直接矛盾**，属确定性缺陷，可直接修：`SessionBatch.cs:96` 声称 `DbBatch` 没有超时面（.NET 8+ 实际有 `DbBatch.Timeout`），`DataSession.cs:292-294` 声称 `IsInTransaction` 返回 false（实现会抛异常）。

编号约定：`P` 并发、`L` 延迟、`M` 内存、`R` 可靠性、`T` 事务。

## 一、并发

### P1 单个 DataSession 同时只允许一个操作，这是并发能力的硬天花板 `[事实]`

`SessionOperationState.cs:81-83` 在 `_isActive` 时直接抛 `"DataSession already has an active database operation."`，是拒绝而非排队。一次 DB 往返期间（远程 RTT 0.3 到 8.5 ms）该会话完全空转，要并发只能由调用方自行开多个 `DataSession`，每个再占一条池连接。对"增加并发"这个目标，这是最大的结构性限制。

建议（代价递增）：
1. 文档化"会话数等于并发度"，给出 `Task.WhenAll` 加多会话的范式。
2. 把 `MinPoolSize`、`PreWarmAsync` 与并发度挂钩写进部署指引（两者已有，但未与并发度关联）。
3. 若要库内解决，可加只读并发通道：`ForRead()` 的查询各自从池取连接、不占单操作门禁，写路径与事务仍串行。此项需重新设计门禁语义，属架构级决策，须裁决后动。

### P2 熔断器是会话级的，起不到保护下游的作用 `[事实]`

`DataSession.cs:51` 构造 `new ResilienceExecutor(options, TProvider.IsTransient)`，`Resilience.cs:60` 每次 `new CircuitBreaker(...)`。会话用完即弃（推荐用法是 per-request），失败计数永远在 1 到 5 之间随会话消失，默认阈值 5 在实践中几乎不可能触发。数据库真挂时每个请求各自重试 4 次再失败，熔断器形同虚设。

建议：把熔断状态提升为按 `(Provider, 连接串)` 键的进程级共享实例（可用 `ConditionalWeakTable` 加不可变快照，与注册表同范式），或提供 `DbOptions.CircuitBreakerScope`（Session/Process）显式选择。这是可靠性收益最大的一项。

### P3 读路由连接是会话级单条复用，没有并发读通道 `[事实]`

`DataSession.cs:215-240` 的 `AcquireReadConnectionAsync` 返回同一个 `_readConnection`。即使放开 P1 的门禁，这条连接也无法同时跑两个 reader。

建议：若采纳 P1 的第 3 条，读通道应改为"每次查询从池取、用完归还"。当前的会话级持有反而丢失了池的并发能力。

### P4 每个事务流都 `new object()` 作为 owner，导致 ExecutionContext 拷贝 `[事实]`

`SessionOperationState.cs:139` `_transactionOwner = new object()` 后立即写 `_currentTransactionOwner.Value`。同文件 `:85-87` 的注释记录了"用 `this` 替代 `new object()` 让第 2 次写命中 EC 短路"的优化，但那只做在操作 owner 上。事务 owner 每次都是新对象，所以每次 `WithTransaction` 付一次约 300 B 的 EC 拷贝。

建议：嵌套事务已被 `EnterTransactionFlow` 拒绝，每会话一个惰性创建的常量 token 即可让重复事务命中 EC 短路。改动面小。

### P5 每次操作多次进入 `lock (_sync)` `[事实]`

`CreateCommand()` 经 `GetActiveTransaction()` 取锁一次（`DataSession.cs:615-616`），`QueryBuilder.GetActiveTransaction()` 又一次，`AcquireExecutionConnectionAsync` 再查一次，`Enter`/`Exit` 各一次。单操作门禁保证锁几乎不竞争，单次成本很低，但一次查询累计 5 到 8 次取放锁。

建议：低优先级。若做 P1 的并发读改造，这个锁会成为真实争用点，届时换 `Interlocked` 状态机。

### P6 默认重试退避没有抖动，多实例同时恢复会形成惊群 `[事实]`

`Resilience.cs:149-155` 的 `GetDefaultBackoff` 是纯指数 `100ms << attempt`（上限 30 s），无随机分量。对比 `PgNotificationListener.DefaultReconnectDelay`（`PgNotificationListener.cs:102-107`）专门加了全量抖动，注释写明理由是"PG 重启瞬间大量监听器同步重连形成二次冲击"。同一仓库，重试路径缺同一层保护。

建议：给 `GetDefaultBackoff` 加抖动（如乘 `0.5 + Random.Shared.NextDouble() * 0.5`）。会改变既有重试时序，需同步调整时序相关测试。

### P7 没有 fan-out 抽象，调用方要手写并发编排 `[事实]`

库提供"一次调用写 N 行"（Bulk 家族），不提供"一次调用跑 N 个独立查询"。多租户、多分片、多表并行加载完全交给调用方。

建议：可作为 P1 的配套，提供薄 helper（如 `ParallelReadAsync`）或至少文档化范式。属能力补齐。

### P8 PG 通知监听器的心跳分支用两个同间隔定时器竞速 `[事实]，触发条件未复现`

`PgNotificationListener.cs:235-255`：`keepaliveCts.CancelAfter(_keepaliveInterval)` 先于循环执行，循环内又建 `Task.Delay(_keepaliveInterval, CancellationToken.None)`，再 `Task.WhenAny`。两个定时器到期时刻几乎相同，代码只处理 `completed == delayTask` 分支。若 `waitTask` 因 `keepaliveCts` 取消而先完成，`await waitTask` 抛出的 `OperationCanceledException` 不满足两个 catch filter（`owner.IsCancellationRequested` 为 false，`IsTransient` 要求 `Data["PalORM.IsTransient"]` 标记），会落到外层 catch 触发 `RaiseError`，监听器永久终止。

实测 `PgNotificationListenerHotPathTests` 5/5 通过，`A2_KeepaliveFailure_TriggersReconnect` 能通过说明测试环境下 delay 分支赢了竞速，故本项定性为结构性风险而非已复现缺陷。

建议：把 `Task.WhenAny` 换成 `await waitTask.WaitAsync(_keepaliveInterval)`。它用 `TimeoutException` 明确区分超时与通知到达，同时消除竞速，并一并解决 R13 的定时器泄漏。改动前建议先加一条"等待期间被取消且 owner 未取消"的定向测试。

### P9 并发下同键重复构建缓存条目（无害，登记用） `[事实]`

`DataSessionCache` 各缓存、`SqlShapeCache.Add`、`PostgreSqlProvider.GetQuotedInsertTarget` 都是 `TryGetValue` 未命中后构建再 `TryAdd`。并发首查会重复构建，`SqlShapeCache` 还会在同一桶留下重复条目（`SqlShapeCache.cs:93`）。注释已声明同输入恒同输出、正确性无影响。

建议：不修。注意容量统计口径（`TotalEntryCount` 会略高于实际形状数）。

## 二、延迟

### L1 默认配置不是直通，每个只读查询固定多付约 272 B 与一个定时器 `[事实]`

`Resilience.cs:19`：`IsPassThrough => _maxRetries == 0 && !_circuitBreaker.IsEnabled`。默认 `MaxRetries = 3`（`DbOptions.cs:48`）、`CircuitBreakerThreshold = 5`（`:84`），所以默认配置下每次 `ToListAsync` 都走 `ResilienceExecutor`：链接 CTS 加 `CancelAfter` 定时器约 168 B、委托 56 B、执行器状态机约 48 B。`QueryBuilderExtensions.cs:160-179` 的注释已实测并记录这 272 B，并说明"把只读内核从 async 局部函数改成 struct 内核加泛型约束"可省约 104 B，结论是"实测耗时无变化，未做"。

建议：默认路径的固定成本，值得重新评估。更省的一条路是让 `ExecuteReadPipelineAsync` 在"调用方未显式配置弹性且命令自带驱动级 CommandTimeout"时直通，把 272 B 降为 0，代价是失去 `PalORM.InfrastructureTimeout` 统一超时标记。属行为变更，须裁决。

### L2 只读查询的超时重试会把延迟放大到 `(MaxRetries+1) × CommandTimeout` `[事实]`

`Resilience.cs:81-107` 每次尝试都新建 `CancelAfter(_timeout)`，超时触发的 OCE 可重试。默认 3 次重试加 30 s 命令超时等于最坏 4 × 30 s 加退避 0.7 s，约 120.7 s；`DbOptions.Production`（`DbOptions.cs:211`）设 `MaxRetries = 5`，最坏约 180.7 s。一个挂起的读查询要两到三分钟后才向上抛错。

建议：把"单次操作总预算"与"单次尝试超时"分开（如新增 `MaxTotalElapsed`），或把默认重试次数降到 1 并文档化。属延迟与可靠性共同风险点。

### L3 三处事务收口点的 COMMIT 没有超时包装 `[事实]`

`DataSession.Transactions.cs:149`（`WithTransaction`）、`:267`（`RunInTransactionScopeAsync`）、`QueryBuilderExtensions.cs:398`（`ToPageAsync`）都直接 `await transaction.CommitAsync(ct)`。`ct` 是调用方令牌，传 `default` 时提交可以无限挂起。

两条批量路径已修过同一问题：`PostgreSqlProvider.CommitWithTimeoutAsync`（`:419-445`）与 `MySqlProvider.CommitWithTimeoutAsync`（`:318-344`）都加了超时并打 `PalORM.InfrastructureTimeout` 标记，注释写明"此前 ct == default 时提交无界等待"。

建议：把 `CommitWithTimeoutAsync` 提升为共享实现（Core 一份，Provider 侧保留独立副本是刻意设计，见 `PostgreSqlProvider.cs:447-450` 的防漂移锚点），在三处事务收口点统一使用。

### L4 `BulkDeleteAsync` 按 500 每批切分，往返次数被放大 100 倍以上 `[事实]`

`DataSession_Bulk.cs:63` `const int batchSize = SqlLimits.InClauseBatchSize;`（500），而 `SqlLimits.MaxBindParameters` 是 65535。删 10 万主键等于 200 次往返，按 5000 每批只需 20 次。

500 这个值来自 `WhereIn`（单条语句内拼 IN 片段，受 SQL 长度与可读性约束），对"每批一次独立往返"的删除路径并非同一约束。

建议：`BulkDeleteAsync` 用独立上限（如 5000，或按参数上限反算），保留 `WhereIn` 的 500。

### L5 `BatchUpsertAsync` 硬编码 900 参数每语句，PG/MySQL 上损失约 70 倍批量 `[事实]`

`DataSession_Bulk.cs:683-684`：`const int maxParametersPerStatement = 900;`，注释理由是 SQLite 的 999 上限。但该方法位于 `DataSession<TProvider>` 内，`TProvider.Dialect` 可用。10 万行乘 10 列在 PG 上：900 参数每语句等于 90 行每批，共 1111 条语句；按 65535 上限等于 6553 行每批，共 15 条语句。

建议：按方言取值（SQLite 900，其余 `SqlLimits.MaxBindParameters`），与 `BulkUpdateBatchAsync` 的 `rowsPerBatch` 算法同源。

### L6 池化逐条 UPDATE 是 N 次往返，而库内已有单往返的 `DbBatch` `[事实]`

`DataSession_Bulk.cs:330` 在行循环里 `await cmd.ExecuteNonQueryAsync(ct)`。带 `[ConcurrencyCheck]` 的实体走这条路径（自动路由条件排除了乐观锁），1 万行等于 1 万次往返。同仓库的 `SessionBatch`（`SessionBatch.cs:91-113`）已用 `DbBatch` 把 N 条语句压成一次往返，注释给出 PG 实测"逐条 4.56 ms 到批量 1.33 ms，3.4×"。

建议：池化逐条路径改用 `DbBatch` 承载 N 条同形 UPDATE。注意乐观锁的逐条 `affectedRows` 判定：`DbBatch.ExecuteNonQueryAsync` 只返回累计行数，需改用 `ExecuteReaderAsync` 逐语句取结果，或把判定改成"总行数等于 N 且无冲突异常"。本项延迟收益最大，但有语义改造量。

### L7 `BulkMergeAsync` 的逐条分支同样是 N 次往返 `[事实]`

`DataSession_Bulk.cs:634-639` 对 `IncrementVersion is not null` 的实体逐个 `SaveCoreAsync`，与 L6 同一根因（乐观锁与集合化冲突）。

建议：与 L6 合并处理。

### L8 PG Binary COPY 每行每列一次 async 写入 `[事实]`

`PostgreSqlProvider.cs:399-412` 的 `WriteRowAsync` 对每列 `await importer.WriteAsync(value, NpgsqlDbType, ct)`。19 列乘 10 万行等于 190 万次 async 调用，每次一个状态机。

已核对本机 Npgsql 10.0.0 的 API 面：`NpgsqlBinaryImporter` 同时提供同步的 `Write`、`StartRow`、`WriteRow`（`~/.nuget/packages/npgsql/10.0.0/lib/net8.0/Npgsql.xml`）。

建议：行循环改用同步 `WriteRow` 或 `Write`，在行边界做 `ct.ThrowIfCancellationRequested()`。Npgsql 对 COPY 的建议也是 CPU 密集段用同步 API。本项同时降分配与耗时。

### L9 `ToPageAsync` 固定两次往返（COUNT 加页查询） `[事实]`

`QueryBuilderExtensions.cs:371-393`：先 `BuildCountSql` 执行标量，再执行页查询。

建议：一，增加"不要 Total"的重载（键集分页常常不需要总数）；二，或用 `COUNT(*) OVER()` 窗口函数一次拿回。前者是纯增量 API，风险最低。

### L10 `PreWarmAsync` 串行建连 `[事实]`

`DataSession.cs:173-192` 是 `for` 循环逐条 `OpenAsync`。注释引用的实测是远程建连约 8.5 ms 每条，预热 100 条即 850 ms 启动延迟。

建议：用有界并发预热（如 `Parallel.ForEachAsync`，`MaxDegreeOfParallelism = 8`）。预热是启动期一次性动作，收益直接体现在启动时间。

### L11 列序校验只在存在首行时执行 `[事实]`

`DataSession.Query.cs:143-151` 与 `:202-210` 把 `ValidateColumnOrder` 放在 `while (await reader.ReadAsync())` 内、`firstRow` 标志下，结果集为空时不校验；而 `GridReader.cs:55/92` 与 `StoredProcBuilder.cs:130` 在读循环之前无条件校验。同一份 SQL 今天不报、明天有数据才报，暴露时机取决于数据分布。

建议：统一到读循环之前（此时 `FieldCount`/`GetName` 已可用）。

### L12 非满批走逐行 `CreateParameter` 回退路径 `[事实]`

`MultiValueBulkInsert.cs:249-258`：`isFullBatch` 为 false（末批，或 `valuesBinder` 为 null）时 `Parameters.Clear()` 加逐行 binder 重建全部参数。生成器已产出 `BindInsertValues`，末批同样可走"预建池加只写 Value"。

建议：末批的池按 `lastBatchLength` 收敛（与 `AttachParameters` 同范式）。收益与末批占比成正比。

### L13 `SessionBatch` 没有给 `DbBatch` 设超时，且注释里的理由不成立 `[事实]`

`SessionBatch.cs:96-98` 注释写"System.Data.Common.DbBatch 无 CommandTimeout 面"。核对 .NET 11 参考程序集：`System.Data.Common.DbBatch.Timeout` 存在（`Microsoft.NETCore.App.Ref/11.0.0-rc.1.26425.128/ref/net11.0/System.Data.Common.xml`，.NET 8 起即有）。当前批路径按驱动默认超时（约 30 s）执行，用户配置的 `CommandTimeout`（如 5 s 或 120 s）在批路径上被静默忽略。

建议：设 `batch.Timeout = DbOptions.ToCommandTimeoutSeconds(...)`，同步修正注释。按三方一致要求，代码与注释一并改。

### L14 MySQL BulkCopy 每批重建 `MySqlBulkCopy` 与全部列映射 `[事实]`

`MySqlBulkCopyInserter.cs:131-143`：每个批次新建 `MySqlBulkCopy` 并逐列 `ColumnMappings.Add`。默认 `batchSize = 1000`，10 万行等于 100 次。

建议：映射只依赖 `(quotedTable, allColumns)`，可缓存 `MySqlBulkCopyColumnMapping[]`。`MySqlBulkCopy` 对象本身能否跨批复用需核实驱动实现后再改。

### L15 `GetEntityFeatures<T>()` 每次调用都做 `Volatile.Read` 加 FrozenDictionary 查找 `[事实]`

`DataSession.cs:470-471` 走 `PalORM_Runtime.EntityFeatures` 属性（`PalORM_Runtime.cs:142`，每次 `Volatile.Read(ref _state)`），而 `From<T>()`（`DataSession.Crud.cs:22`）已取好 `CurrentState` 快照却没用它取 features。一次查询里 `HasTenantFilter`、`GetDefaultFilterForms`、`BindDefaultFilterParameters` 会重复调用。

建议：`GetEntityFeatures` 接受可选快照参数，或在 `From<T>()` 内直接用 `state._entityFeatures`。微项。

### L16 `EntityDataReader.GetOrdinal` 用 `Array.IndexOf` 线性扫描 `[事实]`

`EntityDataReader.cs:81-90`。驱动当前只按序号取值（注释已实测），不是热路径，仅在驱动版本变更后暴露。

建议：不修，保留注释里的实测结论。

### L17 缓存键组装每次插值分配 `[事实]`

`QueryBuilderExtensions.cs:18-21` 的 `EffectiveCacheKey` 每次 `$"{scope}:{builder._cacheKey}"` 产生新字符串，`ToListAsync` 命中路径也走它。

建议：低优先级。可把前缀化 key 缓存在 builder 上（builder 是 struct，注意别引入共享可变状态）。

### L18 `BoundedQueryCache.Set` 每次读 `ConcurrentDictionary.Count` `[事实]`

### M1 `ParameterNameCache` 首次触达即分配 65536 个字符串，约 1.3 MB 常驻 `[事实]`

## 四、可靠性

### R1 主连接一旦断开，会话后续操作全部失败，没有重连 `[事实]`

`DataSession` 在构造时打开连接并持有到 `DisposeAsync`（`DataSession.cs:18`、`:420-457`）。弹性重试包住了命令执行（`ExecuteCoreAsync` 每次调 `AcquireExecutionConnectionAsync`），但主连接永远返回 `_conn`（`QueryBuilder.cs:564-566`），死连接上的重试必然再失败。

建议：会话级重连需要重新初始化连接（含 `SessionSetupSql`、事务状态归零），语义上比"重建读连接"复杂。至少应提供 `DbOptions.SessionReconnect`（默认关），或文档化"长生命周期会话不可用，请用 per-request 会话"。属架构级决策，须裁决。

### R2 读连接失效只按 `State == Open` 判定，重试会复用死连接 `[事实]`

`DataSession.cs:217-223`：`existing.State == ConnectionState.Open` 就直接返回。连接被中间设备静默掐断（NAT 超时、LB 空闲切断、无 FIN/RST）时 `State` 仍是 `Open`，第一次失败后弹性重试再次拿到同一条死连接，重试全废。

建议：读路径捕获瞬时异常时主动丢弃 `_readConnection`（置空并 `DisposeAsync`），让下一次尝试重建。改动小、收益明确，与 `PgNotificationListener` 已做的心跳探测同类。

### R3 `IsInTransaction` 的文档说返回 false，实现会抛异常 `[事实]`

`DataSession.cs:295` `public bool IsInTransaction => GetActiveTransaction() is not null;`，而文档（`:292-294`）明确写"外部设入的事务被 Dispose 时，`GetActiveTransaction` 会响亮抛异常；本属性返回 false（该状态下没有可用事务）"。但 `SessionOperationState.cs:338-345` 的响亮路径（`ITM-640/767`）会抛，且注释写明失效状态不清除，所以每次调用都抛。

影响：`AdvisoryLockExtensions.EnsureInTransaction`（`AdvisoryLockExtensions.cs:96`）调 `IsInTransaction`，事务被外部释放后会把 `ITM-640` 的异常抛给调用方，而不是它自己那句 "requires an active transaction"。

建议：改代码而非改文档。属性查询返回 false 比抛异常更符合调用方直觉，且 `EnsureInTransaction` 的错误消息更有指向性。

### R4 生成器与分析器的判定口径分叉（四处） `[事实]`

1. 默认键判定：生成器 `CommandFactoryEmitter.cs:146` 用 `EqualityComparer<T>.Default.Equals(prop, default)`（`string` 只有 null 算默认），分析器 `PalORMAnalyzer.cs:1124-1141` 把空串也算默认。于是 `SaveAsync` 的实际路由与诊断沉默不一致。
2. 表名比对：`PalORMAnalyzer.cs:1421-1440` 用大小写敏感 `HashSet`，而同文件列名与索引名判定用 `OrdinalIgnoreCase`（`ITM-510` 取最严口径）。`[ForeignKey("Users")]` 指向 `[Table("users")]` 会误报，`TreatWarningsAsErrors` 项目直接阻断编译。
3. `PALORM036` 只读项目级 nullable（`PalORMAnalyzer.cs:674-694`），文件级 `#nullable disable` 漏报，且生成端 `RowFactoryEmitter.cs:98` 不生成 `IsDBNull` 守卫，NULL 列在运行期抛 `SqlNullValueException`。
4. 生成器缺"重复列名"与"软删/租户列存在性"自守卫。`SourceGenerationValidation.cs:28-101` 的注释明确要求"不能只依赖可被 .editorconfig 降级的分析器规则"，规则被抑制时生成物照常发射 `INSERT INTO t (x, x)` 或对不存在列加 `WHERE deleted_at IS NULL`。

建议：第 1、2、4 项各自独立可修，成本低。第 3 项需先写探针测试确认三态（enable/disable/annotations-only）下 `NullableAnnotation` 的实际取值，再改用符号级判据（`NullableAnnotation.None && IsReferenceType`）。

### R5 `InsertReturningKeyOnly` 收窄路径返回调用方实例，与非收窄路径身份语义不同 `[事实]`

`DataSession.Crud.cs:126-135` 返回传入的 `entity`（回填 ID 后），非收窄路径 `:140-150` 返回 `RowFactory` 物化的新实例。同一 API 的返回对象身份随实体形状变化。另外收窄判定的前提是"RETURNING 的整行与插入值恒等"，触发器改写、`DECIMAL` 舍入、`char(n)` 填充等 DB 侧改写会让收窄路径静默返回未被 DB 采纳的值。

建议：收益已兑现（性能报告记录标准 Insert 分配 6000 到 5136 B，宽表 −31%），不撤。在 XML doc 显式声明身份语义与触发器边界。

### R6 `[Converter]` 被提升为 `static readonly` 单例，接口没有线程安全契约 `[事实]`

`RowFactoryEmitter.cs:33` 与 `CommandFactoryEmitter.cs:26` 各生成一份 `_conv_X = new ConverterType()`。`IValueConverter`（`Annotations.cs:154-161`）只声明 `ToProvider` 与 `FromProvider`，全仓库没有"必须无状态或线程安全"的声明。用户写带可变字段的转换器时，语义从"每次调用独占实例"变成"所有并发读取线程共享同一实例"，且读写两侧还是两个不同实例。

建议：在接口与 `[Converter]` 文档写明"实现必须无状态且线程安全"，并补一条 8 线程并发读同一实体转换器列的测试固化契约。这是最容易演变成难复现并发缺陷的一处。

### R7 注册失败不指向具体实体 `[事实]`

`RegistryEmitter.cs:46-54` 驱动的 ModuleInitializer 链里，任一 Converter 构造器抛异常或 `JsonTypeInfo_X` 的 `GetTypeInfo` 返回 null，整个程序集的 `Register` 失败，异常被包成 `TypeInitializationException`，堆栈不指向"哪个实体哪个列"。

建议：注册时逐实体 try/catch 收集失败清单，聚合成带实体名的异常（保持 fail-fast，补齐定位信息）。

### R8 原始 SQL 入口绕过软删与租户过滤 `[事实]`，已文档化

`DataSession.Query.cs:121-128`（`QueryAsyncEnumerable`）、`:177-184`（`QueryAsync`）、`:272-275`（`ExecuteAsync`）、`QueryBuilderExtensions.cs:428-432`（`QueryMultipleAsync`）都在 XML doc 里用 "ITM-572/677 警告" 标明。属已登记的已知边界。

### R9 `GetRawConnection()` 绕过并发门禁与事务边界 `[事实]`，已文档化

`DataSession.Schema.cs:197-201`。逃生舱是合理设计，但返回的连接可被并发使用，会与门禁保护的路径冲突。仅登记。

### R10 `DisposeWaitTimeout` 是 internal，生产环境无法调整 5 分钟挂起 `[事实]`

`DataSession.cs:28-33` 的 `DisposeWaitTimeout` 是 `internal`（注释写明供测试用）。生产上一个被放弃的 `QueryAsyncEnumerable` 枚举器会让 `DisposeAsync` 挂 5 分钟（`SessionOperationState.cs:12`）。

### R11 `GridReader.cs:187` 是库里唯一缺 `ConfigureAwait(false)` 的 await；另有 55 处 `await using` 未加 `ConfigureAwait(false)` `[事实]`

## 五、事务操作的完整可靠性

### T1 三处事务收口点的 COMMIT 无超时（可靠性视角，实现同 L3） `[事实]`

`WithTransaction`、`RunInTransactionScopeAsync`、`ToPageAsync` 都直接 `CommitAsync(ct)`。批量路径已修（`PostgreSqlProvider.cs:419`、`MySqlProvider.cs:318`），并明确了"ct == default 时网络黑洞可让提交永久挂起"。这是当前事务可靠性最明确的一处不对称。

建议：统一超时口径，并复用 `TransactionCleanup.TrySkipRollbackAfterCommitFailure`（`TransactionCleanup.cs:25-33`）的裁决逻辑，保持"提交失败后是否回滚"的判断在三方言一致。

### T2 没有整事务级重试入口 `[事实]`

`DataSession.cs:618-625` 明确写了"事务内读取保持直连"，`Resilience.cs:64-66` 也声明事务内不重试。理由成立（PG aborted transaction 会以次生异常掩盖根因）。但结果是：序列化失败（40001）、死锁（40P01）、SQLite 的 `SQLITE_BUSY`（`SqliteProvider.cs:160-161` 已判为瞬时）这类需要整事务重放的失败，调用方只能自己实现重试循环。

建议：提供显式的 `WithTransactionRetry(Func<CancellationToken, Task> action, int maxRetries, ...)`，语义是"整个事务重放"而非语句重试，并在文档说明它与 `WithRetry` 的区别。这是"事务完整可靠性"里唯一的能力缺口。

### T3 `BeginTransactionAsync` 无超时包装 `[事实]`

`DataSession.Transactions.cs:86-87` `await _conn.BeginTransactionAsync(level ?? _isolationLevel, ct)`，同样只受调用方 `ct` 约束。

建议：与 T1 一起处理。连接已打开，`BeginTransaction` 通常是本地往返，优先级低于提交。

### T4 `SavepointAsync` 与 `RollbackToAsync` 不校验事务是否为当前活动事务 `[事实]`

`DataSession.Transactions.cs:21-45`、`:48-69`：只校验"未释放"与"属于主连接"。传一个同连接但不是当前活动的（比如已提交但未释放的）事务时会生成 `SAVEPOINT` 语句而不报错。

建议：低优先级。可加一条"该事务是当前活动事务"的校验，与 `UseTransaction` 的归属校验同族。

### T5 advisory lock 只提供 xact 版本，且未设置 `lock_timeout` `[事实]`

`AdvisoryLockExtensions.cs` 只暴露 `pg_advisory_xact_lock`（事务结束自动释放），文档也解释了不提供会话级版本的取舍，安全侧是正确的选择。但文档（`:17-21`）明确说"命令级 `CommandTimeout` 不直接生效，锁等待由 `lock_timeout` 或 `idle_in_transaction_session_timeout` 治理"，而库没有提供设置入口。

建议：提供带超时的重载（`pg_try_advisory_xact_lock` 加轮询，或临时 `SET LOCAL lock_timeout`），把"必须传 ct"的文档要求变成 API 保障。当前 `AcquireXactLockAsync` 只受 `ct` 约束，锁等待期间 `ct` 是唯一逃生门。

### T6 事务资源释放顺序与提交后回填顺序正确 `[已确认无缺陷]`

`WithTransaction`（`DataSession.Transactions.cs:143-150`）先 `DisposeTransactionResourcesAsync`（关闭 reader 与 GridReader）再 `EnterTransactionOperation` 加 commit，顺序正确；`BulkUpdateAsync` 的 version 内存回填在提交成功后统一回放（`DataSession_Bulk.cs:264`），符合 `ITM-556`；`RunInTransactionScopeAsync` 的 finally 先 `RestoreTransaction` 再 `DisposeTransactionPreservingAsync`（`:290-294`），与 `ITM-704/707` 的嵌套保证一致。事务参与面（`CreateCommand` 集中赋 `cmd.Transaction`、批量路径逐处显式赋）已逐路径核对，未发现写操作脱离事务的路径。

### T7 `RollbackPreservingAsync` 用 `CreateLinkedTokenSource(CancellationToken.None)` `[事实]`
