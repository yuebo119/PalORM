# RFC：并行读租约（ARCH-001）

> 状态：**提案，待裁决**（2026-09-23）。来源：`docs/review/性能优化任务清单-2026-09-22.md` §十 ARCH-001；
> 证据来自 mimo26flash C11/C12、step5 P1-25、ds41flash P1/P3 与本轮源码复核。
> 本文件不改变任何行为；批准后另立实施任务。

## 一、问题

`SessionOperationState` 的单活动操作门禁让同一会话的任意两个操作完全互斥（`SessionOperationState.cs:75-83`
直接抛 `InvalidOperationException`，不排队）。后果：

1. **并发上限由会话数决定**。"一个请求一个会话、请求内并行发 N 个查询"这一最常见写法被门禁直接拒绝，
   调用方只能开 N 个会话（每个占一条池连接）或串行化。
2. **读路由的物理前提已具备但未开放**。`ForRead()` 已让只读查询走独立物理连接
   （`DataSession.cs:36-57` 的 `_readConnectionString` / `_readConnProvider`），
   与主连接本就是两条连接，多只读操作并发的物理条件存在，是纯策略没开放。
3. **原始 SQL 家族完全不参与读路由**（mimo26flash C12）：`DataSession.Query.cs` 的
   `QueryAsync/ScalarAsync/ExecuteAsync/QueryAsyncEnumerable` 经 `CreateCommand()` 恒走主连接
   （`DataSession.cs:603-605`），长流式枚举全程占住主连接与租约，会话整体冻结到流结束。

## 二、目标与非目标

**目标**：让"同一会话内的只读并发"成为受支持的能力，同时保持写路径与事务的串行语义不变。

**非目标**：不做连接池改造、不做跨会话共享、不改写路径重试语义、不引入新的调度线程。

## 三、候选方案

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| ① 仅文档化 | 明确"并发度 = 会话数"，给出 `Task.WhenAll` + 多会话范式 | 零风险、零 API 变更 | 不解决问题；调用方仍需自建会话池 |
| ② 计数型只读租约 | `ForParallelReads()`（或 `EnterReadOnlyParallel`）：只读操作允许 N 个并发租约，各自绑定读连接；写与事务维持单租约 | 直接解决请求内并行读 | 门禁语义变更（公共 API 决策）；需定义与事务/流式枚举/Dispose 的交互 |
| ③ 读连接从池取 | 只读查询每次从池取连接、用完归还（替代会话级持有单条读连接） | 彻底解决读连接串行；与 ② 正交 | 读连接建立成本（远程约 8.5ms/条，池内复用可摊薄）；失去"读连接初始化一次"的现状 |

## 四、推荐

**② + ③ 组合，分两步**：

1. **第一步（② 的最小形态）**：`ForParallelReads()` 返回一个只读并行作用域，作用域内：
   - 只读操作（`From<T>()` 的 SELECT 家族、原始 SQL 的 Query/Scalar）允许并发持有只读租约，计数上限可配（默认 8）；
   - 写操作、事务、Bulk 家族仍走单租约语义，与并行读互斥（进入写路径时等待并行读租约归零，或直接拒绝并给出明确消息）；
   - 读连接的取得改为"作用域内从池取、用完归还"（即方案 ③ 的读路径），避免多租约争抢同一条 `_readConnection`。
2. **第二步（原始入口接读路由）**：把 `DataSession.Query.cs` 的四个入口在"无事务"时接入 `_readConnProvider`，
   与第一步的池化读连接合并落地。

**不建议**在本轮把写路径也并发化：写路径的串行是事务与乐观锁语义的基础，收益与风险不成比例。

## 五、语义细节（实施前必须逐条定稿）

1. **与事务的交互**：并行读作用域内出现活动事务时，只读操作必须回到主连接（事务快照一致性），
   即"并行读仅在无事务时生效"。违反时显式失败而非静默降级。
2. **流式枚举**（`QueryAsyncEnumerable`）：枚举器持有租约直到 Dispose；并行作用域内的枚举器各占一个租约计数，
   作用域退出时若有枚举器未释放，按现有 `DisposeWaitTimeout` 语义处理（不得静默等待）。
3. **GridReader**：其租约语义是"钉死整个会话"（mimo26flash C8），并行作用域内不允许使用（显式拒绝）。
4. **Dispose 语义**：会话 Dispose 需等待所有并行租约归零，超时沿用 `DisposeWaitTimeout`（R10/PERF-003 相关）。
5. **连接池配比**：并行度 N 意味着最多 N 条读连接；文档必须给出"并行度 × 会话数 ≤ 池容量"的配比指引，
   否则池饥饿会以超时形式暴露（见 P1-27/P1-35 的重试放大）。
6. **熔断与弹性**：并行读各自独立走弹性管线；熔断器作用域按 RES-002 的 `CircuitBreakerScope` 决定共享粒度。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 门禁语义变更 | 现有依赖"重叠即抛"的调用方会看到行为变化 | 新能力走 opt-in 作用域（`ForParallelReads()`），默认行为完全不变 |
| 池饥饿 | 并行度放大连接需求 | 默认并行度 8 + 文档配比指引 + 池容量不足时的显式错误 |
| 只读一致性 | 读连接可能是副本（复制延迟） | 沿用现有 `ForRead()` 契约；并行作用域不改变"读路由 = 可能读副本"的既有语义 |
| 测试矩阵 | 需覆盖并发读、写互斥、事务内降级、枚举器泄漏、Dispose 等待 | 实施任务须带五类定向用例，且每类都能在旧代码上失败 |

## 七、待裁决问题

1. 是否接受"只读并行、写与事务保持串行"这一非对称语义（而不是全并发）？
2. 并行度默认值（建议 8）与是否可配（建议 `DbOptions.MaxParallelReads`）。
3. 写路径遇到活跃并行读时的行为：等待归零（建议）还是直接拒绝？
4. 读连接池化的取舍：接受每次从池取（方案 ③）还是保留会话级单条读连接并只允许并行读作用域内池化（建议后者）？

## 八、若批准的实施分解（供估算，不含在本文件内）

1. `SessionOperationState`：并行租约计数与门禁交互（含写路径等待/拒绝策略）。
2. `DataSession`：`ForParallelReads()` 作用域 + 读连接池化路径。
3. `QueryBuilder`/`QueryBuilderExtensions`：只读路径接入并行租约。
4. `DataSession.Query.cs`：四个原始入口接读路由（无事务时）。
5. 测试：五类定向用例 + 并发压力用例；文档：并发范式与池配比指引。
