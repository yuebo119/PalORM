# 方案：自动 Query Tagging（SourceGen Interceptor）

> 状态：**已实施**（v5.1，2026-07-28）· ADR：[ADR-F](adr/ADR-F-auto-tagging-interceptor.md)
> 来源：行业趋势调研 2026-07-28 · 严格遵循 B28「特性推荐四问」

## 一、背景与动机

### 1.1 现状（[事实] 已核查源码）

PalORM 已有手动 Tagging 能力：

```csharp
// QueryBuilder.cs:363-374
public QueryBuilder<T> Tag(string name) {
    AddClause(QueryClauseKind.Comment, $"/* {ValidateSqlComment(name)} */");
    return this;
}
public QueryBuilder<T> TagWithCaller([CallerMemberName] string? member = null,
    [CallerFilePath] string? file = null, [CallerLineNumber] int line = 0)
    => Tag($"{file}:{line} {member}");
```

**痛点**：用户必须**每次查询显式调用** `TagWithCaller()`，80% 场景会忘记。生产排障时 SQL 日志无法定位到源码调用点——这是高频运维痛点。

### 1.2 行业趋势（[事实] EF Core 2025 已验证）

EF Core 社区 2025 年用 **SourceGen Interceptors**（.NET 8+ 特性）实现自动 Query Tagging：
- 检测 `ToListAsync()` / `FirstOrDefaultAsync()` 等**终态方法**调用
- 在编译期自动注入 `TagWith(file:line member)` 等效注释
- 用户零代码改动，生产 SQL 日志自动带源码定位

**参考**：[Thirty25 博客《Automatic Query Tagging in EF Core Using Source Generator Interceptors》](https://thirty25.blog/blog/2025/04/ef-core-source-gen-interceptors)（2025-04）

### 1.3 B28 四问过滤

| 问 | 答 |
|----|-----|
| ① ORM 职责吗？ | ✅ ORM 生成 SQL，自然负责源码定位标签 |
| ② AOT 可行吗？ | ✅ SourceGen Interceptor 是编译期机制，零反射 |
| ③ 客户自建更好吗？ | ❌ 客户无法自己注入拦截器（必须在 ORM 调用点生成） |
| ④ 真必需吗？ | ✅ 生产排障刚需，`TagWithCaller` 已验证价值但手动调用易忘 |

**结论**：通过四问过滤，值得做。

## 二、技术方案

### 2.1 .NET 8+ Interceptors 机制

[事实] Interceptors 是 .NET 8 引入的实验特性（`InterceptsLocationAttribute`），允许源生成器在**编译期**重写方法调用点：

```csharp
// 编译期由源生成器生成
[InterceptsLocation("Program.cs", 42)]  // 精确到 file:line
public static ValueTask<List<T>> ToListAsync_Intercepted<T>(this QueryBuilder<T> builder, CancellationToken ct = default)
    => builder.TagWithCaller().ToListAsync(ct);  // 原方法前自动注入 Tag
```

**关键约束**（[事实] 来自三十25 博客）：
- 需 `.NET 8+`（PalORM 已 net11.0 ✅）
- `InterceptsLocationAttribute` 类型需源生成器项目自定义（不走 `System.Runtime.CompilerServices`）
- 需在消费项目启用 `InterceptorsPreviewNamespaces`

### 2.2 PalORM 方案：双轨制

**设计原则**：不强制启用——通过 `PalORMInterceptorOptions` 开关控制，默认关闭。

#### 轨道 A：手动模式（现状保留）

`Tag()` / `TagWithCaller()` 保持不变，用户显式调用。

#### 轨道 B：自动模式（新增）

用户在 csproj 启用：

```xml
<PropertyGroup>
  <!-- PalORM Interceptor 预览开关（.NET 8+ Interceptors 是实验特性） -->
  <PalORMAutoTagging>true</PalORMAutoTagging>
  <InterceptorsPreviewNamespaces>$(InterceptorsPreviewNamespaces);PalORM.Interceptors</InterceptorsPreviewNamespaces>
</PropertyGroup>
```

源生成器检测到 `PalORMAutoTagging=true` 后，自动生成拦截器：

```csharp
// PalORM.AutoTagging.g.cs（生成在消费项目）
namespace PalORM.Interceptors;

[InterceptsLocation("Controllers/UserController.cs", 42)]
public static ValueTask<List<User>> ToListAsync_AutoTag_0<T>(this QueryBuilder<T> builder, CancellationToken ct = default)
    where T : class, new()
{
    // 调用现有 TagWithCaller（复用 CallerFilePath 等编译期信息）
    return builder.TagWithCaller().ToListAsync(ct);
}
```

### 2.3 生成器实现（IIncrementalGenerator 扩展）

在 `PalORMGenerator.cs` 新增 Pipeline：

```csharp
// 伪代码——实际实现参考 EF Core thirty25 模式
var queryTerminals = context.SyntaxProvider
    .ForAllInvocations(nameof(QueryBuilderExtensions.ToListAsync))
    .Where(inv => IsQueryBuilderExtension(inv))  // 过滤非 PalORM 同名方法
    .Collect();

context.RegisterSourceOutput(queryTerminals, (spc, calls) =>
{
    var sb = new StringBuilder();
    sb.AppendLine("namespace PalORM.Interceptors {");
    sb.AppendLine("    internal static class AutoTaggingInterceptor {");
    int i = 0;
    foreach (var call in calls)
    {
        // call.FilePath, call.Line, call.MethodName（来自 InvocationExpressionSyntax 位置）
        sb.AppendLine($"        [InterceptsLocation(\"{call.FilePath}\", {call.Line})]");
        sb.AppendLine($"        public static ValueTask<List<{call.TypeArg}>> ToListAsync_AutoTag_{i}<T>(...)");
        sb.AppendLine($"            => builder.TagWithCaller().ToListAsync(ct);");
        i++;
    }
    sb.AppendLine("    }");
    sb.AppendLine("}");
    spc.AddSource("PalORM.AutoTagging.g.cs", sb.ToString());
});
```

### 2.4 被拦截的方法清单

参考 `QueryBuilderExtensions.cs`（已核查），终态方法如下：

| 方法 | 用途 | 拦截必要性 |
|------|------|-----------|
| `ToListAsync<T>()` | 查询列表 | ✅ 最高频 |
| `FirstOrDefaultAsync<T>()` | 查询单行 | ✅ 高频 |
| `FirstAsync<T>()` | 查询单行 | ✅ |
| `SingleOrDefaultAsync<T>()` | 查询单行 | ✅ |
| `ToPageAsync<T,TKey>()` | 分页查询 | ✅ |
| `ExecuteNonQueryAsync<T>()` | UPDATE | ✅ |
| `QueryMultipleAsync<T>()` | 多结果集 | ⚠️ GridReader 不经拦截器（已知限制） |
| `CountAsync` / `LongCountAsync` | 聚合 | ⚠️ 可选 |

## 三、关键决策

### 3.1 为何不强制启用（设计权衡）

| 方案 | 优点 | 缺点 |
|------|------|------|
| **强制启用**（默认开） | 零配置生产可观测 | Interceptors 是实验特性，强制依赖可能 break 用户 |
| **opt-in 开关**（推荐） | 用户可控；不依赖实验特性项目无风险 | 需配置 csproj 一次 |
| **纯手动**（现状） | 零依赖 | 手动调用易忘 |

**决策**：opt-in。理由：(1) Interceptors 是 .NET 8+ 实验特性（[事实]）需 `InterceptorsPreviewNamespaces`；(2) PalORM 设计哲学是无依赖，不应强制用户启用预览特性。

### 3.2 Tag 内容格式

沿用现有 `TagWithCaller` 格式（[事实] `QueryBuilder.cs:374`）：

```sql
/* C:\src\app\Controllers\UserController.cs:42 GetUserList */ SELECT ...
```

**已知限制（保留现状）**：`[CallerFilePath]` 是**编译机绝对路径**，会泄露内部目录结构到 DB 日志。用户可用 [PathMap](https://learn.microsoft.com/dotnet/csharp/language-reference/compiler-options/advanced#pathmap) 规范化。

### 3.3 性能影响

- **编译期**：增量生成器只处理新增/变更调用点，影响极小
- **运行期**：每次查询多一次 `AddClause` 调用（现有 `Tag` 实现），ns 级开销
- **SQL 长度**：+约 60 字节注释，DB 日志增长可忽略

## 四、AOT 兼容性

### 4.1 全链路 AOT 安全

| 链路环节 | AOT 状态 | 依据 |
|----------|----------|------|

| `AddClause(QueryClauseKind.Comment, ...)` | ✅ 安全 | 现有路径，AotTest.MySql 已通过 |

## 八、实施差异说明（B9 教训：方案文字 vs 实施代码）

> 2026-07-28 实施后补充。方案文字基于推断，实施过程发现多个技术约束与方案假设不符。

### 差异 1：Roslyn API 位置

| 方案假设 | 实际事实 |
|---------|----------|
| `SemanticModel.GetInterceptableLocation` 实例方法 | **`CSharpExtensions.GetInterceptableLocation` 扩展方法**（在 `Microsoft.CodeAnalysis.CSharp` 命名空间） |

**影响**：首次 PoC 编译失败 6 个错误。修正：加 `using Microsoft.CodeAnalysis.CSharp`。

### 差异 2：`IncrementalGeneratorInitializationContext` 配置访问

| 方案假设 | 实际事实 |
|---------|----------|
| `context.AnalyzerConfigOptions.GlobalOptions` 同步读取 | `context.AnalyzerConfigOptionsProvider`（增量值提供者，需 `.Select`） |

**影响**：编译错误 CS1061。修正：改用增量管道 `context.AnalyzerConfigOptionsProvider.Select((provider, _) => ...)`。

### 差异 3：MSBuild Property → 源生成器传递机制

| 方案假设 | 实际事实 |
|---------|----------|
| MSBuild Property 自动暴露给源生成器 | 需 `<CompilerVisibleProperty Include="..."/>` 显式声明 |

**影响**：诊断输出 `found=False`（属性未传递）。修正：buildTransitive targets 自动注入 `CompilerVisibleProperty`。

### 差异 4：InterceptsLocationAttribute 命名空间与 file class

| 方案假设 | 实际事实 |
|---------|----------|
| `file sealed class` 在自定义命名空间 | 编译器硬编码要求 `System.Runtime.CompilerServices` 命名空间；file-scoped namespace + 多 namespace 声明冲突（CS8954） |

**影响**：CS8954 + CS9137 错误。修正：用两个 block namespace（非 file-scoped），attribute 放 `System.Runtime.CompilerServices`，拦截器类型放 `PalORM.Generated`。

### 差异 5：TagWithCaller 不能直接复用

| 方案假设 | 实际事实 |
|---------|----------|
| 拦截器方法体 `builder.TagWithCaller().XxxAsync()` | `[CallerFilePath]` 在拦截器中返回**拦截器自身位置**（.g.cs），不是原始调用点 |

**影响**：Tag 注释会指向生成的 .g.cs 而非用户源码。修正：用 `builder.Tag(string)` + 编译期常量（路径从 `InvocationExpressionSyntax` 提取，硬编码到生成的方法体）。

### 差异 6：Roslyn 版本无需升级

| 方案假设 | 实际事实 |
|---------|----------|
| 需升级到 Roslyn 4.12+ 才能用稳定 Interceptors API | 项目已是 **5.6.0**（高于 4.12），API 完全可用 |

**影响**：v1 计划的"Phase 1 Roslyn 升级前置"完全多余。v2 PoC 直接跳过升级，1 天验证通过。
