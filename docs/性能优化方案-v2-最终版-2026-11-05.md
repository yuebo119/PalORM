## 0. 结论

本轮剩余的真实空间有三个来源：已落地未收口的收益、SQLite 读侧的单点、以及 per-op 形态下每操作都会触发的少数路径。继续削减「每次调用的会话固定税」不是方向，理由有三层证据，见 §1。

外部两份方案共提交 15 项候选，8 项与既有裁决冲突、已落地或经核实为伪缺口；1 项（编译期查询特化）成立但需先过覆盖率实验；保留 6 项，其中 4 项可立即执行、2 项待前置探针判定。

外部评审的三块新证据已并入；其两处口径错误已记录在 §1.3，避免下轮沿用。

| 方向 | 内容 | 预期 | 状态 |
|---|---|---|---|
| 大 | SQLite 读侧 `json_each` 多键读 | **实测 4.88× 对参数化 IN**（见 §1.4） | 未落地 |

## 1. 诊断复核

### 1.1 外部两案的诊断准确性

方案甲的诊断有实数据支撑：BDN 基线里 `PalORM_GetByKey` 时延 1.195×、分配 2.329×，`PalORM_Update` 1.322× / 3.753×（对 ADO）。这些数字我逐项复算，准确。方案乙对 `[InterceptsLocation]` 链路（`AutoTaggingEmitter.cs`，9 个终态方法，当前只做 `builder.Tag(...)` 转发）的判断也准确。

诊断准确，但归因需要拆开，见下节。

### 1.2 单行差分的器材拆账

【事实】BDN 器材（`bench/PalORM.Benchmarks/01_CrudBenchmarks.cs`）：

- ADO 臂用 `BenchmarkConfig.OpenSqlite`，只做 `new SqliteConnection` + `Open()`，1584B / 22,122ns
- PalORM 臂用 `DataSession<SqliteProvider>.CreateAsync`，3688B / 26,432ns
- 比值：分配 2.329×、时延 1.195×

【事实】PerfHub 器材（`bench/PalORM.PerfHub/Implementations.cs:2180-2183`）：两臂共享同一夹具连接，PalORM 只多一个 per-op 会话对象且不 `Dispose`。实测（`history-20261102-181157.json`，SQLite/2000）：

| 操作 | ADO 分配 | PalORM 分配 | 分配比 | 时延比 |
|---|---|---|---|---|
| GetByKey | 2127.6 B | 2272.9 B | 1.068 | 1.000 |
| Insert | 2883.0 B | 2836.2 B | 0.984 | 0.988 |
| Update | 2618.5 B | 3187.8 B | 1.217 | 1.000 |

【推断】BDN 的 2.33× 与 PerfHub 的 1.068× 之差约 1415B，对应 `CreateAsync` 相对「共享连接」多做的部分：连接对象创建与 `OpenAsync`、`CancelAfter` 两次定时器武装（`DataSession.cs:197,205` 注释自述每会话约 100B）、Provider 初始化钩子（SQLite PRAGMA）、interceptor 列表复制、`Dispose` 释放路径。PerfHub 注释自述会话构造本身为 968B，`DataSessionPool.cs:5` 自述每操作约 1.5KB 分配差横跨五组基准项，两者是同一现象的两种口径（会话对象 968B，含连接与初始化的全套约 1.5KB）。

由此得到两个硬约束：

1. 只减会话对象（968B）的上限是把 3688B 降到 2720B，即 1.72×，达不到方案甲宣称的 1.3~1.6×。要越过 1.6× 必须同时处理 `CreateAsync` 的连接与初始化路径。
2. 默认池化能整体绕开 1415B + 968B，接近 PerfHub 的 1.068×。但池化已由 `DataSessionPool` 提供，README 已量化推荐（`README.md:280`：`GetAsync` 比每操作新建会话快约 3.8 倍、分配低约 45%）。

结论：固定税这条路的库内空间已被账本判到地板，剩余收益属于形态问题，改代码改不动，改用法可以。

按 B28「特性推荐四问」与 B145「声称新发现前先查已文档化取舍」，逐项对账 `perf-ledger`：

| 形状哈希增量维护 | 乙 P2 第 1 项 | 表 2 弃项 | `QueryBuilder.cs:35-37`：「原增量维护有三个写入者……克隆与直赋路径旁路 Combine 产生残缺哈希」 |
| 结果集溢出路径「两趟全量拷贝」 | 甲 P1-1、乙 P1 第 2 项 | 伪缺口 | 见下节 |
| `CommandBehavior` 两项 | 反例表曾提及 | 表 2 已证伪 | SingleRow +2.7%、SequentialAccess −0.5% |
| 会话构造削减 | 甲 P0-1 | 表 2 降级 | 会话构造占时延 4.5%，低于 5% 线；见 §2 |

伪缺口的核实：`ResultListReader.cs:59-84` 的 `list.CopyTo(buffer)` 只拷 `initialCapacity`（默认 16，`SessionOperationState.cs:521`）个元素，全量拷贝只有收尾一次。对照臂 `AdoNetImpl.QueryAllAsync` 走 List 几何扩容（容量到 32768，约 524KB 进 GC），本实现走 `ArrayPool`（零 GC 分配）加 `list.Capacity = count` 一次 160KB，**已省约 360KB 分配**，代价是 160KB memcpy，占 QueryAll/20000 的 9680µs 的 0.2%。PerfHub 该项分配比 0.992、时延比 0.992，与推断一致。改单遍化会把池化收益换成 GC 分配。

外部评审的两处口径错误，记录以免下轮沿用：

1. 「src 实际是 163 个文件」：163 是含 `bin/obj` 下 73 个生成文件的数，项目源码是 90 个 / 31,143 行。据此推出的「逐文件重读是抽样的」不成立。
2. 「方案引用的 Update 分配比 3.75× 远超 1.5× 门槛，重开条件可能已满足」：3.75× 是 BDN 口径（PalORM 走 `CreateAsync`，ADO 只开连接），账本的 1.25 与 1.5 线是 PerfHub 口径（两臂共享连接）。实测 PerfHub 为 1.217×，未达线。按该读法，任何含 `CreateAsync` 的基准都会自动满足重开条件，这条线将永久失效。

### 1.4 SQLite 读侧复测（Phase 0.2，本轮已跑）

`bench/crossbench/ReadProbe` 独立探针实测（临时库、不依赖容器、2 预热加 10 计时取中位、四形态物化路径逐位相同）：

| 档 | 形态 | µs/键 | 分配 B/键 |
|---|---|---|---|
| 1,000 | PerKey-NewCmd | 7.58 | 1152 |
| 1,000 | PerKey-Reuse | 4.14 | 617 |
| 1,000 | Param-IN-999 | 4.15 | 429 |
| 1,000 | **JsonEach-1P** | **0.85** | **171** |
| 100 | PerKey-Reuse | 4.02 | 622 |
| 100 | Param-IN-999 | 1.71 | 439 |
| 100 | JsonEach-1P | 1.02 | 154 |

三个判据全部命中：

1. JsonEach 对 PerKey-Reuse 是 4.87×（时延）/ 3.6×（分配），对 Param-IN 是 **4.88× / 2.51×**。账本记录「4.9~5.0×，分配 2.5×」，吻合。
2. 综合终版方案的基线「PerKey-Reuse 4.15µs/键」，实测 4.14，一致。
3. **产品当前形态（Param-IN）在 1000 键档已退化到与逐键复用同速**（4.15 对 4.14），100 键档尚有 2.3× 优势。多键场景下现有形态没有优势。

因此 Phase 1 成立，其前置（探针入库）已由既存提交满足。

## 2. P0-1 专项裁决

方案甲的 P0-1（会话构造削减 / 轻量作用域 / 默认池化）是外部两案与评审共同关注的一项，也是唯一存在三方分歧的一项。它的三种可能含义对应三种处置：

| 含义 | 判定 | 理由 |
|---|---|---|
| 库内削减会话构造对象 | 不做 | 表 2 已测：会话构造占时延 4.5%，低于 5% 行动线；且上限 1.72×（§1.2），达不到方案宣称的 1.3~1.6× |
| 改为默认池化 | 不做 | 表 2「池化可配置开关」为用户 2026-10-13 裁决不做；改默认会改变会话生命周期语义（租期复位、归还门禁），属破坏性变更 |
| 新增轻量 API 形态 | 另立议题 | 属 API 设计而非性能优化。若指新的作用域写法，应走 API 设计流程，不进性能批次 |

地面事实是：池化这条路已经铺好且已文档化。`DataSessionPool` 是成熟实现（语义契约、归还门禁、线程安全齐备），README 已给出量化推荐，PerfHub 基准矩阵里 `PooledGetByKey` 与 `GetByKeySession` 已覆盖三方言。**问题不是能力缺失，而是可发现性**：用户看基准矩阵只能看到 per-op 形态的数字，看不到形态切换能拿到什么。

因此本轮的处置是：不做 P0-1 的代码改动，改为交付形态对照数据（§5）。

契约草案：

```csharp
/// <summary>按主键集合批量读取。方言分流：SQLite 单参数 json_each；
/// PostgreSQL = ANY(数组)；MySQL 现有分批 IN（方言感知，G31）。</summary>
public ValueTask<List<T>> GetByKeyManyAsync<T>(
    IReadOnlyList<object> keys, CancellationToken ct = default) where T : class, new();
```

四个设计点（推荐值待确认）：

| # | 决策点 | 推荐 | 理由 |
|---|---|---|---|
| 1 | 返回顺序 | 按主键升序，文档明确不承诺输入序 | 服务端返回序；保输入序需客户端重排，与省往返的目标相悖 |
| 2 | 缺键处理 | 静默跳过，不返回 null 占位 | 与 `GetAsync` 缺键返回 null 的单键语义一致，批量形态用「结果行数可能少于键数」表达 |
| 3 | 空集合 | 返回空 `List<T>`，不抛、不发 SQL | 与既有批量 API 的边界处理一致 |
| 4 | 默认过滤 | 软删与租户过滤照常适用 | `GetAsync` 是主键读且带过滤，批量形态必须同语义，否则是安全缺口 |

B152 的教训是「探针形态与验收器材不同构，实施整轮后验收无感」。每个 Phase 必须先回答下表，答不出则该 Phase 不具备验收条件：
