# PalORM 测试机制重设计方案（2026-11-03）

> 状态：**待裁决**（P0 可独立开工，不依赖其余阶段）
> 定位：不新建测试体系，不重写用例。本方案只处理一件此前无人建模的事：**保证机制自身的结构**。
> 承接关系：《测试体系优化方案-2026-11-01》的 T0-4（地板自收紧）至今未实施，本文给出完整设计；该方案未识别的第 4 类失效（守卫内嵌）本文单列。文中不重开 2026-11-01 已否决的六项范围外条目。

## 三、四类失效模式

| 模式 | 表现 | 现有覆盖 | 缺口 |
|---|---|---|---|
| M1 静默丢弃 | 用例、契约条目被删，覆盖率随之消失，无人察觉 | 测试数地板（只拦总量下降，且常数会腐烂）；今日新增的契约账本 | 总量之外的局部丢弃仍可静默 |
| M2 守卫内嵌 | 不变量写在被它保护的对象内部，对象被删则守卫一起消失 | 无 | 完全裸奔，今日才被点名 |
| M3 判据无判别力 | 断言恒真、断言期望值写错、条目留着但掏空 | 弱断言棘轮（只认几种模式）、变异回放 11 条 | 绝大多数用例从未被证明能失败 |
| M4 声明漂移 | 文档、计数、账本与实现不一致 | G/V/D 系列文本门禁 | 门禁之间互相校验的成本随门禁数增长（今日 V26 改完，V27 报出第五处） |

2026-11-01 方案处理了 M1 与 M4 的一部分，并排了 T0-4 作为 M1 的核心修法，但 T0-4 至今未实施。M2 当时未被识别。M3 靠 T0-3 与 T3-1 的变异分，而 Stryker 自 2026-10-03 起连续失败，变异分至今没有产出过数值。

## 四、设计原则

现有机制的组织方式是「每出现一个缺口就加一条棘轮」。这四条原则用来替换它。

| 原则 | 含义 | 反例（现状） |
|---|---|---|
| P1 判据从产物算 | 测试报告与覆盖率 XML 是唯一事实输入，不对源码做正则推断 | 今日账本脚本用正则从 `.cs` 里抠 `new("C-XXX"` |
| P2 不存数字，存关系 | 地板要么由机器自动回写，要么与基线分支比较；人间只审 diff | 八项地板全是手写常数 |
| P3 守卫在体外 | 不变量写成数据清单，由外部脚本核验；测试只负责执行 | SQLite 全覆盖守卫写在测试方法体内 |
| P4 判别力必须被证明 | 变异分是基线指标，不是可选的月度活动 | 变异分至今无历史值 |

## 五、目标形态

| 层 | 内容 | 输入 | 现在对应什么 |
|---|---|---|---|
| L0 事实 | TUnit 报告、覆盖率 XML | CI 产物 | 已有，但只被少部分门禁使用 |
| L1 意图 | 一份 `intent.json`：必须存在的契约 ID、每条的方言要求、每条的最小断言数、各套件的用例下限 | 人工维护，改动即进 diff | 现在散在 `test-counts.json`、`conformance-contracts.json`、源码文本三处 |
| L2 判据 | 完备性、稳定性、判别力三条比较 | L0 与 L1 的差 | 现在是数十个各自为政的文本检查 |
| L3 事故 | 声明与现实一致的检查（G/V/D/T 的绝大部分） | 源码与文档 | 保留，但职责收窄为只管声明一致性 |

L2 三条比较的定义：

1. **完备性**：报告里出现的契约 ID 集合 ⊇ L1 声明的集合。差集即红。
2. **稳定性**：本轮 `passed` 与覆盖率不低于上一成功轮的自动回写值。
3. **判别力**：本轮变异分不低于上一成功轮。

三条都只读产物，不读源码文本。

## 六、方案

### P0 契约参数化（半天）

**动作**：把两个契约目录的执行方式从「一个 `[Test]` 方法内循环」改为 `[MethodDataSource]` 参数化，每条契约成为一个独立用例。TUnit 1.76 提供 `MethodDataSourceAttribute`，已核实包内存在。

**为什么**：现在 31 条契约产出 5 个用例（能力 1 + 方言 3 + 自检 1 中的 4 个执行用例），失败被拼成一个字符串。参数化后：

- 报告里每条契约独立出现，带 ID，独立标红
- 契约 ID 成为报告数据，完备性判据可读报告而不解析源码
- 删一条契约即少一个用例；删整个方法即少一批用例，两种情况都由 L2 稳定性判据接住
- 今日新增账本脚本的源码解析部分整体退役，只剩「读取报告 + 集合比较」

**验收命令**：

```
dotnet run --project test/PalORM.Integration.Tests -- --treenode-filter "/*/*/*Contract*/*"
# 期望：能力 11 个用例 + 方言 60 个用例（20 × 3）独立列出，每个 displayName 带契约 ID
```

**注入探针**：删掉 `C-JOIN-01` 条目，期望报告少一个用例且完备性判据报出该 ID；还原后转绿。

**回滚**：单提交，`git revert` 即回退。

**对总数的影响**：执行用例约 574 → 640。这正是 P2 存在的理由：结构性改动不该需要人工调地板。

### P1 意图单一真源（半天）

**动作**：把 `bench/baselines/test-counts.json` 与 `bench/baselines/conformance-contracts.json` 合并为一份 `bench/baselines/intent.json`，各门禁改读这一份。

**为什么**：现在同一条事实存在多处。计数器有三处声明文件，契约集合有一处账本，方言要求写在守卫代码里。三处漂移的实例今日已出现两次：删除数写成 18（实为 19）、段数七改八漏了第五处。

合并后 `bench/baselines/` 下只剩性能类与公开 API 类基线，测试治理只有一份意图文件。

**验收命令**：`grep -rn "test-counts.json\|conformance-contracts.json" scripts/ .github/ .githooks/` 返回零行。

**注入探针**：在 `intent.json` 里删掉一个契约 ID，期望完备性判据报「意图有、报告无」。

**回滚**：单提交。

### P2 地板自收紧（一天）

这是 T0-4 的完整设计。2026-11-01 的原文是两条同时生效：`passed >= floor` 防删除，`floor >= 0.95 * passed` 防衰减，并由 CI 在月度第一个工作日自动提交地板更新。

**这条规则的问题**：0.95 的容差意味着 574 个用例里可以静默删掉 28 个；月度粒度意味着最长一个月的衰减窗口。两个容差叠加，M1 只被削弱，没有被关闭。

**两种实现，需裁决**：

| 方案 | 机制 | 关闭 M1 程度 | 代价 |
|---|---|---|---|
| P2-a 自洽下钳 | 保留人工常数，增加 `floor >= passed * 0.98` | 单轮可静默删 2%（约 11 条） | 半天，零运维 |
| P2-b 自动回写 | CI 在 dev 的 push 成功后，若实测高于现值则提交更新，提交信息带 `[skip ci]`；人工不碰地板 | 单轮可静默删 0 条 | 一天，需 `contents: write` 与防循环 |

推荐 P2-b。理由：P2-a 的 2% 仍然是一个需要人记住的常数，而「需要人记住」正是这套机制反复失效的原因。P2-b 把地板变成机器维护的观测值，人只审 diff。

P2-b 的失败降级：CI 无写权限（fork PR、分支保护）时不开 issue，只在 job summary 打印建议值，门禁退化为 P2-a 的判据。

**验收命令**：

```
# P2-b：连续两次 dev push，第二次的 baseline 应含第一次的实测值
gh run list --workflow=verify.yml --limit 2
git log --oneline -1 -- bench/baselines/test-counts.json   # 应有 CI 自动提交
```

**注入探针**：构造 `passed=573` 的报告喂给 `assert-test-counts`，期望报 `573 < 地板 574`。（今日已验证通过）

**回滚**：删除 CI 回写步骤，地板留在最后一次自动值，退回 P2-a 形态。

### P3 判别力基线（两到三天）

**动作**：把变异分从「月度可选活动」改成「相对基线指标」：本轮变异分不得低于上一成功轮，下降即红。范围先限定 Core 与 SourceGen 两个项目。

**为什么**：M3 是四类里唯一没有任何机械覆盖的。11 条回放规则绑定的是 11 个产品片段，对 1569 个用例的判别力没有代表性。

**前置条件**：T0-3（Stryker 配置修好并产出分数）。该任务至今未完成，因此 P3 不能先于它开工。

**验收命令**：`gh run list --workflow=mutation-tests.yml` 连续两周有分数记录，且 `score >= previous_score`。

**注入探针**：把一个存活变异体的断言删掉，期望分数下降并报红。

**回滚**：变异分转 advisory 一周，不阻断。

## 七、备选方案与否决理由

| 方案 | 内容 | 否决理由 |
|---|---|---|
| A 按事故继续加棘轮 | 每发现一个缺口加一个脚本 | 门禁数量已到 33+27+11+24+8 的规模，门禁之间需要互相校验（V26 与 V27 今日互为补漏），边际成本高于收益 |
| B 全量 manifest 驱动 | 1569 个用例逐个声明 ID、目标、判别对象 | 一次性改动全部测试，风险与收益不成比例；2026-11-01 已否决「每个公共 API 强制一条测试」的同类做法 |
| C 换测试框架 | 用 VSTest 生态换更多工具 | TUnit 只支持 MTP，换框架会丢并行与报告能力；2026-11-01 已否决 |
| D 本方案 | 三层判据 + 四个阶段，只改保证机制 | 选它 |

## 八、明确不解决

| 问题 | 为什么机制层解决不了 |
|---|---|
| 断言期望值写错 | 静态检查没有语义。只有变异分能部分覆盖，而变异分只证明「改动会被发现」，不证明「期望值正确」 |
| 门禁被有权提交者删除 | 任何门禁都不保护自己。删脚本、摘钩子段、摘 CI 步、删清单登记，四件一起做仍然绿。本方案只把删除动作从一处 diff 增加到多处 |
| 用例的判据选得对不对 | 这是设计判断，不是机制问题。回放规则与人工评审是唯一手段 |

## 九、自我反驳

按全局规范的辩证流程，对本方案做四条反驳并评分。

| 反思点 | 反驳 | 评分（10 分制） | 结论 |
|---|---|---|---|
| 是否在解决真问题 | 1569 个用例首次全绿，说明现状可用；重设计可能只是把可用的东西改成另一种可用 | 7 | 部分成立。所以 P0 只改观测方式不改断言，P3 设为 advisory 起步 |
| P2-b 是否引入新风险 | CI 自动提交基线，若回写逻辑出错会污染历史并可能触发循环 | 8 | 成立。缓解：只在 dev push 成功时回写、`[skip ci]`、写失败降级为打印建议值 |
| 是否与 2026-11-01 方案冲突 | 该方案的 T0-4 容差是 5%，本文改为 0 并要求自动回写 | 3 | 不冲突，是同方向收紧。但属于对该方案参数的修改，需在附录 A 显式登记 |
| P0 是否值得 | 只把 5 个用例拆成 71 个，覆盖率一点没变 | 6 | 值得。它换掉的是「守卫可被整方法删除」与「正则解析源码」两个结构缺陷，不是覆盖率 |

综合评分 6.0。不到 7 分的原因是 P3 依赖一个至今未完成的前置任务（T0-3），方案的完整闭环不在本轮可控范围内。

**推翻条件**：若三条同时成立，本方案应停止。第一，T0-3 在未来两周内仍无法产出变异分；第二，P0 完成后完备性判据在真实提交中零命中；第三，团队规模保持单人且提交频率低于每周一次。

## 十、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| P0 改动导致用例数与地板不一致，CI 连续红 | 高 | 中 | P0 与 P2-b 同一分支落地；P0 单独落地时手工下调地板并注明 |
| CI 自动回写触发循环构建 | 中 | 中 | 提交信息带 `[skip ci]`；workflow 的 `paths-ignore` 覆盖 baseline 目录 |
| 合并 baseline 文件时漏改某个读取方 | 中 | 高 | P1 的验收就是全仓 grep 零残留，与三方一致纪律同源 |
| 变异分下降被误判为回归（等价变异体） | 高 | 低 | 等价变异体登记表，逐条人工裁决，与 perf-ledger 的「勿重开」表同形态 |
| 意图文件成为新的漂移源 | 中 | 中 | 意图文件只存「必须存在」的集合，不存测量值；测量值全部来自报告 |
