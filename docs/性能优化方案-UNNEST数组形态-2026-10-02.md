# UNNEST 数组形态实施方案（2026-10-02 立项）

> 依据：`docs/性能优化方案-提升空间实施-2026-10-02.md` 第三节（PoC 结论 GO）。用户指令：按立项流程走。
> 前置事实全部来自已完成的两轮实测（探针 `pgplan` / `pgunnest`，42 万行表 2000 行、事务内回滚），
> 以及 `.ai/aot-poc/UnnestAotPoc` 的 AOT 可行性验证。**本文只写方案，不含实现**；未实施前
> 收益数字一律标注来源与口径。

## 一、收益与口径（已实测，非预估）

| 操作 | 现产品路径 | 数组形态 | 时延 | 客户端分配 |
|---|---|---|---|---|
| UPDATE | 16.35ms（VALUES 1000×2） | 11.53ms | **−30%** | 未测 |
| UPSERT | 42.42ms / 2.51MB（VALUES 1000×2） | 38.90ms / 103KB | −8% | **−96%** |
| DELETE | 6.63ms / 833KB（IN 2000 参数） | 3.16ms / 5KB | **−52%** | **−99%** |

口径：PG 18.4，42 万行表，2000 行/次，事务内执行后回滚；时延为墙钟中位，分配为客户端托管分配。
**收益不是普适的**——三项里 UPDATE 与 DELETE 是时延收益，UPSERT 是分配收益（时延只 −8%），
实施后需按项验收而非笼统宣称"快 N 倍"。

AOT 可行性（已实测）：Npgsql 10.0.3 + NativeAOT，发布 0 个 IL/AOT 警告，原生二进制执行
`UPDATE FROM UNNEST`、`INSERT…SELECT UNNEST ON CONFLICT`（插入与更新两分支）、`DELETE = ANY`，
覆盖 bigint/text/int4/numeric/可空 int8/timestamptz/uuid 七种数组，2000 行结果逐项校验通过。

## 二、为什么这正是 PG 的瓶颈（机制，不是形态偏好）

`pgplan` 探针实测的三种形态与计划：

| 形态 | 计划 | 墙钟中位 |
|---|---|---|
| VALUES 2000×1（原产品形态） | Hash Join + 目标表全表 Seq Scan | 45.39ms |
| VALUES 1000×2（现产品形态） | Nested Loop + 主键 Index Scan | 19.50ms |
| UNNEST 数组 2000×1 | Nested Loop + Index Scan | 11.53ms |

关键：**VALUES 行数相对表规模**决定规划器选择。2000 行 VALUES 在 42 万行表上被估成
Hash Join + 全表顺扫；UNNEST 的数组基数估计更准，稳定走索引计划，且单语句可一次承载 2000 行
（VALUES 现受 1000 行/批上限约束，是本轮 6caeada 的产物）。

## 二·五、阶段切分（2026-10-02 实施轮定案）

原方案第七节的五步在实施轮细化为**两个交付阶段**，理由是"阶段 A 会暴露 Provider 数组参数抽象
是否成立"——若它在最简单的单列形态上就跑不通，阶段 B 的多列形态要跟着一起返工。

| 阶段 | 范围 | 为什么这么切 |
|---|---|---|
| **A（本次）** | `BulkDeleteAsync` 单入口 + PG 数组参数 + 键归一化复用 | 三个入口里 SQL 形态最简单（键列单一），能最先跑通「生成器 → Provider → Core」全链路；收益明确（−52% 时延 / −99% 分配） |
| **B（下次）** | `BulkUpdate` / `BulkMerge` 共享同一数组参数层 | 需要多列转置，是 A 的自然延伸；共用 A 已验证的参数抽象 |

**阶段 A 的验收口径**：PG 真库逐位比对（数组形态与现路径对同批输入产生相同的库内行）
+ 空键集 + 租户/软删过滤仍生效 + AOT 复验 + PerfHub PG 子集批对照。

## 三、实施范围（三个组件，按依赖顺序）

### 3.1 源生成器（`PalORM.SourceGen`）：发射**元素级**键数组绑定器

> **路径修正（2026-10-02，实施轮读码后）**：原设计写的是"发射类型化数组绑定"（把每行一参数组
> 改写成每列一数组）。读码后改为**只发射元素级绑定，数组容器由 Core 侧通用代码填充**，理由：
>
> 值转换逻辑（枚举 `StoreAs`、`[Converter]`、`OwnedJson` 序列化、可空 → `DBNull`）已全部在
> `CommandFactoryEmitter.GetParameterValueExpression` 里实现。若为数组形态再发射一份"每列一数组"
> 的等价逻辑，**同一套转换语义就有了两份真源**——将来任何转换器变更都要改两处，
> 正是 B120（同构路径不对称，同一模式只修一半）那一族缺陷的温床。
>
> 新路径让生成的元素级绑定器保持**唯一一份**，Core 侧只做"对每列循环、把元素值写进数组"，
> 不复制任何转换语义。

现状（`CrudMetadata` 契约）：`BindInsertValues` / `BindUpdateValues` 是
`Action<DbParameter[], object, int>`——按列写 Value，池由调用方建。

阶段 A 需要新增的是**主键元素级提取器**（BulkDelete 只需键列）：

```csharp
// 形态示意（真实签名以实现为准）：把键对象归一为 provider 侧元素值
internal static object? NormalizeKey(object key)   // 复用 GenerateBindDeleteBody 的归一化 switch
```

复用点：`GenerateBindDeleteBody` 已有的归一化逻辑（`Convert.ToInt64(key)` / `(string)key` /
`Convert.ChangeType(...)` / Converter 列的 `_conv_X.ToProvider(...)`）——**逐条复用，不重写**。

对 `BulkUpdate` / `BulkMerge`（阶段 B）同理：元素级提取器复用
`GetParameterValueExpression` 的**逐列**形态，Core 侧按列循环填充数组。

**AOT 约束**：不得用反射建数组（G4/G6 门禁）；数组类型在生成期静态确定。PoC 已证明可行。

### 3.2 PG Provider（`PalORM.PostgreSql`）：创建类型化数组参数

现状 `PostgreSqlProvider.CreateParameter(name, value)` 按值推断类型。需要新增数组参数工厂：

```csharp
DbParameter CreateArrayParameter(string name, Array values);
```

要点：
- 走 Npgsql 的类型化数组绑定（`NpgsqlParameter` 的数组重载），**不是**拼 `ARRAY[...]` 文本——
  后者会引入元素级转义与参数上限问题，且 PoC 未验证。
- 空数组与全 NULL 数组的绑定语义须锁定（PG 对空数组的推断可能失败，PoC 的 `@ids` 段需补测）。

### 3.3 Core（`PalORM.Core`）：PG 分支切换形态

切四个入口（**仅 PG 分支，MySQL/SQLite 不变**，见第 4 节为什么）：

| 入口 | 现状 SQL | 数组形态 |
|---|---|---|
| `BulkUpdateAsync` | `UPDATE … FROM (VALUES …)` 1000 行/批 | `UPDATE … FROM UNNEST(@c0, @c1, …) AS v(c0, c1, …)` |
| `BulkMergeAsync` / UpsertBatch | `INSERT … ON CONFLICT … VALUES` 1000 行/批 | `INSERT … SELECT * FROM UNNEST(…) ON CONFLICT …` |
| `BulkDeleteAsync` | `DELETE … WHERE pk IN (@p0…@p1999)` | `DELETE … WHERE pk = ANY(@ids)` |
| `WhereIn`（查询侧） | `WHERE pk IN (@p0…)` | `WHERE pk = ANY(@ids)`（未在 PoC 中测过，需先探针） |

现有 `BatchUpdateSqlBuilder.Build`（含 `BatchUpdateForm` 枚举）是挂靠点：新增
`BatchUpdateForm.UnnestArrays`，与现有 `CaseWhen` / `JoinValuesRow` 同层分派。

## 四、明确不做的（附理由，防实施轮扩范围）

- **MySQL 不做**：MySQL 无数组类型。MySQL 的批量 UPDATE 已走 `JoinValuesRow`
  （服务器 8.4.11 实测生效，对 ADO 地板 0.31×），无 UNNEST 对应物。
- **SQLite 不做**：无数组参数；SQLite 批量走多值 VALUES 或逐条裹事务，既有决策不变。
- **不替换单行 CRUD 路径**：数组形态对单行无意义（1 元素数组比参数化多一层转换）。
- **不动读取路径**：PoC 只测了写侧三项；读取侧的 `WhereIn` 若也切，需独立探针先行。

## 五、失败判据与回退（实施轮必须预先定好）

**何时回退**（任一命中即回退该入口，不做"部分保留"）：
1. 三项收益中任一项**时延变慢 >5%**（分配改善不能抵消时延退化——用户感知在时延）。
2. 分配改善 <50%（PoC 实测 UPSERT −96%、DELETE −99%，低于此说明形态没真正生效）。
3. 真库三方言集成测试出现任何行为差异（尤其：转换器、枚举 `StoreAs`、`OwnedJson`、
   可空列、重复主键的 UPSERT 语义）。

**必须有的锁定测试**（每项都要有修复前红、修复后绿的证据）：
- 逐行结果比对：数组形态与现路径对同一批输入产生**逐位相同**的库内行（PoC 已做 2000 行，实施轮要覆盖转换器/枚举/OwnedJson 实体）。
- 空批次、单行批次、全 NULL 列、重复主键。
- 租户过滤与软删过滤在数组形态下仍生效（`HasTenantFilter` 的追加落位，参照 `BatchUpdateSqlBuilder` 已有的 `usesJoinValuesRow` 落位缺陷 B8 二修）。
- 跨批边界（2000 行 = 单批或 1000×2，取决于最终批宽决策）。

**生成物快照同步**：源生成器 emit 变化会让 `SourceGen.Tests` 的快照全量漂移，
按 B8 纪律先清 `obj/bin` 再构建（增量复用旧 emit 会导致 NRE），快照用机器校验而非目检。

**AOT 三方言复验**：`PalORM.AotTest` / `.MySql` / `.Pg` 三项目发布 + 原生运行；
PG 侧新增数组绑定路径必须在 NativeAOT 下实跑（PoC 的 AOT 结论是在独立项目里得的，
正式实现引入新 API 面后需重验）。

## 六、风险清单（按严重度）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **批宽与内存** | 数组形态单批 2000 行，客户端需先转置出 N 个长度 2000 的数组 = 一次 O(行数×列数) 拷贝。现 VALUES 形态是边拼 SQL 边写参数。**分配省、峰值可能升** | 实施前用探针测峰值堆（PerfHub 已有 `PeakHeapBytes` 采样）；超阈值则降批宽 |
| **参数上限** | 数组形态的约束从"参数个数"变成"数组元素总数"（PG 单语句 65535 参数位仍适用？PoC 2000 行通过，更大规模未测） | 实施轮测 20000 行档；必要时按元素总数分批 |
| **类型推断** | Npgsql 对空数组/全 NULL 数组的类型推断可能失败（需显式 `NpgsqlDbType`） | PoC 补测空数组；测试锁定空列场景 |
| **`StoreAs` 枚举/转换器** | 生成期数组绑定必须复用现有转换器链，不能另写一套 | 与 `BindInsertValues` 同源生成（同列序同谓词） |
| **快照漂移规模** | emit 变化影响所有实体的生成物 | 先跑一实体小样（对齐 B 系列"批量下发前 1 篇小样试跑"） |

## 七、建议实施顺序（每步可独立验证、可独立回退）

1. **补探针**（1 天）：空数组绑定、20000 行档、峰值堆、读取侧 `WhereIn` 是否值得做。**先于任何实现**——
   第 6 节两个风险项只能由探针回答。
2. **源生成器 + PG Provider 的最小闭环**（单实体、单入口 `BulkDeleteAsync`——收益最大且形态最简单）：
   跑通 SQL 形状 + 结果逐位比对 + AOT 复验。
3. **扩到 BulkUpdate / BulkMerge**：共享同一数组绑定器；快照同步。
4. **验收**：PerfHub PG 子集批（`--dialects pg`），三项逐项对照本文第一节数字；门禁比值不劣化。
5. **文档与 CHANGELOG**：收益如实登记（含 UPSERT 时延只 −8% 这个容易被夸大的点）。

## 八、与既有决策的关系（实施前必读，避免推翻已定案的东西）

- **PG 批量 UPDATE 1000 行上限**（6caeada）：那是 VALUES 形态的约束（VALUES 行数相对表规模触发
  Hash Join）。数组形态不受此限，但**实施轮不得顺手删掉 1000 这个常量**——它是 VALUES 回退路径的
  正确取值，两条路径并存。
- **`BatchUpdateForm` 枚举**（MySQL-7）：为 MySQL 8.0.19 引入。新增 `UnnestArrays` 是并列分支，
  不要改动既有两分支的行为。
- **B98 惰性晋升**：与本文无关（那是会话级命令复用），不要混在一起改。
