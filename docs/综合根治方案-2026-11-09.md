## 2. 根因分析

逐个修补 27 项缺陷是治症状。以下是它们背后的六层根因，每层都对应一个「机制缺口」。

### 2.1 根因一：可复现性与可维护性的矛盾（环境层）

**现象**：`global.json` 钉 `11.0.100-rc.2.26504.105` + `rollForward: disable`，本机只装了 rc.3，所有 dotnet 命令失败。

**直接原因**：本机 SDK 随系统更新漂移，仓库钉版零容忍。

**根本矛盾**：`rollForward: disable` 追求「精确复现」，但本机环境不可控。任何一次系统级 SDK 更新都会让本地开发断链。CI 用 `setup-dotnet` 按 global.json 现装，所以 CI 绿而本地红，**两边环境不一致**。

**为什么不是改版本号**：改到 rc.3 只能解决今天，下次系统更新再漂一次。根治需要「本机 SDK 与钉版自动对齐」的机制。

### 2.2 根因二：CI 安全网破损且无人修补（治理层）

**现象**：perf-gate 7 红（NU1109）、nightly 6 红（基线不绿）、mutation 8 红（空转）、flake-ledger 0 run。

**直接原因**：
- perf-gate：CPM 钉 `Microsoft.Bcl.AsyncInterfaces` 10.0.13，上游 BDN 要 10.0.14
- nightly：mutation 基线红（8655242 未推送，nightly 跑的是旧代码）
- mutation：`effectiveMutants=0`，`threshold-break` 从未生效

**根本矛盾**：CI 是安全网，但**网破了没有阻塞机制**。分支保护未配置（main/dev 均 404），所以 CI 红不阻塞合并。CI 红变成「已知状态」而非「待修信号」。

**为什么不是逐个修 CI**：修好三条工作流只能解决今天，没有「CI 红即阻塞」的机制，下次依赖升级还会红。

### 2.3 根因三：门禁判据自身未被验证（防线层）

**现象**：
- D10 正则 `@"当前s*(d{3,})s*"` 缺反斜杠，`s`/`d` 匹配字面字符，**永不命中**
- G32 只在配置含 "Microsoft.CodeAnalysis" 字样时判定，删掉字样即静默 PASS
- SemVer 门禁只认二进制 API 破坏，不检测 CHANGELOG 的 💔 行为破坏段
- 零项即 PASS：集合为空时报 PASS 而非 FAIL

**根本矛盾**：门禁是概率防线，但**防线本身没有被测试**。项目有 V17 探针框架，但只覆盖部分门禁（V17c 10 个探针），新增门禁（D10、G32、SemVer）没有配探针。

**为什么不是逐个修判据**：修好三条判据只能解决今天，没有「新增门禁必须配探针」的机制，下次新增门禁还会失明。

### 2.4 根因四：修复与验证脱节（流程层）

**现象**：8 个未推送提交中 3 个是 src-only（c0409c3、bcf373f、46e7cc9），改动声称修复但撤掉不会变红。

**根本矛盾**：修复流程缺少「锁定测试」环节。Karpathy 准则 #5「修 bug 前先写复现测试」没有机制保障。

**为什么不是逐个补测试**：补好 3 个只能解决今天，没有「src 变更必须伴随 test 变更」的门禁，下次修复还会漏。

### 2.5 根因五：修复范围靠人脑记忆（架构层）

**现象**：FLT-4 连接判死自愈在提交 42c1cda 中声称已修复，实际三处未接线：
- `SqliteProvider.cs:14` 精确匹配 `{ Message: "Connection is not open" }`，驱动实际消息不同，是死代码
- `DataSession.cs:1758` 写路径 `try` 只包 `ValueTask` 构造，不 await，异步异常进不了 catch
- `DataSession_Bulk.cs` 14 个执行体直接 `ExecuteNonQueryAsync`，无包装

**根本矛盾**：修复范围靠「记得改哪些文件」。没有「执行体清单」，修复连接判死时无法机械列出所有应覆盖的路径。

**为什么不是逐个补路径**：补好这三处只能解决今天，没有「修复必须覆盖清单」的机制，下次修复还会漏兄弟路径。

### 2.6 根因六：文档数字与代码脱钩（信息层）

**现象**：
- 诊断计数 45/46 双轨（README 徽章 45、功能特性.md 45，实际 46）
- README 胜场 22/87（中文）vs 51/87（英文），同批 87 格必有一错
- API 参考版本头 v5.5.1（实际 6.8.0）
- 8 个未推送提交未进 CHANGELOG

**根本矛盾**：文档数字手写，无单一事实源。项目已有 D17（诊断计数校验），但只覆盖 README 正文两处，不覆盖徽章、功能特性、胜场、版本头。

**为什么不是逐个改数字**：改好今天，下次数字变化还会漂。需要「文档数字从代码派生」的机制。

## 3. 根治方案

### 3.1 核心思路：四层证据链

根治的目标不是「修好 27 个缺陷」，而是「建立让同类缺陷不再产生或能立即发现的机制」。四层证据链如下：

| 层 | 问题 | 机制 | 载体 |
|---|---|---|---|
| 环境证据 | 本机与 CI 环境不一致 | SDK 自动对齐 + 检查门禁 | 新增 `scripts/check-sdk.cs` |
| CI 证据 | CI 红了无人管 | 分支保护 + 必需检查 + 健康检查 | GitHub 设置 + 新增 `ci-health-check.cs` |
| 门禁证据 | 门禁判据失明 | 每个门禁配变异探针 | 扩展 V17 框架 |
| 修复证据 | 修复无锁定测试 | src 变更必须伴随 test 变更 | 新增 `check-locked-tests.cs` |
| 覆盖证据 | 关键路径无变异验证 | 扩 mutation-rules 覆盖 | 扩展现有规则库 |
| 信息证据 | 文档数字漂移 | 文档数字从代码派生 | 扩展 D17 |

### 3.2 方案一：环境证据（SDK 自动对齐）

**目标**：本机 SDK 与 `global.json` 自动对齐，不依赖人工记忆。

**措施**：
1. **决策**：`global.json` 升 rc.3.26522.148（本机唯一完整版本，rc.2 已被系统更新清成残骸），同步 8 个 workflow 的 setup-dotnet 行为
2. **检查门禁**：新增 `scripts/check-sdk.cs`，校验本机 SDK 是否匹配 `global.json`，不匹配时打印安装命令（`dotnet-install`）并联进 pre-commit
3. **文档同步**：`CONTRIBUTING.md:5`「精确钉住」与 `README.md:270`「rc.2 或更高」矛盾，统一为「精确钉版 + 检查门禁」

**为什么这是根治**：检查门禁让下次 SDK 漂移立即可见，而不是等构建失败才发现。

### 3.3 方案二：CI 证据（安全网）

**目标**：CI 红即阻塞合并，红必登记。

**措施**：
1. **分支保护**：按 `.github/BRANCH_PROTECTION.md` 配置 main/dev（Require PR、Require approvals、Require status checks、Restrict push）
2. **必需检查**：把 verify.yml 的 10 个 job 设为必需检查
3. **健康检查**：新增 `scripts/ci-health-check.cs`，检查最近 7 天各工作流结论，红即打印告警（可联 pre-commit 或周度报告）
4. **修三条红**：perf-gate 升 CPM、nightly 推 8655242 修基线、mutation 查空转

**为什么这是根治**：分支保护让 CI 红成为合并阻塞，从「已知状态」变回「待修信号」。

### 3.4 方案三：门禁证据（探针扩展）

**目标**：每个门禁判据都配变异探针，构造坏输入即红。

**措施**：
1. **修判据**：D10 补反斜杠、G32 重写、SemVer 加行为破坏检测、零项即 PASS 改 FAIL
2. **配探针**：为每个修复配 V17 变异探针（构造坏输入 → 跑 → 断言 exit 1）
3. **扩面**：V17 从 10 个探针扩展到覆盖所有 G 项（目标 ≥30 个）
4. **登记**：新探针进 `bench/baselines/gate-registry.json`

**为什么这是根治**：探针让门禁「可被证伪」，下次判据写错会立即被抓。

### 3.5 方案四：修复证据（锁定测试门禁）

**目标**：src 变更必须伴随 test 变更，例外登记。

**措施**：
1. **门禁**：新增 `scripts/check-locked-tests.cs`，检查 diff 中 src/ 变更时 test/ 是否同步变更
2. **例外登记**：允许 src-only，但必须在提交信息或 `.ai/lessons.md` 登记理由（如「纯重构无行为变更」）
3. **补测**：为 3 个 src-only 提交补锁定测试（撤修复即红）

**为什么这是根治**：门禁让「修复必配测试」成为制度，不再依赖记忆。

### 3.6 方案五：覆盖证据（变异回放扩展）

**目标**：关键路径的修复都有变异回放覆盖。

**措施**：
1. **扩规则**：`mutation-rules.json` 补充 M6/E4/D7/L1 对应规则
2. **补盲区**：`mutation-score.cs:79` 的 `covered` 纳入 problems
3. **补判据**：`assertion-strength-check.cs:130` 剥注释后再匹配断言

**为什么这是根治**：变异回放让「修复是否真覆盖」可机械验证。

### 3.7 方案六：信息证据（文档单一事实源）

**目标**：文档数字从代码派生，不再手写。

**措施**：
1. **扩展 D17**：从 README 正文扩展到徽章（`diagnostics-45_rules`）、功能特性.md、胜场、版本头
2. **派生报告**：README 胜场从 `PerfCli report` 派生（参考性能报告模板的自动生成）
3. **CHANGELOG 门禁**：`changelog-check.cs` 增加「Unreleased 段必须覆盖未推送提交」校验

**为什么这是根治**：单一事实源让数字不再漂移。

### 3.8 方案七：闭环证据（登记销案）

**目标**：已解决的登记及时销案，不再堆积。

**措施**：清理 `.ai/state.md` 三条已解决未销案条目（FIX-3/4/5/7 已完成、diff 覆盖率已验证、core 地板已回调）

**为什么这是根治**：台账准确是决策前提。
