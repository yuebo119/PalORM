## 0. 结论

本轮剩余的真实空间不在继续削减每次调用的固定税，而在三个方向：已落地未收口的收益、SQLite 读侧单点、以及两处无界缓存的容量卫生。

外部两份方案（下称方案甲：削减固定税 / 5 批；方案乙：编译期查询特化）共提交 15 项候选，其中 8 项与 `perf-ledger` 既有裁决冲突、已落地或经核实为伪缺口。方案乙最扎实的发现（9 个终态方法的 `[InterceptsLocation]` 链路只做标签转发）成立，但属于架构级押注，需先做覆盖率实验，不进本轮。

对单行 19~32% 的时延差与 2.3~3.75× 的分配差，本次做了器材拆账：约六成来自 `CreateAsync` 的连接打开、Provider 初始化与释放路径，约四成来自会话对象构造（PerfHub 注释自述 968B）。这决定了只减会话对象的上限是 26%，达不到方案甲宣称的 1.3~1.6×。

| 方向 | 内容 | 预期 | 状态 |
|---|---|---|---|
| 大 | SQLite 读侧 `json_each` 多键读 | 探针 4.9~5.0× 对参数化 IN | 未落地 |
| 中 | MySQL 默认批宽整段单批 | −14.2%~−16.3%（两轮 A/B） | 已落地未推送 |
| 小 | MySQL BulkCopy 六项固定开销 | 每调用 100~200ns 级 + 若干分配 | 未落地 |
| 卫生 | 两处无界缓存容量上限 | 无直接收益，防增长 | 未落地 |
| 条件 | 动态形状多槽 / 构建期免物化 | −32% / 4.6% | 待前置探针判定 |

## 2. 归因修正：单行差分的器材拆账

方案甲用「20k 行慢 3% 对单行慢 19~32%、多分配 2~4×」把战场锁定在固定税。这个差分数值成立，但归因需要拆开，因为两套器材测的不是同一件事。

【事实】BDN 器材（`bench/PalORM.Benchmarks/01_CrudBenchmarks.cs`）：

- ADO 臂用 `BenchmarkConfig.OpenSqlite`，只做 `new SqliteConnection` + `Open()`，1584B / 22,122ns
- PalORM 臂用 `DataSession<SqliteProvider>.CreateAsync`，3688B / 26,432ns
- 比值：分配 2.329×、时延 1.195×

【事实】PerfHub 器材（`bench/PalORM.PerfHub/Implementations.cs:2180-2183`）：两臂共享同一夹具连接，PalORM 只多一个 per-op 会话对象且不 `Dispose`。实测（`history-20261102-181157.json`，SQLite/2000）：

| 操作 | ADO 分配 | PalORM 分配 | 分配比 | 时延比 |
|---|---|---|---|---|
| GetByKey | 2127.6 B | 2272.9 B | 1.068 | 1.000 |
| Insert | 2883.0 B | 2836.2 B | 0.984 | 0.988 |
| Update | 2618.5 B | 3187.8 B | 1.217 | 1.000 |

【推断】BDN 的 2.33× 与 PerfHub 的 1.068× 之差（约 1415B），对应 `CreateAsync` 相对「共享连接」多做的部分：连接对象创建与 `OpenAsync`、`CancelAfter` 两次定时器武装（`DataSession.cs:197,205` 注释自述每会话约 100B）、Provider 初始化钩子（SQLite PRAGMA）、interceptor 列表复制、`Dispose` 释放路径。PerfHub 注释自述会话构造本身为 968B。

【推断】由此得出两个硬约束：

1. 只减会话对象（968B）的上限是把 3688B 降到 2720B，即 1.72×，达不到方案甲宣称的 1.3~1.6×。要越过 1.6× 必须同时处理 `CreateAsync` 的连接与初始化路径。
2. 默认池化可以整体绕开 1415B + 968B，接近 PerfHub 的 1.068×。但池化已经是 README 的推荐形态（`README.md:280`：`GetAsync` 比每操作新建会话快约 3.8 倍、分配低约 45%），且账本表 2 已裁决「池化做成可配置开关」不做。

结论：固定税这条路的库内空间已被账本判到地板；剩下的收益属于形态问题，改代码改不动，改用法可以。本轮不再以「削减 per-op 固定税」为主线。

## 3. 一处核实：结果集溢出路径不是缺口

两案共同指认 `ResultListReader.cs:59-84` 存在「两趟全量拷贝」，方案甲据此立 P1-1，方案乙据此立 P1 第 2 项，裁决报告称其为「两案共同成立」。本次逐行核对，这个判断不成立。

【事实】该段实际流程：

1. `ArrayPool.Rent(Math.Max(initialCapacity * 4, 64))` 租缓冲，此时 `list` 里只有 `initialCapacity` 个元素（默认 16）
2. `list.CopyTo(buffer)` 拷的是这 16 个元素，不是全量
3. 逐行读入 buffer，满了就 `ArrayPool.Rent(2×)` 并把旧 buffer 归还
4. 收尾 `list.Clear()`、`list.Capacity = count`、`CollectionsMarshal.SetCount`、`buffer.AsSpan(0, count).CopyTo(list)` 做一次全量拷贝

【事实】对照臂 `AdoNetImpl.QueryAllAsync` 用 `new List<S1Row>()` 加逐行 `Add`，走标准几何扩容，容量序列到 32768，中间数组全部进入 GC。

【推断】两者的差异不在「拷贝几趟」，而在谁更省分配：

- ADO：List 几何扩容的中间数组共约 524KB 进 GC，最终容量 32768
- PalORM：buffer 走 `ArrayPool`（零 GC 分配），`list.Capacity = 20000` 一次分配 160KB，之后 memcpy 160KB

PalORM 的 GC 分配比 ADO 少约 360KB，代价是一次 160KB 的 memcpy。160KB 顺序拷贝按内存带宽量级约 10~20µs，占 QueryAll/20000 的 9680µs 的 0.2%。PerfHub 实测该操作分配比 0.992、时延比 0.992，与该推断一致。

结论：当前实现已在分配上优于对照臂，改单遍化无法再省，反而可能把 ArrayPool 的池化收益换成 GC 分配。此项从候选池移除。

这条同时说明：两案共识不等于正确。裁决报告把「两案都指认」当作证据强度，而这两案共享同一个静态阅读视角，没有对照臂实现，因此共同错过分母。
