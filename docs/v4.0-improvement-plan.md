# PalORM v4.0 极致改进方案

> 基于 4 路并行深度调研（核心架构 / 源生成器 / 性能 hot path / API 设计）整合产出。
>
> **目标**：在 v3.1 已完成的 IRowFactory 委托化、Converter 单例、快照合并基础上，再榨取 30-50% 性能、消除 API 残留、收口源生成器 emit 不对称、完成 AOT 全链路最后 1 公里。
>
> **状态：📋 待评审**（2026-07-21）。本方案不立即实施，供评审通过后在新会话执行。

## 二、核心改进方案（按收益/风险排序）

### 🥇 优化 A：CommandFactory Converter 单例对齐（P4 + S1）

**这是 v3.1 最大遗留不对称**——RowFactory 已用单例，CommandFactory 仍每次 new。

**预期收益**：百万行 BulkInsert 场景，含 2 个 Converter 列的实体省 **~200 万次 Gen0 分配**。

**改动**：

| 文件 | 改动 |
|------|------|
| `src/PalORM.SourceGen/CommandFactoryEmitter.cs:33`（新增） | emit 类级 `private static readonly IValueConverter<TClr,TProv> _conv_cmd_{prop} = new Converter();` |
| `src/PalORM.SourceGen/CommandFactoryEmitter.cs:95` | BindDelete body 中 `new {ConverterTypeName}()` → `_conv_cmd_{prop}!.ToProvider(...)` |
| `src/PalORM.SourceGen/CommandFactoryEmitter.cs:289` | GetParameterValueExpression 中同理 |
| 快照基线 | `PALORM_UPDATE_SNAPSHOTS=1 dotnet run --project test/PalORM.SourceGen.Tests` 重生成 |

**风险**：低——emit 内局部变更，RowFactory 已验证模式直接复用。

---

### 🥈 优化 B：CRUD 路径 Volatile.Read 合并 + 预构建 SQL（P1 + P2 + P3 + A3）

**问题**：From<T> 已用 `PalORM_Runtime.CurrentState` 单次快照（v3.1 优化 3a），但 CRUD 路径（GetAsync/GetAllAsync/InsertAsync/UpdateAsync/DeleteAsync）仍 3 次独立访问。

**预期收益**：GetByKey 再降 ~10%（从 31μs → ~28μs），贴近 ADO.NET 基线。

**改动**：

| 文件 | 改动 |
|------|------|
| `src/PalORM.Core/DataSession.Crud.cs:255-272`（GetAsync） | 改用 `var s = PalORM_Runtime.CurrentState;` + `s.RowFactories/...`；移除独立属性访问 |
| `src/PalORM.Core/DataSession.Crud.cs:278-292`（GetAllAsync） | 同理 |
| `src/PalORM.Core/CrudMetadata.cs`（新增字段） | `QuotedColumnList` 预构建 `string.Join(", ", cols.Select(Quote))` 结果 |
| `src/PalORM.SourceGen/RegistryEmitter.cs` | emit 时为每个实体计算 `QuotedColumnList`（需 Provider quote 规则——但 emit 时不知道 Provider，方案：emit 三方言各一份 + 运行时按 dialect 选择） |

**实施陷阱**：`QuotedColumnList` 依赖 Provider 的 `QuoteIdentifier`，但 emit 时是 Provider-agnostic。**解决方案**：emit 三方言各一份（`QuotedColumnList_Sqlite/PostgreSql/MySql`），运行时按 `TProvider.Dialect` 选择。这与 MigrationEmitter 三方言 emit 模式一致。

**风险**：中——需在 CrudMetadata 新增字段 + RegistryEmitter emit 三方言。但模式已验证（MigrationEmitter 已做）。

---

### 🥉 优化 C：QueryBuilder 链式 O(N²) 拷贝消除（P8 + P9 + A1）

**问题**：`AddClause` 每次都 `new List<QueryClause>(_clauses)` + `new List<DbParameter>(_parameters)` ——链式构建 N 个子句产生 O(N²) 拷贝。`HasClause` 用 `Exists` 线性扫，每次 AddClause 都 O(n)。

**预期收益**：复杂查询（5+ Where/OrderBy）构建时间下降 50%+。

**改动方案**（三选一，推荐方案 3）：

1. **bitmask + lazy copy**（方案 1）：`byte _kindsMask` 替代 `HasClause` 线性扫；`AddClause` 用 `_copied` 标志位，首次写入时才 `new List`。
2. **class builder**（方案 2）：QueryBuilder 改 class，彻底消除 struct 副本隔离需求。
3. **immutable array + builder**（方案 3，推荐）：内部 `_clauses` 改 `ImmutableArray<QueryClause>`，`AddClause` 返回新实例时 COW 共享只读视图；`_parameters` 同理。

**风险**：高——QueryBuilder 是核心 API，struct 语义被用户依赖（虽然公共 API 表面不变）。必须：
- 先写 benchmark 对比三方案
- 跑全套 156 + 104 + 149 测试
- S3 反向验证：如改后查询性能反而下降，回退

---

### 🏅 优化 D：零分配 List + 参数批处理（P5 + P6 + P7）

**预期收益**：QueryAll 10K 行再省 ~3 次 Gen0 + 1 次 List 分配；BulkInsert 1K 行省 ~1万次 Add 虚调用。

**改动**：

| 文件 | 改动 |
|------|------|
| `QueryBuilderExtensions.cs:64` | `var list = new List<T>(16);` 起步 Capacity（或读 cache 命中时的 hint） |
| `QueryBuilderExtensions.cs:19,68` | 缓存命中时返回 `ImmutableArray<T>` 或 document 调用方复制语义 |
| `CommandFactoryEmitter.cs:251` | emit 改用 `cmd.Parameters.AddRange(preAllocatedArray)` —— 但 DbParameter 数组需先创建，权衡：批量 Add 数组 vs 逐个 Add，ADO.NET 实测批量快 2-3x |

**风险**：低——纯性能优化，API 不变。

---

### 🎖 优化 E：源生成器 emit 工程化（S2 + S3 + S4 + S5）

**预期收益**：编译速度提升 ~20%（大实体项目）；生成代码体积下降 ~15%。

**改动**：

| 文件 | 改动 |
|------|------|
| 所有 Emitter | `new StringBuilder()` → `StringBuilderPool.Rent()` + `using` 归还；`AddSource(hint, SourceText)` 替代 `AddSource(hint, string)` |
| RowFactoryEmitter + CommandFactoryEmitter | 合并为 `EntityFactory_{suffix}` 单文件（每实体省 ~12 行） |
| MigrationEmitter.cs:25 | 删 legacy `CreateTable` 字段（dialect 字典恒有 Sqlite 键，不可达） |
| CommandFactoryEmitter BindUpsert | 改为调用 BindInsert 后追加 PK 行 |

**风险**：低——emit 输出内容不变，只是工程化优化。快照基线需重生成。

---

### 🎁 优化 F：API 残留收口（API1-API7 + A7）

**预期收益**：代码清晰度 + 用户预期管理。

**改动**：

| API | 处理 |
|-----|------|
| `DiffAsync` | `[Obsolete("Use ValidateSchemaAsync")]` + 文档说明 |
| `[Column].Length/Precision/Scale/TypeName/StoreAs` | PALORM017 升级为 Error，强制用户明确"未实现" |
| `NamingConvention.ApplyNaming` | `[Obsolete("Compile-time only, see [Column]")]` |
| `WithMetrics(name)` | 删除 name 参数（当前不作为标签） |
| `GetRawConnection()` | 重命名 `DangerousGetRawConnection` + `[Obsolete("Use GetRawConnection")]` 渐进迁移 |
| `IRowFactory<T>` | 保持 public + XML doc（v3.1 已收口）；v4.0 评估后决定 |

**风险**：低——除 `GetRawConnection` 重命名外，都是 `[Obsolete]` 标注。

---

### 🚀 优化 G：AOT 最后 1 公里（T1 + T2 + T3）

**预期收益**：完整 AOT 兑现 + 文档完善。

**改动**：

| 文件 | 改动 |
|------|------|
| `DataSession.Query.cs:48,57,213` + `StoredProcBuilder.cs:98` | `Convert.ChangeType` 改为源生成特化（为每个 T 生成 switch case） |
| `test/PalORM.AotTest/Program.cs` | 增加枚举列 + Guid 列实体覆盖 |
| `docs/AOT部署指南.md` | 补充三方言原生 lib 的 RID 解析说明 |

**风险**：中——Convert.ChangeType 改源生成特化需新增 Emitter。

## 七、与 v3.1 的关系

| 维度 | v3.1（已完成） | v4.0（本方案） |

| 方案项 | 方案声称 | 实际评估结论 |
|--------|---------|-------------|
| **C** QueryBuilder O(N²) 拷贝消除 | "复杂查询 5+ Where 构建时间下降 50%+" | 构建时间占 QueryAll 4.73ms 的 0.02%（微秒级），非瓶颈。重构将重新引入 QUERY-001 已修复的 struct 副本隔离 bug |
| **预构建 SQL**（QuotedColumnList） | 每查询省 ~150ns + 1 次字符串分配 | emit 三方言版本复杂度高，9-30KB 额外生成代码换取微秒级收益，YAGNI 跳过 |
| **2-E emit 工程化 4 子项** | 编译速度提升 ~20%，生成代码体积下降 ~15% | S2 StringBuilderPool 跨版本不稳定；S3 合并 Emitter 破坏所有快照基线；S4 CreateTableSql 实际仍被 MigrateAsync.Keys 使用；S5 BindUpsert 改调 BindInsert 增加状态参数 |
| **AddRange 参数批处理** | 大 IN/批量路径省 N 次分配 | ADO.NET Provider 行为不一致，风险高于收益 |
| **Tracing/Metrics 短路** | 默认场景省 ~50ns/查询 | 已是 const string + intern，零分配 |
| **Convert.ChangeType 源生成特化** | AOT 安全 | 经评估确认 Convert.ChangeType 走 IConvertible 接口分发，AOT 安全；CI 已实际 PublishAot 验证 4 个 job |

### 实施偏差的关键反思

**方案调研 Agent 可能从代码模式推断出"理论瓶颈"，但缺乏运行时数据验证**：

1. **QueryBuilder O(N²)**：调研 Agent 看到 `new List<>(_clauses)` 每次 O(n) 拷贝，理论上是 O(N²)。但实际 N（子句数）通常 < 10，O(N²) = 100 次操作 ~ 微秒级，相对 DB 往返（毫秒级）可忽略。**方案文字"复杂查询 50%+ 优化"误导**——优化的是微秒级构建时间。

2. **emit 工程化**：调研 Agent 看到 `new StringBuilder()` 后 `ToString()`，理论上可池化。但 Emitter 只在编译期跑一次，运行时无影响。**收益仅是编译速度（~20%），但破坏快照基线的成本更高**。

3. **Convert.ChangeType**：调研 Agent 看到"反射/运行时代码生成"风险信号，推断 AOT 不安全。但 `Convert.ChangeType(object, Type, IFormatProvider)` 实际走 IConvertible 接口分发，AOT 编译器对基元类型已知。**需验证实际行为而非凭直觉**。

### 实施后的 SOP 沉淀

实施任何性能优化方案前，必须：

1. **验证瓶颈属实**：用 benchmark 确认方案声称的瓶颈在运行时确实显著（占总耗时 >5%）
2. **评估复杂度/收益比**：YAGNI——微秒级优化不值得毫秒级重构
3. **检查现有机制覆盖**：避免重复造轮子（如 PALORM017 已覆盖 [Column].Length 告警）
4. **承认跳过**：在方案文档补「评估后跳过」表，说明每项跳过的具体理由

详见 `.ai/lessons.md` B10。

### 优化 B 的直接效果验证（最终确认）

v4.0 GetByKey 路径（单次快照）：
  var state = PalORM_Runtime.CurrentState;
