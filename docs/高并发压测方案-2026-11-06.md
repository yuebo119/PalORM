# PalORM 高并发压测方案（2026-11-06）

> 来源：用户要求「设计一个全方位的高并发压测」，覆盖死锁、资源争抢、脏数据、数据幻觉，并逐条对照 5 个已列风险点。
> 本文件是设计载体，不含实现代码。状态：待用户裁决是否立项实施。

## 0. 结论与设计前提

现有套件把「会话内并发门禁」「池化串租」「租户过滤 SQL 正确性」打得很实：`SessionConcurrencyTests` 40 例 TCS 精确编排、`ConcurrencySoakTests` 8 线程 × 3 轮 × 30 秒、`SessionFanOutStressTests` 64 会话、`GetByKeyConcurrentReuseTests` 200 次并发点查逐次核 `Id`、`TransactionIsolationTests` 12 例隔离级别语义。新方案**不重复造这些**，把资源集中在两块空白：

1. **跨会话共享可变状态**：进程级查询缓存、静态 SQL 槽代际、SQLite 池化原生句柄的 PRAGMA、进程级熔断器。这是产品内唯一没被单会话门禁覆盖的共享面。
2. **数据库层时序**：副本复制延迟、超时重试重复写、隔离级别下的软删/幻读交错、多进程咨询锁。

三条设计纪律（用户已在本项目多轮确立，违反即返工）：

- **行为断言优先**：每条用例必须有「读到什么值/多少行/哪个租户」的具体判据，禁止以「零异常」「不抛」作为主判据。零异常只是最低门槛，不构成「无竞态」证明（`AuditProbeTests.cs:8-9` 注释自承）。
- **门禁必须能失败**：每个探针交付前用已知坏输入证明会红（控制体换 no-op、故意制造错位），否则是假绿。
- **区分取舍与缺陷**：ADR-O 的写后读陈旧窗口、无 `[ConcurrencyCheck]` 实体的 last-writer-wins、原始 SQL 绕过默认过滤，都是**用户已裁决或文档化契约**，压测目的是量化窗口与固定基线事实，不是把它们当 bug 报。

## 2. 分层压测矩阵

分 5 层，逐层加大不确定度。L0/L1 进 PR 门禁（快、确定性）；L2/L3 进 nightly（真库、分钟级）；L4 只做一次性定案（多进程、需编排）。

| 层 | 目标 | 并发度 | 时长预算 | 环境 | 失败判据 |
|---|---|---|---|---|---|
| L0 确定性交错 | 证明特定调度窗口下门禁行为 | 2~8 任务，TCS/Barrier 编排 | <30s | 共享内存 SQLite | 行为断言 |
| L1 负载 | 跨会话共享状态、资源争抢 | 8~64 会话 | <60s | 共享内存 SQLite | 全表校验和 + 值对账 |
| L2 真库时序 | 隔离级别、复制延迟、死锁重试 | 2~16 会话 | 2~5min | PG/MySQL 真库 | 具体值/错误码/行数 |
| L3 长稳浸泡 | 长时间混合读写后全表一致性 | 8~16 worker | 10~30min | 共享内存 + 真库各一轮 | checksum + 逐行值 |
| L4 多进程 | 跨进程互斥、SQLite 文件库 WAL 争用 | 2~4 进程 | 一次性 | PG 咨询锁 / SQLite 文件库 | 死锁率 + 受害者计数 |

### 通用基建（先建，后写用例）

三类复用件，避免每个用例内联：

1. **`ConcurrencyHarness`**（新，放 `test/PalORM.Integration.Tests/Conformance/`）：封装 `CancellationTokenSource(硬超时)`、`Barrier(N)`、确定性种子（`PALORM_CONCURRENCY_SEED`，默认 20261106）、结构化 `Violation` 收集（`ConcurrentBag<记录含 worker/轮次/期望/实际>`）、最终 `checksum` 计算。TUnit 无 `[Timeout]`，硬超时由 harness 兜底，避免死锁用例挂死 CI。
2. **`VerifyAllRowsAsync`**（基于 `SharedSqliteDb.QueryRawAsync`）：整表读回后按主键分区，断言「N 写者 × M 行 = N×M 行、每行 Owner/Seq 正确、无重复主键、无空洞、无跨租户行」。现有 `SessionFanOutStressTests.cs:49-50` 只核总数不核值，这是要补的核心判据。
3. **`FaultyConnection` 并发化改造**：现状 `_plans` 是 `List<FaultPlan>`（非线程安全），无并发注入 API。压测前先把它换成按序号分区的 `ConcurrentDictionary<int, FaultPlan>` 或多实例各持一份 plan，否则 L0 的并发故障注入本身有竞态，会污染结论。

每条给：编号 / 层 / 靶点 / 场景 / **可证伪判据** / 门禁能失败验证。判据一律是具体值，不写「不抛异常」。

### 3.1 对应用户列的 5 个风险点

| ID | 层 | 场景 | 可证伪判据 | 能失败验证 |
|---|---|---|---|---|
| C-01 池归还后旧引用复活 | L0 | 会话 `DisposeAsync` 归还 → 池 `RentAsync` 被新请求租出 → **旧引用**再发 `InsertAsync`/`GetAsync`。用 TCS 把「旧引用发操作」卡在新租期已建立之后 | ① 若产品有租期校验：旧引用应抛 `ObjectDisposedException`/明确拒绝，新租期数据不受污染；② 若产品无校验（当前 [推断]）：记录「两异步流共用同一 `DbConnection`」为**实测事实**，并断言新租期读到自己写入的值、`COUNT` 恰为 1（不许旧引用写入的行混进新租期） | 故意让旧引用成功写入一行带专属标记的数据，新租期的 `COUNT`/值断言必须红（证明该判据能检出污染）；仅删 TCS 信号只能让场景不成立，不构成能失败验证 |
| C-02 `TryEnterFast` CAS × Dispose/Park 全交错 | L0 | 8 任务：`Enter`/`Exit`/`DisposeAsync`/`Park`/`Unpark`/`WithTenant` 随机交错，`PALORM_CONCURRENCY_SEED` 驱动 1000 轮；每轮末核 `_state`/`_fastState`/`_disposing` 三标志一致性 | 每轮末 `EnsureAvailable` 放行当且仅当 `_state==0`；在飞操作数归零后 Dispose 必须完成；无双 `Exit` 使计数变负；拒绝路径必须抛精确异常消息 | 注入一次「Enter 后不 Exit」的坏输入，violations 必须非空 |
| C-03 快速释放嵌套锁 + `_isActive` 弱内存 | L0/L1 | 并发 `DisposeAsync`（无拦截器，走 `TryCompleteFastDispose` 快路径）与 `EndParallelReadsAsync`（取 `_parallelReadPoolLock`）交错 500 轮；ARM64 另跑一轮 | 无互等（硬超时兜底）；`_parallelReadConnections` 池计数归零；`IdleCount` 恰为归还数；无 `SynchronizationLockException` | 人为在 `_parallelReadPoolLock` 内反向取 `_sync`（测试专用注入），能复现死锁则证明检测有效 |
| C-04 PG 多进程咨询锁反向加锁 | L4 | 2 进程各持一把 `pg_advisory_xact_lock`，按相反顺序请求第二把；双方 `WithTransactionRetry` 重放，重放顺序保持不变；一组传 `ct`、一组不传 | 至少一方收到 `40P01`；传 `ct` 组在超时内退出；不传 `ct` 组记录实际阻塞时长；重放后最终 `COUNT` 与业务期望一致；统计「活锁」判据 = 连续 N 轮双方都被选为受害者且无一方成功 | 把两进程锁序改成同向，死锁/活锁计数应归零 |
| C-05 `SqlSlots<T>` 无代际号 | L0 | `RestoreStateForTesting()` 恢复注册表后，8 会话并发对同一 T 跑 `GetAllAsync`/`CountAsync`/`UpdateAsync`/软删，其中注册表已把该 T 的表名换掉 | 若旧槽残留：会报 `no such table: 旧表名` 或返回旧列集 → 记录为**实测事实**；若产品已修：全部走新表名且 `COUNT` 正确 | 用真实「旧表名仍在库中」的双表夹具，让旧 SQL 能执行但值错，断言逐行值应红 |

| C-24 DDL × DML 并发 | L2 | 一边 `MigrateAsync`/建索引，一边并发 CRUD | 现有 `MigrationRaceHarnessTests.cs:51-52` 只有「零异常」弱断言，本例补：表结构符合预期、`COUNT` 正确、无半建表 |
| C-25 共享实体对象回填竞态 | L1 | 同一实体实例被 2 会话并发 `InsertAsync`/`UpdateAsync`（`SetId`/`IncrementVersion` 无锁写） | 记录最终 Id/Version 的「后写者胜」形态为基线事实；断言不出现「Id 指向另一会话的行」这类静默损坏 |
| C-26 原始 SQL 跨租户 | L1 | 8 租户并发走 `QueryAsync`/`Compile` 原始 SQL（不套默认过滤） | 按契约记录「返回全量」为基线事实；断言自动过滤入口（`From<T>()`）不受影响 |

## 4. 判定与报告口径

### 4.1 失败分级

| 级别 | 定义 | 处置 |
|---|---|---|
| P0 | 数据错乱：读到别的租户/别的租期的行、丢行、重复行、值错乱、主键串到别的行 | 立即停，锁定测试（红→绿），修产品 |
| P1 | 死锁/永久挂起/资源泄漏：硬超时命中、`IdleCount` 漂移、租约计数不归零 | 停，复现时序，修产品 |
| P2 | 已文档化取舍被量化确认（ADR-O 陈旧窗口、last-writer-wins、副本延迟、熔断淘汰重置、原始 SQL 绕过） | 登记基线数字与配方，不判失败 |
| P3 | 契约性边界（旧引用复活、共享实体对象、`CreateBatch` 无租约、`IgnoreFilters` 粘性） | 记录为「支持形态确认」或「文档需补一句」，由用户裁决 |

**关键**：P2/P3 不算缺陷。方案交付报告必须逐条标级别，禁止把「零异常通过」写成「无并发问题」。

### 4.2 统计与可复现性

- 每条用例输出：种子、并发度、轮数、时长、violations 明细（含 worker/轮次/期望/实际）、P0/P1/P2/P3 计数、全表 checksum。
- 并发调度种子 `PALORM_CONCURRENCY_SEED` 落盘，失败可单种子重放（对齐现有 `PALORM_FUZZ_SEED` 惯例）。
- 昂贵命令只跑一次并 `| tee` 落盘，退出码可见（B104 纪律）；不把脚本管进 `tail`/`grep`。
- 比值型指标（死锁率/陈旧率）只作定性，禁止跨机绝对值比较（B100 纪律）。
- 每个用例交付前跑「门禁能失败」验证：把关键防护换成 no-op 或注入错位，断言必须红；不红 = 该用例无判别力，删除或重写。

### 4.3 结论层输出格式

固定七节（对齐本项目性能报告惯例，避免过度设计）：总体结论 → 关键发现速览（带 P 级与置信度）→ 逐用例判读 → 环境与夹具现状 → 全量结果附表 → 判读纪律与指标定义 → 产物与后续行动。每条发现标 [事实]/[推断]/[猜测]，推断项给「需什么实验才能升格为事实」。

## 7. 范围外（明确不做）
