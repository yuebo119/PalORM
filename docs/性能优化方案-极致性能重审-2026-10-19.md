- 日期：2026-10-19
- 基线：`dev` @ `0fc7db0`（工作树干净）
- 方法：全量重读 `src/`（78 个文件 / ~20k 行）+ 三路并行代码探查 + 实测基线交叉验证
- 立场：**不继承任何既有结论**。既有分析只作为"可复用的量具与纪律"，结论一律从源码与实测重新推导；无实测支撑者标注为"待验证"。

## 0. 一句话结论

> **PalORM 的查询内核已经接近极致，真正的性能债不在"怎么写 SQL"，而在"每次操作要不要新建一个 DataSession"——每操作固定成本 ≈ 2.3 KB 分配 + ≈ 6.5 µs，占单行 CRUD 总耗时的 23%。**

复用会话形态下，PalORM 每操作 **1066 B / 4.98 µs**，已优于 Dapper 的 **3347 B / 9.56 µs**（快 1.92×、省 3.14× 分配）。
每操作新建会话形态下，PalORM 退化到 **4136 B / 28.26 µs**，劣于 ADO.NET 地板（**1584 B / 21.54 µs**，分配 2.61×）。

**两者的差值就是本次优化方案的主战场。** 其余是次要战场。

## 1. 诊断：从数据到机制的因果链

### 1.1 决定性对照——同一个产品，两种会话口径

| 夹具 | 会话口径 | 臂 | 时延 | 分配 | 备注 |
|---|---|---|---:|---:|---|
| DapperSuite（16:24 批） | **per-scope**（范围内一次连接/会话） | 手写 ADO | 4.70 µs | 778 B | 地板 |
| DapperSuite | per-scope | **PalORM QueryFirst\<T\>** | **4.98 µs** | **1066 B** | 🟢 优于 Dapper 1.92×、省 3.14× 分配 |
| DapperSuite | per-scope | Dapper Query\<T\> (buffered) | 9.56 µs | 3347 B | |
| CrudBenchmarks（16:03 批） | **per-operation**（每操作新建 DataSession） | ADO.NET GetByKey | 21.54 µs | 1584 B | 地板 |
| CrudBenchmarks | per-operation | Dapper GetByKey | 24.20 µs | 2320 B | |
| CrudBenchmarks | per-operation | **PalORM GetByKey** | **28.26 µs** | **4136 B** | 🟥 分配 2.61× ADO、1.78× Dapper |

**推论（两个差值）**：

```
ADO.NET  每操作建连成本  = 21.54 - 4.70 = 16.84 µs  /  1584 - 778  =  806 B
PalORM  每操作会话额外税 = 28.26 - 21.54 =  6.42 µs  /  4136 - 1584 = 2552 B
```

即：**PalORM 在"连接已就绪"的前提下，每次操作仍要多付 ≈ 2.3 KB 分配 + ≈ 6.5 µs。**
这 2.3 KB 与仓库内 `DataSessionPool` 类文档自述的"每操作 ~1.5KB 分配差横跨 Count/GetByKey/Update 五组基准项"同量级。

### 1.2 这 2.3 KB 花在哪（逐项源码级归因）

| # | 成本项 | 源码位置 | 单次代价 | 性质 |
|---|---|---|---|---|
| C1 | **弹性执行器包装**——`DbOptions.MaxRetries` 默认 **3**，`IsPassThrough` 恒假，读路径每次进执行器：超时 CTS + `CancelAfter` 定时器 + 委托转换 + 熔断进出 | `Resilience.cs:21,154-158`；`QueryBuilderExtensions.cs:215-217`；`DataSession.Query.cs:234-241` | **≈272 B**（代码注释自测：168+56+48） | 语义可配，但**默认值使绝大多数查询永不直通** |
| C2 | **操作门禁的 AsyncLocal 写**——每次 `Enter` 写 `_currentOperationOwner.Value` → ExecutionContext COW | `SessionOperationState.cs:145-146` | ≈72 B（EC 48 + map 24） | per-op 会话结构上**永不预热**（门槛 `PrewarmThreshold=2`），故每操作一次 |
| C3 | **会话对象图**——`DataSession` + `SessionOperationState` + `Lock` + 拦截器 `List` + `_readConnInitializer` 委托 + `_readConnInvalidator` 委托 | `DataSession.cs:32-91,93-139`；`SessionOperationState.cs:8-48` | ≈250–350 B | 可压到 1 个对象 + 0 委托 |
| C4 | **`options.Interceptors?.ToList() ?? []`**——每次建会话分配一个空 `List` | `DataSession.cs:187` | ≈32 B | 空列表可直接共享 |
| C5 | **连接对象本身**——`new SqliteConnection(cs)` / `new NpgsqlConnection(rewritten)` + 驱动侧连接串解析 | `SqliteProvider.cs:91`；`PostgreSqlProvider.cs:65` | ≈806 B | SQLite **无连接串改写缓存**，PG 有 |
| C6 | **命令 + 参数**——`GetAsync` 走 `TryAcquireGetByKeyCommand`，**阈值 3** ⇒ 每操作新建会话永不晋升 ⇒ 每次 `CreateCommand()` + `CreateParameter()` | `DataSession.Crud.cs:233,281-320,391` | ≈180 B | 阈值是为"永不 Dispose 的会话"设计的，per-op 会话**必然** Dispose，阈值对它无意义 |
| C7 | **租约/状态机盒**——`SessionOperationLease`（struct，已优化）、`ReadCommandLease`（struct，已优化） | 多处 | ≈0 | 已优化，无需动 |
| C8 | **列序校验**——首行每列一次 `reader.GetName(i)` | `ColumnOrderValidator.cs:29-40` | 每列 1 次字符串取用 | 随列数线性 |

**关键洞察（C1 + C2 + C6 合计 ≈ 520 B）**：这三项的共同点是——**它们是为"长会话多次操作"设计的机制，在"每操作一会话"形态下全部退化**。这正是 `DataSessionPool` 类文档指出的"全部惰性晋升复用槽在会话活不过 3 次操作的形态下结构性永不生效"。

这三处不是产品缺陷，但会让优化方向被误导，**必须先修尺子**。

### 1.4 跨方言现状（PalORM ÷ ADO.NET，全量批 2026-10-19 16:38）

时延比 / 分配比。**分配是确定性指标，时延在 PG/MySQL 上被 ~200 µs 远端 RTT 主导**——单行操作在 PG 上的时延比接近 1.0 属"看不见 ORM 开销"，不代表内核高效。

| BulkInsert | 1.00 / 0.97 / 0.99 | 1.05 / 0.99 | 0.96 / 1.00 | 🟢 持平地板，分配远优于 Dapper（0.11–0.38×） |
| BulkUpdate | 0.99 / 1.01 | 0.44 / 0.55 ⚠地板病 | 0.34 / 0.30 ⚠地板病 | 🟢 产品形态更优，需修地板才有判别力 |
| BulkDelete | 0.73 / 0.52 | 0.69 / 0.95 | 1.03 / 1.02 | 🟢 优于地板 |

| GetByKey（时延） | 0.66 / 1.00 | 0.98 / 0.94 | **1.18 / 1.14** | 🟥 MySQL 单行劣于地板 |

**读法**：
- **批量族 = 已解决**（PG Binary COPY / MySQL LOAD DATA / PG UNNEST / SQLite 多值 VALUES），分配比 Dapper 低 3–20×。
- **单行族 = 未解决**，且三方言一致地高 17–47% 分配——这不是方言问题，是**每操作固定成本**问题。
- **Count 分配比 1.4–2.9× 是最刺眼的单行项**——一次 COUNT 分配 2.3–9.8 KB，说明 C1+C2 几乎构成 Count 的全部开销。

## 2. 方案总纲

**排序原则：先让尺子准（M 层）→ 再砍固定成本（L1）→ 再抠内核（L2/L3）→ 最后做协议级与架构级（L4/L5）。**

理由：M 层不修，L1 的收益无法归因（量具把产品优势藏起来、把地板缺陷算到产品头上）；L1 的收益量级（2.3 KB / 6.5 µs）比 L2/L3（数百 B / 亚 µs）大一个数量级。

| 层 | 主题 | 目标 | 预期总收益 | 优先级 |
|---|---|---|---|---|
| **M** | 测量保真 | 让比值有判别力 | 使 L1–L4 可归因 | 🔴 P0 |
| **L1** | 每操作固定成本 | 消灭 2.3 KB / 6.5 µs | 单行分配比 2.6× → ≤1.4× | 🔴 P0 |
| **L2** | 物化与读取 | 每行每查询的残余开销 | −100~300 B/行·查询 | 🟡 P1 |
| **L3** | 批量与事务 | 消除可预知的重复计算 | 批量分配 −5~15% | 🟡 P1 |
| **L4** | 方言协议 | 用上未启用的协议能力 | SQLite BulkUpdate 10–50× | 🟡 P1 |
| **L5** | 架构级 | 编译期下沉 | 中期收益 | 🟢 P2 |

## 3. M 层——测量保真（先修尺子）

### M1 🔴 修地板 BulkUpdate 形态

- **动作**：把 ADO 地板臂的批量 UPDATE 改成与产品同代的形态——MySQL ≥8.0.19 用 `UPDATE t JOIN (VALUES ROW(…)) AS v(…) ON …`，PG 用 `FROM UNNEST(@u0,@u1,…) AS v(…)`。
- **为什么**：现地板用 `CASE WHEN`（MySQL）与 `UPDATE FROM (VALUES …)`（PG），产品用更优形态。当前 BulkUpdate 组 P/ADO = 0.30–0.55 会让人误以为"产品比手写快 3 倍"，实际是**地板落后**（产品同负载实测 156.7 ms vs 271.7 ms）。不修地板，该组永远背着一个假的"领先"，且真正的地板差距不可见。
- **风险**：低。改的是基准夹具，不动产品。需同步更新 `perf-budgets.md` 的该项基线。
- **验证**：地板改完后，BulkUpdate 组 P/ADO 应落到 1.0–1.6 区间；若仍 <0.67，说明产品形态仍有领先空间，另立专项。

### M2 🔴 统一三臂连接配置口径（让产品的 PG 调优可见）

- **动作**：三臂统一使用**同一份连接串改写后的配置**——要么 PalORM 臂改为经 `CreateAsync` 自建连接，要么给三臂统一加上 `MaxAutoPrepare=100` 等同款参数。
- **为什么**：现基准 PalORM 臂注入外部连接，产品的 `MaxAutoPrepare=100` / `AutoPrepareMinUsages=2` / `NoResetOnClose=true` / 16KB 缓冲**全部不生效**。Npgsql 官方基准：预备 306 B/op vs 未预备 2.37 KB/op。**这 7.7× 的差距正是 PG 单行分配比 1.46× 的最大潜在来源。**
- **风险**：中。改变了地板与 Dapper 臂的量级（它们也会变快），需重录基线。
- **验证**：改完后 PG GetByKey 分配比应显著下降；同时三臂绝对值都会下降，跨批不可比，须重录。

### M3 🔴 增补"会话税"独立测量项

- **动作**：在 PerfHub 新增 3 个可归因项：
  1. `SessionCreate`——只建会话不查询（地板 = 裸连接 open）
  2. `SessionRent`——会话池租还（地板 = 无）
  3. `QueryOnly`——复用会话的纯查询（地板 = 复用连接的纯查询）
- **为什么**：当前所有比值把"会话税"和"查询税"混在一个分母里。拆开后，每项优化都能落到具体数字上——这是 M1/M2 之外 L1 全部工作的验收前提。
- **风险**：低。新增项，不改既有项。

### M4 🔴 复测 PG 20000 档 4 项异常

- **动作**：对 `GetAllAsync/PG/20000`、`WideQueryAll/PG/20000`、`UpsertBatch/PG/20000`、`Count/PG/20000` 跑 3 批窗口复测。
- **为什么**：这 4 项跨批摆动 1.85–3.07×，是本批最大的未定性异常。**不复测不归因**——但也绝不能因为"可能是噪声"就放过：3.01× 若坐实，是 PG 上最重要的读路径回归。
- **候选假设（待排除，勿当结论）**：
  1. PG 统计信息失真（已知机制：BulkDelete 把表播到 20 万行使 autovacuum 记错 `reltuples` → Count 拿到 7 倍高估 → 计划器选 Parallel Seq Scan，实测 28.85 ms vs 1.62 ms）。**这最可能同时解释 Count 与 UpsertBatch 两项**——播种后强制 `ANALYZE` 可验证。
  2. 物化路径差异：`S1Row` 的 `Name` 列长度随行号增长，20k 档下字符串体量远大于 2k 档；若物化侧出现逐行字符串复制，差距会随档位放大。
  3. 计划器形态翻转：`UPDATE … ON CONFLICT` 在 20k 行上的计划可能与 2k 档不同。
- **验证**：先跑假设 1（成本最低、机制已知）——播种后 `ANALYZE` 再测；若 3.01× 消失，结论即"数据面问题，非产品回归"。

## 4. L1——每操作固定成本（最高 ROI）

### A1 🔴 默认弹性策略直通化（预计 −272 B/读，−1 次定时器/读）

**现状**：`DbOptions.MaxRetries` 默认 **3**（`DbOptions.cs:55`），`CircuitBreakerThreshold` 默认 **5**（`:94`）⇒ `ResilienceExecutor.IsPassThrough` 恒假 ⇒ **每一次读查询都进执行器**，付出超时 CTS + `CancelAfter` 定时器 + 委托转换 + 熔断进出（代码自测 272 B/查询，且"与结果行数无关"）。

**这是一个"默认值让最热路径永不直通"的经典反模式**：对 micro-ORM 而言，默认重试的期望收益（网络偶发失败）远小于其对**每一条正常查询**的固定抽取税。

**建议（按优先级递进，可分期落地）**：

| 方案 | 动作 | 收益 | 语义影响 |
|---|---|---|---|
| **A1-a（推荐首选）** | **延迟建 CTS**：执行器不在尝试前建超时 CTS，改为——首次 `await` 前建不可取消的 CTS 不可行；改用**驱动侧 `DbCommand.CommandTimeout` 承担单次尝试超时**，执行器只在**首轮失败后**才引入总预算 CTS | −~200 B/读，去掉 1 个 `CancelAfter` 定时器 | 失去"覆盖连接获取 + 读取器迭代"的超时；需评估是否可接受 |
| A1-b | `MaxRetries` 默认改 0（熔断阈值保持 5，但读路径在"未显式配置重试"时不套执行器） | −272 B/读全免 | **默认不再自动重试**——行为变更，需 CHANGELOG + 迁移说明 |
| A1-c | 保持默认 3，但让**首次尝试**走无包装直通路径，仅在失败后进入完整重试语义 | −~200 B/读 | 需确认"首次失败即抛"与"重试 3 次"的语义差异（这是真正的行为变更） |

**推荐路径**：**A1-c**——它保留了"失败会重试"的语义，只把"成功路径的包装成本"降下来。实现上：执行器内核拆成"直通首发"与"重试续跑"两段，首发用 `operation(state, ct)` 直调（不建 CTS），失败后再进入带超时与退避的重试循环。

**风险**：🔴 高。这是行为语义改动，必须配套：
- 单测锁死"首次失败仍重试 N 次"；
- `PalORM.InfrastructureTimeout` 标记在 A1-c 下由"首轮即超时"路径产出，需回归 `TransactionCleanup` / `Resilience` 相关断言；
- 门禁与基线需重录。

### A2 🔴 操作门禁只在事务流写 AsyncLocal（预计 −72~120 B/操作 + 去掉一次 EC COW）

**现状**：`SessionOperationState.Enter` 每次都写 `_currentOperationOwner.Value`（`:145-146`），触发 ExecutionContext COW。而这个 AsyncLocal 的**唯一实质用途**是跨异步流的事务归属校验（`_currentTransactionOwner`）与操作归属判定（`IsCurrentOperationScope`）。

**问题**：`ThrowIfEnterBlocked` 中只有 `_transactionOwner is not null` 时才读 `_currentTransactionOwner.Value`；`CanFastReenterOwner` 同理。**也就是说，非事务流下的 `_currentOperationOwner` 写入对判定几乎没有作用，却让每次操作付一次 EC 拷贝。**

**建议**：把 `_currentOperationOwner` 的写入**门控在"存在事务流"或"存在在飞事务"时**：
- 事务流内（`_transactionOwner is not null`）→ 照写（归属校验必需）；
- 事务流外 → **不写**，`IsCurrentOperationScope` 改用非 EC 的判据（例如租约持有的 owner token 与 `_activeOperationOwner` 的引用比较）；
- `PrewarmCurrentOperationOwner` 同步门控。

**风险**：🟡 中。触碰并发/流归属语义，必须用架构不变式测试锁死：
- 同流重入放行、异流重入拒绝；
- 事务归属判定不变；
- per-op 会话长循环下 EC map 不再增长（这恰好解掉 `AsyncLocal` O(N²) 隐患的另一条路径）。

### A3 🔴 会话池成为"推荐默认形态"（预计 −2.3 KB / −6.5 µs 每操作）

**现状**：`DataSessionPool<TProvider>` 已实现且语义完备（瞬态复位、复用槽保留、归还门禁、租/还零解析），但：
1. README 快速 Start 仍以 `DataSession.CreateAsync` 为主路径；
2. PerfHub 的主臂（per-operation）**不使用池**，只有 `PooledGetByKey` 一个项用；
3. 池没有 DI 集成（无 `IServiceCollection` 扩展、无 scoped 注册）。

**建议**：
- **A3-a**：`DbOptions` 增加 `SessionLifetime` 语义，或提供 `DataSessionFactory`/`ISessionFactory` 抽象 + 内置池实现，**让"每请求一会话"自动走池**；
- **A3-b**：补 `Microsoft.Extensions.DependencyInjection` 集成包（`AddPalORM<TProvider>()` → `AddScoped<DataSession<TProvider>>` 走池）；
- **A3-c**：PerfHub 新增 per-operation 与 pooled 两口径的**成对项**，让"池 vs 非池"的收益成为一等公民指标。

**为什么这是最大单点**：它一次性消掉 C1（会话构造）、C3（对象图）、C4（空 List）、C5（连接）、C6（命令不晋升）五项，并让 C1 的复用槽、A9 查询槽、P1-1 直查槽**全部真正激活**。

**风险**：🟡 中。池的归还门禁（有事务/在飞操作/并行读作用域）会在误用时抛异常——需明确文档化"归还前必须收口"。另需回归并发用例（`SessionConcurrencyTests`）。

### A4 🟡 会话对象图瘦身（预计 −150~250 B/操作）

| 动作 | 位置 | 收益 |
|---|---|---|
| 拦截器空列表**共享静态空数组**，不分配 `List` | `DataSession.cs:187,106-108` | −32 B + 一次 `ToList` 迭代器 |
| `SessionOperationState` 与 `DataSession` **合并**（去掉独立对象 + 独立 `Lock`） | `DataSession.cs:35`；`SessionOperationState.cs:22` | −~100 B + 一次锁对象 |
| `_readConnInitializer` 委托改为**静态 + 实例方法分离**（有 `ReadSessionSetupSql` 时才建实例委托） | `DataSession.cs:123-136` | −64 B |
| `_parallelReadPoolLock` 惰性化（与 `_parallelReadConnections` 同步） | `DataSession.cs:91` | −24 B |
| `ResilienceExecutor` 已惰性 ✅ / `ProviderDelegates` 已静态缓存 ✅ | — | 已达标 |

**风险**：🟢 低。纯结构重构，须过 `SessionConcurrencyTests` 与 `ArchitectureInvariantTests`。

### A5 🟡 SQLite 连接串解析缓存（预计 −100~300 B/操作）

**现状**：PG 有 `RewrittenConnectionStringCache`（`PostgreSqlProvider.cs:72-77`），**SQLite 没有对等物**——`new SqliteConnection(cs)` 每次由驱动重新解析连接串（`DbConnectionOptions` 内部字典，量级可观）。

**建议**：给 SQLite Provider 加同款改写缓存（键 = 连接串，值 = 规范化连接串），把 `new SqliteConnection(cached)` 交给驱动；或用 `SqliteConnectionStringBuilder` 预规范化。**注意**：Microsoft.Data.Sqlite 的池化以"连接串相等"为键，规范化不改变池行为。

**风险**：🟢 低。注意 `Pooling=False` 与共享内存库的语义差异（`ResolveConnectionMode` 已区分）。

### A6 🟡 命令复用阈值按"会话是否可释放"分档

**现状**：`CommandReusePromotionThreshold = 3`（`DataSession.Crud.cs:233`），理由是"外部连接 + 一次性会话 + 不 Dispose ⇒ 命令泄漏原生句柄"。但 per-op 会话**必然** Dispose（A3 池化后更是必然归还），阈值 3 对它**结构性无效**。

**建议**：给会话加一个 `_ownsLifetime` 标志（自建连接 / 池化会话 = true；外部注入连接 = false）。`true` 时晋升阈值降到 1——单行 CRUD 的命令与参数在会话存续期内复用（对 A3 池化形态收益巨大：租期内的第 2 次同型操作起省掉 `CreateCommand` + `CreateParameter`）；`false` 时保持 3。

**风险**：🟡 中。必须确认命令在会话释放时被可靠释放（`DisposeReusableCrudCommandsAsync` 已存在），并回归"外部连接 + 不 Dispose"的历史用例。

## 5. L2——物化与读取路径

### B1 🟡 RowFactory 调用去 castclass（每行 1 次）

**现状**：RowFactory 以 `object` 存于注册表（`RegistryFragment.RowFactories`），消费端每次物化做 `((Func<DbDataReader, T>)metadata.RowFactory)(reader)`（`DataSession.Crud.cs:657/1074/1105/1116/1166/1286`、`DataSession.Query.cs:283/391`、`ResultListReader.cs:25/37/50/61`、`GridReader.cs:59/97`、`StoredProcBuilder.cs:150`）。

`castclass` 对引用类型不分配，但**每行一次类型检查 + 一次无法内联的间接委托调用**（委托来自 `object` 字段，JIT 无法去虚化）。

**建议**：把 `object RowFactory` 换成**泛型接口** `IRowFactory<T> { T Read(DbDataReader r); }`，注册表按 `Type` 存 `object`，但消费端经 `EntityRuntimeInfo` 携带**已转型**的强类型委托（`EntityRuntimeInfo.RowFactory` 已是 `object`——改为按 `T` 的泛型静态槽取 `Func<DbDataReader,T>`，避免每行 castclass）。

**收益**：每行省 1 次 castclass + 1 次不可内联的间接调用。20k 行时约 −0.2~0.5 ms（PG 20000 档 16.2 ms 的 1–3%）。
**风险**：🟢 低。纯类型层改动，AOT 友好（接口实现由生成物提供）。

### B2 🟡 白名单外类型的装箱兜底

**现状**：`RowFactoryEmitter.cs:234` 对白名单外的 provider 类型发 `(T)r.GetValue(ordinal)` → **每行每列一次装箱 + 拆箱**（`TimeSpan` 等类型命中）。

**建议**：扩充 provider 类型白名单（至少补 `TimeSpan` → `r.GetFieldValue<TimeSpan>(i)`），或对未知类型生成"读为 `object` 后走 `Convert`"的显式分支并标注。
**风险**：🟢 低。

### B3 🟡 列序校验降本

**现状**：`ColumnOrderValidator.Validate` 首行对每列调 `reader.GetName(i)`。可关闭（`DbOptions.ValidateQueryColumnOrder=false`），但默认开启是正确性护栏。

**建议**：保留护栏、降低代价——只在**列数不匹配**时逐列取名比对（快速路径：先比 `reader.FieldCount` 与期望列数，相等则跳过取名；不等时再逐列取名给出精确诊断）。或缓存"上次校验通过的结果集形状哈希"。
**风险**：🟢 低。默认行为不变（仍能拦住错位），只是把"每列取名"从热路径挪到异常路径。
**注**：`DbOptions.ValidateQueryColumnOrder` 已是 public 开关，默认值由 `DbOptions` 决定（实测默认为开）——**这是"可关闭的默认值"，需在文档中显式标注**。

### B4 🟡 可空列的双读合并

**现状**：可空列生成 `r.IsDBNull(ordinal) ? null : r.GetString(ordinal)`（`RowFactoryEmitter.cs:118-122`）——一次额外的 reader 访问。
**建议**：对已知 provider 类型，用单一调用返回 `T?` 的路径（`GetFieldValue<T?>` 或驱动的 nullable getter）替代。收益小但零风险。
**风险**：🟢 低。

## 6. L3——批量与事务

### C1 🔴 BulkUpdate 的 DbBatch 路径：每行每列 new DbParameter

- **位置**：`DataSession_Bulk.cs:925`（`batchCommand.CreateParameter()`）、`:860`（每行 `batch.CreateBatchCommand()`）。
- **现状**：MySQL/PG 的"池化逐条"路径上，每行每列新建一个 `DbParameter`、每行新建一个 `DbBatchCommand`。
- **建议**：批次级预建 `DbParameter[paramsPerRow]` 池 + 逐行就地写 `Value`（复用 `BindUpdateValues` 的"只写 Value"契约——它已经存在，只是这条路没走）。
- **预期**：该路径分配从 O(行×列) 降到 O(列)。
- **风险**：🟡 中。`DbBatchCommand.Parameters` 集合在 Add 后不可改（ADO.NET 契约），需为每行建 batch command 但参数对象可跨行复用（需验证驱动是否允许把同一 `DbParameter` 实例 Add 到多个 batch command——**Npgsql/MySqlConnector 多数不允许**，则退化为"每行一个 batch command + 参数池"两段式）。

### C2 🟡 逐行闭包 `() => incrementVersion(entity)`

- **位置**：`DataSession_Bulk.cs:797, 879`。
- **建议**：改 `static` lambda + state 参数（`Resilience.cs:101-106` 已有同型先例）。
- **预期**：乐观锁实体的 BulkUpdate 每行省 ~64 B。

### C3 🔴 三处"每次调用"的能力探测

- **位置**：`DataSession_Bulk.cs:1184-1189`（`CreateUpdateColumnArrays(1)` + 每列探测参数）、`:1879-1884`（Upsert 同款）、`:369-372`（`buildKeyArray([],0,0)` + `CreateArrayParameter`）。
- **现状**：每次 Bulk 调用都重建探测数组与探测参数，**探测结果随即丢弃**——纯重复计算，且能力只取决于 (实体类型, 方言)。
- **建议**：按 `(Type, Dialect)` 静态缓存探测结论（与 `DataSessionCache.UpdateRowParamsCache` 同型）。
- **预期**：每次 Bulk 调用省一次数组族 + 每列一个参数对象（列数 × ~80 B）。

### C4 🟡 UNNEST 列参数名 `$"@u{c}"` 每列每批插值

- **位置**：`BatchUpdateSqlBuilder.cs:171-172`；调用点 `DataSession_Bulk.cs:1249, 1265, 1937, 1946`。
- **建议**：静态 `string[]`（按列数缓存），零分配。

### C5 🟡 `BatchInsertReturningAsync` 列清单未缓存

- **位置**：`DataSession_Bulk.cs:1553-1556`——`QuoteIdentifier` ×2 + `string.Join` + LINQ，**每次调用重建**；而 `MultiValueBulkInsert.cs:16-17, 78-89` 有同款缓存。
- **建议**：对齐 `MultiValueBulkInsert` 的缓存口径。

### C6 🟡 事务收口的 CTS + 定时器

- **位置**：`TransactionCleanup.cs:147-149`（提交）、`:92-96`（回滚）——每事务 1 个 `CancellationTokenSource` + 1 个 `CancelAfter` 定时器。
- **建议**：改走 `PooledCts`（`PooledCts.cs` 已有租借池，`DataSession.CreateAsync` 的建连路径已用）。
- **预期**：每事务省 ~170 B + 1 个定时器。
- **风险**：🟡 中。`CancelAfter` 的定时器在 `TryReset` 后是否残留需验证（`PooledCts` 文档已述双检硬化）。

### C7 🟡 `HasTenantFilter` / `GetEntityFeatures` 每次调用一次字典查找，且单次批量调用内被调 2–3 次

- **位置**：`DataSession.cs:861-862, 905-910`；调用点 `DataSession_Bulk.cs:52, 57, 63, 745, 750, 1080, 1741, 1758, 1831`。
- **建议**：并入 `EntityRuntimeInfo` 合并视图（`Features` 已在其中），消除重复查找。

## 7. L4——方言协议级

### D1 🔴 SQLite 批量 UPDATE：`UPDATE … FROM (VALUES …)` 未被尝试

**这是本方案中唯一"单点数量级收益"的产品项。**

- **现状**：`BulkUpdateAsync` 在 SQLite **强制回退逐行**（`DataSession_Bulk.cs:980-981` → `ExecuteBulkUpdateRowByRowAsync`）。已试过的替代形态只有 `CASE WHEN`，实测慢 6.4×（`DataSession_Bulk.cs:594, 954`）。
- **未被尝试的形态**：SQLite **3.33.0 起支持 `UPDATE … FROM (VALUES (…),(…)) AS v(…)`**（`UPDATE … FROM` 是 SQL:2003 特性，SQLite 2020-08 加入）。仓库内 SQLite 引擎为 3.54（`SqliteProvider.cs:141-154` 注释"2026-10-14 SQLite 3.54 适配轮"）⇒ **能力具备**。
- **收益形态**：当前 SQLite BulkUpdate 2000 行 = 2000 次语句执行（单事务内）；改 `UPDATE FROM (VALUES …)` 后 = 4 次语句（参数上限 999 / 每行参数数）。**预期 10–50×**，且对齐 PG 的 UNNEST 形态。
- **风险**：🟡 中。需实测确认 SQLite 规划器在 `UPDATE … FROM` 上的行为（是否真走索引、是否触发全表扫），并处理"同一行被匹配多次"等边界。**必须 A/B 实测后再定论，不得先写结论。**
- **顺带**：SQLite 的 `BulkDelete`（0.73/0.52 优于地板）已是多值形态，无需动。

### D2 🟡 MySQL `LOAD DATA LOCAL INFILE` 的启用条件

- **现状**：`MySqlProvider.cs:203-209` 判据 `local_infile=ON` → 走 `MySqlBulkCopy`（实测 4.84×）；关闭时回退多值 INSERT。
- **建议**：把 `AllowLoadLocalInfile` / `local_infile` 提升为 `DbOptions` 的显式一等项（当前只在基准侧追加），并在文档中给出"何时值得开"（批量写入为主的服务端 + 信任边界内）。
- **风险**：🟢 低。注意 `local_infile` 的安全面（服务端读本地文件）。

### D3 🟡 PG 预备语句策略显式化

- **现状**：`MaxAutoPrepare=100` / `AutoPrepareMinUsages=2` 硬编码在 `PostgreSqlProvider.RewriteConnectionString`（`:117-120`），**不暴露为 `DbOptions` 项**。
- **建议**：提升为 `DbOptions` 显式项（如 `MaxAutoPrepare` / `AutoPrepareMinUsages`），并在 README 的"PG 进阶配方"表里写清"何时该调高/调低/关掉"（语句形状极多时 100 条不够；形状单一且高频时 5~10 更优）。
- **风险**：🟢 低。

### 9.2 验收口径（沿用仓库既有纪律）

- **分配是确定性指标**（复现性 >1%），作为主判据；**时延在 PG/MySQL 上被 ~200 µs RTT 主导**，只作展示。
- **地板健全性**：任一 ORM 臂快过 ADO 地板 >10% → 该轮相关项作废（`Report.cs:362-379`）。**M1 未做之前，BulkUpdate 组读数一律不作为结论。**
- **未复测不归因**：PG 20000 的 4 项在 3 批复测前不得定性。
- **不可比项**：`Build*` 地板直接返回插值字面量（`Program.cs:862-872`），比值记 0 + Note，不删项。
- **P95/P99 只展示不门禁**。
- **判定窗口**：3 批中位数，不做单批判定。
- **形态隔离**：跨夹具/跨口径（per-operation vs per-scope）绝对值不可比，只比同批比值。
