## 五之一、已确认产品缺陷（2026-10-29 复核）

首轮零失败之后，逐条追问"这些记录下来的行为是否合理"，发现七条应判为缺陷而非契约：前三条影响最大，后四条属同族不一致。全部已修并有锁定测试。

| 编号 | 缺陷 | 证据 | 严重度 |
|---|---|---|---|
| D1 | PostgreSQL 上 DateTime 列读回 Kind 丢失，导致"读出改回写"抛 `ArgumentException` | 根因是列用 `timestamp`（无时区）而参数用 `DbType.DateTime`（Npgsql 视为 timestamptz）。**已修复（2026-10-29）**：列类型改为 `timestamptz`，读回 Kind=Utc、刻度不变、往返可用；回归测试 `PostgreSql_DateTimeRoundTrip_ReadThenWriteBackSucceeds`；老库需手工 `ALTER COLUMN ... TYPE timestamptz` | P0（已修） |
| D2 | `BulkInsertAsync` 不回填自增主键，与同产品 `BulkMergeAsync`（PG/SQLite 多行 INSERT..RETURNING 按序回填）不一致 | 0b 阶段实测：首版批量测试三项静默失败（按 Id=0 更新影响 0 行），`BulkDelete` 一项假通过。**已修（2026-10-29）**：新增 `BulkInsertReturningAsync`（PG/SQLite 回填，MySQL 明确拒绝），原 `BulkInsertAsync` 保持 COPY/LOAD DATA/行预编译的最快形态不动，分工写进 API 参考与 B11 契约；回归测试 `BulkInsertReturningTests` 四项 | P0（已修） |
| D3 | `ForUpdate` / `ForShare` 在 SQLite 上构建期不拒绝、执行期由数据库报语法错 | 实测 `SqliteException: near "UPDATE": syntax error`；源码注释登记为 ITM-639，但登记不等于合理：正确形态是构建期按方言抛 `NotSupportedException`。**已修复（2026-10-29）**：`QueryBuilder.ThrowIfRowLockUnsupported` 在 SQLite 上构建期拒绝，连带五处断言改口，行锁形态断言移到 PG 侧 | P1（已修） |

同族不一致（应改，但严重度低于上述三条）：

| 编号 | 现象 | 问题 |
|---|---|---|
| D4 | 命令超时抛 `NpgsqlException`（`Exception while reading from stream`），连接超时抛 `TimeoutException` | **已修（2026-10-29）**：解包与耗时判定统一收在 `CommandTimeoutNormalizer`，弹性执行器出口、直调 catch 兜底、四个读入口（`ScalarAsync` / `GetAsync` / `GetAllAsync` / 查询管线）全部覆盖。E4 契约收紧为直接断言 `TimeoutException` |
| D5 | `SaveAsync` 对并发令牌实体在运行期抛 `NotSupportedException`，`BulkUpdateBatchAsync` 在编译期由 PALORM031 拦下 | **已修（2026-10-29）**：新增编译期诊断 PALORM054（Error），`SaveAsync<T>` 且 `T` 带 `[ConcurrencyCheck]` 即报错并给出替代路径 |
| D6 | `ToPageAsync` 静默覆写用户已设的 `Skip()`、`Take()` | **已修（2026-10-29）**：`Skip()` 与键集分页语义冲突（续页锚点），改为抛 `InvalidOperationException` |
| D7 | MySQL 上 `WithTimeout` 对长查询不生效 | 探针实测驱动行为**按路径分叉**：标量路径在 1 秒中断查询后**不抛异常**、返回部分结果（`SELECT SLEEP(5)` 返回 1）；列表路径抛 `MySqlException`（`ErrorCode=CommandTimeoutExpired`，内层 `QueryInterrupted` 1317），类型既非 `TimeoutException` 也不含超时内层。**已修（2026-10-29）**：`CommandTimeoutNormalizer` 在 MySQL 且设置了命令超时时按耗时判定，成功返回与抛出异常**两条路都先看是否越过截止线**，越过即归一为 `TimeoutException`（`Stopwatch.GetTimestamp` 无分配）。已接入 `ScalarAsync` / `GetAsync` / `GetAllAsync` 与查询管线（`ToListAsync` / `FirstOrDefaultAsync` / `ForEachAsync` / `ToPageAsync`，含分页在事务内的批执行形态） |

### 判据设计的教训

D1 到 D3 在首轮全部"通过"，根因是判据把"当前行为"当成"合理行为"固化：时间矩阵的判据是"刻度相等 + Kind 等于该方言实测值"，它接受 Kind 丢失；批量测试改用显式主键形状绕开了回填问题；SQLite 的 `ForUpdate` 断言按实测写成"抛 SqliteException"。

这对应方案 §5.2 已经写下的纪律「契约期望值一律从文档取，测试只登记实际值并交由评审」。实现只做到了"登记实际值"，缺了"交由评审"这一步。评审要回答的问题恰好是"这个行为合理吗"，本轮补上之后三条缺陷才浮出。

## 五之二、端到端用户路径（2026-10-29 追加）

D1 暴露的盲区是「单个操作都正确，两个操作的接缝出错」。为此新增 10 条端到端用例（`EndToEndPathTests`），专测连续的用户动作：

| 路径 | 覆盖什么 |
|---|---|
| 读-改-写（三方言） | 从库里读出的实体改字段后写回，正是 D1 失效的路径 |
| 跨方言迁移（SQLite 到 PostgreSQL） | 读一个库写入另一个方言，逐行逐列比对（含 long 极值、空串、emoji、引号） |
| 事务内先读后写 | 事务内读到旧值、写完读到新值、提交后新会话读到新值 |
| 软删复活再更新 | 软删、`IgnoreFilters` 读回、置空 `deleted_at`、再出现在默认查询里 |
| 批量写后逐键回读 | `BulkInsert` 后按主键逐条 `GetAsync`，逐值比对 |
| 分页遍历后逐页更新 | 25 行分三页遍历并逐页更新，验证全量被改且无重复 |
| 并发令牌读改写 | 更新后版本自增，旧实体写入抛 `ConcurrencyConflictException` |
| 删除后重建同主键 | 物理删后同主键再插入成功 |
