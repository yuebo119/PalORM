# 二进制列（byte[]）最佳实践

> 适用版本：v5.x 起（ADR-G）。每条规则的依据见文末"实证基础"。

## 一、选型决策树（先于一切）

```
要存的数据是什么？
├─ 结构化 JSON ──────────────→ [OwnedJson]（可投影、可查询），不要用 byte[]
├─ 二进制 ≤ 数百 KB，整存整取 ─→ 原生 byte[]
├─ 需要全文检索/按内容搜索 ───→ 重新设计：引用列 + 独立文本列（或伴生哈希列等值查）
├─ > 16MB、CDN 分发、冷数据 ──→ 对象存储；库里只存 URL + 哈希 + 大小
└─ 必须在 SQL 里做前缀模糊匹配 → PG/MySQL 用 byte[] LIKE（字节级，实测可用）；
                                 SQLite 主场 → 唯一推荐 Base64 TEXT 的场景（SQLite LIKE 对 BLOB 语义损坏）
```

## 二、实体声明规范

```csharp
#nullable enable  // 必须：disable 上下文下 byte[]? 不生成 IsDBNull 守卫（ITM-536）

[Table("attachments")]
public partial class Attachment
{
    [Key] public long Id { get; set; }

    // CA1819 是 ORM 列误报（数组属性），零警告项目定点抑制
#pragma warning disable CA1819
    [Column("content")] public byte[] Content { get; set; } = [];
#pragma warning restore CA1819

    [Column("preview")] public byte[]? Preview { get; set; }   // 可空 → IsDBNull 守卫
    [Column("content_sha256")] public string ContentSha256 { get; set; } = ""; // 推荐伴生列
}
```

四条硬规则：

1. **实体文件启用 `#nullable enable`**——可空二进制列的守卫生成依赖 NRT 注解；
2. **伴生哈希/大小列**成对声明——框架没有 MaxLength，大小治理在应用层；哈希列同时服务完整性校验与去重查询；
3. **更新走重新赋值**（`entity.Content = newData`）——无变更跟踪，语义即"你给什么写什么"；
4. **主键不用 byte[]**——技术可行（VARBINARY(255)）但引用相等陷阱多，用 long/Guid。

## 三、DDL 与索引

| 方言 | 数据列 | 索引/主键列 | 实测行为 |
|---|---|---|---|
| PostgreSQL | `BYTEA` | 直接 btree（大值 TOAST 外置） | 100KB 行 + 索引插入成功 |
| SQLite | `BLOB` | 直接索引 | 等值/排序全过；LIKE 失效 |
| MySQL | `LONGBLOB` | 框架自动 `VARBINARY(255)` | 无前缀建索引报 1170 |

规则：**只对真正需要等值查找的列建索引**（如去重哈希列）；纯载荷列永远不建。
MySQL 侧 255 字节前缀是框架决策，选择性不足时改用哈希列索引。

## 四、读写模式

- **读**：整存整取是设计形态（无流式 API）。大 BLOB 表用 `ToPageAsync` 分页或拆表（元数据表 + 内容表按键取）；50MB 行 = 50MB 进托管堆。
- **过滤**：等值过滤三方言可用——`db.From<T>().Where($"content = {needle}")`，含 0x00 字节（AotTest 原生二进制锁定）；字节级 LIKE 仅 PG/MySQL；FTS/正则/JSON 语义操作一律出局。
- **大小自检**（应用层，框架不查）：写入前校验 `content.Length` 门槛；MySQL 部署确认 `max_allowed_packet ≥ 最大载荷`（LONGBLOB 4GB 是类型上限，非传输上限）。

## 五、批量写入路径

- SQLite / MySQL 默认：参数化多值 INSERT，byte[] 直通（`DbType.Binary` 显式分派）；
- PG：Binary COPY 自动启用，bytea 原生；
- MySQL BulkCopy 加速（可选）：服务端 `SET GLOBAL local_infile=ON`（GLOBAL-only 变量，需特权，
  只对新连接生效）——不开则自动回退多值 INSERT，功能无损。载荷 MB 级、批量万行级才值得开。

## 六、存量 Base64 TEXT 迁移 SOP

1. 新增 BLOB 列（`ALTER TABLE ... ADD COLUMN content_blob LONGBLOB`），不动旧列；
2. 分批回填：PG `UPDATE ... SET content_blob = decode(content_text, 'base64')`、
   MySQL `FROM_BASE64`、SQLite 读出解码写回；
3. 实体切 `byte[]`，旧列只读保留一个发布周期；
4. 行数 + 哈希对账后删旧列；删列前保留回滚视图或反向脚本。

## 七、已知边界

| 边界 | 影响 | 绕行 |
|---|---|---|
| `TimeSpan`/`int[]` 等仍被 PALORM016 拒绝 | 声明即编译错 | TimeSpan 走 `[Converter]` 出口 `long` |
| 无 MaxLength/档位配置 | LONGBLOB 一刀切 | 应用层大小自检（见四） |
| 无流式读取 | 大对象全量进内存 | 拆表按键取；超大者对象存储 |

## 八、落地检查清单

- [ ] 决策树过了一遍，byte[] 是正确选择（≤ 数百 KB、整存整取）
- [ ] 实体文件 `#nullable enable`，可空列 `byte[]?`
- [ ] CA1819 定点 pragma
- [ ] 伴生哈希/大小列就位，索引建在哈希列上
- [ ] 写入路径有应用层大小门槛
- [ ] MySQL 部署确认 `max_allowed_packet`
- [ ] 往返测试包含 0x00 字节和 NULL 两种形态
- [ ] 大 BLOB 表读取走分页/按键，不是全拉
