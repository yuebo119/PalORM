# 性能优化方案 step17-P0：事务内写路径分段探针（2026-10-04，收档）

> 起点提问（用户）：GetByKey / Update / InsertReturningId / TxHundredInserts / TxRollback 能否极致优化。
> 前置裁决（用户指定）：跑 P0 探针拿分段数据——可砍段 ≥300 ns/行做 P1+P2；150~300 只做 P1；<150 登记定性收档。
> **结论：可砍段合计 ~60 ns/行（中位，全部在噪声带内）< 150 ns 线 → 收档，P1/P2 均不做。**
> 不改产品代码；本轮产物为探针（`.ai/perf-probe/WriteFastPathDiag.cs`，本地工具）与本登记。

## 一、背景

step16 后的剩余差距形态（PerfHub 11:08 批，SQLite 2000 档）：

| 操作 | P/ADO 时延 | 每行差 | 分配 vs ADO |
|---|---|---|---|
| TxHundredInserts | 1.34× | 649 ns/行 | -32%（已最优） |
| TxRollback | 1.55× | 654 ns/行 | +3%（step16 已收窄 356→29 B/行） |

两项都是"同会话同事务同形态循环写"，PL-2 命令复用（阈值 3）必然命中，复用命中段
（Transaction/Timeout 重设 + SQL 同值守卫 + BindValues 只写参数 Value）已与 ADO 臂的
"单命令跨行复用 + 每行 SetP"同构。差距只能在每行管道固定成本里。

## 二、探针设计（WriteFastPathDiag，形态阶梯 + 段级累加）

SQLite 文件库 WAL、同连接同事务、500 行/轮、预热 20 轮 + 60 轮迭代、墙钟 Stopwatch；
表列形状对齐 perf_s1（5 列）。地板 = ADO 臂天花板写法（单命令 + 参数池就地改值）。

| 格 | 形态（在上一格基础上累加一个段） |
|---|---|
| ① | ADO 地板：每行 SetP×5 + ExecuteNonQueryAsync |
| ①b1 | +1 层 async ValueTask 包装 |
| ①b3 | +3 层 async 链（近似 UpdateAsync→Core→ExecuteRows 层数） |
| ①ct | +每行 CommandText 读取 + string.Equals(Ordinal)（复用同值守卫） |
| ①c | +每行重设 Transaction/CommandTimeout（复用必做项） |
| ①m | +每行元数据发现：Volatile.Read + typeof×2 + FrozenDictionary×2 + 方言分派 + 分支 |
| ①o | +每行 outcome 判定：affected 检查 + 乐观锁字段分支（产品语义成本） |
| ①all | 全段累加（产品复用命中路径的理论骨架） |
| ② | 产品 UpdateAsync（单会话 500 行 + 回滚） |
| ①i / ②i | INSERT 族（显式主键 `[Key(AutoIncrement=false)]`，对齐 PerfHub S1Row 的 InsertNoReturning 形态） |
| ②a | 自增默认 [Key] 的 InsertAsync（INSERT..RETURNING 读回路径，对照格） |

段级复刻物与 `DataSession.Crud.cs` 真实序列逐段对应（FrozenDictionary 用 16 个互不相同
BCL 类型键模拟真实注册规模）。运行：`dotnet run --project .ai/perf-probe/PerfProbe.csproj -c Release -- writefastpath`。

## 四、裁决与定性

**裁决：可砍段 ~60 ns/行 < 150 ns 线 → 登记定性收档，P1（元数据快速通道）与 P2（层数压缩）均不做。**

1. **P1 预估被实测证伪**：方案预估元数据发现段 100~250 ns/行，实测 ①m 单段不可分辨
   （FrozenDictionary<Type,·> 查找 + typeof 在 .NET 11 上是 ~10 ns 级）。缓存 (state,
   metadata, sql) 快照的收益上界远低于改动风险（ITM-675 热重载一致性守卫的复杂度）。
2. **剩余 ~580 ns/行是 ~10 个 20~80 ns 管道小段的累积**：EnterOperation 租约（lock ×2 +
   AsyncLocal 同值守卫读）、OwnerPrewarmed 预热检查、弹性判定（Volatile.Read +
   IsPassThrough + GetActiveTransaction）、复用槽判定（EntityType typeof 比较 +
   BindValues 委托间接调用 vs 地板直接 pool[i].Value）、真 async 状态机同步完成成本
   （UpdateCoreAsync 含 using lease 的 try/finally 骨架）等。没有单段 ≥150 ns，
   逐段砍的 ROI 不成立：每段省不到 100 ns，却各自承担行为风险与 AOT/快照复验成本。
3. **产品语义成本不可砍**（方案的既定边界不变）：affected==1 幂等断言、乐观锁 outcome、
   操作归属、唯一冲突翻译。砍掉它们 PalORM 即退化为 ADO。
4. TxHundredInserts 1.34× / TxRollback 1.55×（SQLite 档）为**该 API 形态的结构性比值**：
   逐行公共 API vs ADO 天花板手写循环。产品对同场景的更快路径是 Bulk/SessionBatch
   （TxBulkInsert 0.98~1.11× 持平），文档与 README 的 API 选型指引已覆盖。

## 五、旁支登记

1. **分配侧复核通过**：② +30 B/行与 step16 登记的 29 B/行闭环，本轮无回归。
2. **①' 地板复测暴露 WAL 长会话漂移**：连续 ~3 万行写回滚后地板尾部可漂 +20~70%
   （WAL 文件膨胀），PerfHub 每操作播种间隔掩盖了该效应；探针以 ①'/② 顺序交叉校准。
3. **自增读回形态成本登记**：默认 [Key]（自增）实体在事务内逐行 InsertAsync 比显式主键
   形态慢 ~2.3 µs/行、多分配 245 B/行（INSERT..RETURNING 单往返 + 标量读回 + ID 回填，
   SQLite 本地档）。这是产品语义（自增 ID 必须读回）非缺陷；高频逐行插自增实体的用户
   应改用 BulkInsertAsync（批量读回一次）。不立项。
4. **测量方法**：段级复刻解释了产品差额的 ~10%（60/580），其余为散布小段——形态阶梯法
   对"多个 <100 ns 小段累积"的形态已到分辨极限（噪声 ±70~150 ns/格）。若未来需要再
   细分，须换 dotnet-trace CPU 采样或 ETW，成本高于收益，不建议。
