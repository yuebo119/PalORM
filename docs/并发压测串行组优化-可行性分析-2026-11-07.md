# 并发压测串行组优化可行性分析（2026-11-07）

> 触发：全量 Integration 实际耗时 137.3 s（200 轮）/ 117.6 s（默认 20 轮，714/714），其中挂
> `ExtBulkTable` 串行键的用例是主要瓶颈。本文只做只读测量与方案估算，不改测试代码。
> 状态：待裁决是否立项实施。

## 1. 现状测量

数据源：默认轮数（20）的全量 Integration 报告（714 条、实际耗时 117.6 s）。

| 项 | 数值 |
|---|---|
| 全量用例累计耗时 | 1,031 s |
| 并行度（累计 ÷ 实际耗时） | 7.5× |
| 实际耗时 | 117.6 s |
| 串行组（`ExtBulkTable`）用例 | 63 类 / 290 条 / **累计 105.1 s** |
| 串行组占累计耗时 | 10.2%，但它是串行链，接近实际耗时的下界 |

串行组按测试名 + 类名归类（关键词法，存在少量误归类）：

| 归组 | 条数 | 累计耗时 |
|---|---|---|
| 纯 PG | 75 | 22.0 s |
| 纯 MySQL | 60 | 29.7 s |
| 双方言 / 方言无关 | 116 | 48.9 s |
| 纯 SQLite | 18 | 1.2 s |
| 未识别 | 24 | 3.3 s |
| 合计 | 290 | 105.1 s |

62 个含串行类的文件中，**33 个含一种以上方言归组**，即类级属性不足以拆分，混合类需要方法级键。

### 迁移成本实测

临时探针（已删除）在暖态各跑 3 次 `MigrateAsync`：

| 方言 | 单次耗时 |
|---|---|
| PostgreSQL | 284 / 288 / 370 ms |
| MySQL | 322 / 340 / 437 ms |

串行组内 `MigrateAsync` 调用 74 次（分布在 23 个文件），上限成本 22.2 s（按 0.30 s）到 29.6 s（按 0.40 s）。

## 2. 方案 A：按方言拆串行键

**做法**：把 `ExtBulkTable` 拆成 `ExtBulkPg`、`ExtBulkMySql` 两个键；纯方言用例只持本方言键，单条测试内同时访问两个服务器的用例继续持共享键 `ExtBulkTable`。类级属性放不下时用方法级 `[NotInParallel("ExtBulkPg")]`。

**预期收益**（按上表估算）：拆分后串行链约为
`max(纯 PG 22.0, 纯 MySQL 29.7) + 双方言 48.9 + SQLite 1.2 + 未识别 3.3 = 83.1 s`，
比 105.1 s 少约 22 s，占全量实际耗时上限约 19%。

**风险**：低。串行键保护的是同一服务器内的 DDL 竞态，PG 与 MySQL 是两个独立服务器；拆分后同方言内仍完全串行。需要确认的只有 33 个混合类里哪些测试真的同时访问两库（这些保留共享键）。

**工作量**：纯方言类 22 个可改类级属性；混合类按测试逐个判定，预计 30 到 40 个文件有改动。

## 3. 方案 B：真库用例共享一次迁移

**做法**：测试侧提供 `EnsureMigratedAsync`，按（方言, 连接串）在进程内只迁移一次，用例改调它。

**预期收益**：上限 22 到 30 s（全部 74 次调用归零），与方案 A 量级相当且两者收益不叠加。

**风险**：高。改变 schema 建立时序，依赖「每次迁移后干净 schema」的用例可能失败；迁移类用例（漂移检测、索引、并发迁移）必须保留自己的调用，边界要逐个甄别。

## 4. 结论与建议

先做方案 A。收益可估、语义风险低、与现有串行键的职责一致。方案 B 暂不做：收益与 A 重叠，且引入 schema 时序耦合。

## 5. A/B 协议（若立项）

| 项 | 约定 |
|---|---|
| 基线 | 当前 HEAD 全量 Integration，默认轮数，3 次 |
| 变体 | 拆分后同配置，3 次 |
| 顺序 | B/A/B/A/A/B 交替，抵消容器与机器漂移 |
| 指标 | 实际耗时中位数为主，累计耗时与族计数为辅 |
| 通过判据 | 三次均 714/714、0 失败、0 跳过；串行组累计耗时下降 ≥15%；实际耗时中位数下降 ≥10% |
| 反向验证 | 若实际耗时无改善，回退拆分并记录，不保留「看起来更并行」的空改动 |
