# 并发压测串行组优化可行性分析（2026-11-07）

> 触发：全量 Integration 实际耗时 137.3 s（200 轮）/ 117.6 s（默认 20 轮，714/714），其中挂
> `ExtBulkTable` 串行键的用例是主要瓶颈。本文只做只读测量与方案估算，不改测试代码。
> 状态：A 与 C1 均已试点，同类降约 45%；但 TUnit 不支持多键（§8），且保守整类归类只省约 3 s（§10）。结论：暂缓铺开，记入待办。

## 1. 现状测量

数据源：默认轮数（20）的全量 Integration 报告（714 条、实际耗时 117.6 s）。

| 项 | 数值 |
|---|---|
| 全量用例累计耗时 | 1,031 s |
| 并行度（累计 ÷ 实际耗时） | 7.5× |
| 实际耗时 | 117.6 s |
| 串行组（`ExtBulkTable`）用例 | 63 类 / 290 条 / **累计 105.1 s** |
| 串行组占累计耗时 | 10.2%，但它是串行链，接近实际耗时的下界 |

串行组按测试名 + 类名归类（关键词法，存在少量误归类）：

| 归组 | 条数 | 累计耗时 |
|---|---|---|
| 纯 PG | 75 | 22.0 s |
| 纯 MySQL | 60 | 29.7 s |
| 双方言 / 方言无关 | 116 | 48.9 s |
| 纯 SQLite | 18 | 1.2 s |
| 未识别 | 24 | 3.3 s |
| 合计 | 290 | 105.1 s |

62 个含串行类的文件中，**33 个含一种以上方言归组**，即类级属性不足以拆分，混合类需要方法级键。

### 迁移成本实测

临时探针（已删除）在暖态各跑 3 次 `MigrateAsync`：

| 方言 | 单次耗时 |
|---|---|
| PostgreSQL | 284 / 288 / 370 ms |
| MySQL | 322 / 340 / 437 ms |

串行组内 `MigrateAsync` 调用 74 次（分布在 23 个文件），上限成本 22.2 s（按 0.30 s）到 29.6 s（按 0.40 s）。

## 2. 方案 A：按方言拆串行键

**做法**：把 `ExtBulkTable` 拆成 `ExtBulkPg`、`ExtBulkMySql` 两个键；纯方言用例只持本方言键，单条测试内同时访问两个服务器的用例继续持共享键 `ExtBulkTable`。类级属性放不下时用方法级 `[NotInParallel("ExtBulkPg")]`。

**预期收益**（按上表估算）：拆分后串行链约为
`max(纯 PG 22.0, 纯 MySQL 29.7) + 双方言 48.9 + SQLite 1.2 + 未识别 3.3 = 83.1 s`，
比 105.1 s 少约 22 s，占全量实际耗时上限约 19%。

**风险**：低。串行键保护的是同一服务器内的 DDL 竞态，PG 与 MySQL 是两个独立服务器；拆分后同方言内仍完全串行。需要确认的只有 33 个混合类里哪些测试真的同时访问两库（这些保留共享键）。

**工作量**：纯方言类 22 个可改类级属性；混合类按测试逐个判定，预计 30 到 40 个文件有改动。

## 3. 方案 B：真库用例共享一次迁移

**做法**：测试侧提供 `EnsureMigratedAsync`，按（方言, 连接串）在进程内只迁移一次，用例改调它。

**预期收益**：上限 22 到 30 s（全部 74 次调用归零），与方案 A 量级相当且两者收益不叠加。

**风险**：高。改变 schema 建立时序，依赖「每次迁移后干净 schema」的用例可能失败；迁移类用例（漂移检测、索引、并发迁移）必须保留自己的调用，边界要逐个甄别。

## 4. 结论与建议

先做方案 A。收益可估、语义风险低、与现有串行键的职责一致。方案 B 不做：收益与 A 重叠，且引入 schema 时序耦合。

**后续实测修正（见 §7 至 §9）**：方案 A 的单类试点成立，但 TUnit 1.76 不支持一条用例声明多个 `[NotInParallel]` 键，双方言用例无法同时阻塞两个方言键，铺开必须改为会话工厂方言信号量或分阶段执行。

## 7. 试点结果（2026-11-07，`TransactionIsolationTests`）

同一类内有 6 条 PG 用例与 5 条 MySQL 用例，适合验证双键并发。三次基线、三次变体交替执行：

| 配置 | 结果 | 实际耗时（三次） |
|---|---|---|
| 基线：类级 `ExtBulkTable` | 11/11 全绿 | 11.13 / 10.87 / 11.08 s |
| 变体：方法级 `ExtBulkPg` ×6 + `ExtBulkMySql` ×5 | 11/11 全绿 | 6.09 / 6.37 / 6.14 s |

**结论**：去重后约 45% 的耗时下降，机制成立，PG 与 MySQL 的用例在同一进程内可以重叠。

## 8. 铺开阻塞：TUnit 不支持一条用例多键

试点后验证「双方言用例同时持两把键」的可行性，结果是编译期直接失败：

```
error CS0579: "NotInParallel" 特性重复
```

即 TUnit 1.76 不允许同一条用例声明两个 `[NotInParallel]` 键。由此产生两个后果：

1. **双方言用例无法同时阻塞两个方言键**。纯方言用例持 `ExtBulkPg` 时，会与持共享 `ExtBulkTable` 键的双方言用例重叠，而后者可能正在读写 PG。
2. **部分铺开同样不安全**。只把一部分类改成方言键，新键与剩余 `ExtBulkTable` 用例跨键并行，隔离性不成立。试点测量时只跑单个类，所以安全；全量跑会破坏隔离。

因此「按方言拆键」不能机械铺开，需要先换掉隔离机制。

## 9. 可选路径（需单独立项）

| 路径 | 做法 | 代价 / 风险 |
|---|---|---|
| C1 会话工厂方言信号量（推荐） | `TestDb.PostgreSqlAsync/MySqlAsync`（及直接建会话的测试基座）创建会话时获取方言信号量，会话 `Dispose` 释放；双方言用例按固定顺序 PG→MySQL 获取两把，避免死锁。测试体不改，改动集中在测试基础设施 | 需覆盖绕过 `TestDb` 的直接 `DataSession.CreateAsync` 调用；取消与异常路径必须释放；验证双方言用例的死锁顺序 |
| C2 分阶段执行 | 双方言用例与纯方言用例分两次进程运行，各自内部并行；runner 合并报告 | 命令与报告合并复杂度上升；两次进程的启动成本；CI 编排改动 |
| C3 维持现状 | 保留 `ExtBulkTable` 全串行 | 全量实际耗时维持约 117.6 s |

**建议**：先做 C1 的两类试点（`TransactionIsolationTests` 与 `ConcurrencyRealDbTests`），用同一套 A/B 判据验证；通过后再移除全组的 `ExtBulkTable` 属性。C2 作为 C1 不可行时的备选。C3 是默认状态。

## 10. C1 试点与铺开收益复核（2026-11-07）

**试点做法**：新增测试侧方言闸门（PG 与 MySQL 各一把信号量，`[Before(Test)]` 按用例名推断方言并获取，`[After(Test)]` 释放），`TransactionIsolationTests` 去掉类级 `ExtBulkTable` 后只跑该类。

| 配置 | 结果 | 实际耗时（三次） |
|---|---|---|
| 基线：类级单键全串行 | 11/11 全绿 | 11.13 / 10.87 / 11.08 s |
| C1 闸门：PG 与 MySQL 分别持锁 | 11/11 全绿 | 6.02 / 6.02 / 6.21 s |

C1 机制成立，约 45% 下降，且用例体零改动。试点后已还原，避免与剩余 `ExtBulkTable` 用例跨键并行。

**铺开收益复核（关键）**：按「整类要么纯方言、要么双方言」的保守归类，62 个串行类里 37 个同时引用两种 Provider，累计 90.6 s；纯 PG 类 5.0 s，纯 MySQL 类 3.0 s。若这些双方言类整类持两把锁，串行链只从 98.7 s 降到 95.7 s，**收益约 3 s，不值得**。

只有做到**方法级**归类，让同一类里的纯 PG 用例与纯 MySQL 用例分别持锁，才回到 §2 估算的约 22 s 串行节省（实际耗时预计省 10 到 20 s）。代价是给约 290 个测试方法逐条标注方言，并在基类按方法名反射读取属性；62 个类要去掉 `ExtBulkTable` 并继承基类。

**结论**：C1 的机制已验证，但收益完全取决于方法级归类。按当前 CI 的 Integration job 3 m 19 s 看，10 到 20 s 的改善优先级低于改动面（62 类 + 290 方法）与误归类风险。建议暂缓，记入待办；若后续 CI 时长成为约束，再按方法级方案单独立项。
