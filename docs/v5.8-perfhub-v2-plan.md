> 状态：**已实施完毕**（阶段 1-5 全部落地；各阶段提交见 git log，实施中踩的坑已回填各任务验收说明）
> 日期：2026-09-21 · 前置：PerfHub v1 已上线（commit `eeed2c7`，18 项矩阵）
> 本文档是 PerfHub 第二代的完整设计：测试矩阵、三臂实现契约、测量口径、公平性与科学性规则、任务清单。

## 0. 为什么有 v2（v1 实测暴露的三个公平性缺陷）

v1 用同一套夹具跑了 v5.5.1 与 HEAD 各 380 项，交叉分析暴露出三处**某臂没写行业最优实现**导致的不公平：

| # | 缺陷 | 谁吃亏 | 后果 |
|---|---|---|---|
| 1 | Dapper 批量插入用 multi-exec（每行一次往返），地板与 PalORM 都是集合式 | Dapper | MySQL 20000 行批插 31 s/次，被夸大慢 ~100× |
| 2 | ADO.NET 地板批量 UPDATE 逐行裸 autocommit，PalORM 在 PG/MySQL 发集合式单语句、且裹事务 | 地板 | PalORM 显得"比地板快 98%"——真地板不可能被 ORM 超过 |
| 3 | Build 组不是同类对比：ADO/Dapper 返回预写字面量，PalORM 真在构建 SQL | 语义 | 该组差值只能读作"ORM 构建税" |

另有一个实验设计硬伤：两版**顺序跑**（相隔 33 分钟），同机 ADO.NET 地板单项漂移最高 50%，跨版本绝对值被污染，只能靠地板归一化补救。v2 的科学性设计（交替 A/B）由此而来。

**推论（v2 的第一原则）**：每个测试项必须先定义三臂各自的**行业最优实现**（三臂契约），实现违反即 bug；报告加机械门禁"任一 ORM 比地板快 >10% 即判定地板实现有缺陷"。

## 1. 目标与边界

**测什么**：ORM 数据面热路径在三数据库上的相对性能——同一份数据、同一条连接、同一操作语义下，PalORM / Dapper / 手写 ADO.NET 三臂对照，以及 PalORM 跨版本演化。

**不测什么**（如实声明，不装覆盖）：方言特有类型（JSON/数组/枚举/全文检索）、连接池参数、断连重试/超时、10 万行以上规模曲线、隔离级别与锁行为。

## 2. 测试矩阵

每项 × **3 数据库**（SQLite 进程内 / MySQL 远程 / PostgreSQL 远程）× **2 档位**（2,000 / 20,000 行）× **3 实现**（ADO_NET 地板 / Dapper / PalORM）。除 GenerateRows（不碰库）外全部项在三个数据库各跑一遍。

| 组 | # | 测试项 | 行业最优实现要点 |
|---|---|---|---|
| Build | 1 | BuildGetByKeySql | 编译期生成 + 形状缓存（读作 ORM 构建税，**非同类对比**） |
| | 2 | BuildComplexQuerySql | 同上 |
| CRUD | 3 | GetByKey | 显式列 + 参数化 + 索引 seek |
| | 4 | QueryAll | 单查询按序号物化（列按序号取，不逐行 GetOrdinal） |
| | 5 | StreamAll | 真流式（reader 逐行回调，不物化再枚举） |
| | 6 | Insert | 参数化单条 |
| | 7 | Update | 参数化按 PK |
| | 8 | BulkInsert | **PG: Binary COPY · MySQL: MySqlBulkCopy（`local_infile=ON`，协议级 ~4.84×）· SQLite: 多值 VALUES 单命令**；Dapper 统一多值 VALUES 500 行/批 |
| | 9 | BulkUpdate | **PG: `UPDATE ... FROM (VALUES ...)` · MySQL: `CASE WHEN ... WHERE id IN` · SQLite: 逐条但必须裹单事务**（autocommit 每行一次 journal 同步，差一个数量级；CASE WHEN 在 SQLite 实测慢 6.4×，不用）；三臂同构 |
| | 10 | BulkDelete | `IN` 分批（500）；SQLite 裹事务 |
| | 11★ | UpsertBatch | PG/SQLite: `ON CONFLICT DO UPDATE` · MySQL: `ON DUPLICATE KEY UPDATE`（8.0.20+ 行别名语法 `AS new`）；PalORM 用 `BulkMergeAsync`（已有，`BulkMergeSetBasedTests` 锁口径） |
| | 12★ | InsertReturningId | PG/SQLite: `RETURNING` · MySQL: 合并 `INSERT...; SELECT LAST_INSERT_ID()`——三臂各 1 RTT |
| Query | 13 | KeysetPage | 键集 seek（OFFSET 深翻页是反模式，刻意不测） |
| | 14 | WhereIn | 显式占位符 + 分批（PG 的 `= ANY(array)` 破坏三方言同构，记口径差） |
| | 15 | Count | 精确 `COUNT(*)`（近似计数超范围） |
| | 16★ | WideQueryAll | S2 宽实体 19 列——物化器按列数伸缩性；按序号取列 |
| | 17★ | IncludeJoin | 1:N 装配：ADO=两查询手工分组（无行放大）· Dapper=multi-mapping JOIN · PalORM=`Include`（**策略差异即测量对象，标注**） |
| Transaction | 18 | TxSingleInsert | 事务内复用命令重绑参数（不逐条 CreateCommand） |
| | 19 | TxTenInserts | 同上 |
| | 20 | TxHundredInserts | 同上 |
| | 21 | TxBulkInsert | 事务内 loader / 多值 VALUES |
| | 22 | TxRollback | 500 行更新后回滚（上限从 1000 降，回滚成本由撤销量决定） |
| Baseline | 23 | GenerateRows | 不碰库，数据生成内存基线 |
| Concurrency | 24 | Concurrent_Mixed80_20 | 池化连接、每线程一条、预热 1 s + 计时 2 s；SQLite 单写者负扩展是库特性非 ORM 缺陷 |

★ = v2 新增。**规模**：22 × 3 × 2 × 3 = 396 单操作项 + 并发 54 + 基线 2 = **452 项测量**。

## 3. 数据集

| 表 | 用途 | 说明 |
|---|---|---|

| perf_s1_seed（新） | 播种快照 | 重置 = `DELETE FROM 主表; INSERT INTO 主表 SELECT * FROM 快照表`——服务端一条 SQL，替代客户端逐行重播 |
| perf_wide（新） | 16 WideQueryAll | 19 列，复用 docs StandardShapes.S2 列型白名单 |

## 4. 测量口径

| 指标 | 口径 |
|---|---|
| 时延 | **全路径**（SQL 构建 → 执行 → 物化），取中位数；预热、prepare 播种不计时 |
| 分配 | `GC.GetTotalAllocatedBytes` 精确计数（确定性指标） |
| 堆峰 | `GC.GetGCMemoryInfo` 后台高频采样（标注为采样值，.NET 无精确峰值 API） |
| 并发 | ops/s + p50/p95/p99（多线程下分配计数被干扰，不测，B74） |
| 迭代 | **自适应**：`clamp(时间预算 ÷ 预热后单次耗时, 3, 2000)`；预算 Build 1 s / 普通项 1.5 s / 批量与事务项 4 s——单测量耗时结构性有上界 |

**全局底座**（所有项共用）：全链路异步；三臂统一参数化（禁拼接值）；不显式 `Prepare()`（真实应用依赖驱动隐式语句处理，且三驱动行为不一，记口径边界）；列按序号取；单操作项共用一条已打开连接（隔离池化噪声），并发项每线程一条池内连接。

## 5. 公平性规则（机械可查）

1. **三臂契约前置**：每项先定义三臂各自的行业最优写法（§2 表），实现违反即 bug
2. **地板健全性门禁**：报告自动检查"任一 ORM 比地板快 >10%"即标红并指认地板缺陷——真地板不可能被 ORM 超过
3. **写操作主键空间**：每轮互不重叠的确定性主键段，prepare 在预热前与计时前各重置一次
4. **会话生命周期**：PalORM 每操作新建 `DataSession`（与 Dapper 无状态扩展方法对等）；报告声明"每请求复用会话会更好"（此前 profile 实测 QueryAll 可快 35~40%）
5. Build 组、IncludeJoin 的"策略不同构"在报告显式标注

## 6. 科学性设计

- **跨版本一律交替 A/B**：块 = 库 × 档，两版轮流、R 轮取中位；报告展示逐轮配对比值 + 轮间散布，散布大即判"不可分辨"，不硬出结论
- **地板归一化**为跨版本唯一可信口径：`(新_PalORM/新_地板) ÷ (旧_PalORM/旧_地板)`，同轮地板抵消机器漂移；地板漂移 >18% 标 ⚠
- 版本排序按语义化版本号（`v5.5.1` 升序在前，`HEAD` 等非语义化标识最后），与两轮执行顺序无关

## 7. CLI 与报告

```bash
--profile core|full        core=原 18 项，full=22 项（默认）
--impls ado,dapper,palorm  版本对比可省 Dapper 臂
--dialects / --tiers       默认三库 × 2000/20000
--budget-seconds N         自适应迭代预算
bash scripts/perfhub-ab.sh <基线worktree> <轮数>   交替 A/B 编排器
```

报告七段：①按组总览 ②ORM vs 地板（含健全性门禁）③并发 ④版本对比 + 地板归一化 ⑤**A/B 配对比值（新）** ⑥增长曲线（SVG）⑦口径与未覆盖声明。

**时间预算**：全量三方言 ~13 min（Dapper 批插与地板批更换成最优形态后，两个大象项变亚秒）；只 SQLite ~3.5 min；A/B 五轮 × 关注项 ~20 min。

## 附：v1 存疑项档案（阶段 4.3 的对象）

v1 数据中两项"地板稳定但 PalORM 慢 13~45%"始终未能归因：`PostgreSQL/StreamAll/2000`（1.34×）与 `MySQL/QueryAll/20000`（1.20×）。已排除：分配回归（分配量逐位相同）、SELECT 管线新增开销（逐行比对一致）、机器漂移（同轮地板稳定）；PG QueryAll 2000 已由 Dapper 独立库同向变慢（1.31×）证明是服务端状态。这两项只有交替 A/B 能定论。
