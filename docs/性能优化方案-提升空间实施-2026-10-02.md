## 一、产品改动

| # | 改动 | 提交 | 终验数字（时延 / 分配） |
|---|---|---|---|
| 1 | SQLite 初始化 PRAGMA 每个池化物理连接只完整执行一次，复用时只重设 `foreign_keys = ON`；新增 `IDbProvider.InvalidateConnectionInitialization`（会话 SQL 执行前作废登记） | 47b6aa9、7b1ea39 | 探针 `lifecycle`，文件库 WAL：`CreateAsync+GetAsync` 16.62µs/6408B → 8.08µs/3880B，对手写 ADO（5.63µs）2.84× → 1.44× |
| 2a | PG 批量 UPDATE（`UPDATE … FROM VALUES`）单批上限 1000 行 | 6caeada | BulkUpdate/PG/2000：41.55ms → 14.87ms，对 ADO 2.65× → 0.99×；分配 3.44MB → 2.18MB |
| 3 | PG 批量 UPSERT（BulkMerge 集合化路径）单批上限 1000 行 | 5e77be6 | UpsertBatch/PG 分配 4.31MB → 2.71MB（2000 行）、19.77MB → 12.55MB（2 万行），时延 0.99× / 1.03× |
| 4 | 结果列表池化收集 + 精确分配（`ResultListReader`，五处物化循环收敛） | 8dd024a、1cc4524 | SQLite QueryAll/20000 分配 3339K → 2984K（对 ADO 0.89×）；BDN QueryAll 1,546,550B → 1,364,368B（对 ADO 1.003×）；时延持平 |

**第 1 项的边界**：只有池化文件库会复用原生句柄。探针实测共享内存库（`Mode=Memory;Cache=Shared`）与 `Pooling=False` 每次 Open 都是新句柄，这两种形态不查不登记，行为与改前逐位相同。47b6aa9 曾对每个新句柄都写弱表，BDN 共享内存库 CRUD 臂因此多分配 25~33B/会话，7b1ea39 修复后回到改前（GetByKey 4888B、Insert 4856B、Update 6520B）。PerfHub 与 BDN 都不经过"池化文件库 + 每请求 CreateAsync"形态，本项收益只在探针中可见，目前没有门禁覆盖。

**第 1 项的行为变化**：会话中途用原始 SQL 改过的调优 PRAGMA（cache_size 等）会随池化句柄带入后续会话；`foreign_keys` 每会话重设不受影响；需要每会话复位的设置放进 `SessionSetupSql`。三个锁定用例在 `SqlitePooledInitializationTests`，跳过逻辑、外键重设、作废登记三处变异各自转红已核实。

**第 2a 项的根因**（探针 `pgplan`，42 万行表，事务内执行后回滚）：

| 形态 | 计划 | 墙钟中位 |
|---|---|---|
| VALUES 2000×1（原产品形态） | Hash Join + 目标表全表 Seq Scan | 45.39ms |
| VALUES 1000×2（地板形态） | Nested Loop + 主键 Index Scan | 19.50ms |
| 产品 BulkUpdateAsync（改后） | 同上（1000 行/批） | 16.35ms |
| UNNEST 数组 2000×1 | Nested Loop + Index Scan | 11.53ms |

统计陈旧（ANALYZE 于 2K 行时）同形态。触发因素是 VALUES 行数相对表规模，1000 不是普适安全线，只是与地板同宽、在该场景实测保持索引计划的值。此前把 2.65~2.83× 定性为"服务器时段波动"是误判。

**第 4 项的时延结论**：分析轮推断"宽表 2 万行慢 18% 主要来自列表扩容触发 LOH/GC"，被探针 `listbuild` 证伪：同一读取器上两种收集策略时延差在 ±3% 噪声带内，分配差与预测吻合（2 万行 -364KB）。宽表差距真正的来源是器材不对等，见第二节 M2。

## 二、测量层修正

**M1 预热时间下限（968424e）**。原规则只有次数上限 `maxIterations/5`（多数项 40 次），微秒级操作的预热不足 1ms。三批数据里，SQLite 首个进场的 ADO 臂单行操作在 2000 档比自身 20000 档慢 21~42%，第三个进场的 PalORM 臂是 0.87~0.98，所以 2000 档出现了"PalORM 比 ADO 快 21~35%"的读数。新规则：次数到顶后还须满 0.5s，硬上限 `maxIterations×100`。终验批中 SQLite 2000 档 QueryAll/StreamAll/Insert/Update 的 P/ADO 由 0.50~0.79 回到 1.01~1.13。

- GetByKey/SQLite/2000 仍是 0.79×，不能用预热解释，原因未查。
- 副作用：M1 之后 SQLite 20000 档单行操作的绝对时延三臂同步上移 30~50%（GetByKey ADO 7.3 → 11.3µs，两批复现）。同批比值不受影响，原因未查；推测与加长预热的写入量撑大 WAL 有关，未验证。
- 均值离群：终验批 Insert/SQLite/2000 的 ADO 臂中位数 17.1µs、均值 45.6µs（errRatio 0.58）。

**M2 三项器材对等化（0a40b27）**：

| 项 | 原不对等 | 修正 | P/ADO 改前 → 终验 |
|---|---|---|---|
| WideQueryAll | ADO 臂逐行映射后丢弃，不持有 2 万个宽实体 | ADO 臂建列表并持有 | SQLite/20000：1.18× → 1.00× |
| IncludeJoin | ADO 臂每行只读两列、不建实体 | ADO 臂逐行物化父列实体 | SQLite 1.09× → 0.86×；PG 1.35× → 1.08× |
| TxRollback | ADO/Dapper 只更新 1 列；PalORM 更新 4 列并靠抛异常回滚 | 三臂同为整行 UPDATE + 显式 RollbackAsync | SQLite 1.95× → 1.51× |

TxRollback 余下的 1.51×（每行约 +0.6µs、+300B）是 `UpdateAsync` 每次调用的真实固定开销，与 TxHundredInserts 1.33× 同族。

## 三、UNNEST 数组形态 PoC（结论：GO，单独立项）

- **AOT**：`.ai/aot-poc/UnnestAotPoc`（Npgsql 10.0.3，NativeAOT）发布 0 个 IL/AOT 警告，原生二进制执行 UPDATE FROM UNNEST、INSERT…SELECT UNNEST ON CONFLICT（插入与更新两分支）、DELETE = ANY，覆盖 bigint/text/int4/numeric/可空 int8/timestamptz/uuid 七种数组，2000 行结果逐项校验通过。
- **性能**（探针 `pgplan` / `pgunnest`，42 万行表，2000 行，事务内回滚）：

| 操作 | 产品现路径 | 数组形态 | 时延 | 客户端分配 |
|---|---|---|---|---|
| UPDATE | 16.35ms（VALUES 1000×2） | 11.53ms | -30% | 未测 |
| UPSERT | 42.42ms / 2.51MB（VALUES 1000×2） | 38.90ms / 103KB | -8% | -96% |
| DELETE | 6.63ms / 833KB（IN 2000 参数） | 3.16ms / 5KB | -52% | -99% |

- **实施要点**（立项时用）：
  - 生成器按实体发射"按列转置"的类型化数组绑定，可空、转换器、OwnedJson、枚举都映射到数据库端类型。
  - PG Provider 负责创建类型化数组参数。
  - Core 在 BulkUpdate / BulkMerge / BulkDelete / WhereIn 的 PG 分支切换形态；MySQL、SQLite 不变。
  - 生成物形态变化需同步快照，三方言 AOT 发布与原生运行需复验。

## 四、基线重录评审（record-index，176 项）

终验批健康 clean、零失败登记；重录前结果库门禁 5 项 FAIL，都是"PalORM 臂自身持平、地板变快"，即 M1 修正首档地板所致。重录后两道门禁：BDN 27/27、结果库 176 项 0 FAIL。比值变动 ≥15% 的 26 项（基线比值口径为 MeanNs）分四类：

1. **M1 修正首档地板**：Update/SQLite/2000 0.65 → 1.10、QueryAll/SQLite/2000 0.60 → 1.02、StreamAll/SQLite/2000 0.73 → 1.10、OwnedJsonQuery/SQLite/2000 0.91 → 1.23、QueryAll/MySQL/2000 0.70 → 1.05 等。
2. **M2 器材对等化**：WideQueryAll/SQLite/20000 1.19 → 1.00、IncludeJoin SQLite 1.02 → 0.86 / PG 1.32 → 1.10、TxRollback/SQLite 1.87 → 1.40。
3. **产品改动**：BulkUpdate/PG/2000 2.69 → 0.98。
4. **远程服务器状态**：QueryAll/PG/20000 1.42 → 1.06、StreamAll/PG/20000 1.41 → 1.01（旧基线录在 PG 慢态）；MySQL 的 GetByKey/Update/QueryAll/StreamAll 20000 档在终验批与即时复测批 `filtered/recheck-mysql-20k` 之间两臂互换（例：GetByKey 1.21 ↔ 0.84、QueryAll 0.75 ↔ 1.20），噪声带约 ±20%。

**已知地雷**：

- **Insert/SQLite/2000 基线比值 0.46**：来自上述 ADO 臂均值离群（中位口径是 1.13）。下一个不离群的批次大概率在此项假报 FAIL。
- **MySQL 20000 档**：QueryAll 基线录在 0.75（快态），服务器回到慢态时可能假报 FAIL。

建议门禁比值改用中位数，或改为多批取带。
