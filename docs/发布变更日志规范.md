# PalORM 发布变更日志规范（强制标准）

> **本文档是每次发版的强制执行标准。违反任何一条 = 发布不合规。**
> 适用于：CHANGELOG.md 条目、GitHub Release Body、NuGet Package Release Notes。

---

## 一、核心原则

| 原则 | 含义 | 违反后果 |
|------|------|---------|
| **真实** | 每项声明必须可验证（git diff/测试输出/构建日志） | 禁止发布 |
| **准确** | 数字（测试数/版本号/文件数）必须来自实际运行结果 | 禁止发布 |
| **完整** | 破坏性变更必须显式标注，不得隐瞒 | 禁止发布 |
| **可追溯** | 每项修复/新增必须关联 ITM 编号或 Issue | 禁止发布 |

---

## 二、变更日志标准格式（七段结构）

```markdown
## [X.Y.Z] — 版本标题（一句话概括核心变化）

> 变更规模：N 个提交 · N 个文件 · +N/−N 行
> 背景说明（可选：设计文档/ADR 链接/迭代轮次）

### 💔 破坏性变更（如有，必须放最前面）

- **API 变更**：旧签名 → 新签名 + 迁移代码示例
- **行为变更**：旧行为 → 新行为 + 影响范围

### ✨ 新增

- **特性名**：一句话描述
  - 实现细节（具体到文件/方法名）
  - 锁定测试名（证明行为被测试覆盖）

### 🐛 修复

| 问题 | 影响 | 修复方式 |
|------|------|---------|
| 问题描述（ITM-XXX） | 对用户的影响 | 代码层面的具体修改 |

### ⚡ 性能（如有）

- 优化描述 + BenchmarkDotNet 数据（无数据则标注"机制改进，未基准"）

### 📦 依赖升级

| 包名 | 旧版本 | 新版本 |
|------|--------|--------|
| Package.Name | X.Y.Z | A.B.C |

### 🧪 验证

- **N 个测试全绿**：Core N + SourceGen N + Integration N（含 PG/MySQL 真库）
- **Native AOT** 三平台 publish 零错误 + 原生二进制运行通过
- **快照基线** N 份一致

### 📚 参考

- [设计文档](链接)
- [ADR](链接)
```

## 三、数字准确性检查清单（发布前必做）

| # | 检查项 | 验证命令 | 要求 |
|---|--------|---------|------|
| 1 | 测试总数 | `dotnet run --project test/PalORM.Core.Tests -c Release` ×3 | 三套实测数字之和 |
| 2 | 依赖版本 | `git diff <prev_tag>..HEAD -- Directory.Packages.props` | 逐行与 diff 比对 |
| 3 | 提交数 | `git log <prev_tag>..HEAD --oneline \| wc -l` | 精确数字 |
| 4 | 文件变更数 | `git diff <prev_tag>..HEAD --stat \| tail -1` | 精确数字 |
| 5 | 行数变更 | `git diff <prev_tag>..HEAD --shortstat` | +N/−N 格式 |
| 6 | 破坏性 API | `git diff <prev_tag>..HEAD -- src/ \| grep "^-.*public"` | 逐个检查是否为公共 API 变更 |
| 7 | AOT 验证 | `dotnet publish test/PalORM.AotTest -c Release` + 运行 | 0 错误 + PASSED |
| 8 | 快照数 | `ls test/PalORM.SourceGen.Tests/Snapshots/*.snap \| wc -l` | 精确数字 |

## 四、GitHub Release Body 额外要求

Release Body 在七段结构基础上增加以下段（由 CI 自动生成）：

```
# PalORM vN.N.N
[与上一版本对比] | [NuGet] | [完整变更日志]

## 📦 发布包（动态从 artifacts 生成）
## 📥 安装（按场景分组的 dotnet add package 命令）
## 🚀 30 秒上手（完整可运行 C# 代码）
--- 
| 📖 文档 | 📋 变更 | 🏗️ ADR | 🐛 Issues |（资源导航）
```

## 五、禁止事项

| 禁止 | 原因 |
|------|------|
| ❌ 使用"约""大概""左右"等模糊词 | 数字必须精确 |
| ❌ 声称的测试数未实际运行验证 | 测试数会随提交变化 |
| ❌ 遗漏破坏性变更（API 签名/行为变化） | 下游用户会 break |
| ❌ "修复了若干问题"类的模糊描述 | 每项必须具体 |
| ❌ 复制上一版本的数字（必须重跑验证） | 版本间数字会变 |
| ❌ 将基础设施改进混入产品特性段 | 分开列出 |
| ❌ 声称"性能提升 N%"无基准数据 | 有数据才写数字 |

## 六、发布流程（强制顺序）

```
1. 完成代码变更 + 全量测试通过
2. 升版本号（Directory.Build.props <Version>）
3. 运行 §三 检查清单（8 项数字验证）
4. 按 §二 格式编写 CHANGELOG.md 条目
5. git commit + push main
6. git tag vX.Y.Z + push tag → CI 自动打包发布
7. CI 自动从 CHANGELOG 提取版本段 → 生成 Release Body
```

## 七、历史教训（为什么有此规范）

| 事故 | 根因 | 防线 |
|------|------|------|
| v5.2.0 首版 Release 声称 507 测试 | Core 从 191→195 未同步 | §三 #1 强制三套实测 |
| v5.2.0 首版遗漏破坏性变更 | CrudColumns 构造函数 2→3 参数未标注 | §三 #6 强制 diff public API |
| "声称未交付"四例 | 提交消息声称的修复未实际在 diff 中 | 每项修复必须 grep diff 确认 |
| CHANGELOG 与 Release Body 不一致 | 手动维护两份数据 | CI 自动提取消除手工不同步 |
