# PalORM 发布变更日志规范（强制标准）

> 适用于三处输出：`CHANGELOG.md` 条目、GitHub Release Body、NuGet 包 `<releaseNotes>`。
> 三者的内容来源只有一个：**`CHANGELOG.md` 的版本段**。Release Body 由 `scripts/release-notes.cs` 从该段派生（本地预览与 CI 同一实现），禁止手写第二份变更内容。

---

## 一、两套规范的分工（先纠正一个常见混淆）

| 规范 | 管什么 | 本项目执行方式 |
|------|--------|---------------|
| **Semantic Versioning 2.0.0** | 只规定版本号格式（`MAJOR.MINOR.PATCH[-pre][+build]`）与递增规则，全文不涉及变更日志格式 | `scripts/release-version-scan.cs` 格式门禁（正则断言 + 升级类型推导） |
| **本文件（变更日志规范）** | 版本段怎么写、什么必须显式标注、哪些数字必须实测 | `scripts/pre-release-check.cs` 段校验 + `release.yml` pack 前断言 |

结论：不存在"按 SemVer 重新生成 CHANGELOG"这件事，SemVer 不定义日志格式。CHANGELOG 的通行格式规范是 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，本项目按其精神做了轻量化取舍（见 §三）。

---

## 二、版本号语义与本项目的破坏性判定

| 变更性质 | 版本号 | 判定依据 |
|---------|--------|---------|
| 公共 API 签名删除或修改，已编译消费者必须重新编译 | **MAJOR** | `git diff <prev_tag>..HEAD -- src/` 中出现 `^-.*public` |
| 向后兼容新增（新 API、新诊断码、新 Provider 能力） | **MINOR** | 旧代码无需改动即可升级 |
| 仅缺陷修复，对外行为不变 | **PATCH** | 修复前后调用方代码与结果一致 |
| 预发布 | `-preview.N` | 仅 `workflow_dispatch` 手动触发 |

**行为变更的处置（本项目已有先例，明文记录以免重复争论）**：查询结果可能变化、默认值改变、批量上限调整这类"签名没变但结果会变"的变更，严格 SemVer 语义下属破坏性。本项目的实际政策是 **MINOR + `💔` 段显式标注 + 升级指南兜底**，理由是零 API 破坏且升级成本可控。

- 已生效先例：v6.5.0（`Where(A).OrWhere(B).Where(C)` 运算符优先级修正，查询结果可能变化），当时版本裁决由 7.0.0 回落至 6.5.0。
- 历史偏离（不再重复）：v5.2.0（`CrudColumns` 构造 2→3 参）与 v5.4.0（移除 legacy 无方言 SQL 生成段）在 MINOR 中引入了签名破坏。这两例发生在本政策确立之前，已发布不可改，新版本不适用此放宽。
- 新版本若出现真正的签名破坏，仍必须升 MAJOR，行为变更政策的宽松不延伸到此。

## 三、CHANGELOG 版本段标准结构（头条 + 两段，轻量）

```markdown
## [X.Y.Z] - YYYY-MM-DD

一句话概述（≤80 字，本版主体变化，Release 页首行）

### 💔 破坏性/行为变更

- **短标题**：调用方要做什么 + 必要细节

### 变更要点

- **短标题**：一句话描述
```

规则：

1. **头条一句话**：版本标题下第一段（普通段落或 `>` 引用均可），不分行，≤80 字。它是 Release body 的首行，写本版主体变化，不写细节。
2. **条目必须带短标题**：形态固定为 `- **短标题**：细节`，短标题 2~32 字符（含英文标识符与反引号），标题后跟冒号。短标题进 Release body，冒号后的细节只留在 CHANGELOG。
3. **`### 💔` 段只在存在破坏性或行为变更时出现**，位置必须在版本标题之下、其余内容之上。它是段落标题，不是行内前缀。该段条目的细节必须是调用方要做什么（迁移动作），Release body 只保留其第一句。
4. **`### 变更要点` 承载新增、修复、性能、依赖升级、文档等全部其余条目**。
5. **`〔内部〕` 标记**：仅面向仓库维护者的条目（测试断言搬迁、基准工具、探针、门禁脚本）在细节末尾加 `〔内部〕`。这类条目保留在 CHANGELOG 供审计，不进 Release body。
6. 日期必须与 `git log -1 --format=%ad --date=short vX.Y.Z` 一致（tag 提交日，不是发版操作日）。
7. 每条一个事实、一句话，禁止"修复了若干问题"式概括。
8. 性能数字必须来自实测（PerfHub 批次或 BenchmarkDotNet），写清口径（方言、档位、样本）。无实测就写"机制改进，未基准"。
9. **`## [Unreleased]` 是可选的未发布累积段**（Keep a Changelog 约定），存在时置于文件最顶部，按同一形态书写（头条 + 短标题条目）。门禁跳过它的版本号与日期校验，但校验形态。
10. **历史段冻结**：格式标准变更（如 2026-10-26 由七段长表改为三段式、2026-11-05 增头条与短标题）不回改既有版本段。历史段允许保留副标题（如 `## [6.7.0] - 2026-10-23 · 请求级查询管道`）与其原有结构，门禁只校验目标版本段与 `[Unreleased]`。

参考实例：

```markdown
## [6.8.0] - 2026-10-26

SQLite 批量写入全面换形态，批插与批删分别提速 3.5~3.9 倍与 15 倍以上。

### 💔 破坏性/行为变更

- **`batchSize` 不再决定语句形状**：SQLite 上 `batchSize` 不再影响语句形态（≤0 仍拒绝），批内重复主键改为后行覆盖前行。

### 变更要点

- **项目协议改为 Apache-2.0**：本版起由 AGPL-3.0-only 变更（v6.7.0 及以前发布物仍为 AGPL-3.0-only）。
- **SQLite 批插改行预编译**：`BulkInsertAsync`/`BulkMergeAsync` 批插 3.5~3.9×、批 upsert 2.4~3.1×。
```

## 四、机械门禁（由脚本执行，不靠自觉）

| 校验项 | 执行位置 | 失败后果 |
|--------|---------|---------|
| 版本号符合 SemVer 2.0.0 + 升级类型推导 | `release-version-scan.cs` | exit 1，禁止 push tag |
| CHANGELOG 顶部第一个版本等于目标版本 | `pre-release-check.cs` | exit 1，禁止 push tag |
| 版本标题格式 `## [X.Y.Z] - YYYY-MM-DD` | `pre-release-check.cs` 与 `release.yml` | exit 1 |
| 日期等于 tag 提交日 | `pre-release-check.cs` | exit 1 |
| 版本段至少 1 条 `- ` 条目 | `pre-release-check.cs` 与 `release.yml` | exit 1 |
| `### 💔` 段存在时其下有条目 | `pre-release-check.cs` | exit 1 |
| PATCH 版本段出现 `### 💔` | `pre-release-check.cs` | exit 1（2026-11-05 由警告升级：政策要求行为变更走 MINOR） |
| 声明升版段低于 API 实际变化所需 | `semver-bump-check.cs`（预检第 2 步 + `release.yml` pack 前） | exit 1，见发布规范 §1.4 |
| 头条存在且 ≤80 字 | `release-notes.cs --check`（预检第 2 步 + `release.yml` pack 前） | exit 1 |
| 每条 `- ` 条目带短标题 `**…**：` | `release-notes.cs --check` | exit 1 |
| 派生 body 体量 ≤1400 字符 | `release-notes.cs --check` | exit 1 |
| CHANGELOG 含目标版本号 | `release.yml` pack 前 | exit 1，禁止发布 |

校验只针对**目标版本段**（CHANGELOG 顶部第一个版本）与可选的 `[Unreleased]` 段，不扫历史段，历史记录不可回改。`[Unreleased]` 只校验头条与短标题形态，版本号与日期校验对它不适用。

## 五、数字准确性检查清单（发布前必做）

| # | 检查项 | 验证方式 |
|---|--------|---------|
| 1 | 测试总数 | 三套实测运行计数之和，禁止沿用上一版数字 |
| 2 | 依赖版本 | `git diff <prev_tag>..HEAD -- Directory.Packages.props` 逐行比对 |
| 3 | 破坏性 API | `git diff <prev_tag>..HEAD -- src/` 中 `^-.*public` 逐条判定 |
| 4 | 性能数字 | 引用 `bench/perfhub/results/` 或 CrossBench 批次文件，注明批次号 |
| 5 | AOT 验证 | `dotnet publish test/PalORM.AotTest* -c Release` 零错误，原生二进制运行通过 |
| 6 | 快照数 | `ls test/PalORM.SourceGen.Tests/Snapshots/*.snap \| wc -l` |

测试与文档的具体条数由 `verify-ai-system.cs` 与 CI 地板断言接管，本文件不重复维护（避免两处数字漂移）。

## 六、禁止事项

| 禁止 | 原因 |
|------|------|
| 使用"约""大概""左右"修饰数字 | 数字必须精确 |
| 声称的测试数未实际运行 | 数字随提交变化 |
| 遗漏破坏性变更（API 签名或行为变化） | 下游会 break |
| "修复了若干问题"类模糊描述 | 每条必须具体 |
| 复制上一版本的数字 | 版本间数字会变 |
| 把基础设施改进（基准工具、质量脚本、探针）写进版本段 | CHANGELOG 面向包消费者，不面向仓库维护者 |
| 手写第二份 Release Body 变更内容 | 与 CHANGELOG 必然漂移，由 CI 自动提取消除 |

## 七、Release Body 与 tag 发版内容的生成（唯一路径，禁止手工撰写）

**发版统一口径（2026-10-26 用户定标，2026-11-05 收敛为单实现）**：每个版本的 GitHub Release Body（即"tag 的发版内容"）一律由 `scripts/release-notes.cs` 从 `CHANGELOG.md` 对应版本段派生。禁止任何形式的手写第二份变更内容，禁止在 Release 页面直接编辑变更条目。

单一实现在本地与 CI 共用（本地预览 = CI 产物，不再维护 awk 与 C# 两套提取逻辑）：

```bash
# 预览下一个未发布版本（不写盘）
dotnet run --file scripts/release-notes.cs -- unreleased

# 预览指定版本并落盘
dotnet run --file scripts/release-notes.cs -- 6.9.0 --write full-release-body.md

# 形态校验（头条 / 短标题 / 体量），pre-release-check 第 2 步与 release.yml pack 前各跑一次
dotnet run --file scripts/release-notes.cs -- 6.9.0 --check
```

派生规则：

| Body 区块 | 来源 | 处理 |
|-----------|------|------|
| 首行概述 | 版本段第一段 | 原样，超过 80 字校验失败 |
| `## ⚠️ 升级须知` | `### 💔` 段 | `**短标题**：第一句`，无该段时整块省略 |
| `## 本版变更` | 其余段落的条目 | 只取 `**短标题**`，跳过 `〔内部〕` 条目 |
| 包清单 | 实际 `artifacts/packages/*.nupkg` | 一行：一个 NuGet 链接 + 包名列表，包增减零维护 |
| 页脚 | 计算 | 完整变更日志 + `compare` 链接（上一版本取自 CHANGELOG 下一段） |

被删除的历史元素与理由：`# PalORM vX.Y.Z` 标题（与 Release 页标题重复）、发布包表格（与页面 Assets 列表重复）、底部资源表五行（README/Issues/Discussions 是页面自带入口）、原样嵌入的完整变更明细（使用者不需要审计级证据，改为链接）。

**历史 Release 的修正流程**（仅用于已发布版本的排版修正，不改变已发布包；2026-10-26 与 2026-11-05 各实操过一次）：

```bash
# 1. 用同一实现重新生成本地 body（tag 名注入，不再从 workflow 里抽 awk）
dotnet run --file scripts/release-notes.cs -- <版本号> --write full-release-body.md --tag v<版本号>
# 2. 覆盖 Release body
gh release edit v<版本号> --notes-file full-release-body.md
# 3. 清理临时产物（full-release-body.md 在仓库根生成，未入 gitignore）
```

注意：tag 本身（轻量 tag 只是一个提交指针）不因该操作改变，指向的 commit 保持原样，已发布的 NuGet 包不动。若确认需要让 tag 指向含新 CHANGELOG 的提交，那是重打 tag 的另一类动作，须单独评估（会把 tag 之后的改动一并带进该版本的 tag 内容，通常不应做）。

## 八、发布流程（强制顺序）

```
1. 完成代码变更，全量测试通过
2. 按 §二 判定升级类型，升 Directory.Build.props 的 <Version>
3. 按 §三 编写 CHANGELOG 版本段（头条 + 短标题条目，日期 = 当日）
4. 本地预览 Release body：dotnet run --file scripts/release-notes.cs -- <新版本>
5. 运行 dotnet run --file scripts/pre-release-check.cs -- <新版本>（含 §四 全部校验）
6. commit + push 到 main
7. git tag vX.Y.Z + push tag，CI 自动打包发布并派生 Release Body
```

第 4 步是 2026-11-05 新增：此前 body 只能在 tag 推上去之后才看到成品，不合格时只能事后 `gh release edit`（v6.8.0 与 v6.5.0 都发生过）。现在预览与 CI 走同一实现，推 tag 前 body 已定稿。

## 九、历史教训（为什么有本规范）

| 事故 | 根因 | 防线 |
|------|------|------|
| v5.2.0 首版 Release 声称 507 测试 | Core 计数从 191 变 195 未同步 | §五 #1 强制实测 |
| v5.2.0 首版遗漏破坏性变更 | `CrudColumns` 构造 2→3 参未标注 | §五 #3 强制 diff public API |
| 4 例"声称未交付" | 提交消息声称的修复不在 diff 中 | 每条修复 grep diff 确认 |
| CHANGELOG 与 Release Body 不一致 | 手工维护两份 | CI 自动提取，单一内容源 |
| `net10` 分线与主线的 CHANGELOG 格式曾分叉 | net10 从 CHANGELOG 压缩提交之前切出，保留了 4065 行七段长表；主线已压缩为逐版要点 | 2026-10-26 用户指令改为「dev 最新代码并入 net10、冲突取 dev」，net10 现与主线同格式；4065 行长表仅存于 net10 旧提交 `a03c5ed` 的 git 历史 |
| 七段长表的"变更规模 · 锁定测试名 · ITM 编号"三项在主线长期无人计算 | 规则与主线现实脱节（ITM 编号体系已废弃，测试名与 CI 重复，提交数/文件数/行数每次要手工统计） | 2026-10-26 主线降级为三段式并接机械化门禁（§四）；net10 分线随合并同步（历史长表不再保留在工作树） |
| Release 页体量失控 | body 直接嵌入 CHANGELOG 原文，条目的审计级证据（基准批次、依据句）一并上页；实测按字符统计 v6.5.0 30 973、v6.7.0 13 076、v6.8.0 1 192，摆动 26 倍且无上限 | 2026-11-05 改为单源派生（§七）：头条 + 短标题 + 体量 1400 字符门禁 |
| 发布页信息三处重复 | 标题重复页面标题、发布包表重复 Assets 列表、导航两处指向同一链接 | 2026-11-05 删除这三类元素，包清单压成一行 |
