# PalORM 发布变更日志规范（强制标准）

> 适用于三处输出：`CHANGELOG.md` 条目、GitHub Release Body、NuGet 包 `<releaseNotes>`。
> 三者的内容来源只有一个：**`CHANGELOG.md` 的版本段**。Release Body 由 `release.yml` 自动提取，禁止手写第二份变更内容。

---

## 一、两套规范的分工（先纠正一个常见混淆）

| 规范 | 管什么 | 本项目执行方式 |
|------|--------|---------------|
| **Semantic Versioning 2.0.0** | 只规定版本号格式（`MAJOR.MINOR.PATCH[-pre][+build]`）与递增规则，全文不涉及变更日志格式 | `scripts/release-version-scan.cs` 格式门禁（正则断言 + 升级类型推导） |
| **本文件（变更日志规范）** | 版本段怎么写、什么必须显式标注、哪些数字必须实测 | `scripts/pre-release-check.cs` 段校验 + `release.yml` pack 前断言 |

结论：不存在"按 SemVer 重新生成 CHANGELOG"这件事，SemVer 不定义日志格式。CHANGELOG 的通行格式规范是 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，本项目按其精神做了轻量化取舍（见 §三）。

---

## 二、版本号语义与本项目的破坏性判定

| 变更性质 | 版本号 | 判定依据 |
|---------|--------|---------|
| 公共 API 签名删除或修改，已编译消费者必须重新编译 | **MAJOR** | `git diff <prev_tag>..HEAD -- src/` 中出现 `^-.*public` |
| 向后兼容新增（新 API、新诊断码、新 Provider 能力） | **MINOR** | 旧代码无需改动即可升级 |
| 仅缺陷修复，对外行为不变 | **PATCH** | 修复前后调用方代码与结果一致 |
| 预发布 | `-preview.N` | 仅 `workflow_dispatch` 手动触发 |

**行为变更的处置（本项目已有先例，明文记录以免重复争论）**：查询结果可能变化、默认值改变、批量上限调整这类"签名没变但结果会变"的变更，严格 SemVer 语义下属破坏性。本项目的实际政策是 **MINOR + `💔` 段显式标注 + 升级指南兜底**，理由是零 API 破坏且升级成本可控。

- 已生效先例：v6.5.0（`Where(A).OrWhere(B).Where(C)` 运算符优先级修正，查询结果可能变化），当时版本裁决由 7.0.0 回落至 6.5.0。
- 历史偏离（不再重复）：v5.2.0（`CrudColumns` 构造 2→3 参）与 v5.4.0（移除 legacy 无方言 SQL 生成段）在 MINOR 中引入了签名破坏。这两例发生在本政策确立之前，已发布不可改，新版本不适用此放宽。
- 新版本若出现真正的签名破坏，仍必须升 MAJOR，行为变更政策的宽松不延伸到此。

## 三、CHANGELOG 版本段标准结构（三段式，轻量）

```markdown
## [X.Y.Z] - YYYY-MM-DD

### 💔 破坏性/行为变更

- 变更内容（一句一条，逐项可验证）

### 变更要点

- 变更内容（一句一条，逐项可验证）
```

规则：

1. **`### 💔` 段只在存在破坏性或行为变更时出现**，位置必须在版本标题之下、其余内容之上。它是段落标题，不是行内前缀。
2. **`### 变更要点` 承载新增、修复、性能、依赖升级、文档等全部其余条目**。
3. 日期必须与 `git log -1 --format=%ad --date=short vX.Y.Z` 一致（tag 提交日，不是发版操作日）。
4. 每条一个事实、一句话，禁止"修复了若干问题"式概括。
5. 性能数字必须来自实测（PerfHub 批次或 BenchmarkDotNet），写清口径（方言、档位、样本）。无实测就写"机制改进，未基准"。
6. **`## [Unreleased]` 是可选的未发布累积段**（Keep a Changelog 约定），存在时置于文件最顶部，内容同样按下述两段组织。门禁跳过它，取其后第一个版本段作为目标版本。
7. **历史段冻结**：格式标准变更（如 2026-10-26 由七段长表改为三段式）不回改既有版本段。历史段允许保留副标题（如 `## [6.7.0] - 2026-10-23 · 请求级查询管道`）与其原有结构，门禁只校验目标版本段。

参考实例：

```markdown
## [6.8.0] - 2026-10-26

### 💔 破坏性/行为变更

- SQLite 上 `batchSize` 不再决定语句形状（≤0 仍拒绝），批内重复主键改为后行覆盖前行。

### 变更要点

- 项目协议自本版起由 AGPL-3.0-only 改为 Apache-2.0（v6.7.0 及以前发布物仍为 AGPL-3.0-only）。
- SQLite `BulkInsertAsync`/`BulkMergeAsync` 改为行预编译形态，批插 3.5~3.9×、批 upsert 2.4~3.1×。
```

## 四、机械门禁（由脚本执行，不靠自觉）

| 校验项 | 执行位置 | 失败后果 |
|--------|---------|---------|
| 版本号符合 SemVer 2.0.0 + 升级类型推导 | `release-version-scan.cs` | exit 1，禁止 push tag |
| CHANGELOG 顶部第一个版本等于目标版本 | `pre-release-check.cs` | exit 1，禁止 push tag |
| 版本标题格式 `## [X.Y.Z] - YYYY-MM-DD` | `pre-release-check.cs` 与 `release.yml` | exit 1 |
| 日期等于 tag 提交日 | `pre-release-check.cs` | exit 1 |
| 版本段至少 1 条 `- ` 条目 | `pre-release-check.cs` 与 `release.yml` | exit 1 |
| `### 💔` 段存在时其下有条目 | `pre-release-check.cs` | exit 1 |
| PATCH 版本段出现 `### 💔` | `pre-release-check.cs` | 警告（不阻断，历史先例见 §二） |
| CHANGELOG 含目标版本号 | `release.yml` pack 前 | exit 1，禁止发布 |

校验只针对**目标版本段**（CHANGELOG 顶部第一个版本），不扫历史段，历史记录不可回改。

## 五、数字准确性检查清单（发布前必做）

| # | 检查项 | 验证方式 |
|---|--------|---------|
| 1 | 测试总数 | 三套实测运行计数之和，禁止沿用上一版数字 |
| 2 | 依赖版本 | `git diff <prev_tag>..HEAD -- Directory.Packages.props` 逐行比对 |
| 3 | 破坏性 API | `git diff <prev_tag>..HEAD -- src/` 中 `^-.*public` 逐条判定 |
| 4 | 性能数字 | 引用 `bench/perfhub/results/` 或 CrossBench 批次文件，注明批次号 |
| 5 | AOT 验证 | `dotnet publish test/PalORM.AotTest* -c Release` 零错误，原生二进制运行通过 |
| 6 | 快照数 | `ls test/PalORM.SourceGen.Tests/Snapshots/*.snap \| wc -l` |

测试与文档的具体条数由 `verify-ai-system.cs` 与 CI 地板断言接管，本文件不重复维护（避免两处数字漂移）。

## 六、禁止事项

| 禁止 | 原因 |
|------|------|
| 使用"约""大概""左右"修饰数字 | 数字必须精确 |
| 声称的测试数未实际运行 | 数字随提交变化 |
| 遗漏破坏性变更（API 签名或行为变化） | 下游会 break |
| "修复了若干问题"类模糊描述 | 每条必须具体 |
| 复制上一版本的数字 | 版本间数字会变 |
| 把基础设施改进（基准工具、质量脚本、探针）写进版本段 | CHANGELOG 面向包消费者，不面向仓库维护者 |
| 手写第二份 Release Body 变更内容 | 与 CHANGELOG 必然漂移，由 CI 自动提取消除 |

## 七、Release Body 的组装方式（已实现，无需手工干预）

`release.yml` 的 `Extract Release Notes` 步骤：

1. `awk` 提取 CHANGELOG 目标版本段，跳过版本标题行本身，避免与 Body 顶部的 `# PalORM vX.Y.Z` 重复。
2. 动态生成包表格，读实际 `artifacts/packages/*.nupkg`，包增减零维护。
3. 拼装固定外壳：对比链接、NuGet 链接、安装命令、30 秒上手、资源导航。
4. 版本段原文嵌入 `## 📋 变更明细`。

因此 CHANGELOG 里写的 `### 💔 破坏性/行为变更` 与 `### 变更要点` 会原样出现在 Release 页面，层级正确。改 CHANGELOG 格式即改变 Release 展示，CI 侧零改动。

## 八、发布流程（强制顺序）

```
1. 完成代码变更，全量测试通过
2. 按 §二 判定升级类型，升 Directory.Build.props 的 <Version>
3. 按 §三 编写 CHANGELOG 版本段（日期 = 当日）
4. 运行 dotnet run --file scripts/pre-release-check.cs -- <新版本>（含 §四 CHANGELOG 校验）
5. commit + push 到 main
6. git tag vX.Y.Z + push tag，CI 自动打包发布并提取 CHANGELOG 生成 Release Body
```

## 九、历史教训（为什么有本规范）

| 事故 | 根因 | 防线 |
|------|------|------|
| v5.2.0 首版 Release 声称 507 测试 | Core 计数从 191 变 195 未同步 | §五 #1 强制实测 |
| v5.2.0 首版遗漏破坏性变更 | `CrudColumns` 构造 2→3 参未标注 | §五 #3 强制 diff public API |
| 4 例"声称未交付" | 提交消息声称的修复不在 diff 中 | 每条修复 grep diff 确认 |
| CHANGELOG 与 Release Body 不一致 | 手工维护两份 | CI 自动提取，单一内容源 |
| `net10` 分线与主线的 CHANGELOG 格式分叉 | net10 从 CHANGELOG 压缩提交之前切出，保留了 4065 行七段长表；主线压缩为逐版要点 | 2026-10-26 起两线统一为三段式（§三），net10 历史段冻结不回改（§三 规则 7） |
| 七段长表的"变更规模 · 锁定测试名 · ITM 编号"三项在主线长期无人计算 | 规则与主线现实脱节（ITM 编号体系已废弃，测试名与 CI 重复，提交数/文件数/行数每次要手工统计） | 2026-10-26 主线降级为三段式并接机械化门禁（§四）；net10 分线同步（历史段保留原格式） |
