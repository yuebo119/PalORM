## 1. 结论

当前工程实现分 **3.55 / 10**（八维加权，方法见 §2），架构设计分 **6.6 / 10**。差距集中在两处：判别力证据只覆盖 4.3% 的执行用例，以及门禁自身的存活监测面漏掉了全部数据门禁。

达到 L2（可信）需 **37.7 人日**，分值落到 **6.80**。性价比拐点是阶段 0 加阶段 1，共 9.5 人日把分值推到 5.25：此后每 0.1 分的代价从 0.43 人日升至 1.40 人日起。

本版最重要的一条新发现是判据载体问题，不是判据松紧问题：V14 只收「无参跑到底并打印完成标记」的脚本，三个需要报告或 XML 入参的数据门禁从设计上进不了存活监测面，这条缺口没有任何既有机制兜底。

需要同时更正第二版初稿的一处过度判断：初稿称 sourceMarkers 地板 1,070 对实测 1,525 的 29.8% 松动意味着「删 455 个标记门禁全绿」。复核 D10 后该结论不成立——D10 对三处文档声明做硬等值，任何增删都必须显式改声明，删标记时 D10 会先红。地板过松的真实危害是误导读数与无从维护（见 §3.4），不是可被利用的删测试通道。

## 3. 差距的根因

首版给了三个闭环缺失。本版补充第四个，且它是前三个的前置。

### 3.1 判据层级：覆盖率证明被执行，证明不了改坏会被发现

一个方法行覆盖 100%，断言写成 `Assert.That(result).IsNotNull()`，把返回值改成常量照样通过。2026-11-03 审计的 S2 阶段删改了一批恒真断言与假绿用例，它们全部落在行覆盖之内（明细见该轮报告，本文不复述具体条数以免与当时的删除清单脱节）。覆盖率是必要条件，判别力是另一根轴。

### 3.2 判据载体形态：需要入参的检查进不了存活监测面

V14 的登记条件是"无参跑到底并打印完成标记"，`assert-test-counts`、`assert-coverage`、`diff-coverage` 都需要报告或 XML 入参，因此从设计上就进不去。结果是最重要的数据门禁恰好是全仓唯一没有存活监测的一批脚本。首版把这条归因为"忘了登记"，那不是根因：即使现在去登记，三个脚本在 pre-commit 环境下也跑不出完成标记。

修法是给脚本加 `--self-check` 模式，用内嵌夹具自证（好输入 exit 0、坏输入 exit 1），再登记进 V14 与 V17d。这条路同时解决"脚本能跑"与"判据能失败"两个问题，是阶段 0 的真正入口。

### 3.3 异常路径：对照测试集中在成功路径

全仓 159 处 `Assert.Throws`（2026-11-04 实测）大部分落在参数校验。批量插 1,000 行在第 600 行失败时，已写入的行是否回滚、连接是否可用、会话状态是否污染，这三问任何成功路径用例都测不到。2026-11-03 修掉的串行键丢失（1/4 偶发）属于这一类。

### 3.4 门禁自检的单向性：只证明能红，不证明能拦住

V17d 已经对 sourceMarkers 有探针，但方向只有"把地板改成 99999"这一种，证明的是地板过高会报错。地板过松这个方向零覆盖，所以 1,070 这个 2026-10-18 的定值在用例涨到 1,525 后长期没人动，也没有任何门禁提示它已失去意义。

这条缺口不会放过真实缺陷（删除标记由 D10 的硬等值拦截，两道门禁都在 pre-commit 与 CI 运行），危害在另外两处：一是读数误导，基线文件写着 1,070，读者会以为地板还在防 1,070 以上的删除；二是常数无从维护，靠人工在加用例时记得同步一个与声明无关联的字段。2026-11-04 的处置是把地板与声明同源，由 D10 的 `--fix` 一并写回，不再加一道精确匹配。

门禁自检的通用要求仍是双向：既证明会红，也证明在应该红的具体方向上会红。本次为 sourceMarkers 补的正是过松方向。

## 4. 目标分级

| 级别 | 可验证定义 | 八维分 | 判断 |
|---|---|---:|---|
| L1 可用 | 当前状态：能测出契约写到的行为违背 | 3.55 | 已达成 |
| L2 可信 | 八维逐项达到 §2.2 的 7 分锚点；具体读数 = 12 类分支 ≥80、判别力分数 ≥60、五类故障各 ≥3 用例、夜间 ≥1,000 场景、六门禁双夹具、零未解释 flake、digest 固定 | 6.80 | **推荐目标** |
| L3 顶级 | 条件覆盖或 MC/DC 接入核心路径、变异分本体 ≥80、故障注入含资源类、覆盖引导 fuzz、驱动版本矩阵 | 8.50 | 收益递减，不建议 |

推荐 L2 的理由：PalORM 的失效面是 SQL 文本、方言分支、池与事务状态机。这三类风险的判别手段是契约、故障注入、随机化，形式化验证与 MC/DC 100% 针对的是内存安全与分布式一致性，边际收益低于成本。

## 5. 优化路线

各阶段的动作表按主题合并展示；可执行任务编号、涉及文件与逐行工作量见任务清单。

### 5.0 排序原则与依赖

排期按"先修判据载体，再扩判据内容"排。理由：阶段 1 到 4 全部是新增门禁，如果门禁的存活监测面仍有洞，新增门禁会复制同一个洞。

```
阶段 0 修断链（含 --self-check 载体）
   ├── 阶段 1 判别力 ──┐
   └── 阶段 2 异常路径 ─┴── 阶段 3 随机化
                              └── 阶段 4 机制自检（依赖 0-3 的清单稳定）
                                        └── 阶段 5 覆盖与配置
```

阶段 1 与阶段 2 可并行（只共享测试夹具目录）。阶段 4 必须最后，因为它要把前三阶段新增的门禁全部纳管。

| 动作 | 验收判据（可执行） |

后两项不在首版范围内，是执行阶段 0 时踩到的既存缺陷：V14 因台账引用改名报告长期红（本地 `--fast` 跳过 V14，所以从未暴露），V17c 的 D11 探针因版本改为引用生成常量而变成空操作。两者不修，V14 与 V17c 的"如期报红"都无从判定，后面的 FIX-4 与 FIX-5 也就失去验收基线。

成本 1.7 人日，比首版 1.1 高 0.6：自检模式 +0.4（首版当成纯登记），两项既存门禁修复 +0.2；sourceMarkers 一项由 0.3 降到 0.2，不需要改两处判据，只需接线与验证。

分值：D2 1→2（+0.20），D6 3→5（+0.20），合计 **3.95**。

### 5.3 阶段 2：异常路径闭环（10 任务，9.0 人日）

| 动作 | 验收判据 |
|---|---|
| `FaultyConnection` 与 `FaultyReader` 包装：按调用序号注入异常、延迟、取消 | 框架自身 5 条单测，注入按序号精确生效 |

## 6. 关键设计决策

### 6.1 先造自检模式，再登记门禁

可选方案有两个。方案 A 给脚本加 `--self-check` 内嵌夹具，方案 B 参照 `probe-template` 的既有做法，只判退出码 2 加打印用法。

选 A。方案 B 零成本但证不出任何事情：退出码 2 表示"参数不对"，与判据是否有效无关，`assert-coverage` 把地板判据删掉也照样 exit 2。方案 A 多花 0.5 人日，换来的是"坏输入必须 exit 1"这条可执行证据。

### 6.2 自建回放而不是继续等 Stryker

Stryker 的 MTP 预览 runner 自 2026-10-03 起 `effectiveMutants=0`。等上游零成本但不产出证据；换 VSTest 影子工程要给 TUnit 用例建第二套运行形态，双维护成本高于收益（见 6.4）。

自建回放的边际成本低：注入、还原、期望 ID 判定的基础设施已存在（35 条规则在用），新增规则是加一条数据。约束是单条从注入到判定不超过 15 秒，全量不超过 5 分钟；超过这个成本，规则会退化成季度快照。

### 6.3 故障注入优先于 MC/DC

MC/DC 提升的是条件组合覆盖，故障注入提升的是异常路径验证。本仓库已知缺陷（串行键丢失、批量部分失败、池状态污染）全部属于后者。先补异常路径，再用分支覆盖查漏。

### 6.4 不建 VSTest 影子工程

影子工程能解锁 Stryker，代价是每条用例的依赖注入、生命周期、并行语义都要适配两套框架。上游修复前这笔投入的回报低于自建回放。2027 年上游仍无进展时重评。

### 6.5 fuzz 必须常驻

一次性 fuzz 的发现率随语料固定而衰减。当前 `PALORM_FUZZ_SEED` 在 `.github/` 下零引用，等于 D 层从未启用。常驻的判据不是"跑过一次"，是语料目录随轮次增长且失败样本可重放。

### 6.6 目标定 L2

见 §4。

### 6.7 属性测试选型（FUZ-2 决策，2026-11-04）

**结论：继续用自建生成器（DGenerator + ScenarioShrinker），不引入 FsCheck。**

三条理由：

1. **依赖政策**：项目依赖按「标准库能不做就不加」管理，新增属性测试库需要文档化理由；当前生成维度（6 种列类型的边界池、8 种条件形态、4 种操作序列、5 档批量）用自建生成器已完全覆盖。
2. **收缩器已就位**：方案 §7.4 要求失败样本可收缩，ScenarioShrinker 已在用并被 ShrinkerTests 覆盖；换 FsCheck 需要把 DScenario 适配成它的 Arbitrary，收缩行为还要重新验证一遍。
3. **重放是现成的**：固定集回归与夜间语料都依赖「同种子同场景」这一性质，DGenerator 直接提供；FsCheck 的随机源与种子模型要额外接线。

反证与复活触发器：如果将来要验证的是**跨列不变量**（例如 amount = qty × ratio）或**跨方言往返不变量**，FsCheck 的 Arbitrary + 属性表达会更省事，届时重估。
