## 1. 已落地：SessionBatch 参数物化延后

### 问题

`SessionBatch.Append` 每条语句建 N 个 `DbParameter` 存进 `_statements`，执行时再
`CloneParameter` 克隆一遍，同一批参数被分配两次。PerfHub `SessionBatchInserts/2000` 实测
PalORM 比 ADO 臂多 1.2KB/条（SQLite）与 1.68KB/条（PG），而延迟比值仅 1.02，属纯分配问题。
对照 ADO 臂 `SessionBatchSequentialAsync`：只建 7 个参数、20 行逐行就地改值。

### 改法

`_statements` 由 `List<(string, IReadOnlyList<DbParameter>)>` 改为
`List<(string, FormattableString?)>`，直接持有调用方的 `FormattableString`（本就已分配，
零额外开销）；参数在执行期由新增的 `AddParameters` 一次物化，`CloneParameter` 删除。

值语义不变：`FormattableString` 是纯值载体，Append 后调用方无法改动其内容；重复执行每次
重建参数，与"每执行克隆一份"逐位等价。Append 的空白校验与 `@pN` 命名纪律保留。

### 实测（SessionBatchDiag，20 条/批，三方言各三次复现）

| 方言 | 改动前 B/条 | 改动后 B/条 | Δ/条 |
|------|------------|------------|------|
| SQLite | 1266 | 994 | −272 |
| PostgreSQL | 2376 | 1624 | −751 |
| MySQL | 2680 | 2238 | −442 |

延迟：PG 约 −10~15%（949 → 803~856 µs/批），SQLite 与 MySQL 持平。

提交：`e2ef96d`。

## 2. 更正：上轮建议里三项的前提不成立

### 2.1 OrderBy 表达式树是**已文档化的设计取舍**，不是新发现

`docs/API参考.md:120` 的性能提示原文：

> 表达式类构建器…C# 在调用点构造表达式树，**库无法缓存**——每次调用都重建，实测每棵树
> 512 字节加 0.5~1.6 µs。热路径上把 lambda 提到 `static readonly` 字段即可消除
> （`UPDATE`+`Set` 分配 −18%，单行查询 +`OrderBy` 分配 −12%）。

数字与 `OrderByExprDiag` 探针完全一致（512 B）。项目已选择"保留 Expression 形参换编译期
类型安全 + 文档给出规避方案"，并已在 README 单列一节。

**因此不做破坏性 API 迁移**：改成 `Func<T,TKey>` + `[CallerArgumentExpression]` 会推翻一个
已文档化的设计决定，且是二进制不兼容变更（10 处公共签名），需要 ADR 与版本决策。本轮另发现
一条硬约束：`Select(params Expression<Func<T,object?>>[] members)` 的 params 数组**无法**用
`CallerArgumentExpression` 逐元素捕获，即该迁移无法覆盖全部表达式 API，会留下两套列名写法。

### 2.2 租户参数装箱：每操作没有装箱

上轮称"`BindDefaultFilterParameters` 每操作一个 `CreateParameter` 加 `_tenantId` 装箱"。
核对实现：`_tenantId` 是 `object?` 字段（`DataSession.cs:454`），装箱发生在 `WithTenant`
调用时一次；`BindDefaultFilterParameters` 只把该引用传给 `TProvider.CreateParameter`，
每操作不发生装箱。租户三项（TenantCount/TenantCountWhere/TenantGetAll）的 +1.1KB 是
QueryBuilder 链式路径的构建成本，与 OrderBy 项同源。**无可减项，不做改动。**

### 2.3 分母漂移判据没有缺口（我的证据用错了对照）

上轮称"门禁只标 2 项漂移，实际 4 项翻转来自地板"。复算发现我拿的是 12:39 批做对照，
而门禁比的是 `perfhub-index-baseline.json`（19:43 重录版）：

| 项 | 基线比值 | 限（×1.3） | 本批 | 判定 |
|----|---------|-----------|------|------|
| TenantCountWhere/SQLite/2000 | 1.128 | 1.467 | 1.104 | 在限内 |
| IncludeJoin/SQLite/2000 | 0.844 | 1.097 | 0.857 | 在限内 |
| MySQL/Count/2000 | 0.804 | 1.045 | 1.036 | 在限内 |
| MySQL/StreamAll/2000 | 0.681 | 0.885 | 0.703 | 在限内 |
| WideQueryAll/PG/2000 | 0.946 | 1.230 | 1.361 | 超限，门禁已标漂移 |

四项相对**真实基线**都没有翻转，判据工作正常。这与 step13 §8 记的"陈旧基线对照误判方向"
是同一个陷阱，本轮再犯一次，记录在案。**判据不扩展。**

### 2.4 维度 8 的方言覆盖缺口是已文档化的驱动限制

上轮称"MySQL/PG 单操作项的往返数未测、维度 8 口径偏乐观"。核对 `Program.cs:262` 附近注释：
计数装饰器**只对 SQLite 生效**，原因是 PG/MySQL 的驱动专有协议路径与包装层不兼容
（PG 上 `PostgreSqlProvider.BulkInsertAsync` 直接要求 `NpgsqlConnection`），2026-09-22 已实测
并记录。**非缺口，不改。**（`PreparedReuse` 全库恒 0 属实，因为夹具从不调 `AsPrepared`；
这是"指标已备但无夹具触发"，登记为遗留。）
