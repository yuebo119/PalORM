### 1.1 夹具定位与项归属（一套夹具一件事）

三套夹具并存是刻意的（外部锚点 + 能力矩阵 + 微基准各自不可替代），但**每个测量项必须有唯一权威夹具**，
其余出现只能作为"交叉验证副本"，且必须在结果里标注（不进基线、不进门禁、报告里带口径标注）。

| 夹具 | 定位 | 权威覆盖 | 不覆盖（交给别处） |
|---|---|---|---|
| `bench/PalORM.Benchmarks` | 微基准 + 负载 + 长稳 + 启动/GC/二进制 | 维度 1/3/4/5/7/9/10/11/12；形状 S1-S5 × 档位 100-100k；SQL 构建税（`04_SqlBuildBenchmarks`）；多臂对照的**形状敏感性** | 跨方言一致性（PerfHub）、与官方数字对照（DapperSuite） |
| `bench/PalORM.PerfHub` | 跨方言 × 跨实现的能力矩阵 | 维度 2/6/8 + 跨方言 CRUD/批量五形态/事务五形态/KeysetPage/WhereIn/IncludeJoin/UpsertBatch/InsertReturningId/宽表 | 形状敏感性（微基准）、启动/长稳（微基准） |
| `bench/PalORM.DapperSuite` | 与 Dapper 官方数字可对照的外部锚点 | 官方 Post 形状下的单行查询对照；**换驱动/换大版本时的哨兵**。**只跑 SQLite**（官方数字本身是单机 SQLite 的，跑 PG/MySQL 得不到可对照的外部锚点；哨兵一个方言足够——2026-09-23 精简省 2/3 时间） | 门禁基线（官方档位与形状固定，不适合卡回归阈值） |

> 交叉验证副本的现有实例：PerfHub 的 `BuildGetByKeySql`/`BuildComplexQuerySql` 与微基准
> `04_SqlBuildBenchmarks` 同测"SQL 构建税"；PerfHub 的单条 CRUD 与微基准 `01_CrudBenchmarks`
> 同测单操作。保留两者是刻意的（不同档位/不同方言覆盖），但**基线只取微基准**。
>
> **`Build*` 在 PerfHub 侧比值不计比（PL-4，2026-09-24 起机械执行）**：地板那两项直接
> `return` 插值字面量（`Implementations.cs` 的 `BuildGetByKeySql`/`BuildComplexQuerySql`），
> 不构造任何 SQL——拿它当分母量的是"生成一条 SQL 文本"本身，而那是产品相对裸 ADO.NET 的价值
> 而不是税（实测三方言 6.5~7.1×，毫无判别力）。现在 `Program.NonComparableOperations`
> 把这两项的 `Ratio` 记 0 并在 `Note` 注明原因，绝对值与分配仍照登；
> 记 0 即自动被 `PerfGate` 的 `Ratio > 0` 过滤排除出索引基线、关键项速览与最差比值表。
> 想真比这项就把地板也接到生成器上——那就测不到差异了，所以结论是"登记不计比"而非"删项"。

## 2. 标准数据形状（唯一权威定义）

**实现唯一真源**：`bench/PalORM.Benchmarks/StandardShapes.cs`。
探针项目（`.ai/perf-probe`，gitignored）如需同形实体，从该文件复制并在文件头注明
"复制自 StandardShapes.cs @ <提交>"。禁止各基准自定义"差不多的实体"。

| 形状 | 用途 | 列构成 |
|---|---|---|
| **S1 Narrow** | 点查/热路径/负载测试的基线形状 | `Id`(主键,非自增) + `Name`(64) + `Qty`(int) + `Price`(decimal(18,4)) + `Marker`(long)，共 4 数据列 |
| **S2 Wide** | 列宽放大验证（行列相乘规模） | `Id` + 19 数据列，覆盖类型白名单（long/int/short/string/bool/decimal/double/float/DateTime/Guid/可空变体/byte） |
| **S3 Sparse** | null 密度敏感性 | S1 同构但全部可空，**确定性 70% null**（`i % 10 < 7` 置 null） |
| **S4 Blob** | 二进制列 | `Id` + `Name` + 32 B / 1 KB / 64 KB 三个 `byte[]`（内容由行号确定性生成） |
| **S5 LongText** | 长文本 | `Id` + `Summary`(64) + `Body`（2000 字符，由行号确定性生成） |

**派生形状登记表**（除 S1-S5 之外、允许存在的形状，逐条登记理由与列构成；新增必须在此登记）：

| 派生形状 | 归属夹具 | 列构成 | 为何不能直接用 S1-S5 |
|---|---|---|---|
| `Post`（13 列） | DapperSuite | `Id`(int,主键) + `Text` + `CreationDate`/`LastChangeDate`(DateTime) + `Counter1..9`(int?) | 来自 Dapper 官方基准套件，改了就不能与官方数字对照（本夹具的存在理由就是外部锚点） |
| `perf_s1` | PerfHub | 与 S1 同构（4 数据列） | 无实质差异，命名沿用 PerfHub v2 方案；等价于 S1，跨夹具比较时按 S1 看待 |
| `perf_wide`（19 列） | PerfHub | 与 S2 同构 | 同 `perf_s1`，等价于 S2 |
| `perf_autoinc` | PerfHub | `Id`(自增主键) + S1 数据列 | S1 是**非自增**主键（点查可控），自增键是"插入后回填"专项（`InsertReturningId`）的前置形状 |
| `perf_child` | PerfHub | `Id` + `ParentId` + S1 数据列 | 1:N 装配（`IncludeJoin`）需要子表；S1-S5 都是单表形状 |
| `BenchBinary` / `BenchBinaryText` | 微基准 `08_BinaryBenchmarks` | `Id` + `Name` + `byte[]`（256B / 64KB）/ 同构但 `Text` 列存 Base64 | 二进制列专项要两个**代表点**（小 payload / 大 payload）比较原生 BLOB 与 Base64 TEXT 的插入与读取全成本；S4 的 32B/1KB/64KB 三点里，32B 与 1KB 对本专项无判别力（都在"小 payload"一侧），故取 256B 与 64KB。2026-09-23 登记（原为未登记的自定义形状） |

> 登记的是"允许存在"，不是"免于口径要求"：派生形状同样必须确定性种子、必须标注档位、
> 必须在结果里带形状标识。`perf_s1`/`perf_wide` 与 S1/S2 的等价关系写在此处，
> 避免下一个人以为这是两套不同的形状。

**行数档位**（BDN 微基准）：`100 / 1_000 / 10_000 / 100_000`。
报告必须标注档位；未标注档位的数字不得进入 BENCHMARKS.md。

> **PerfHub 用另一套档位**：`2_000 / 20_000`。它测的是跨方言跨实现的一致口径
> （21 项矩阵见 `bench/perfhub/README.md`），关心的是"中小表与中大表两个量级下的端到端表现"，
> 与 BDN 的"逐档精细统计"目的不同。两套档位不可混用——跨系统比绝对值没有意义，
> 只有同系统内的比值可比。跨版本对比必须走交替 A/B（`scripts/perfhub-ab.sh`），
> 顺序跑两轮的绝对值对比无效（v1 实测地板单项漂移 50%）。

> **DapperSuite 是第三套系统**：`bench/PalORM.DapperSuite/`——Dapper 官方性能套件的三臂移植版
> （数据集 `Post` 13 列 / 固定 5000 行 / `Step()` 轮转 / `Job.ShortRun + Launch 1 + Warmup 2 +
> Iteration 10 + UnrollFactor 500`），ADO.NET 手写 / Dapper / PalORM 同表同 SQL 对比。
> 它**不用本文件的档位与种子规则**：档位固定 5000 行（官方 `Step()` 上界），种子按官方
> `Post` 形状由行号派生；DDL 亦非 `MigrateAsync` 产物（官方未提供建表脚本，本套件按 `Post`
> 形状生成三方言同构 DDL）。运行：`bash scripts/dappersuite-run.sh`（不带参跑三方言；`perf.sh full` 只传 `sqlite`，理由见 §1.1）；口径差登记见
> `bench/PalORM.DapperSuite/README.md`。

**种子规则（确定性，无随机）**：所有列值由行号 `i` 派生
（`Name = $"row-{i}"`、`Qty = i % 1000`、`Price = i * 0.25m`、null 按 `i % 10 < 7`）。
任何一次种子生成的库内容逐位相同——这是"两次测量可比"的前提。

**DDL**：默认一律经 `MigrateAsync`（源生成产物），禁止手写 CREATE TABLE——
手写 DDL 会绕过方言真源，且使"基准测的库"与"迁移产出的库"不一致。
**登记在案的例外**：`DapperSuite`（官方形状与官方未提供建表脚本，手写三方言同构 DDL 是其口径差 D4）
与 `PerfHub`（其自建 4 表待迁到 `MigrateAsync`，见 §5 的待办登记）。例外必须在此处逐条登记，
未登记的例外视为违规。

## 3. 标准环境

每次记录基线或发布对比数据时，**必须**同时记录（基线 JSON 的 `environment` 节已强制）：

- CPU / OS / .NET SDK 精确版本 / BDN 或工具版本 / 数据库服务器版本与网络位置（本地 or 远程）
- GC 模式（Server/Workstation）与构建配置（Release）
- 连接串来源：环境变量或 gitignored 的 `.env.test`，**任何凭据不入 git**

跨机器、跨网络位置的绝对值**禁止直接比较**（同机 ADO.NET 地板实测漂移 43%）。
跨环境比较一律用"同轮 ORM/地板比值"。

## 4. 测量口径

| 指标 | 口径 | 纪律 |
|---|---|---|
| 分配 | `GC.GetTotalAllocatedBytes(precise: true)`，除以操作数 | 复现性 >1%，可当确定性事实；两次采样差异 >1% 必须查明再引用。**但"确定性"只对稳态重复成立**：实测**重建后首次运行**有 4/67 项分配量偏移 2.5–8.8%（1941→2119 等），第二次运行即回落到与后续各次一致的值——故录基线前应先跑一轮热身批次丢弃，或对比时确认差异不是"首跑效应"（2026-09-23 反向验证：还原改动后重跑仍给出新值，证明与改动无关） |
| 耗时（单线程） | BDN 中位数，或探针 Stopwatch 中位数 | 绝对值只作量级参考（同机漂移可达 43%）；跨组比较用同轮比值 |
| 耗时（**并行/负载**） | 每操作 Stopwatch 采样 → 近邻秩 p50/p95/p99 | **禁止在并行测试套件里做时间断言**——TUnit 并行下墙钟比值实测在 0.2~0.8 间漂移；并行场景的断言用计数与对象同一性 |
| **档位** | 行数**进入**测量的项跑全部档位；行数**不进**测量的项只在最小档跑一次 | 两档跑同一个测量等于把同一件事做两遍。2026-09-23 实测：PerfHub 的 8 项属此类（`Build*` 不碰库、签名里没有行数；`InsertReturningId` 用每次清空的独立自增表；`IncludeJoin` 固定 50 父×3 子；`Tx*` 条数固定；`TxBulkInsert` 与 `BulkInsert` 近重复），砍掉它们的第二档省下每方言 21 个重复测量 |
| 预热 | BDN 3 次；负载测试每档 ≥1.5 s 预热不计数；PerfHub 单操作预热**按时间收敛**（至少 3 次，累计达 1.5 s 即停，上限 `maxIterations/5`） | 无预热的数字不得发布。预热次数不得是无界的时间成本：固定 40 次对慢操作意味着 40 × 单次耗时（实测 20K 档 Dapper BulkInsert 单次 1.36 s → 54 s 预热，是计时段 4 s 的 13 倍），而 JIT/驱动缓冲/语句缓存在前几次即达成 |
| 噪声底 | 任何阈值/门禁必须标注其依据的实测噪声与余量倍数 | 耗时比门禁 +30% = 实测噪声 ±11% 的 2.7 倍（先例） |

### 4.1 口径登记（对比成立的前提，缺一不可比）

同一对比内的所有臂必须**逐位同口径**，且口径写进结果 JSON。两项各自都有实测代价：

| 口径 | 要求 | 反例（实测） |
|---|---|---|
| **连接配置口径** | 同一对比内所有臂的 journal_mode / synchronous / cache_size / mmap_size / pooling / 会话级 SET 必须同值，并逐项登记 | SQLite 上 WAL + 64MB cache + mmap（数据全量驻留）与默认配置（2MB cache、无 mmap）是两个不同的测量区间：同一个修复在前者 −30%、在后者 0%（2026-09-22 实测）。只给 ORM 臂配、不给地板臂配，比的就是连接配置而不是 ORM |
| **会话与连接生命周期口径** | 声明是"每操作新建"还是"每范围建一次"，且全臂一致；ORM 的会话创建成本不得只落在一臂上 | 一臂复用连接、另一臂每次建连会让比值混入建连成本（`.ai/lessons.md` B76；PerfHub 与 DapperSuite 曾因此给出不可比的分配量：4.0 KB/op 对 2946 B） |

### 4.2 环境健康度（每批必标）

健康度判据：**地板行散布的中位数**（`StdDev/Mean`，取中位数是因为 sub-µs 项的调度抖动会支配最大值、
而最小值会漏掉只影响慢项的争用），与**该夹具自报的阈值**比较：

- 超过阈值判 `noisy`：该批数据标 ⚠️ 或重跑；
- 阈值必须是自己实测的噪声底上界，不得借用别的夹具的阈值（BDN 长跑 unroll 500 × 10 迭代实测
  ±11%，取 0.10；PerfHub 自适应短跑实测 0.16–0.21，取 0.25）；
- 结论写进结果库信封的 `regime.health` / `regime.healthRatio` / `regime.healthThreshold`，与数字同存亡；
- 判据来源：2026-09-22 两批数据因虚拟机争用使手写地板 StdDev 达均值的 83%（11.77 µs 对 4.76 µs），
  靠人工发现，代价是两轮重跑。

### 4.3 测试库的服务端吞吐（2026-09-23 实测，读 MySQL 绝对值前必看）

MySQL 测试库（`192.168.200.120`，8.4.11）的**写路径**吞吐约 **1.2 万行/秒**（82 µs/行），
比健康的 InnoDB 慢约一个量级。诊断脚本 `.ai/perf-probe/MySqlUsageDiag.cs.off`（本地留档），
逐项排除结果如下——**夹具用法不是瓶颈，改 SQL 写法救不了**：

| 试过的"最佳实践" | 结果 |
|---|---|
| 分批（20 条 × 1000 键）对单条 20000 键大语句 | 1.84 s 对 1.81 s，**0% 收益** |
| 预编译语句复用（同 SQL 文本改参数值） | **1% 收益** |
| 事务包裹（20 条裹一个事务 对 每条自动提交） | **6% 收益** |
| 避开 IN 列表（改 `WHERE Id <= 1000` 范围删除） | **同样 90 µs/行** |
| 本会话关掉 binlog（`sql_log_bin=0`） | **12% 收益**（92.9 → 81.5 ms） |

对照组说明慢在哪：读路径快 7 倍（`COUNT(*)` 全表 0.2 µs/行、按主键取 1000 行 12.3 µs/行），
网络 RTT 中位 **0.51 ms**（内网正常）。故既不是网络、也不是 IN 求值或缓冲池，
而是 InnoDB 写路径本身（undo/redo/页修改）——指向存储或虚拟机的写吞吐。
服务端配置 `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` + `log_bin=ON` 是
**持久性优先**（MySQL 8 默认，生产正确），实测每次提交约 2.2 ms；但改这些设置会让基准
不再代表生产，**不建议为跑分改测试库配置**。

**读 MySQL 数字的纪律**：① 绝对值被服务端写吞吐支配，不代表健康服务器；
② 三臂（ADO/Dapper/PalORM）撞同一面墙（`BulkDelete` 实测 1.80–1.86 / 1.81–1.84 / 1.83–1.84 s），
故**同轮比值仍有效**，只有比值可用——这与 §3「跨环境不比绝对值」同源；
③ 夹具侧唯一有效的对策是**别写超过需要的行数**（`BulkDelete` 的播种行数预算即为此设，见 §5）。

## 5. 流程

| 场景 | 动作 |

  漏了这两项，于是同一个测量项在不同臂之间比的根本不是同一个库。
  **2026-09-23 已产出候选基线并完成人工复核**（`bench/reports/perfhub-index-baseline.candidate.json`，
  152 项、0 项丢失、共同项比值中位变化 +14.9%）：
  复核中唯一需要判定的是 `BulkUpdate/PostgreSQL/2000`（PalORM 34.4 ms → 65.6 ms，+91%）。
  **用 `scripts/perfhub-ab.sh` 对旧提交 `f9a4b51` 做交替 A/B 三轮，结论是"产品快了约 30 倍，旧值是伪影"**：

  | 版本 | 轮 1 | 轮 2 | 轮 3 | 对同轮地板 |
  |---|---:|---:|---:|---:|
  | HEAD | 72.1 ms | 44.7 ms | 40.9 ms | 1.59 / 2.62 / 2.40 |
  | `f9a4b51`（旧） | 1159.9 ms | 1213.0 ms | 1159.5 ms | 62.1 / 71.1 / 69.3 |

  两版的地板臂相当（17~19 ms），故环境可比；同一份旧代码今天实测 1.16~1.21 s（±2%），
  而旧基线记录的 34.4 ms 在**任何流程位置都复现不出来**。
  判定依据（批内自相矛盾）：旧基线那一批（2026-09-22 20:12）的地板比现在**慢 2 倍**
  （37839 对 18694 µs），PalORM 却比现在**快 34 倍**——同一批内两者方向相反，故该值不可信。
  代码侧：两版的批/逐条分叉条件逐字相同，`BulkUpdateAsync` 的差异只在 `BULK-001` 的批大小上界
  （`InClauseBatchSize` → `min(方言参数上限, MaxRowsPerBatch)`）。
  **结论：采用候选基线**（65.6 ms 是当前流程位置下可复现的值）。
  附带观察：同一批里 PG 的 Dapper 臂在 43.5–69.8 ms 间跳（±50%），故 PG 上不宜对 Dapper 比值卡紧阈值。
- **MySQL 方言曾整列失败：`BulkDelete` 播种超配 16.7 倍 + 驱动默认 30 s 超时（已修，数字留档）**。
  2026-09-23 全量跑测里 MySQL 在 tier 20000 档失败，内因是 `SocketException`（995 = 操作被中止，
  MySqlConnector 命令超时后中止 socket 的签名），随后连接 Broken。逐段探针
  （`.ai/perf-probe/MySqlSeedDiag.cs`，远程 MySQL 8.4）实测：
  100 万行档的**三条单命令都超过 30 s**——快照拷贝 94.6 s、`DELETE FROM perf_s1` 107.3 s、
  快照重置 114.0 s；而 tier 2000 档的播种是 10 万行、全部在 9 s 内，故那档能跑通。
  **为什么是 100 万行**：播种行数 = 迭代上限 × 档位行数（50 × 20000）。
  而实测每轮删 20000 键 = 20 条 DELETE（`BulkSql.BatchRows` = 1000）、单轮 **2.02 s**
  （每条语句 101 ms，远程 RTT 主导）→ 4 s 预算只跑 **3 轮**，实际只需 **6 万行**。
  **修法三处**：① 播种类语句显式设 600 s 命令超时（被测命令仍用默认，保持"挂住就快失败"）；
  ② MySQL 用 `TRUNCATE` 替代 `DELETE`（107.3 s → 近瞬时；PG/SQLite 保持 DELETE）；
  ③ 播种改由**总行数预算 20 万行**反推轮数（档位 2000 得 50 轮不变，档位 20000 得 10 轮）。
  代价：SQLite 档位 20000 的样本数由 49 降到 10（其删除快，预算不再是瓶颈）——
  10 个样本对中位数仍够（BDN 默认 15 轮），分配量复现性从 0.07% 量级降到约 0.3%，
  仍远优于 §4 的 1% 门槛。**随基线重录一并生效**。

- **schema 2（规划）**：增加负载测试节——线程档位、p50/p95/p99、ops/s、读写比；
  就绪后由 `--workload` 的 JSON 输出对接，门禁暂不卡分位数（先积累噪声底）。
- `BENCHMARKS.md` 只保留**方法论与里程碑结论**；明细与逐次数字以结果库为准。
  历史事实：2026-09-19 之后 PerfHub 与 DapperSuite 的数字从未登记进 BENCHMARKS.md（断档已由结果库接管）。
- 结果库条目的必填项：日期、提交号、夹具、形状、档位、口径登记（§4.1 两项）、环境节、健康度（§4.2）。
- **PL-2 单行 CRUD 复用（2026-09-24）的读数纪律**：该改动把单行 Insert/Update 的每操作分配
  砍掉 38.1~39.7%（TxHundredInserts）与 44.3~45.0%（TxRollback），三轮逐位复现——
  分配是 `GC.GetTotalAllocatedBytes` 精确计数，确定性可复现。**绝对耗时不可读**：单轮跑测里
  地板臂自身能慢 2~5.4 倍（`TxHundredInserts` 地板 215.8 → 1165.5 µs、`Count` 6.3 → 11.1 µs，
  后者是纯 SQLite 微操作、不碰被测产品代码）。可读的口径是**同轮内 PalORM ÷ 地板**
  （分母与被测量同环境，漂移约掉），用 B→A→B→A 交替配对跑三轮；PL-2 用这个口径得到
  `TxHundredInserts` 5.79×→1.71×、`TxRollback` 4.34×→1.53×（三轮方向无例外）。
  **就地 `git checkout HEAD~1 -- <文件>` 切 A 臂的批次，信封 `Commit` 字段读到的是 B 提交号**——
  区分两臂只能看 `label`（`ab/pl2-a/*` / `ab/pl2-b/*`），别信 Commit。
  环境噪声量级参考：本机 32 核、负载 5.62 时 200 µs 级测量可被放大 2~5 倍。

## 7. 禁止事项

- ❌ 跨机器/跨网络位置比较绝对毫秒
- ❌ 无对照组、无预热、无形状标注的新基准进入结果库或 BENCHMARKS.md
- ❌ 并行测试套件里的墙钟断言（用计数/对象同一性替代——RegistryIncrementalCostTests 先例）
- ❌ 手写 CREATE TABLE 造基准库（§2 登记在案的例外除外）
- ❌ 单次运行下结论（分配除外，见 §4）
- ❌ 拿中位数代表"性能"——对外报告并发路径必须给 p95/p99
- ❌ 跨口径比较（连接配置口径或会话口径不同的两次测量，只能各自内部比比值）
- ❌ 结果库条目缺口径登记或健康度标注（缺项的数字不得引用）
