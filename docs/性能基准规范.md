### 1.1 夹具定位与项归属（一套夹具一件事）

三套夹具并存是刻意的（外部锚点 + 能力矩阵 + 微基准各自不可替代），但**每个测量项必须有唯一权威夹具**，
其余出现只能作为"交叉验证副本"，且必须在结果里标注（不进基线、不进门禁、报告里带口径标注）。

| 夹具 | 定位 | 权威覆盖 | 不覆盖（交给别处） |
|---|---|---|---|
| `bench/PalORM.Benchmarks` | 微基准 + 负载 + 长稳 + 启动/GC/二进制 | 维度 1/3/4/5/7/9/10/11/12；形状 S1-S5 × 档位 100-100k；SQL 构建税（`04_SqlBuildBenchmarks`）；多臂对照的**形状敏感性** | 跨方言一致性（PerfHub）、与官方数字对照（DapperSuite） |
| `bench/PalORM.PerfHub` | 跨方言 × 跨实现的能力矩阵 | 维度 2/6/8 + 跨方言 CRUD/批量五形态/事务五形态/KeysetPage/WhereIn/IncludeJoin/UpsertBatch/InsertReturningId/宽表 | 形状敏感性（微基准）、启动/长稳（微基准） |
| `bench/PalORM.DapperSuite` | 与 Dapper 官方数字可对照的外部锚点 | 官方 Post 形状下的单行查询三臂对照；**换驱动/换大版本时的哨兵** | 门禁基线（官方档位与形状固定，不适合卡回归阈值） |

> 交叉验证副本的现有实例：PerfHub 的 `BuildGetByKeySql`/`BuildComplexQuerySql` 与微基准
> `04_SqlBuildBenchmarks` 同测"SQL 构建税"；PerfHub 的单条 CRUD 与微基准 `01_CrudBenchmarks`
> 同测单操作。保留两者是刻意的（不同档位/不同方言覆盖），但**基线只取微基准**。

## 2. 标准数据形状（唯一权威定义）

**实现唯一真源**：`bench/PalORM.Benchmarks/StandardShapes.cs`。
探针项目（`.ai/perf-probe`，gitignored）如需同形实体，从该文件复制并在文件头注明
"复制自 StandardShapes.cs @ <提交>"。禁止各基准自定义"差不多的实体"。

| 形状 | 用途 | 列构成 |
|---|---|---|
| **S1 Narrow** | 点查/热路径/负载测试的基线形状 | `Id`(主键,非自增) + `Name`(64) + `Qty`(int) + `Price`(decimal(18,4)) + `Marker`(long)，共 4 数据列 |
| **S2 Wide** | 列宽放大验证（行列相乘规模） | `Id` + 19 数据列，覆盖类型白名单（long/int/short/string/bool/decimal/double/float/DateTime/Guid/可空变体/byte） |
| **S3 Sparse** | null 密度敏感性 | S1 同构但全部可空，**确定性 70% null**（`i % 10 < 7` 置 null） |
| **S4 Blob** | 二进制列 | `Id` + `Name` + 32 B / 1 KB / 64 KB 三个 `byte[]`（内容由行号确定性生成） |
| **S5 LongText** | 长文本 | `Id` + `Summary`(64) + `Body`（2000 字符，由行号确定性生成） |

**派生形状登记表**（除 S1-S5 之外、允许存在的形状，逐条登记理由与列构成；新增必须在此登记）：

| 派生形状 | 归属夹具 | 列构成 | 为何不能直接用 S1-S5 |
|---|---|---|---|
| `Post`（13 列） | DapperSuite | `Id`(int,主键) + `Text` + `CreationDate`/`LastChangeDate`(DateTime) + `Counter1..9`(int?) | 来自 Dapper 官方基准套件，改了就不能与官方数字对照（本夹具的存在理由就是外部锚点） |
| `perf_s1` | PerfHub | 与 S1 同构（4 数据列） | 无实质差异，命名沿用 PerfHub v2 方案；等价于 S1，跨夹具比较时按 S1 看待 |
| `perf_wide`（19 列） | PerfHub | 与 S2 同构 | 同 `perf_s1`，等价于 S2 |
| `perf_autoinc` | PerfHub | `Id`(自增主键) + S1 数据列 | S1 是**非自增**主键（点查可控），自增键是"插入后回填"专项（`InsertReturningId`）的前置形状 |
| `perf_child` | PerfHub | `Id` + `ParentId` + S1 数据列 | 1:N 装配（`IncludeJoin`）需要子表；S1-S5 都是单表形状 |

> 登记的是"允许存在"，不是"免于口径要求"：派生形状同样必须确定性种子、必须标注档位、
> 必须在结果里带形状标识。`perf_s1`/`perf_wide` 与 S1/S2 的等价关系写在此处，
> 避免下一个人以为这是两套不同的形状。

**行数档位**（BDN 微基准）：`100 / 1_000 / 10_000 / 100_000`。
报告必须标注档位；未标注档位的数字不得进入 BENCHMARKS.md。

> **PerfHub 用另一套档位**：`2_000 / 20_000`。它测的是跨方言跨实现的一致口径
> （22 项矩阵见 `bench/perfhub/README.md`），关心的是"中小表与中大表两个量级下的端到端表现"，
> 与 BDN 的"逐档精细统计"目的不同。两套档位不可混用——跨系统比绝对值没有意义，
> 只有同系统内的比值可比。跨版本对比必须走交替 A/B（`scripts/perfhub-ab.sh`），
> 顺序跑两轮的绝对值对比无效（v1 实测地板单项漂移 50%）。

> **DapperSuite 是第三套系统**：`bench/PalORM.DapperSuite/`——Dapper 官方性能套件的三臂移植版
> （数据集 `Post` 13 列 / 固定 5000 行 / `Step()` 轮转 / `Job.ShortRun + Launch 1 + Warmup 2 +
> Iteration 10 + UnrollFactor 500`），ADO.NET 手写 / Dapper / PalORM 同表同 SQL 对比。
> 它**不用本文件的档位与种子规则**：档位固定 5000 行（官方 `Step()` 上界），种子按官方
> `Post` 形状由行号派生；DDL 亦非 `MigrateAsync` 产物（官方未提供建表脚本，本套件按 `Post`
> 形状生成三方言同构 DDL）。运行：`bash scripts/dappersuite-run.sh`；口径差登记见
> `bench/PalORM.DapperSuite/README.md`。

**种子规则（确定性，无随机）**：所有列值由行号 `i` 派生
（`Name = $"row-{i}"`、`Qty = i % 1000`、`Price = i * 0.25m`、null 按 `i % 10 < 7`）。
任何一次种子生成的库内容逐位相同——这是"两次测量可比"的前提。

**DDL**：默认一律经 `MigrateAsync`（源生成产物），禁止手写 CREATE TABLE——
手写 DDL 会绕过方言真源，且使"基准测的库"与"迁移产出的库"不一致。
**登记在案的例外**：`DapperSuite`（官方形状与官方未提供建表脚本，手写三方言同构 DDL 是其口径差 D4）
与 `PerfHub`（其自建 4 表待迁到 `MigrateAsync`，见 §5 的待办登记）。例外必须在此处逐条登记，
未登记的例外视为违规。

## 3. 标准环境

每次记录基线或发布对比数据时，**必须**同时记录（基线 JSON 的 `environment` 节已强制）：

- CPU / OS / .NET SDK 精确版本 / BDN 或工具版本 / 数据库服务器版本与网络位置（本地 or 远程）
- GC 模式（Server/Workstation）与构建配置（Release）
- 连接串来源：环境变量或 gitignored 的 `.env.test`，**任何凭据不入 git**

跨机器、跨网络位置的绝对值**禁止直接比较**（同机 ADO.NET 地板实测漂移 43%）。
跨环境比较一律用"同轮 ORM/地板比值"。

## 4. 测量口径

| 指标 | 口径 | 纪律 |
|---|---|---|
| 分配 | `GC.GetTotalAllocatedBytes(precise: true)`，除以操作数 | 复现性 >1%，可当确定性事实；两次采样差异 >1% 必须查明再引用 |
| 耗时（单线程） | BDN 中位数，或探针 Stopwatch 中位数 | 绝对值只作量级参考（同机漂移可达 43%）；跨组比较用同轮比值 |
| 耗时（**并行/负载**） | 每操作 Stopwatch 采样 → 近邻秩 p50/p95/p99 | **禁止在并行测试套件里做时间断言**——TUnit 并行下墙钟比值实测在 0.2~0.8 间漂移；并行场景的断言用计数与对象同一性 |
| 预热 | BDN 3 次；负载测试每档 ≥1.5 s 预热不计数 | 无预热的数字不得发布 |
| 噪声底 | 任何阈值/门禁必须标注其依据的实测噪声与余量倍数 | 耗时比门禁 +30% = 实测噪声 ±11% 的 2.7 倍（先例） |

### 4.1 口径登记（对比成立的前提，缺一不可比）

同一对比内的所有臂必须**逐位同口径**，且口径写进结果 JSON。两项各自都有实测代价：

| 口径 | 要求 | 反例（实测） |
|---|---|---|
| **连接配置口径** | 同一对比内所有臂的 journal_mode / synchronous / cache_size / mmap_size / pooling / 会话级 SET 必须同值，并逐项登记 | SQLite 上 WAL + 64MB cache + mmap（数据全量驻留）与默认配置（2MB cache、无 mmap）是两个不同的测量区间：同一个修复在前者 −30%、在后者 0%（2026-09-22 实测）。只给 ORM 臂配、不给地板臂配，比的就是连接配置而不是 ORM |
| **会话与连接生命周期口径** | 声明是"每操作新建"还是"每范围建一次"，且全臂一致；ORM 的会话创建成本不得只落在一臂上 | 一臂复用连接、另一臂每次建连会让比值混入建连成本（`.ai/lessons.md` B76；PerfHub 与 DapperSuite 曾因此给出不可比的分配量：4.0 KB/op 对 2946 B） |

### 4.2 环境健康度（每批必标）

健康度判据：**地板行散布的中位数**（`StdDev/Mean`，取中位数是因为 sub-µs 项的调度抖动会支配最大值、
而最小值会漏掉只影响慢项的争用），与**该夹具自报的阈值**比较：

- 超过阈值判 `noisy`：该批数据标 ⚠️ 或重跑；
- 阈值必须是自己实测的噪声底上界，不得借用别的夹具的阈值（BDN 长跑 unroll 500 × 10 迭代实测
  ±11%，取 0.10；PerfHub 自适应短跑实测 0.16–0.21，取 0.25）；
- 结论写进结果库信封的 `regime.health` / `regime.healthRatio` / `regime.healthThreshold`，与数字同存亡；
- 判据来源：2026-09-22 两批数据因虚拟机争用使手写地板 StdDev 达均值的 83%（11.77 µs 对 4.76 µs），
  靠人工发现，代价是两轮重跑。

## 5. 流程

| 场景 | 动作 |
|---|---|
| **长稳初筛** | `dotnet run --project bench/PalORM.Benchmarks -- --stability 180`（3 分钟初筛；30 分钟档属 CI/手动，判定阈值为初筛口径：吞吐跌 >20% 或工作集增 >30%） |
| **一键全量** | `bash scripts/run-full-perf.sh`——负载×2 + 内存曲线 + 启动量具 + BDN + 门禁判定，产出 `bench/reports/perf-report-<时间戳>.md`（约 8–10 min） |
| 日常开发 | `bash scripts/run-benchmarks.sh sqlite`（快速档 1/3/5，约 5 min） |
| 提交门禁 | `perf-gate.yml`：周调度 + `[perf]` 标签 PR；`tools/PalORM.PerfGate check` 对照 `bench/baselines/perf-baseline.json` |
| 优化轮 | `.ai/perf-probe` 写 A/B 探针 → 同进程同口径对比 → **S3 反向验证**（摘掉改动确认退化）→ 数据进 CHANGELOG |
| 基线重录 | 影响基线的改动合入后：跑完整档 → `PerfGate record` → **快照 diff 即评审材料**，逐项人工过 |
| 修性能门禁 | 先跑 `run-mutation-tests.sh` 类变异探针证明门禁能失败，再信任它的绿 |

**统一入口**（2026-09-22 起，包装下列动作，不改变各自口径）：

| 命令 | 动作 |
|---|---|
| `bash scripts/perf.sh smoke` | 三套夹具各跑最小档（SQLite）冒烟，验证夹具本身可用 |
| `bash scripts/perf.sh full` | 微基准全量 + 负载/内存/启动 + PerfHub 三方言 + 门禁判定 |
| `bash scripts/perf.sh compare <基线worktree> <轮数>` | 交替 A/B（PerfHub 编排器），跨版本对比的唯一可信方式 |
| `bash scripts/perf.sh gate` | 只跑门禁判定（读最近一批结果） |
| `bash scripts/perf.sh report` | 从结果库重新生成统一索引报告 |

**新增基准的准入清单**（缺一不收）：
① 声明覆盖的维度号；② 使用 StandardShapes 或 §2 派生形状登记表中的形状，并标注行数档位；③ 含对照组
（raw ADO.NET 或改前实现）；④ 标注测量口径（§4 中的哪一行）+ 口径登记（§4.1 两项）；⑤ 预热；⑥ 确定性种子。

## 6. 报告与记录

- **结果库（唯一登记处）**：`bench/results/`。三套夹具每次跑测写一份 `<夹具>-<时间戳>.json`，
  公共信封见 `bench/results/README.md`；`bench/results/latest-<夹具>.json` 指向该夹具最近一次。
  索引报告由 `bash scripts/perf.sh report` 生成到 `bench/reports/perf-index.md`。
  **子集批次必须带标记**：PerfHub 的 `--quick` 冒烟写 `label=quick`，微基准的 `--filter` 跑写 `label=filtered`；
  未标记的批次会被读成全量，故标记是准入条件（结果库门禁跳过带标记的批次）。
- 基线文件：`bench/baselines/perf-baseline.json`（schema 1：分配 ±20%、分配比 ±10%、耗时比 ±30%）。
- **schema 2（规划）**：增加负载测试节——线程档位、p50/p95/p99、ops/s、读写比；
  就绪后由 `--workload` 的 JSON 输出对接，门禁暂不卡分位数（先积累噪声底）。
- `BENCHMARKS.md` 只保留**方法论与里程碑结论**；明细与逐次数字以结果库为准。
  历史事实：2026-09-19 之后 PerfHub 与 DapperSuite 的数字从未登记进 BENCHMARKS.md（断档已由结果库接管）。
- 结果库条目的必填项：日期、提交号、夹具、形状、档位、口径登记（§4.1 两项）、环境节、健康度（§4.2）。

## 7. 禁止事项

- ❌ 跨机器/跨网络位置比较绝对毫秒
- ❌ 无对照组、无预热、无形状标注的新基准进入结果库或 BENCHMARKS.md
- ❌ 并行测试套件里的墙钟断言（用计数/对象同一性替代——RegistryIncrementalCostTests 先例）
- ❌ 手写 CREATE TABLE 造基准库（§2 登记在案的例外除外）
- ❌ 单次运行下结论（分配除外，见 §4）
- ❌ 拿中位数代表"性能"——对外报告并发路径必须给 p95/p99
- ❌ 跨口径比较（连接配置口径或会话口径不同的两次测量，只能各自内部比比值）
- ❌ 结果库条目缺口径登记或健康度标注（缺项的数字不得引用）
