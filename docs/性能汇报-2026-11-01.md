## 3. 异常判读（门禁 0 项 FAIL）

门禁本身零失败；以下五项是需要人工过目的判读项。核心判据层级（B100）：分配 > 绝对耗时 > 同轮比值 > 跨轮比值。

### A. 并发 t4/t8 比值被高估（工具缺陷，非性能回归）

🔍 **证据链**：报告 §关键项速览显示 MySQL `Concurrent_Mixed80_20 (t8)` 比值 **1.73**、t4 **1.12**；原始台账同批数据为 ADO t8 313.3 ms / PalORM 329.7 ms = **1.05**，ADO t4 206.5 ms / PalORM 213.5 ms = **1.03**。上一批同样现象（显示 1.90，实际 1.04）。

⚖️ **判定**：`bench/PalORM.PerfHub/Program.cs:1429-1431` 的地板查找按 `方言 + 操作 + 行数` 匹配，**未比较 `ConcurrencyThreads`**，`results.Find` 取到首个匹配即 t1 行——于是 t4/t8 全部除以 t1 地板。受影响为每批 3 方言 × 2 档 = 6 行，并随结果库进入索引基线的同名项。

修正后的并发比值（按线程档匹配，两批均如此）：

| 方言 | t1 | t4 | t8 |
|---|---:|---:|---:|
| SQLite | 1.00 | 1.05 | 1.02 |
| MySQL | 0.94 | 1.03 | 1.05 |
| PostgreSQL | 0.92 | 1.00 | 1.01 |

👉 **处置**：修法为地板匹配追加 `&& b.ConcurrencyThreads == m.ConcurrencyThreads`（1 行）。改动会改变新批次的比值口径，与既有索引基线（用旧口径录制）不可直接比较，须同批重录 `bench/baselines/perfhub-index-baseline.json`（`record-index --batches 3`）并复跑门禁。**本报告未改代码**，比值结论以上表为准。

### B. 快于地板 >33% 的项（地板健全性待核）

🩺 **症状**：PG BulkDelete 2000 **0.66** / 20000 **0.47**，PG UpsertBatch 2000 **0.59** / 20000 **0.62**；另有 MySQL TxRollback 0.61、IncludeJoin 0.59（后两项不在四组表）。

🔍 **证据**：①形态差异有源码依据——PG 删除走 `= ANY(@ids)` 数组参数，ADO 地板走 IN 占位符；PG upsert 同为数组形态。②跨批稳定：2026-10-30 批 BulkDelete PG/20000 即 0.42，本轮 0.47。③地板臂自身健康：本批 HealthRatio 0.131（阈值 0.35），地板未漂移。

⚖️ **判定**：不是地板实现缺陷，而是"产品形态优于基准臂写法"；比值照常展示，但结论应表述为"批量族快于手写 SQL"，不当作异常。MySQL TxRollback 0.61 / IncludeJoin 0.59 机制本轮未核查，仅登记为既有稳定值，不作归因。

👉 **处置**：无动作；若将来把 ADO 地板改成同形态数组参数，这些比值应回落到 ~1.0，届时应同步改基线。

### C. PG WideQueryAll/2000 单批高位

🩺 **症状**：PalORM 1.68 → **2.12 ms**（+26%），同批 ADO 1.71 → 2.00 ms（+17%），Dapper 1.68 → 1.73 ms（+3%）；比值 0.98 → 1.06。

🔍 **证据**：近八批 PalORM 区间 1.68–2.12 ms（2026-10-25 曾出现 1.99），ADO 区间 1.71–2.00 ms；本批分配 525.7 → 528.3 KB（+0.5%，无代码路径变化）；三项 ErrorRatio 均 <0.7%，不是抖动，是两臂同时进了高位窗口。

⚖️ **判定**：单批高位、两臂同向，比值仍在 1.30 预算内。按"未复测不归因"，**不判回归**。该项不在四组表（Query 组默认不列）。

👉 **处置**：下一批若仍在 2.0 ms 以上再立案；本轮不动作。

### D. SQLite SessionBatchInserts 三臂同向抬升

🩺 **症状**：ADO 281.5 → 357.2 µs（+27%）、Dapper 366.7 → 418.6 µs（+14%）、PalORM 288.5 → 310.6 µs（+8%）。

🔍 **证据**：该项 ErrorRatio 15–37%（本批最高噪声项之一）；三臂同向，且 PalORM 涨幅最小；分配三臂均不变（ADO 28.7 KB、PalORM 41.8 KB）。

⚖️ **判定**：环境态（SQLite 批量提交的检查点/fsync 相位），非 PalORM 回归。

👉 **处置**：无。

### E. SQLite BuildComplexQuerySql 的单臂抬升

🩺 **症状**：PalORM 2.50 → 4.30 µs（1.72×），ADO/Dapper 保持 0.40/0.20 µs。

🔍 **证据**：分配 3489 → 3494 B（+0.1%），ErrorRatio 0.2–0.3%。分配作为确定性指标未变，说明代码路径未变，变化落在亚 5 µs 量级的计时上。

⚖️ **判定**：按 B100 判据层级（分配优先于绝对耗时），不判回归。该项属 Build* 组，比值本就记 0（地板实现返回插值字面量，PL-4）。

👉 **处置**：无；连续两批同向再立案。

## 6. 指标定义与判读纪律（附录）

- **时延**：`MedianNs`（全路径中位数），冷热同批；P/ADO = PalORM ÷ ADO.NET − 1（正 = 慢 = 劣）；P/Dapper 以 Dapper 为基准。
- **分配**：`AllocatedBytesPerOp`（确定性指标，不受调度影响），色标与阈值同为 -30% / -10% / -1% / 0 / +1% / +10% / +30% 六级。
- **预算**：P/ADO ≤ 1.30 为门禁线；≥1.50 或 ≤0.67 加 📌 待判读（两个方向都过目）；地板健全性要求任一 ORM 臂不得快过 ADO 超过 10%——超出时先查形态差异再下结论。
- **判据层级**：分配 > 绝对耗时 > 同轮比值 > 跨轮比值；地板自身漂移 >18% 则该轮相关项作废。
- **共移核对**：某一项变慢时先看三臂是否同向；三臂同向 = 环境态，单臂独走才立案。
- **未复测不归因**：单批观察只能登记为"待确认"，不得写成结论。
- **可比性**：跨机绝对值不可比；同批比值、分配、往返数可比。P95/P99 只展示不门禁。
