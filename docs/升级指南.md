# PalORM 升级指南

> **定位**：跨版本升级的行为变更与迁移动作。**README 不承载升级内容**，全部集中于此。
> **完整版本历史与逐版本修复项见 [CHANGELOG](../CHANGELOG.md)。**
>
> 阅读顺序：先看你要跨越的每一版小节，数据正确性修复优先。

---

## 未发布（下一版本）：SQLite 自增主键默认不再生成 AUTOINCREMENT

一项**行为变更**（仅影响 SQLite 的新建表）。SQLite 官方文档对 `AUTOINCREMENT` 的说明是 "imposes extra CPU, memory, disk space, and disk I/O overhead and should be avoided if not strictly needed"；本仓实测 20 万行顺序插入慢 43%（202.1 对 141.2 ms）。因此默认生成的 DDL 从 `INTEGER PRIMARY KEY AUTOINCREMENT` 改为 `INTEGER PRIMARY KEY`。

- **语义差异**：不带 `AUTOINCREMENT` 时，新行 ROWID 取当前表内最大值加一。若物理删除了 ROWID 最大的行，新插入可能**复用**该值，且新 ROWID **不再严格升序**（SQLite 官方 autoinc 文档）。带 `AUTOINCREMENT` 时插入前查 `sqlite_sequence`，单调递增且永不复用。
- **影响面**：仅 SQLite、仅 `[Key]` 自增主键（`int`/`long`，未写 `AutoIncrement = false`）、且仅**新建表**（`MigrateAsync` 只建不改，已有表不受影响）。PostgreSQL 的 `GENERATED BY DEFAULT AS IDENTITY` 与 MySQL 的 `AUTO_INCREMENT` 本身不复用，不受本项影响。
- **升级动作**：按下表决定是否给实体加 `[Key(PreventIdReuse = true)]`。

  | 表的形态 | 建议 |
  |---|---|
  | 只追加、从不删（日志、事件、流水、审计） | 不加。没有删除就没有复用，43% 是纯收益 |
  | 只软删除（`[SoftDelete]`，行不物理删除） | 不加。行一直在，最大值不变，不复用 |
  | 会用 `HardDeleteAsync` 或原生 DELETE 物理删 | 评估是否依赖 ID 单调或 ID 不复用 |
  | 对外暴露 ID（API 返回、客户端缓存、幂等键） | 加。避免新行复用旧 ID 被误认作旧对象 |
  | 用 `ToPageAsync(orderBy: x => x.Id)` 做 keyset 分页 | 加。否则删除最大行后新行的 ID 小于续页锚点，该行永远读不到 |

- **另一处配套**：`[Key(PreventIdReuse = true)]` 与 `AutoIncrement = false` 并存是静默无效组合（应用侧赋值的主键不经 ROWID 分配），现在由 `PALORM055` 在编译期报错。

## 从 6.x 升级到 7.0.0：投影与 UPDATE 修饰符收紧、分页自愈

7.0.0 是主版本跃迁（无公共 API 签名破坏，按用户裁决升 MAJOR）。三条**行为变更**（详见 [CHANGELOG](../CHANGELOG.md) 7.0.0 段），升级前请核对：

- **`Select(...).ToPageAsync()` 改为抛异常**：此前该组合在 PostgreSQL 默认批分页路径静默返回全列实体，与「Select 投影必抛 NotSupportedException」契约不一致。**升级动作**：需要投影分页时改用 `QueryAsync<T>` 投影类型（配合自己的分页条件），不要在实体 `From<T>()` 上叠加 `Select` 后调用 `ToPageAsync`。PALORM033 诊断现在覆盖该终端，构建期即可发现。
- **UPDATE 拒绝 Select/WithCache/AsSplitQuery**：这三个修饰符此前在 UPDATE 构建路径静默丢弃，调用方误以为生效。**升级动作**：从 `ExecuteNonQueryAsync` 的 builder 上移除这三个修饰符；需要缓存或投影请用查询入口。
- **批分页连接故障后自愈**：PostgreSQL 默认单往返批分页此前无判死置位，外部终止连接后该入口持续用坏连接。**升级动作**：无需代码改动；调用方若此前为绕过该缺陷而手动重建会话，可移除该补偿逻辑，失败一次后重连自动完成。

## 从 6.8.0 升级到 6.9.0：批量写入与时间类型默认行为对齐 PostgreSQL

四项**破坏性/行为变更**（详见 [CHANGELOG](../CHANGELOG.md) Unreleased 段），升级前请核对：

- **MySQL 批插默认整段单批**：`BulkInsertAsync(entities)`（不带 `batchSize` 的重载）默认批宽由 1000 行/批改为整段单批，与 PostgreSQL 一致。**升级动作**：需要限制单次 LOAD DATA 持锁行数时改用带 `batchSize` 的重载；`local_infile=OFF` 的多值回退路径仍按 1000 行/语句钳制。
- **PG `DateTime` 列改 `timestamptz`**：列类型由无时区的 `timestamp` 改为 `timestamptz`，`DateTime` 在 PG 上统一表示 UTC 时刻。**升级动作**：已有库需手工 `ALTER TABLE ... ALTER COLUMN ... TYPE timestamptz`（`MigrateAsync` 只建不改），否则「读回再写回」会抛 `ArgumentException`。
- **`ToPageAsync` 遇 `Skip()` 抛异常**：builder 上已设的 `Skip()` 由静默忽略改为抛 `InvalidOperationException`（键集分页以 `lastValue` 锚点续页，OFFSET 语义不适用）。**升级动作**：移除 `ToPageAsync` 路径上的 `Skip()` 调用。
- **SQLite 行锁 API 构建期抛异常**：`ForUpdate()` / `ForShare()` 由执行期数据库报错提前到构建期抛 `NotSupportedException`（SQLite 无行级锁）。**升级动作**：移除 SQLite 上的这两个调用。

## 从 6.4.x 升级到 6.5.0：查询语义两处修复（结果可能变化）

两项**用户可见行为修复**，升级前请核对：

- **WHERE/OR 链式优先级（C16）**：`Where(A).OrWhere(B).Where(C)` 此前生成 `(A) OR (B) AND (C)`（SQL 求值为 `A OR (B AND C)`，与方法文档承诺的链式形态不符），本版修复为 `((A) OR (B)) AND (C)`。**混合 Where/OrWhere 链的查询结果可能变化**：纯 AND 链、纯 OR 链与 OR 收尾链的 SQL 文本逐字不变，无需动作。`WhereIn`/`WhereNotIn` 同受此修复覆盖。**升级动作**：检索代码中混合 `Where`/`OrWhere` 链，确认查询结果符合链式直觉预期。
- **FormattableString 引号内花括号（C17）**：引号内 `{N}`/`}` 此前被替换或误抛 `FormatException`（JSON 文本 `'{"a":1}'` 无法书写），修复后引号内一律原样透传。此前为绕过该缺陷手写拆串的代码可还原为直书 JSON 字面量。

其余为纯新增（会话池 `DataSessionPool`）与内部性能/修复，无迁移动作。

## 从 6.3.x 升级到 6.4.0：Production 预设熔断作用域变更

`DbOptions.Production` 预设自 6.4.0 起显式设 `CircuitBreakerScope = Process`（此前为 Session）。影响与动因：

- **变化**：使用 `Production` 预设时，熔断失败计数按 (Provider, 连接串, 阈值, 冷却) 跨会话累计。一请求一会话的部署下，数据库持续故障时请求快速失败（熔断开闸），而非此前每个请求各自重试 5 次再失败、熔断从不触发的虚设形态。
- **不变**：裸 `new DbOptions { ... }` 默认仍为 `Session`；长生命周期会话与测试场景零变化。
- **多租户注意**：多租户共用一个连接串时熔断器为租户间共享粒度，需要租户级隔离的部署用独立连接串，或 `with { CircuitBreakerScope = CircuitBreakerScope.Session }` 显式回退。

## 从 6.2.x 及更早升级到 6.3.x（数据正确性修复，强烈建议）

6.3.0 修复了 **R-UNNESTB：PG auto-prepare × 命令复用槽交互下的批量操作静默错数**（影响 5.7.0 ~ 6.2.0 共 7 个版本）；6.3.1 在此之上恢复了 BulkDelete IN 形态的池化性能（20K 键 37 ms 快态带，0.55× 地板）。

R-UNNESTB 触发条件：连接串启用 `MaxAutoPrepare`（PalORM 默认调优会设为 100，见[配置参考 §3.1](配置参考.md#31-postgresql6-项)）且同一会话执行第 3 个及后续等长批量批次；后果是第 3 批起静默重发第 2 批的参数（批量删除少删行、批量 UPSERT 写错键），无异常无告警。

- **升级到 6.3.1** 即彻底修复（参数对象从建立到释放全程稳定，auto-prepare 缓存引用不再错配）
- **暂不能升级的止血**：连接串显式加 `MaxAutoPrepare=0`（代价是失去自动预编译的查询延迟收益，Npgsql 默认即 0）
- 风险面自查：若历史负载满足触发条件，建议对受影响表的批量操作结果做一次对账（行数/键集合核对）

6.3.0 同时包含 PG 三条批量写走数组形态（`UPDATE FROM VALUES(...)` 的 UNNEST 化与 `DELETE ... = ANY(数组)`，批量族时延 −40~74%），行为面无破坏。

## 从 5.x 升级到 6.0

四项破坏性变更（详见 [ADR-N](adr/ADR-N-v6.0-破坏性变更汇总.md)）：

| 删除/变更 | 迁移动作 |
|---|---|
| `IRowFactory<T>` 接口 | 无——零实现零消费，若外部代码引用了它（不存在官方用法），删除引用即可 |
| `DataSession.DiffAsync<T>()` | 换用 `ValidateSchemaAsync<T>()`，需要 `[DIFF]` 前缀时自行拼接 |
| `DbOptions.NamingConvention`（含 `ApplyNaming`） | **删除该设置即可——行为从未生效过**（列名映射在编译期由 `[Table]`/`[Column]` 注解决定）；要改列名用 `[Column("...")]` |
| `DbOptions.PoolExplicitlyConfigured` | 无——零读方内部标记；`WithPool`/`PALORM_MAX_POOL_SIZE` 行为不变 |
| `[Column]` 的 `Length/Precision/Scale`：`int?` → `int`（0=未设置） | 无——`[Column(Length = 64)]` 语法在 5.x 从未可编译过（CS0655）；v6.0 起该语法首次真正可用并参与 DDL |
