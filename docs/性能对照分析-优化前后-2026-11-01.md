# 性能对照分析：优化前 → 优化后（2026-10-28 批 → 2026-11-01 批）

> 目的：把「极致性能轮」（2026-10-31 22:41 至 2026-11-01 09:01，15 个提交；含结果与文档回写共 17 个）带来的增强与退步逐项拆开，并给出可复现的判据。
> 结论先行：核心比值面（PalORM 相对手写 SQL 地板）没有移动；真正的改善集中在批量、事务、RETURNING 与 SQL 构建；唯一新增退步是 LINQ 物化每操作 +1.5 KB，根因是会话级容量启发字典在每操作新建会话下只付成本、拿不到收益。

## 3. 退步项

### 3.1 LINQ 物化每操作 +1.5 KB（唯一有实质影响的新增退步；已修复，见 §8.1）

| 项 | 优化前 | 现在 | 变化 |
|---|---:|---:|---:|
| QueryAll / SQLite / 2000 | 299,421 B | 301,032 B | +1,611 B |
| QueryAll / MySQL / 2000 | 393,051 B | 394,840 B | +1,789 B |
| WhereIn / SQLite / 2000 | 42,850 B | 44,355 B | +1,505 B |
| IncludeJoin / SQLite / 2000 | 26,370 B | 27,849 B | +1,479 B |
| KeysetPage / SQLite / 2000 | 19,185 B | 20,367 B | +1,182 B |
| OwnedJsonQuery / SQLite / 2000 | 18,504 B | 19,936 B | +1,432 B |
| BDN QueryAll | 1,363,096 B | 1,364,592 B | +1,496 B |

**根因（代码级）**：M4.6「物化容量启发」把容量记录从 DataSession 移到 `SessionOperationState`，用 `ConcurrentDictionary<Type,int>` 保存「上次同实体物化行数」，并让 LINQ 路径也接上（`QueryBuilderExtensions` 第 185 至 191 行）。`RecordMaterializedCount` 在行数 >16 时首次调用会创建该字典，约 1.5 KB。

**判别证据（不是推断）**：
- 只有返回行数 >16 的操作上涨（QueryAll / WhereIn / IncludeJoin / KeysetPage）；单行 GetByKey 仅 +1 B（探针），直查 GetAllAsync 仅 +6 B（全批），流式 StreamAll 为 -106 B（全批）。这与「超过 16 行才建字典」的触发条件一一对应。
- 三点探针里 P1 到 P2 的增量就是这 +1.5 KB，与段 A/B 无关。
- 三段对照下，直查路径（GetAllAsync）本来就有这个字典（M4.6 前已存在于 DataSession），所以它不涨；涨的只有新接入的 LINQ 路径。

**触发条件**：每操作新建会话（本仓库的基准形态）时，字典建一次、用一次、随会话丢弃，纯成本；只有同一会话内第二次物化同类型实体时，容量提示才生效（省下 List 倍增的中转数组）。也就是说，这项优化在「每请求复用会话」的生产形态下有效，在「每操作一会话」的量具形态下只体现成本。

## 6. 建议

1. **容量启发改为惰性晋升**（与 B98 同型）：首次物化只把 `(Type, 行数)` 存进会话内联字段，第二次同类命中才创建字典。每操作会话形态下成本归零，复用形态下收益保留。（已于 §8.1 实施）
2. **D7 超时判定再条件化一次**：当前按方言判定，MySQL 默认路径仍每命令付约 290 B；可收窄到「实际配置了命令超时」才进入判定。（§8.2 部分实施，剩余成本见该节）
3. **会话复用类优化的验收口径改用池化形态**：M4.1 复用槽、M4.6 容量启发的收益只在 `DataSessionPool` 或每请求会话下可见，用每操作会话验收必然显示为负数或零。
4. **其余不动**：批量（-3.5%）、事务（-17.9 KB）、RETURNING（-3.3 KB）、SQL 构建（-449 B）的收益已由多面证据确认，无需回退。

### 8.1 容量启发改惰性晋升（完成）

`SessionOperationState` 改为先记内联槽（实体类型 + 行数），出现第二种实体类型才升级为 `ConcurrentDictionary`。每操作一会话时字典永不创建；复用会话时同类型第二次命中即拿到提示。

|---|---:|---:|---:|
| QueryAll / SQLite / 2000 | 301,133 B | 299,363 B | **-1,770 B** |
| WhereIn / SQLite / 2000 | 44,408 B | 42,770 B | **-1,638 B** |
| IncludeJoin / SQLite / 2000 | 27,856 B | 26,204 B | **-1,652 B** |

BDN：`PalORM_QueryAll` 1,364,592 B → 1,362,976 B（**-1,616 B**），回到优化前水位（1,363,096 B）。

代价：会话对象多两个字段（Type 8 B + int 4 B，对齐后 **+16 B/会话**），BDN 单行项 +0.4% 至 +0.7%，低于 5% 不做线。

测试：新增两条行为测试（同类型第二次物化命中提示、两种实体升级后各自命中）；池化字段分类表补登记三个字段。

### 8.2 超时包装归零（完成）

分两步：

1. **包装瘦身**：两个 `RunAsync` 重载加同步完成快路径，挂起路径合并为单一 `async Task` 内核（状态机盒本身即 Task），去掉「async ValueTask + AsTask」的双分配。单命令成本 329 B → 264 B。
2. **内联进进入方法**：把 D4/D7 判定与异常归一搬进 `GetByKeyEntryAsync` / `GetAllEntryAsync` / `ScalarEntryAsync` 自己的状态机。起点在方法首行取（早于 `EnterReadOnly`，窗口覆盖连接获取与租约进入），每个返回点过 `Complete` 判定，方法级 `catch` 做归一。三个公共入口不再套包装层。

| 项 | 优化前 P0 | 包装层 | 内联后 | 相对 P0 |
|---|---:|---:|---:|---:|
| GetByKey / MySQL | 5,324 B | 5,644 B | 5,424 B | +100 B |
| GetByKeySession / MySQL | 102,662 B | 110,380 B | 105,329 B | **+2,667 B**（原 +7,910 B） |
| PooledGetByKey / MySQL | 125,508 B | 132,271 B | 125,975 B | **+467 B**（原 +7,645 B） |

内联本身再省 5,051 B（GetByKeySession）与 6,296 B（PooledGetByKey），单命令约 158 B。

**剩余**：查询管线（`QueryBuilder` 的 ForEach / List / Rows / 分页三处）仍走 `WithCommandTimeoutCheck` 的包装层，约 264 B/命令；本轮范围按约定只做三个进入方法，管线如需归零可同法处理。

**验证**：E4 契约组连跑 5 次全绿；Core 726/726；Integration 574/574。

### 8.3 D7 边界漏判（既有缺陷，已修复）

**症状**：`E4_MySql_CommandTimeout_ThrowsTimeoutException` 偶发失败（基线代码 3 次跑 2 次失败，报「no exception was thrown」）。

**驱动实测**：`SELECT SLEEP(5)` 在 `CommandTimeout=1s` 下连续 8 次探针都在 **1004 至 1021 ms** 返回，没有一次早于 1 s。也就是说耗时判定本该每次都触发，漏判不来自驱动时序。

**根因**：调用点写成 `RunAsync(Entry(...), Begin(...), timeout)`。C# 实参从左到右求值，`Begin` 在进入方法的同步段（建连接、开 reader）之后才取时间戳，判定窗口被截短几十毫秒，恰好落在 `elapsed >= timeout` 的边界之前。查询管线六处调用点同样把起点取在尝试启动之后，注释里"窗口含连接获取"实际不成立。

**修复**：三个 DataSession 入口（Get / GetAll / Scalar）与查询管线六处调用点，一律把时间戳提前到启动操作之前；`WithCommandTimeoutCheck` 改为接收起点（0 表示判定关闭），`CommandTimeoutNormalizer` 的 Task 重载同步改为接收起点，杜绝"方法内部取起点"的形态。

**验证**：E4 契约组连跑 5 次全绿（修复前 3 至 4 次里失败 2 至 3 次）；新增 6 条单测锁四条判据（成功也判耗时、内层超时解包、未越线异常原样上抛、起点为 0 关闭判定）；Core 726/726、Integration 574/574。

### 8.4 修复轮结论

- 分配面：LINQ 物化回到优化前水位（略低于）；MySQL 会话类从 +8 KB 收到 +0.5 至 +2.7 KB，剩余部分来自查询管线仍保留的包装层。
- 时延面：无回退（快路径与内联都只减分配）。
- 测试：Core 726/726；Integration 574/574（§8.3 修复后 E4 契约组连跑 5 次全绿）。
