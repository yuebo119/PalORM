# ADR-O：查询缓存的写联动失效策略

> 状态：**提案（待用户裁决）** · 来源：`docs/v6.0-requirements.md` §四"明确不做项"去向承诺（"写联动查询缓存失效 | v6.1 候选 + 独立 ADR"）· 2026-09-30 未完成任务实现轮补立
> 关联：ADR-C（CacheStore 全局状态）· `docs/v6.0-requirements.md` §四

## 背景

`WithCache` 查询缓存现行失效策略是 **TTL 过期 + 容量淘汰**，文档化定位为最终一致。写操作（Insert/Update/Delete/Bulk 族）不主动失效相关缓存条目：写后立即读同一键，在 TTL 窗口内读到旧数据。

requirements 否决理由有二：① TTL 有兜底，最终一致是文档化定位；② **key 反解涉及 ADR-C 全局状态**（按 key 反推表名需要解析缓存键，缓存键含租户/过滤命名空间，反解逻辑与 ADR-C 的全局状态裁决纠缠）。

## 选项

| 选项 | 方案 | 工作量 | 风险 |
|------|------|--------|------|
| C1 维持现状 | TTL 兜底，文档定位不变 | 零 | 写后读旧窗口（已文档化） |
| C2 进程级写联动失效 | 写路径按表名广播失效（条目创建时登记表名标签，免 key 反解）；跨会话失效需进程级注册表 | 中 | **命中 ADR-C 约束**（进程级可变注册表 = 全局状态，并发失效与租户交错面是 ITM-866 同族风险源） |
| C3 会话级失效 API | `DataSession.EvictQueryCache()`（本会话缓存全清）+ 文档建议"写后失效"由调用方按需调用 | 小 | 责任转移给用户（忘调 = 等价 C1，无更差） |
| C4 移除 WithCache | 缓存特性整体退场 | 大 | binary-breaking；既有用户面受损 |

## 分析

- **B28 四问**：① ORM 职责内（缓存特性的一致性语义属其自身契约）；② AOT 可行（事件广播零反射）；③ 客户自做（C3 即客户可自达的手动形态，无更优 DIY）；④ 真必需——**零用户反馈**。
- requirements 的"key 反解"否决理由只命中 C2 的**反解变体**；条目创建时登记表名标签可绕开反解，但 C2 的跨会话面仍撞 ADR-C 全局状态裁决（ITM-866 租户缓存交错刚在 v6.0.1 修复，同类面不宜再开）。
- C3 无全局状态增量（本会话缓存本就是会话作用域），语义即文档定位的显式化。

## 推荐

**C1 维持现状 + C3 作为轻量候选登记**：产品面不做写联动失效（维持 TTL 最终一致定位与"留待真实请求重开"哲学）；若未来出现真实用户反馈，C3 是首选落点（小、无 ADR-C 风险），C2 需先修订 ADR-C。
