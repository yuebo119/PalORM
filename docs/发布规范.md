# PalORM 发布规范（SOP）

> 本规范定义 PalORM 项目从代码变更到 NuGet 发布的标准流程。
> 所有版本发布（含补丁版/小版本/大版本）必须遵守。

## 一、版本号管理

### 1.1 唯一真源：Directory.Build.props

**所有 src/ 项目的 `<Version>` 必须由 `Directory.Build.props` 集中管理**，单个 csproj **不得**硬编码 `<Version>`。

```xml
<!-- Directory.Build.props（唯一版本源） -->
<PropertyGroup>
    <Version>5.0.0</Version>
</PropertyGroup>
```

**禁止**：
```xml
<!-- src/PalORM.Core/PalORM.Core.csproj（错误做法） -->
<Version>5.0.0</Version>
```

### 1.2 版本号语义（SemVer）

| 版本段 | 何时升级 | 示例 |
|--------|---------|------|
| **Major**（5.x.x） | 破坏性 API 变更、不兼容升级 | v5.0.0 → v6.0.0 |
| **Minor**（x.1.x） | 新增功能、向后兼容 | v5.0.0 → v5.1.0 |
| **Patch**（x.x.1） | bug 修复、向后兼容 | v5.0.0 → v5.0.1 |
| **Preview** | 预发布（仅手动 workflow_dispatch） | v5.1.0-preview.1 |

### 1.3 三方一致验证

升版本时，**同一次提交**内必须同步更新所有引用版本号的位置：

| 位置 | 文件 | 示例 |
|------|------|------|
| 版本真源 | `Directory.Build.props` | `<Version>5.0.1</Version>` |
| README badge | `README.md` | `version-5.0.1-512BD4` |
| tag 名 | git tag | `v5.0.1` |

**验证命令**（应零残留）：
```bash
grep -rn "<Version>5\.0\.0" src/ 2>/dev/null        # csproj 残留扫描
grep "version-5\.0\.0" README.md                     # README badge
git tag --list "v5.0.*"                               # tag 历史
```

## 二、公开发布包范围

### 2.1 发布清单（5 个包）

| 包 ID | 项目路径 | 用途 | 公开发布 |
|-------|---------|------|---------|
| `PalORM.Core` | `src/PalORM.Core/` | 运行时核心（DataSession/QueryBuilder/注解） | ✅ |
| `PalORM.SourceGen` | `src/PalORM.SourceGen/` | 源生成器（RowFactory/CommandFactory/SqlFile） | ✅ |
| `PalORM.Sqlite` | `src/PalORM.Sqlite/` | SQLite provider | ✅ |
| `PalORM.PostgreSql` | `src/PalORM.PostgreSql/` | PostgreSQL provider（含 JSONB/LISTEN/NOTIFY） | ✅ |
| `PalORM.MySql` | `src/PalORM.MySql/` | MySQL provider | ✅ |
| ~~`PalORM.Testing`~~ | `src/PalORM.Testing/` | 内部测试工具库 | ❌ `IsPackable=false` |

### 2.2 包公开发布的判定标准

新增 src/ 项目是否公开发布，按以下顺序判断：

1. **目标消费者**：是否面向 PalORM 项目外的开发者？仅内部测试用 → 不发布。
2. **API 稳定性**：是否提供 semver 承诺？随项目内部需求变更无承诺 → 不发布。
3. **消费场景**：独立消费者（非 PalORM 项目）是否有合理使用场景？无 → 不发布。
4. **公共 API 面**：发布是否会让消费者困惑 PalORM 的公共 API？会 → 不发布。

**判定为不发布**：在 csproj 加 `<IsPackable>false</IsPackable>`，并在 `release.yml` 的 pack 循环和 `test-package-contract.sh` 中排除。

## 三、分支与合并流程

### 3.1 分支保护规则

```
feature/xxx ──PR──▶ dev ──PR──▶ main
    │                 │            │
    └── 开发分支      └── 集成测试   └── 生产发布（含 tag）
```

- **main**：仅接受来自 dev 的 PR 合并，禁止直接 push
- **dev**：接受来自 `feature/*` 的 PR 合并
- **feature/\*\***：从 dev 创建，PR 到 dev

### 3.2 合并权限规则（强制）

| 合并方向 | 谁触发 | 频率 |
|---------|--------|------|
| `feature/*` → `dev` | 贡献者自主（CI 通过后合并） | 每个 feature 完成时 |
| `dev` → `main` | **仅人工确认后**（用户/维护者明确指示"合并到 main"） | **按需**——不是每次 dev 更新都合并 |
| `main` → `dev`（反向同步） | 维护者（保持 dev 不落后 main 太多） | 按需 |

**关键规则**：
- ❌ **禁止 AI/自动化工具自主合并到 main**——dev → main 是发布动作，必须用户明确确认
- ❌ **禁止"每次 dev 更新就同步到 main"**——main 应保持稳定，只在准备发版时合并
- ✅ dev 可以自由积累多个 feature，等到准备发布版本时再一次性合并到 main

### 3.3 PR 类型与 `--delete-branch` 使用

| PR 类型 | base | `--delete-branch` | 说明 |
|---------|------|-------------------|------|
| `feature/*` → `dev` | dev | ✅ 删 feature | 标准 feature 流程 |
| `dev` → `main` 同步 | main | ❌ **不删 dev** | dev 是常驻分支 |
| `fix/*` → `main`（紧急修复） | main | ✅ 删 fix | 跳过 dev 的紧急通道 |

**关键**：`dev` 和 `main` 是常驻分支，合并 PR 时**绝不**用 `--delete-branch` 删除它们。

## 四、发布前验证清单

### 4.1 本地必跑（提交前）

```bash
# 1. 工作树清洁
git status --short

# 2. 全量构建（含 SourceGen 和测试项目，0 警告 0 错误）
dotnet build PalORM.ci.slnf -c Release --no-incremental -warnaserror

# 3. 模拟 CI 环境（GITHUB_ACTIONS=true）跑测试
GITHUB_ACTIONS=true dotnet run --project test/PalORM.Core.Tests -c Release --no-build
GITHUB_ACTIONS=true dotnet run --project test/PalORM.SourceGen.Tests -c Release --no-build

# 4. 包契约脚本（验证公开发布包的依赖关系）
bash scripts/test-package-contract.sh

# 5. 本地 pack 验证（应生成 5 个 nupkg，不含 Testing）
rm -rf /tmp/release-preview && mkdir -p /tmp/release-preview
for proj in Core SourceGen Sqlite PostgreSql MySql; do
    dotnet pack "src/PalORM.$proj/PalORM.$proj.csproj" -c Release --no-build -o /tmp/release-preview
done
ls /tmp/release-preview/ | wc -l   # 应输出 5
```

### 4.2 nuspec 元数据检查

每个 nupkg 解压后的 `.nuspec` 必须包含：

```bash
unzip -p /tmp/release-preview/PalORM.Core.*.nupkg '*.nuspec' | grep -E "<(id|version|projectUrl|repository|releaseNotes|license)"
```

**必须字段**：
- `<id>` 正确（如 `PalORM.Core`）
- `<version>` 与 Directory.Build.props 一致
- `<projectUrl>` 指向 GitHub 仓库
- `<repository url=... commit=.../>` 含 commit hash（证明 SourceLink 生效）
- `<releaseNotes>` 指向 CHANGELOG.md
- `<license type="expression">AGPL-3.0-only`

## 五、触发发布

### 5.1 tag 触发（标准发布）

```bash
# 1. 确认本地 main 与远程一致
git checkout main
git pull origin main
git log -1 --format="%h %s"

# 2. 确认版本号已更新到目标版本
grep "<Version>" Directory.Build.props

# 3. 打 tag（tag 名格式：v + 版本号，如 v5.0.1）
git tag v5.0.1
git push origin v5.0.1

# 4. 观察 Actions 运行
# https://github.com/yuebo119/PalORM/actions/workflows/release.yml
```

### 5.2 workflow_dispatch（手动补发）

适用场景：tag 触发失败需重发，或预览版发布。

1. 访问 https://github.com/yuebo119/PalORM/actions/workflows/release.yml
2. 点 **Run workflow**
3. 输入版本号（必须与 Directory.Build.props 的 `<Version>` 完全一致）
4. 点 **Run workflow**

**注意**：`workflow_dispatch` 触发时 `GITHUB_REF_NAME` 是分支名不是 tag 名，release.yml 已通过 `inputs.version` 处理此差异。

### 5.3 不应触发发布的场景

- ❌ PR 合并到 dev（dev 不发布，仅集成测试）
- ❌ PR 合并到 main 但未打 tag（main 上的代码 ≠ 发布版本）
- ❌ 直接 push 到 main（违反分支保护，且不会触发 release.yml）

## 六、release.yml 工作流规范

### 6.1 触发条件

```yaml
on:
    push:
        tags: ['v*']              # 标准触发：tag 推送
    workflow_dispatch:             # 手动触发：补发/预览
        inputs:
            version: { required: true }
```

### 6.2 必须的 step 顺序

| 顺序 | step | 作用 | 失败处理 |
|------|------|------|---------|
| 1 | Resolve version | 从 tag/input 解析版本号 | 解析失败 → exit |
| 2 | Verify version matches props | tag 版本 vs Directory.Build.props | 不一致 → exit（防误发） |
| 3 | Restore + Build | 全量构建，warnings as errors | 编译失败 → exit |
| 4 | Unit tests | Core.Tests + SourceGen.Tests | 测试失败 → exit |
| 5 | Integration tests | PG + MySQL service container | 测试失败 → exit |
| 6 | Pack | 5 个公开发布项目 | pack 失败 → exit |
| 7 | Verify package count | 断言 nupkg 数 = 5 | 数量不对 → exit（防漏发） |
| 8 | Push to NuGet.org | `--skip-duplicate` | push 失败 → exit |
| 9 | Create GitHub Release | 仅 tag 触发时 | 创建失败 → exit |

### 6.3 关键配置

```yaml
concurrency:
    group: release-${{ github.ref }}
    cancel-in-progress: false    # 发布不可中断，防半成品

permissions:
    contents: write              # 创建 GitHub Release 必需

services:
    postgres: { image: postgres:17, ... }    # integration test 依赖
    mysql:    { image: mysql:8.4, ... }      # integration test 依赖
```

### 6.4 secrets 配置（一次性）

| Secret 名 | 用途 | 获取方式 |
|-----------|------|---------|
| `NUGET_API_KEY` | 推送到 nuget.org | https://www.nuget.org/account/apikeys（Push 权限，Glob Pattern=`PalORM.*`，365 天有效期） |

## 八、回滚与补救

### 8.1 发布失败（workflow 报错）

| 失败 step | 补救 |
|----------|------|
| Build/Test 失败 | 修复代码 → 重新合并到 main → 重打 tag（见 8.3） |
| Pack 失败 | 检查 csproj 改动是否破坏 pack → 修复 → 重打 tag |
| Push 部分失败 | `--skip-duplicate` 会自动跳过已 push 的包；workflow_dispatch 重发即可 |
| GitHub Release 创建失败 | 手动在 https://github.com/yuebo119/PalORM/releases/new 创建 |

### 8.2 误发布（不该发的版本发出去）

**NuGet 不支持删除已发布版本**，只能 listed=false 隐藏：

1. 访问 https://www.nuget.org/packages/<包名>
2. 点 **Manage package**
3. **Listing** 区域取消 **List in search results**
4. **Save**

效果：
- ✅ nuget.org 搜索结果不显示
- ✅ 直接 URL 仍可访问（已下载项目仍能恢复）
- ✅ `dotnet add package <包名> --version <版本>` 仍工作

### 8.3 重打 tag

```bash
# 删本地+远程旧 tag
git tag -d v5.0.1
git push origin :refs/tags/v5.0.1

# 在最新 main 上重打
git checkout main && git pull origin main
git tag v5.0.1
git push origin v5.0.1
```

## 九、发布实践教训（v5.0.0 实测，2026-07-27）

> 以下教训来自 v5.0.0 首次发布的实际踩坑过程。

| # | 教训 | 详情 | 规范化 |
|---|------|------|--------|
| 1 | **CI 配置改动需全量集成测试覆盖** | release.yml 首次只配 PG service，但 `dotnet run` 跑全量 integration tests，MySQL 测试因缺 `PALORM_MYSQL_HOST` 失败 | §6.2 step 5 必须配 PG + MySQL service |
| 2 | **ContinuousIntegrationBuild=true 触发路径归一化** | dotnet/roslyn#55860：DeterministicSourcePaths=true 把 `[CallerFilePath]` 归一化为 `/_/` 虚拟路径，破坏 ArchitectureInvariantTests 的 src 目录定位 | 测试项目（`.Tests`）必须在 csproj 覆盖 `<ContinuousIntegrationBuild>false</ContinuousIntegrationBuild>` |
| 3 | **git diff --check 对 Windows CRLF 行为不一致** | Windows 开发者工作区经 autocrlf 转换后，diff 输出附加 CR，`--check` 把 CR 当 trailing whitespace 误报 | ci.yml gate 的 `git diff --check` 失败降级为 warning（不阻断合并） |
| 4 | **gh pr merge --delete-branch 会删主分支** | `dev → main` 的 PR 用了 `--delete-branch` 误删 dev 分支 | §3.2 表格明确：dev/main 是常驻分支，PR 合并时不删 |
| 5 | **内部测试库不应公开发布** | PalORM.Testing 是项目内部测试工具，发布到 nuget.org 混淆公共 API 面 | §2.2 判定标准 + IsPackable=false |
| 6 | **cherry-pick 前先确认 base 分支** | 从本地 main 而非 dev 拉了 feature，PR diff 含无关 commit（fe32651） | §3.1 feature 必须从 dev 创建 |
| 7 | **trailing whitespace 调试不能超过 3 次尝试** | 陷入 CRLF 调试循环 5+ 次仍无果，违反全局规范"修复尝试 ≤ 3 次" | 遇到环境相关的 CI 问题，超过 3 次降级为 warning 跳过 |
| 8 | **首次发布的 tag 应基于已过 CI 的 commit** | v5.0.0 tag 打在了未通过 CI 的 commit 上，触发后才发现 release.yml 配置错误 | §4.1 本地必跑清单 + §5.1 tag 前确认 main 已过 CI |
| 9 | **dev → main 合并必须人工确认** | AI/自动化工具不应自主合并 PR 到 main——dev → main 是发布动作，每次合并都改变生产发布基线。曾发生连续 4 个 PR 被自动合并到 main，绕过了发布时机的判断 | §3.2 合并权限规则：dev → main 仅人工确认后触发，禁止"每次 dev 更新就同步" |

## 十、版本发布模板

### 10.1 补丁版（v5.0.0 → v5.0.1）

```bash
# 1. 创建 feature 分支
git checkout dev && git pull origin dev
git checkout -b fix/issue-xxx

# 2. 修复代码 + 测试
# ... 编辑代码 ...
dotnet build PalORM.ci.slnf -c Release --no-incremental -warnaserror
GITHUB_ACTIONS=true dotnet run --project test/PalORM.Core.Tests -c Release --no-build

# 3. 升版本（同一次提交）
# 编辑 Directory.Build.props: <Version>5.0.0</Version> → <Version>5.0.1</Version>
# 编辑 README.md: version-5.0.0 → version-5.0.1
git add Directory.Build.props README.md
git commit -m "修复：xxx + 升版本 5.0.1"

# 4. PR 流程：feature → dev → main
# 5. 重打 tag：git tag v5.0.1 && git push origin v5.0.1
```

### 10.2 小版本（v5.0.1 → v5.1.0）

新增功能时，除 §10.1 步骤外：

```bash
# 升版本前更新 CHANGELOG.md（新增 Features 段落）
# 检查新增 API 是否需要补充 README 示例
# 检查新增 src/ 项目是否需要加入发布清单（§2.2 判定）
```

### 10.3 大版本（v5.x → v6.0.0）

破坏性 API 变更时，除 §10.2 步骤外：

```bash
# 在 docs/adr/ 新增 ADR 记录破坏性变更决策
# README 加迁移指南
# 考虑是否保留 v5.x 的 LTS 分支
```
