## 1. 结论

- **当前全量墙钟**：T2 采纳后为 17m01s 与 16m26s，中位 16m44s（1004s）[事实]；T2 前为 19m34s 与 19m37s（中位 19m35s）。交错读改造前的 18m20s 是一日前的批次，其差额主要来自 discarded pass（76s）。日常反馈由 L0 快线承担（2m50s，见 §7.3）。
- **结构**（T2 前的阶段 0 分解，用于归因）：PerfHub 占 70.9%（834s / 1175.5s），微基准步占 28.5%（334s），门禁与统一报告合计 4s，`Report.Build` 解析 359 份历史 JSON 仅 **0.46s**。
- **PerfHub 内部**（T2 前）：计时循环 406s（34.5% of full）、预热 247s（21.0%）、重置/播种 67s（5.7%）、交错读 discarded pass 76s（6.5%）、夹具固定 8s、未归因 4.8s（0.6%）。预热与计时合计 653s，占全量 55.5%。
- **保守方案**：T2（采样预算减半）实测把全量从 19m35s 降到 16m44s（省 2m51s）。T5b（固定开销合并，10 至 30s）未做，做了也在 16.4 分钟量级。达不到作战卡的 ≤11 分钟，也达不到按 T2 前基线折算的 60% 线（11m45s）。
- **≤11 分钟的可行性**：T4 三方言并行的探针已否决（三路 PG 中位 +8.0%、p95 47.4%）；T2 已到噪声允许的边界（0.25 倍出现 9 项迭代下限）；BDN 本机拆分受生成工程目录隔离限制不可行。结论：**不改覆盖的前提下，全量 ≤11 分钟不可达**。已落地 L0 快线（2m50s）承担日常反馈；若全量 ≤11 是硬指标，只能裁覆盖，需要用户显式批准（红线 #3）。

## 6. 为什么安全（本轮只加插桩）

- **插桩开销 A/B**：同一参数（SQLite/2000，非 quick）4 批交替 off→on→on→off。运行耗时 103s / 101s / 103s / 102s；逐项墙钟合计 96.2s / 93.7s / 96.5s / 95.2s。差异 ≤1%，方向不一致，**低于作战卡 2% 阈值** [事实]。插桩形态：每阶段一次 `Stopwatch.GetTimestamp()`，每项一个计时对象，均在计时循环之外。
- **测量语义未变**：history JSON、结果库信封、门禁阈值、预热/迭代/预 GC 规则逐字未改；计时数据写独立旁车 `perf-timing-*.json`。
- **两次全量一致性**：总墙钟 1174s vs 1177s（+0.3%）；PerfHub 834s vs 828s（−0.7%）；阶段占比最大差 0.6pp。
- **最慢 20 项复现性**：18/20 在 ±10% 内 [事实]；两项越界均为 MySQL/20000/BulkInsert（ADO 6.49→4.91s，r=1.32；PalORM 6.35→7.16s，r=0.89）。根因：自适应迭代数由单次 probe 决定（ADO 两轮 probe 0.06s vs 0.09s → 70 vs 42 轮），属既有的采样设计方差，不是插桩引入。**这条同时是 T2 的前置风险：预算减半会把部分慢项推向 3 轮下限**。
- **门禁**：两轮全量的 BDN 27/27 与结果库库门禁均 OK（`[3/5]` 退出码 0）。
- **未做**（模式 A 边界）：变异探针、覆盖对账、基线重录、新快线验证——这些属于阶段 2-5，需在实施时按作战卡 §8 补齐。

## 7. 风险、回滚与后续

### 7.1 T4 并行可行性裁决（2026-10-24 探针，结论：不采纳）

探针设计：同构建、同参数（两档、无并发）下比较三种执行形态，全部写 `tmp/probe-*` 隔离目录（`--result-dir`/`--no-report`/`--no-envelope`）：

| 对照 | 覆盖项 | 中位偏移 | p95 逐项偏差 | >10% 项 | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| 顺序 A/A（同构建，两轮） | 387 | 4.7% | 21.3% | 83 | 逐项复现性噪声底 |
| 三路并行 vs 单进程顺序（SQLite） | 129 | +4.8% | 14.0% | 16% | 在噪声底内 |
| 三路并行 vs 单进程顺序（MySQL） | 129 | +3.1% | 33.3% | 36% | 超出 |
| 三路并行 vs 单进程顺序（PostgreSQL） | 129 | +8.0% | 47.4% | 52% | 明显越界 |
| 两路 SQLite∥MySQL（MySQL） | 129 | +0.7% | 22.4% | 24% | 接近噪声底 |

关键混杂量：当前全量是单进程内 SQLite→MySQL→PG，MySQL/PG 进场时进程已暖；并行形态下每个方言都是各自进程的首个方言。探针先用单方言独立进程做了位置控制，上表已是控制后的结果。结论：

- 三路并行不可用：PG 的中位偏移 +8%、p95 47%，超过顺序 A/A 的噪声底一倍以上。
- 两路 SQLite∥MySQL 数值上可用（MySQL +0.7%），但 PG 单独成进程后位置效应仍在，整套基线需重录；且两路只能省约 280s，叠加 T2 后落在 11 分钟线附近，收益与代价不成比例。
- **裁决：不采纳 T4**（含两路版本），保留 `--result-dir`/`--no-report`/`--no-envelope` 三个隔离开关作为未来复测能力。重开触发：出现核隔离（进程亲和）或独立数据库主机，且能重做上述 A/A。

结论：0.5 倍的逐项散布不宽于同时段环境漂移，分配偏差也不扩大；0.25 倍把 9 项推到 3 轮迭代下限且 p95 回升，停用。逐操作 signed 中位偏移绝大多数在 ±5% 内（最大 KeysetPage +11.7%，而该操作的绝对偏差中位 15.6%，属噪声）。同时段 1.0 到 0.5 的 PerfHub 墙钟从 901s 降到 652s。

采纳值（2026-10-24 起为默认）：预热预算 1.5→0.75s；计时默认 1.5→0.75s；批量族 4→2s；TxRollback/WideQueryAll 2→1s；并发 2→1.5s；Build 保持 1s（亚微秒级、受 2000 次上限约束，缩预算无收益）；首档 0.5s 预热下限不变。

验收（两轮全量）：17m01s / 16m26s，中位 16m44s（T2 前 19m35s，省 2m51s / 14.6%）；PerfHub 659s / 645s（前 834/828s）；两轮门禁均通过（BDN 27/27、结果库 0 FAIL）。新预算下两轮 A/A 的逐项时间偏差中位 8.8%、p95 37.3%，与同期环境漂移（8.1%/34.4%）同量级；两轮间 signed 中位 -6.4% 属时间趋势，不是预算偏移。

### 7.3 L0 快线（2026-10-24，已落地）

- 覆盖：BulkInsert / BulkUpdate / BulkDelete / UpsertBatch / GetAllAsync / GetByKey，三方言、20000 档，55 项测量（18 个判定键）。
- 实测墙钟：2m50s 至 3m27s（PerfHub + L0 判定 1~2s），目标 ≤5 分钟，余量 ≥1.5 分钟。
- 基线：`bench/baselines/perfhub-l0-baseline.json`，从 3 个 `verify-l0` 批次逐键取中位数；与全量索引基线分开（子集上下文不同，2026-10-24 探针实测逐项偏差可达 100%）。基线含 AllocBytes（全量索引基线此前只记比值与中位）。
- 判定：PalORM 比值相对基线 +30%、分配 +20%、三方言缺一即 FAIL。**不做"噪声带内不判失败"降级**：L0 是判据面，假 FAIL 的代价是复测一次，漏报的代价是放过回归；分母漂移保护保留。
- 单批噪声：先试过"单批判定 + 首轮红自动复测"，实测 6 个正常批次里出现 2 次误报（3 键同时跳 45~77%，复测即过），且复测把单次墙钟推到 6m27s，超过 5 分钟目标。改为与全量门禁同源的 **3 批窗口中位数**（B203）：单批离群被吸收，持续回归需连续 2 个 L0 批次才越线；单次墙钟回到 2m50s。
- 检测力（窗口探针）：连续 2 批注入比值 +45%（同时抬中位、隐含地板不变）→ FAIL；单批注入 → PASS（负对照，证明窗口按设计吸收单批尖峰）；连续 2 批分配 +25% → FAIL；最新批次缺 MySQL → FAIL。
- 真实批次：采用窗口判定后跑 `PerfCli l0`，2m50s、18 键 0 失败（1 项分母漂移告警）。
- 与全量的关系：L0 不替代全量。全量仍覆盖 BDN 门禁、两档位、全部 30 项；L0 只承担每次提交的关键项反馈。

### 7.4 BDN 门禁集拆分（2026-10-24，本机不可行，不采纳）

- 目标：把 27 项 BDN 门禁集拆成 2 至 3 个进程并行，把 290 至 300s 压到 120 至 150s。
- 障碍：BDN 的生成工程目录按"解决方案根 + 程序名"定位，程序名是"程序集名 + folderInfo + 分区编号"，而分区编号在每个进程内都从 1 起。同一 checkout 内两个进程必然撞目录；`--artifacts` 只隔离结果输出，不隔离生成工程。生成工程用绝对 HintPath 引用基准 DLL，但 CsProjGenerator 仍在**当前工作目录的子树**里按项目名找 csproj。
- 隔离试跑：在 `tmp/bdn-iso` 放哨兵 `.sln` 作为解决方案根后运行单类，BDN 报 `Unable to find PalORM.Benchmarks in ... and its subfolders`，benchmark 构建失败（0 执行）。可行的隔离只有独立 worktree 或仓库副本，而 vendored BDN 子树不在 git 内，复制成本高。
- 收益上限：类拆分是 23 项 Crud（约 227s）对 4 项 OrmComparison（约 41s），最大只省约 40 至 60s；要省 2 至 3 分钟必须再拆 Crud 的 23 项，进一步依赖上述隔离。
- 结论：不采纳本机 BDN 拆分。重开触发：BDN 支持按进程隔离生成目录（或 vendored fork 的 `BuildPartition.GetProgramName` 加进程标识并同步进 `bench/bdn-overlay`），且 Crud 内部分组能做出平衡拆分。CI 级拆分（不同 checkout 的独立 job）可行，但只影响 CI 墙钟且重复 restore/build，本轮未改。
