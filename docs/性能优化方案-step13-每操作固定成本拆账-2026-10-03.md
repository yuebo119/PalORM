## 1. 结论

最新批显示 PalORM 在绝大多数操作上已与 ADO.NET 持平或更优（BulkUpdate/MySQL 0.30×、
BulkUpdate/PG 0.57×、BulkDelete/PG 0.47×、UpsertBatch/PG 0.80×）。剩余差距只有两个形状：
**读/单行路径的常量级分配开销**（与行数无关），以及**少数单方言读路径 1.1~1.3× 的时延**。

本轮把常量级开销拆到段级，并按预定验收标准逐项判定。**结论是读路径的可减项全部低于
项目的 200 B T5d 线**：唯一过线的候选（读路径去 lambda）经三方言 A/B 实测为净负收益，
已回滚；唯一真正过线的单项在 QueryBuilder 链式路径（`OrderBy(Expression)` 调用点表达式树
512 B/op），需要公共 API 决策，本轮只产出风险清单与探针。

## 3. 已落地后回滚：读路径去 lambda（三方言 A/B 未通过）

### 改动内容

按写路径 P2-1 的既有形态，把 `GetAsync` / `GetAllAsync` 从
`ExecuteReadPipelineAsync(async token => {...})` 改为直调，并在 `ResilienceExecutor` 上新增
**internal** 状态化重载 `ExecuteAsync<TState, T>(TState, Func<TState, CancellationToken, Task<T>>, ...)`
（公共委托版转调它，`static (op, token) => op(token)` 由编译器缓存）。

### 验收实测（MultiDialectReadDiag，同态 A/B，各三次复现）

| 方言 | 改动前 | 改动后 | Δ |
|------|--------|--------|---|
| SQLite | 2696 | 2584 | **−112** |
| PostgreSQL | 3567 | 3608 | **+41** |
| MySQL | 5217 | 5257 | **+40** |

**判定：净负收益，回滚。** 假设被证伪：文档初稿预期"PG/MySQL 真实异步 I/O 下状态机会装箱，
收益更大"，实测相反。机制是泛型状态机现在内嵌 `GetByKeyReadState`（5 字段、40 B）而非
8 B 的委托引用；PG/MySQL 下状态机确实装箱，但装箱体增大 40 B，把 lambda 的收益吃掉还倒亏。
SQLite 的 I/O 同步完成、状态机不装箱，所以只有它拿到 −112 B。

回滚后复测确认回到 2696 / 3567 / 5218，构建与测试全绿。

### 该方向的正确边界

- 只对 **SQLite**（同步完成）是正收益，且 −112 B < 200 B 线。
- 要同时在 PG/MySQL 上为正，需要让状态机装箱体不增大（例如状态只传会话引用、待处理参数
  存会话字段）。那会引入隐式状态（会话本已由租约保证单操作），为 ~112 B 得不偿失。

## 4. 实测后不采纳

| 候选 | 实测 | 判定 |
|------|------|------|
| 读路径去 lambda | SQLite −112 / PG +41 / MySQL +40 | 净负，已回滚（§3） |
| 写路径同形态状态化 | 1168 vs 同态对照 1192 = **−24 B/行** | 低于线，回滚 |
| 惰性 `ResilienceExecutor` | 前提不成立：默认配置 `MaxRetries=3` + 熔断阈值 5，执行器默认即被使用 | 不适用 |
| 惰性读连接委托 | 单侧约 56 B × 2；且 `CreateReadOrPrimaryCommandAsync` 以 `_readConnProvider is null` 判定读路由回退，惰性化会静默改路由语义 | 风险高于收益 |
| `ReusableQuerySlot` 惰性 | 对象 4 字段约 56 B | 低于线 |
| 只读标量/聚合路径状态化 | 与写路径同形，预估 −24 B 量级 | 低于线 |

F1 的结论仍然成立（会话构造可减上界 72 B）。本轮补充一条：`ResilienceExecutor` 的 264 B
在默认配置下不可省，它不是"默认必建"的假设问题，而是默认配置确实启用了重试与熔断。

## 5. QueryBuilder 链式路径：唯一过线单项与 API 提案

### 段级拆账（QueryBuilderPathDiag）

| 段 | 分配 B/op |
|----|-----------|
| (1) `From<T>()` 仅建 builder | 1288（会话 968 + builder 与惰性槽约 320） |
| (2) `+ Where(FormattableString)` | 1608（+320） |
| (3) `+ OrderBy(表达式)` | 2408（**+800**） |
| (4) `+ Take(100)` | 2408（+0） |
| (5) 完整链式 + `ToListAsync`（执行） | 5672 |
| (6) 链式 + `FirstOrDefaultAsync`（执行） | 3528 |
| (7) 专用 `GetAsync`（执行） | 2696 |
| (8) 裸表达式树构造 | **512** |
| (9) 裸 `FormattableString` 构造 | 88 |

最大单项是 (8)：`OrderBy` 的 `Expression<Func<T,TKey>>` 形参让调用点每次构造表达式树，
512 B/op，且表达式树不缓存（`static` lambda 只缓存委托，不缓存树）。

### 提案与探针（OrderByExprDiag）

把排序/成员选择族的 `Expression<Func<T,TKey>>` 改为 `Func<T,TKey>` +
`[CallerArgumentExpression]`：静态 lambda 作为 `Func` 是编译器缓存的委托，源文本以编译期
常量传入。

调用点成本实测：

| 形态 | 分配 B/op |
|------|-----------|
| 现状 `Expression<Func<T,long>>` | 536 |
| 提案 `Func<T,long>` + CallerArgumentExpression | 160 |
| 提案 `Func<T,object?>`（Select/GroupBy 形态） | 160 |
| 非 static 捕获 lambda | 240 |

提案的 160 B 来自原型解析器的 `Trim`/切片子串分配；改为 span 解析后应归零，即
**调用点净收益约 −500 B/op 每个表达式实参**。

### 风险与破坏面清单

**影响面**（`src/PalORM.Core/QueryBuilder.cs`）：

- 公共 API 共 11 处形参：`OrderBy`(173)、`OrderByDescending`(184)、`ThenByDescending`(188)、
  `ThenBy`(192)、`Select(params [])`(202)、`WhereIn`(236)、`WhereNotIn`(242)、`GroupBy`(338)、
  `Set`(356)、`Include`(373-374，两个表达式)、`IncludeThen`(390-391，两个表达式)。
- 内部助手 `AddWhereComparison`(741)、`AddOrderBy`(753)、`GetQualifiedColumnName`(1328)、
  `GetColumnName`(1331) 同改。
- **转发型 API 是硬约束**：`QueryBuilderExtensions.ToPageAsync`(420) 把
  `Expression<Func<T,TKey>> orderBy` 当参数传递。提案形态下它必须自己声明
  `[CallerArgumentExpression]` 并把捕获文本往下传；而它的签名里 `orderBy` 之后紧跟
  `TKey? lastValue = default`，插入新参数会移动位置参数，对既有调用方是源破坏。

**解析面**（`MemberResolver.GetMemberName` 当前只接受两种形态，ITM-616 显式拒绝嵌套）：

| 源文本 | 探针结果 |
|--------|----------|
| `static x => x.id` | 解析成功 |
| `x => x.status` | 解析成功 |
| `(x) => x.id` | 解析成功 |
| `static x => (object)x.id` | 解析成功 |
| `x => x.id + captured` | **静默解析出伪列名**（原型缺陷，必须显式拒绝） |
| lambda 存变量后传入 | 响亮拒绝（能力回退：变量形态不再支持） |

**风险条目**：

1. 二进制不兼容：11 处公共签名变更，需 ADR 与发布说明。
2. 解析器必须 span 化，否则 160 B/op 的子串分配会吃掉三分之一的收益。
3. 解析器必须做标识符白名单校验；朴素切片会把 `x => x.id + captured` 静默变成列名
   `id + captured`（探针已复现该失败模式），这是从"编译期类型安全"退到"运行期文本解析"
   后新增的静默错误面。
4. lambda 存变量后传入的形态失去支持，且只能响亮失败（`CallerArgumentExpression` 捕获的是
   变量名而非表达式文本）。已 grep 全仓：当前无此类调用点。
5. 动态构造表达式（反射/LINQ 建树）会失效。已 grep 全仓：`src/` 内无此类用法。
6. `Select(params [])` 与 `Include`/`IncludeThen` 的双表达式形态需要逐个补
   `CallerArgumentExpression` 参数，机械但量大。

**建议的验证计划**（若立项）：先写 span 解析器 + 标识符白名单的单测（含上表全部形态与
拒绝用例），再改 `MemberResolver` 与 `QueryBuilder` 的 11 处签名，最后跑
`QueryBuilderPathDiag` 复测调用点分配与全套测试 + 快照 + 门禁 G26（QueryBuilder 保持 struct）。

## 6. 器材问题（影响结论可信度，非产品缺陷）

1. **BDN `ADO_NET_Update` 零参数**（`bench/PalORM.Benchmarks/01_CrudBenchmarks.cs:177`）：
   命令文本把常量内联为字面量（`SET status = 'U', total = 999 WHERE id = 5000`），
   而 PalORM 臂走 `Set()` 建 2 个参数。记录在案的分配比 8.27×（本批 6.97×）**不可比**。
   同一操作在 PerfHub（两臂都参数化）只有 1.41×。
   处置建议：ADO 臂补参数化并重录基线；或按 B95 纪律标 `Ratio=0` + `Note` 说明分母不干同一件事。
2. **PerfHub 的"每操作一会话"形态**：A9 命令复用、预编译在门禁里永不生效
   （晋升阈值 3 不可达）。探针显示长会话形态 1248 B/op 已低于 ADO 地板 1304 B/op（0.96×），
   而 PerfHub 报的是 2.07×。建议补一条长会话臂，把推荐用法纳入门禁。
3. **HTML 报告的子集批污染（本轮实测踩中并已修）**：`Report.cs` 原用 `runs[^1]`
   （按文件名排序的最后一个历史文件）当"最新"渲染。子集批会顶掉它，使整份报告缩水成
   单方言，且在更新的全量批落地前一直坏。实测：一次 `--dialects pg` 复测批把
   `bench/perfhub/report.html` 变成只剩 PostgreSQL（176 处 PG、0 处 MySQL）。
   `latest.json` 有守卫（`IsSubsetLabel` + `DetectCoverageRegression`），报告侧一个都没有。
   **修法**：与 `latest.json` 对齐判据——跳过子集标签批，且方言覆盖面不得回退
   （真子集不采纳），并在报告里加 `DialectCount` 助手。修后报告恢复三方言覆盖。
   注意**标签守卫拦不住无标签的子集批**：实测 20:02/20:04 两批是 79 项 SQLite 单方言、
   `label` 为空，只有覆盖面判据能拦住。这与 latest.json 侧早已记录的
   "判定不能只信 label"是同一族教训，报告侧此前未同步。

## 8. 测量方法教训（本轮新增三条）

1. **同步 lambda 内的 `AsyncLocal` 写会造成 O(N²) 测量污染。** 用"同步 lambda 内新建
   `AsyncLocal` 并首次写"标定 `EnterReadOnly` 的 EC 拷贝成本，实测 400,933 B/op。根因是
   同步 lambda 的写发生在测量循环自身的执行流上，EC 的 map 条目只增不减。产品侧写在
   async 方法帧内、方法返回时 EC 被还原，故 `会话 + GetAsync` 在 20000 次迭代下恒定
   （不随迭代增长）。对照：同一 `SessionOperationState` 复用实例 + `EnterReadOnly` = 0 B。
2. **陈旧基线对照会误判方向。** 写路径改动首次判定为"+32 B 回归"，实为拿改动后的 1168
   与 2026-10-02 录制的基线文件 1136 比较，而非同态对照。同态对照实测 1192，真实差值是
   −24 B。结论：探针结论必须同态 A/B，不得跨时间点比绝对值。
3. **`GetAllocatedBytesForCurrentThread` 对真实异步 provider 无效。** 首版多方言探针用它，
   实测 PG 1060 B/op，小于会话构造本身（968 B），明显不可能。根因是 PG/MySQL 的异步续体
   在线程池线程上继续，该 API 只计当前线程。改用 `GetTotalAllocatedBytes(true)`（PerfHub
   `Measure` 同口径）后 PG 3609、MySQL 5259，三次复现稳定在 ±1 B。

## 9. 测试隔离修复（Integration 套件）

Integration 的外部库用例共享 PG/MySQL 的 `palorm_bench` 库，DDL 争同一系统目录。
守卫机制已存在（类级 `[NotInParallel("ExtBulkTable")]`），但覆盖不全：20 个引用
`ExternalDatabase` 的类里有 5 个缺守卫（其中 `DialectDifferenceTests` 是注释误报，实为纯
SQLite）。实测表现：修复前 3 次运行出 2 次失败，且失败项不固定
（`42P07 relation "pg_test" already exists`、`42710 type "merge_entities" already exists`），
属并行 DDL 竞态。

修复：给 `ConnectionStringOverrideTests`（含 `MySqlConnectionStringOverrideTests`）、
`DisposedTransactionDialectTests`、`PgBulkCacheConcurrencyTests` 补类级守卫，
给 `ForeignKeyDdlTests` 的两个真库用例补方法级守卫（该类含纯 SQLite 用例，不整体串行化）。
键复用 `ExtBulkTable`（必须同键才能与既有守卫互斥）。

修复后 Integration 连跑 4 次全绿（268/268）。
