# step13：每操作固定成本拆账与优化（2026-10-03）

> 数据源：`bench/perfhub/results/history-20261003-123952.json`（12:39 全量批，434 项）、
> `history-20261003-125126.json`（12:51 floor-drift 复测批，254 项）、
> `bench/reports/logs-20261003-121858/gate.log`（BDN 门禁）、
> `.ai/perf-probe/` 下的 `PerOpDecompDiag`（perop）/ `QueryBuilderPathDiag`（qbpath）/
> `WritePathDiag`（writepath）三个探针。
>
> 口径：分配为确定性指标（`GC.GetAllocatedBytesForCurrentThread`），耗时只作量级参考；
> 每段 N 次摊销、多轮交替；同机同批比值可比，跨机绝对值不可比。

## 1. 结论

最新批显示 PalORM 在绝大多数操作上已与 ADO.NET 持平或更优（BulkUpdate/MySQL 0.30×、
BulkUpdate/PG 0.57×、BulkDelete/PG 0.47×、UpsertBatch/PG 0.80×）。剩余差距只有两个形状：
**读/单行路径的常量级分配开销**（与行数无关，2000 与 20000 档数值几乎相同），以及
**少数单方言读路径 1.1~1.3× 的时延**。

本轮把常量级开销拆到段级，结论是：**读路径每操作固定成本的可减空间已接近下限**，
唯一超过 200 B T5d 线的单项在 QueryBuilder 链式路径（`OrderBy(Expression)` 的调用点
表达式树 512 B），而它需要公共 API 决策，本轮未动。

## 3. 本轮落地

### 读路径去 lambda（step13，−112 B/op，默认配置）

`GetAsync` / `GetAllAsync` 原经 `ExecuteReadPipelineAsync(async token => {...})`，
每次调用构造 async lambda（display class + 委托）并多一层 async 包装状态机。
本轮按写路径 P2-1 的既有形态改为直调：

- `ResilienceExecutor` 新增 **internal** 状态化重载
  `ExecuteAsync<TState, T>(TState state, Func<TState, CancellationToken, Task<T>> operation, ...)`，
  公共委托版转调它（`static (op, token) => op(token)` 由编译器缓存）。
  新增重载是 `internal`，**不进公共 API 面**。
- `GetAsync` / `GetAllAsync` 把命令文本、过滤子句等形态参数备齐后交给
  `ExecuteGetByKeyReadAsync` / `ExecuteGetAllReadAsync`；直通分支（策略直通或事务内）
  直接调 async 核心方法，非直通分支传值类型状态 + `static` lambda。

实测：默认配置 2696 → **2584**（−112）；直通弹性 2552 → **2368**（−184）；
长会话 1248 → **1136**（−112）。

> **低于 T5d 200 B 线的说明**：SQLite 下异步 I/O 同步完成，被省掉的主要是包装状态机
> 与闭包；PG/MySQL 的真实异步 I/O 下状态机会装箱，预期收益更大但**本轮未实测**
> （需 PerfHub 三方言批次 A/B）。据此保留该改动，若后续实测确认收益仍低于线，应回滚。

### 配套：架构不变式的忠实修法

`GetAllAsync` 的过滤子句求值被移入 `GetAllReadCoreAsync` 后，
`ArchitectureInvariantTests.AllEntityTableEntryPoints_RouteThroughDefaultFilter`
（源码扫描守卫，检查实体表入口方法体是否经过默认过滤路由）报 FAIL。
修法不是加"内核调用名凭证"（该测试对聚合家族有先例），而是把
`GetDefaultFilterWhereClause<T>()` **留在入口点求值**、以参数传入内核——
过滤决策仍由入口点持有，守卫强度不变。

## 4. 实测后不采纳

| 候选 | 实测 | 判定 |
|------|------|------|
| 写路径同形态状态化（`ExecuteWriteRowsAsync`） | 1168 vs 同态对照 1192 = **−24 B/行** | 低于线，回滚（`WritePathDiag`） |
| 惰性 `ResilienceExecutor` | 前提不成立：默认配置 `MaxRetries=3` + 熔断阈值 5，执行器默认即被使用 | 不适用 |
| 惰性读连接委托 | 单侧约 56 B × 2；且 `CreateReadOrPrimaryCommandAsync` 以 `_readConnProvider is null` 判定读路由回退，惰性化会静默改路由语义 | 风险高于收益，不做 |
| `ReusableQuerySlot` 惰性 | 对象 4 字段约 56 B | 低于线 |
| 只读标量/聚合路径状态化 | 与写路径同形，预估 −24 B 量级 | 低于线 |

**F1 的结论仍然成立**（会话构造可减上界 72 B），本轮补充一条：`ResilienceExecutor` 的
264 B 在默认配置下不可省——它不是"默认必建"的假设问题，而是默认配置确实启用了重试与熔断。

## 5. QueryBuilder 链式路径拆账（QueryBuilderPathDiag，同一会话形态）

| 段 | 分配 B/op |
|----|-----------|
| (1) `From<T>()` 仅建 builder | 1288（会话 968 + builder 与惰性槽约 320） |
| (2) `+ Where(FormattableString)` | 1608（+320） |
| (3) `+ OrderBy(表达式)` | 2408（**+800**） |
| (4) `+ Take(100)` | 2408（+0） |
| (5) 完整链式 + `ToListAsync`（执行） | 5672 |
| (6) 链式 + `FirstOrDefaultAsync`（执行） | 3528 |
| (7) 专用 `GetAsync`（执行） | 2696 |
| (8) 裸表达式树构造（`Expression<Func<T,long>> e = static x => x.id`） | **512** |
| (9) 裸 `FormattableString` 构造 | 88 |

**最大单项是 (8)：`OrderBy` 的 `Expression<Func<T,TKey>>` 形参让调用点每次构造表达式树，
512 B/op，且表达式树不缓存（`static` lambda 也只缓存委托，不缓存树）。**
`OrderBy` 单段 800 B 中，512 B 来自调用点、约 288 B 来自 `MemberResolver` 解析 +
`ClauseNode` 分配 + 字符串插值。

这解释了 KeysetPage 同时是"时延 1.09~1.17×"与"分配 +1.75~2.87 KB"的唯一一项：
链式路径 = 会话 968 + builder 320 + Where 320 + OrderBy 800。

### 提案（需公共 API 决策，本轮未动）

把排序/成员选择族（`OrderBy`/`ThenBy`/`GroupBy`/`WhereIn`/`WhereNotIn`/`Select`）的
`Expression<Func<T,TKey>>` 形参改为 `Func<T,TKey>` + `[CallerArgumentExpression]`：
`static x => x.id` 作为 `Func` 是编译器缓存的静态委托（0 B），源文本经
`CallerArgumentExpression` 以编译期常量字符串传入（0 B），列名从文本解析。

- 收益：每个链式查询 −512 B/op 起（`Select` 为每成员 512 B + 数组）。
- 风险：源码兼容但**二进制不兼容**；解析源文本的健壮性（括号、别名、非简单成员访问）
  需要在入口显式拒绝并给清晰错误；`MemberResolver` 的语义面需要重测。
- 判定门槛：>3 文件 + 新外部行为假设，按项目前置门要求先出风险/破坏面清单与 10 分钟探针。

## 6. 器材问题（影响结论可信度，非产品缺陷）

1. **BDN `ADO_NET_Update` 零参数**（`bench/PalORM.Benchmarks/01_CrudBenchmarks.cs:177`）：
   命令文本把常量内联为字面量（`SET status = 'U', total = 999 WHERE id = 5000`），
   而 PalORM 臂走 `Set()` 建 2 个参数。记录在案的分配比 8.27×（本批 6.97×）**不可比**。
   同一操作在 PerfHub（两臂都参数化）只有 1.41×。
   处置建议：ADO 臂补参数化并重录基线；或按 B95 纪律标 `Ratio=0` + `Note` 说明分母不干同一件事。
2. **PerfHub 的"每操作一会话"形态**：A9 命令复用、预编译在门禁里永不生效
   （晋升阈值 3 不可达）。探针显示长会话形态 1136 B/op 已优于 ADO 地板 1304 B/op（0.87×），
   而 PerfHub 报的是 2.07×。建议补一条长会话臂，把推荐用法纳入门禁。

## 8. 测量方法教训（本轮新增）

**同步 lambda 内的 `AsyncLocal` 写会造成 O(N²) 测量污染。** 首版探针用
"同步 lambda 内新建 `AsyncLocal` 并首次写"标定 `EnterReadOnly` 的 EC 拷贝成本，
实测 400,933 B/op。根因：同步 lambda 的写发生在测量循环自身的执行流上，
EC 的 map 条目只增不减，每次写克隆整张 map。产品侧写在 async 方法帧内、
方法返回时 EC 被还原，故 `会话 + GetAsync` 在 20000 次迭代下恒为 2584 B（不随迭代增长）。
对照：同一 `SessionOperationState` 复用实例 + `EnterReadOnly` = 0 B（短路生效）。
结论：`EnterReadOnly` 的 AsyncLocal 写在产品形态下远低于 200 B 线，不是可减项。

**陈旧基线对照教训**：写路径改动首次判定为"+32 B 回归"，实为拿改动后的 1168 与
2026-10-02 录制的基线文件 1136 比较，而非同态对照。同态对照实测 1192，
真实差值是 −24 B（小收益）。**结论：探针结论必须同态 A/B，不得跨时间点比绝对值。**
