## 二、新判定项逐项分析

### 2.1 链式查询族：KeysetPage / WhereIn / OwnedJsonQuery（SQLite 2000 档）

**读数**（err ≤1%，可判别）：

| 项 | ADO | PalORM | Δ | 比值 |
|---|---|---|---|---|
| KeysetPage | 55.5µs | 63.6µs | +8.1µs | 1.15× |
| WhereIn | 128.5µs | 139.0µs | +10.5µs | 1.08× |
| OwnedJsonQuery | 59.4µs | 76.2µs | +16.8µs | 1.28× |

**模式识别**：短操作（50~130µs 量级）固定客户端成本可见化——20000 档（QueryAll/
TenantCount/StreamAll）全部回落到 0.99~1.06×，证明差距不随行数缩放。
MySQL/PG 同项 err 7~8%（网络往返主导，step16-P2 定性外推），库侧不可测。

**构成**（step13 QueryBuilderPathDiag 已拆账）：链式构建 = From+builder ~320B +
Where 格式化 ~320B + **OrderBy(Expression) 表达式树 512B** + 执行段，合计比专用
GetAsync 路径多 ~3KB 分配。夹具三臂 SQL 已核同构（seek 谓词/LIMIT/列清单同款）。

**方案与判定**：
- 挂账提案维持：step13 §5 的表达式树 → `Func + [CallerArgumentExpression]`
  （调用点 -500B/op，11 处公共签名 + 转发 API 兼容 + span 解析器白名单，风险清单在档）。
- **收益口径修正**：该提案主要收益是分配（-500B/op），时延收益有限（表达式树构造
  CPU 远小于 8µs 差距主体）——8~17µs 的时延差主体是整条链式构建+物化管道的复合成本，
  与 step17-P0 结论同构（多小段累积，无单段 ≥150ns 级可砍）。
- **状态：维持挂账待裁决**（要不要为 -500B/op 的分配收益承担 11 处签名变更，属 API
  战略决策）。OwnedJsonQuery 的 16.8µs 中还含 OwnedJson emit 反序列化路径，若立项
  探针可一并分段。

### 2.2 TenantCount / TenantCountWhere（SQLite 2000 档）——唯一未解释的可判别差距

**读数**（err1%，可判别；20000 档回落至 0.99~1.03×）：

| 项 | ADO | PalORM | Δ | 比值 | 分配差 |
|---|---|---|---|---|---|
| TenantCount | 67.4µs | 80.8µs | +13.4µs | 1.20× | +1.1KB |
| TenantCountWhere | 69.5µs | 84.1µs | +14.6µs | 1.21× | +1.1KB |

**已排除的假设**（本轮逐一核对）：
1. SQL 不同构 ✗——产品 `CountAsync` 组合句缓存（PERF-002/T4/PG-5）与 ADO 臂
   `Dataset.WhereTenant` 同源同款 WHERE；参数名不影响 SQLite 计划。
2. WithTenant 克隆开销 ✗——返回 this，仅租约 + 两字段写（µs 级以下）。
3. 读标量路径缺直通分支 ✗——`ExecuteReadScalarAsync` 已有 IsPassThrough/事务直通
   （A2 同型）；且 GetByKey 全管道 6.3µs（含 SQLite 执行）反证弹性包装非 13µs 级。
4. 分配异常 ✗——+1.1KB 与 GetByKey 的 +0.9KB 同源（会话构造），非大项。

**矛盾点（为何必须探针）**：13.4µs 的客户端差 > GetByKey 整个操作的耗时（6.3µs），
已知管道小项（租约/缓存查找/参数绑定/弹性包装）合计解释不了；而 SQL 同构下数据库
执行时间应相同。归因链未闭合。

**方案：立项 P0 探针**（step17 模式复用，不改产品代码）：
TenantCountDiag 五段阶梯——① ADO 同款 SQL 直测 → ② 产品 CountAsync+WithTenant →
拆段：非租户 Count（4.3µs 量级）+ WithTenant 增量 / 组合句缓存命中路径 /
BindDefaultFilterParameters / 弹性非直通包装 / 数据库执行对照（同连接先后背靠背）。
若可砍段 ≥5µs → 立项修复；否则登记定性收档。

**B28 四问**：ORM 职责 ✓（租户自动过滤是安全特性，其性能成本归库）；AOT ✓；客户
自己做 ✗（裸 ADO 失去租户过滤安全性）；必需性 ✓（17% 是全景最大未解释差）。

### 2.3 TxBulkInsert / UpsertBatch（SQLite）~9%

**读数**：TxBulkInsert Δ1.48ms/16.63ms（1.09×，err1%）、UpsertBatch Δ1.42ms/16.18ms
（1.09×，err0%）。分配持平（0.94~0.96a）。

**已核**：批宽两侧一致（产品 min(999 参数, 5000 行)/5 列 = 199 行/语句 = 夹具
`EffectiveBatchRows`），非切分差异。740ns/行的 CPU 形态差在批量绑定路径
（MultiValueBulkInsert vs ADO 臂参数池直写）。

**判定：登记，低优先**。绝对量 1.4ms 在 16ms 操作上，且分配侧已持平；收益上限
~9% 且根因在毫秒级批量路径的绑定细节，探针成本与收益不成比例。若未来批量族再
立项（如 BulkUpdate/SQLite 的逐条裹事务形态升级）可顺带分段。

### 2.4 IncludeJoin（PostgreSQL）1.23×

**读数**：Δ128.8µs/569.1µs（err1%）。SQLite/MySQL 同项反向优（0.90×/0.73×）。

**判定：登记不改**。三臂装配策略不同构是 v2 既定标注（ADO JOIN+手工 / Dapper
multi-mapping / PalORM Include JOIN+装配），不同构项比值不构成优化目标（B95 同族
纪律）；两方言反向优证明 Include 装配本身不慢，PG 特有形态差在"不同构"的解释面内。

### 2.5 SessionBatchInserts（SQLite）分配 +13.3KB

**读数**：40.9KB vs 27.6KB（1.48a，err9% 弱判别）；时延 1.10×（err9% 弱）。

**判定：登记 step14 遗留小项**。SQLite 回退路径（无 DbBatch 支持，单命令复用逐条）
每条 ~666B 分配差 × 20 条；绝对量 13KB/操作，不立项。

## 三、分配侧全景结论

PalORM 分配劣势集中在**单行短操作的会话构造**（968B，F1 证伪：可减上界 72B <
200B T5d 线）与 Count 族（同源）；链式族另有构建 ~3KB（其中 OrderBy 表达式树
512B 是唯一已量化、方案完备的单项）。批量族分配全面持平或大幅优（PG UpsertBatch
0.19a、BulkDelete 0.11a）。**分配侧无新空间，除挂账的 OrderBy 提案外全部定案。**

## 四、时延侧全景结论

SQLite 本地档可判别的剩余差距按量级排序：

| 差距 | 量级 | 状态 |
|---|---|---|
| TxRollback / TxHundredInserts | ~580~900ns/行 | step17-P0 收档（结构性） |
| 链式族（KeysetPage/WhereIn/OwnedJson） | 8~17µs/操作 | 本轮判定：挂账提案吃分配、时延主体为链式复合成本 |
| **TenantCount 族** | **13~15µs/操作** | **未解释，本轮唯一新立项（P0 探针）** |
| TxBulkInsert/UpsertBatch | ~9%（1.4ms/17ms） | 登记低优先 |
| 单行 CRUD 族 | 0.4~1µs/操作 | step16/17 定案 |

MySQL/PG 档的 err 7~9% 项全部为网络往返主导（step16-P2 定性），库侧不可测。
