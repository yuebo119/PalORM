# PalORM 深检引擎（deep-check-engine v1.0）

> audit 与 review 共用的检查引擎——同一套流定义、误判库、视角账本、验证规则。
> 两个入口是同一引擎的两个 profile：**review profile**（每次实质提交，diff 范围）与
> **audit profile**（里程碑节点，全量 + 趋势 + 预判）。触发、范围、产出格式见各 profile 文件；
> 本文件只定义"怎么查"，不定义"何时查、产出什么"。
> **检查依据**：[`docs/编码规范.md`](../docs/编码规范.md)（167 条 STD 规则 × 17 类）← [`docs/踩坑目录.md`](../docs/踩坑目录.md)（302 项陷阱）

## 执行前强制项（两 profile 通用）

1. 加载 [`audit-system/known-false-positives.md`](audit-system/known-false-positives.md)（误判知识库，只增不删）
2. 读取 [`audit-system/perspective-stats.md`](audit-system/perspective-stats.md) 最近 3 轮 → P3 自适应视角选择
3. `bash scripts/review-snapshot.sh` → 锚定 commit + 基线数据
4. 声明范围：必须评审 / 明确不评审 / 抽样策略——三项缺一不可

## 七流定义（检查对象 = 手写代码；`*.g.cs` 仅验语义不评风格）

| 流 | 检查焦点 | PalORM 专项 |
|------|---------|-----------|
| 架构流 | Provider 依赖方向·命名空间一致性·循环依赖 | 对照 docs/架构设计.md |
| 安全流 | SQL 注入·输入校验·密钥泄露 | FormattableString 参数化查询 |
| 资源流 | IDisposable/IAsyncDisposable·DbConnection 释放·连接池 | ADO.NET 连接管理·租约 |
| 并发流 | lock/共享状态·竞态·async void | SessionOperationState 门禁覆盖 |
| 错误流 | catch(Exception) OCE 过滤·异常类型 | 主异常保留（清理异常挂 Exception.Data） |
| AOT流 | IsAotCompatible·STJ 源生成·零反射·零 Expression.Compile() | 源生成器覆盖完整性 |
| 生成语义流 | 编译期生成物与运行时假设的一致性 | **大部分已机械化，见下** |

## 核心原则

```
1. 先发现，后判断——禁止在信息不完整时下结论
2. 证据驱动——每项发现标注可信度（✅⚠❓）+ 至少 1 个信息源
3. 逐行优于抽样——抽样结论必须标注 ⚠
4. 实现质量 ≥ 架构设计——不因"架构清晰"而忽略"配置缺失"
5. 有害度驱动优先级——危害 × 复杂度，不是"容不容易修"
6. 区分"没找到"和"不存在"——零发现必须附覆盖度证据
```

## 交叉验证与 [推断] 零容忍

| 发现级别 | 最低验证要求 |
|:--------:|-------------|
| P0/P1 | Read 源码 + 探针实证（编译探针/真库用例/生成物断言/`dotnet build`） |
| P2 | Read 源码 + grep 交叉验证 |
| P3 | 至少 1 个信息源（标注 ⚠） |

**[推断] 零容忍**（教训：ITM-317/318 挂账一轮才实测收口，ITM-301 当轮编译探针直接定 P0）：

1. P0/P1 发现禁止以 ⚠[推断] 状态定稿。定稿前必须转化为可执行探针之一：
   - **编译探针**：/tmp 最小工程复现目标 API → 编译通过/失败
   - **真库用例**：写入 Integration.Tests，CI 服务容器（postgres:17 + mysql:8.4 + 三平台 AOT）执行；本机不可达标注"待 CI 证实"
   - **生成物断言**：SourceGen 类推断写入 SourceGen.Tests 断言或快照
2. 探针结果（证实/证伪）写入报告信息源列；证伪项转误判知识库候选模式。
3. P2/P3 允许 [推断] 定稿，行动项标注"修复前先补探针证实"。

## 影响判定（危害 × 复杂度矩阵）

| | 高危害 | 中危害 | 低危害 |
|------|:------:|:------:|:------:|
| **易修复**（< 1h） | P0 紧急 | P1 近期 | P2 |

## 发现下沉审查（收口时强制，两 profile 通用）

> 原则：评审证明会反复出现的发现类别，逐一变成机械防线；评审收缩到机器构不着的语义判断。
> 阶梯：提示词 → 脚本门禁（gate-check/assertion-strength-check） → Roslyn 诊断（PALORM0xx） → 测试（快照/对称性/架构） → 类型系统。

每个 P0/P1 发现收口时必须回答：

| 问题 | 是 → 动作 |
|------|----------|
| 可被 grep/正则机械检测？ | 下沉为 gate-check.sh G 项或专项脚本 |
| 可在编译期由分析器捕获？ | 下沉为 PALORM0xx 诊断 + 负向测试 |
| 可被生成物断言/快照/对称性测试捕获？ | 下沉为 SourceGen.Tests 用例 |
| 属于"所有 X 必须经过 Y"的架构不变式？ | 下沉为架构测试（ArchitectureInvariantTests） |
| 都不是（需语义判断）？ | 保留为提示词检查项 + 误判库模式 |

下沉结果记录在行动项账本的「下沉审查」段（模板见 action-items-template.md）。

## 质量指标（替代主观评分）

> 三层加权综合分与十维度小数分已废止——评分不可复现且与实现质量脱节（误判模式 6 的系统性根源）。
> 两 profile 统一记录以下四项客观指标至 [`metrics.md`](metrics.md)：

| 指标 | 定义 | 数据源 |
|------|------|--------|
| 缺陷逃逸率 | 真库/CI/用户发现而深检未发现的缺陷数（每轮） | metrics.md 逃逸账本 |
| 复发率 | 同类 ITM（同根因分类）再次出现的数量 | 行动项账本 ID 对照 |
| 按流发现密度 | 每流每千行审查代码的 P0-P2 发现数 | perspective-stats.md |
| P0/P1 修复时延 | 报告定稿 → 修复提交的 commit 间隔 | git log |

审计 profile 的趋势判断基于这四项指标的轮次对比，不再输出综合分。

## 历史教训速查卡

| 如果遇到… | 记住… |
|-----------------|--------|
| "grep 显示有 N 处 X" | grep 做定位，不做计数判断。逐行读后再下结论 |
| "这个分析器应该会在 X 时报错" | dotnet build 验证。不许猜分析器行为 |
| "代码看起来有并发竞态" | 读完整 lock 块。不许读半截下结论 |
| "这段代码缺异常过滤" | 检查上下文。可能有前置 catch(OCE){throw;} |
| "这个修复很简单，P2 吧" | 判断危害，不是复杂度。连接泄漏不是 P2 |
| "Core 层应该加个 Helper" | Core 只放接口+record+enum。Helper 放 Provider 或独立工具类 |
| "这个文件可以移到其他 Provider" | 检查是否破坏 Provider 独立性 |
| "架构分层很清晰" | 检查配置完整度和资源释放。观感不等于实现质量 |
| "Provider 间代码重复" | 检查是否是方言差异导致的刻意独立（误判模式 P2） |
| "*.g.cs 文件有问题" | 排除源生成器生成文件。只评手写代码 |
| "SQLite 测试过了" | SQLite-only 测试掩蔽 MySQL/PG 缺陷（BulkDelete 参数重名教训）——方言敏感变更必须三方言验证 |
| "测试里构造了这个异常" | 手工 `new XxxException(code)` 走不到驱动的真实错误码填充路径（ITM-403：扩展码恒 0，主码判定假绿）。断言驱动异常行为的探针必须真库触发 |
| "上一轮已经修过这类问题" | 区分补丁与根治：修复只覆盖已发现的触发形态（如逐子句前缀）= 补丁，同根因换个入口即复发（ITM-307→401 两轮）；根治 = 让该类形态在结构上不可表达（如 WHERE 统一括组）。评审补丁式修复时必答"还有哪些入口能触发同根因" |

## 子代理执行纪律（会话中断三次丢失全部子代理进度的教训）

1. **探针先行，委托靠后**：能被一个探针（DryRun SQL / 真库最小用例 / dotnet build）直接证实或证伪的疑点，主线程立即做——本轮最有价值的 P1（ITM-401）来自主线程 5 分钟探针，而三个后台评审子代理因会话中断全部丢失。
2. 子代理只委托**边界清晰的全量枚举面**（逐 catch 判定、逐文件逐行流），且提示词必须自包含（误判库摘要 + 判定规则内嵌），使其结论不依赖主线程上下文。
3. 主线程在等待子代理期间持续做增量探针，不空转；子代理丢失时按其范围重新派发，不尝试恢复半成品。
