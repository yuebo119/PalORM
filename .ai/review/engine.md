# PalORM Review 检查引擎（review/engine v2.3）

> **review 系统的检查引擎**——审计与评审已彻底合并为单一 review 系统（2026-07-19），
> 入口与触发档位见 [`prompt.md`](prompt.md)；本文件只定义"怎么查"。
> **宗旨：质量为先**（2026-07-19 裁决）。所有优化都在保持最高质量的前提下进行——
> 默认执行方式是**地毯式逐行、逐文件阅读全部范围内代码**；探针、机械防线、档位分级
> 都是在此之上叠加的证据强化与流程编排，**不是阅读的替代品**。
> **检查依据**：[`docs/编码规范.md`](../../docs/编码规范.md)（167 条 STD 规则 × 17 类）← [`docs/踩坑目录.md`](../../docs/踩坑目录.md)（302 项陷阱）

## 执行前强制项

1. `bash scripts/gate-check.sh` 全绿（门禁是前置，引擎不重复门禁已覆盖的检查）
2. 加载 [`known-false-positives.md`](known-false-positives.md)（误判知识库，只增不删）
3. `bash scripts/review-snapshot.sh` → 锚定 commit + 基线数据
4. 声明范围：必须检查 / 明确不检查 / 抽样策略——三项缺一不可

## 地毯式逐行 × 探针并用（质量为先裁决）

> 两者是**串联关系，不是二选一**：逐行负责"发现面"（不遗漏），探针负责"证据面"（不误判）。
> v2.0 曾把逐行"降级为找疑点的手段"——该表述已废止：它以速度换质量，违反宗旨。

1. **逐行是默认**：范围内每个手写 `.cs` 文件逐行读完，七流视角同时在场；范围由档位决定
   （diff 档=触及文件全文，全量/里程碑档=src/ 全部手写代码），范围内不抽样、不跳读。
   抽样只允许出现在"明确不检查"声明覆盖的范围外区域，且结论必须标 ⚠。
2. **探针是定稿要求**：逐行发现的每个 P0-P2 疑点必须转化为可执行探针证实或证伪
   （[推断]零容忍）。每流的标准探针形态：
   安全流=构造攻击输入真库跑；生成语义流=快照 diff + 编译探针；并发流=交错断言用例；
   错误流=真库触发异常矩阵；资源流=泄漏路径最小复现；AOT流=publish+原生运行；架构流=依赖 grep+架构测试。
3. **机械防线先跑**：快照/对称性/架构/性质测试与门禁在逐行**之前**执行——它们的失败直接
   给出逐行的重点区域；它们的通过**不豁免**对应区域的逐行（防线只覆盖已知形态，
   逐行负责未知形态——OrWhere 双变体正是防线通过后逐行+探针发现的）。
4. 探针骨架用 `bash scripts/probe-template.sh <名称>` 生成（/tmp 最小工程引用本仓库项目），成本 ~30 秒。
5. **覆盖度可审计**：报告段 1 声明"逐行覆盖的文件清单与行数"；零发现的流必须附
   覆盖度证据（读了哪些文件、跑了哪些探针）——"没找到"和"不存在"的区分靠这条成立。

## 七流定义（检查对象 = 手写代码；`*.g.cs` 仅验语义不评风格）

| 流 | 检查焦点 | PalORM 专项 |
|------|---------|-----------|
| 架构流 | Provider 依赖方向·命名空间一致性·循环依赖 | 对照 docs/架构设计.md |
| 安全流 | SQL 注入·输入校验·密钥泄露 | FormattableString 参数化查询 |
| 资源流 | IDisposable/IAsyncDisposable·DbConnection 释放·连接池 | ADO.NET 连接管理·租约 |
| 并发流 | lock/共享状态·竞态·async void | SessionOperationState 门禁覆盖 |
| 错误流 | catch(Exception) OCE 过滤·异常类型 | 主异常保留（清理异常挂 Exception.Data） |
| AOT流 | IsAotCompatible·STJ 源生成·零反射·零 Expression.Compile() | 源生成器覆盖完整性 |
| 生成语义流 | 编译期生成物与运行时假设的一致性 | **大部分已机械化，见下** |

## 并行地毯协议（v2.2——速度靠并行取得，不靠缩减覆盖）

> 全量/里程碑档的 src/ 约 8000+ 行。串行逐行是速度瓶颈；分片并行把墙钟时间除以片数，
> 每片内部仍是完整地毯——总阅读量不变，质量不降。

1. `bash scripts/review-scope.sh [--diff] [--partitions N]` 生成**应读清单 + 按行数均衡分片 + 覆盖度账本模板**。
2. 每片派一个子代理，提示词自包含五要素：①片内文件清单（逐行读完）②七流问题卡全文（见下）
   ③误判库速版（15 模式一行摘要）④产出格式（疑点表：位置/流/描述/建议探针）⑤范围与预算边界（见下）。
3. **子代理只产疑点不定级**——定级、探针、定稿门收敛到主线程统一执行（避免各片标准漂移）。
4. 主线程在等待期间执行：机械防线全跑 + 跨片关注点（分片切不开的全局不变式：
   过滤覆盖完整性、参数编号空间、注册表键集、跨文件调用契约）。
5. 会话中断纪律：子代理丢失按片重派（片即范围声明，可精确重发）；主线程增量成果随做随记。
6. 覆盖度账本逐文件勾销；未勾销文件出现在报告 = 报告视为草稿。

### 子代理范围与预算边界（v2.3——0937e7f 轮片 2 失控教训）

> 教训：片 2 读完清单后持续做无上界的"反证性交叉阅读"（读他片文件核实疑点），
> 墙钟时间数倍于其余三片，最终靠主线程发消息催收才交付。边界宽松即可——
> 反证搜索本身有价值（该轮多个疑点因它免于误报），要限的是"无上界"，不是"做反证"。

1. **主职责是片内清单**：清单读完 = 交付条件达成。清单外的反证性阅读允许且鼓励
   （查前置 catch/幂等保护/调用方契约是定稿门要求），但属于"锦上添花"——
   反证做不完就把疑点标 ❓ 移交主线程，不追求片内自证完备。
2. **软预算**：片外阅读量以不超过片内清单行数的一半为参考线（约 1000 行）。
   接近参考线时优先收口输出，把未完成的反证写进疑点表"建议探针"列。
3. **主线程催收时限**：任一分片耗时超过已交付分片平均耗时的 3 倍仍未完成，
   主线程 SendMessage 催收（"基于已读内容立即输出交付物，未读完的如实标注"）——
   不等到无限期。催收产出按正常交付处理，未覆盖部分记入报告盲区声明。
4. **等待姿势**：主线程等完成通知，不做轮询式阻塞等待（超时回吐的中间转录
   既慢又耗上下文）；等待期即第 4 条的机械防线与跨片不变式窗口。

## 七流问题卡（v2.2——逐行时"带着问题读"，发现率与精准度的主杠杆）

> 逐行不是漫读。每流一张卡：读到对应形态时逐问核对。卡内问题全部来自本项目真实 ITM——
> 每条都抓到过真缺陷。新根因类出现时向对应卡追加一问（下沉审查表新增动作）。

**架构流卡**：这个公共入口经过默认过滤路由了吗（ITM-302/404）？partial 文件里的入口登记了吗（405）？
这个"对称"实现三方言真的对称吗——差异有登记吗（303/304）？死接口成员有 Obsolete+期限吗（331）？

**安全流卡**：这个插值进 SQL 的值是编译期常量还是运行时可控（标识符必须走 QuoteIdentifier）？
Quote 转义覆盖内嵌引用符吗？用户条件括组了吗——OR 能穿透默认过滤吗（307/401）？
异常消息/日志里有连接串或 PII 吗？NUL/注释定界符拒绝了吗（212）？

**资源流卡**：这个 Create 后抛异常的路径，资源谁释放（CreateAsync 泄漏教训）？租约的所有权
转移点明确吗（operationTransferred 形态）？CTS 有 using 吗？枚举器被放弃时租约会退出吗（330）？

**并发流卡**：这个可变字段的写入在门禁/锁内吗（AddInterceptor 形态）？两个 Volatile 字段的
发布顺序读方真的依赖吗？AsyncLocal 跨事务流泄漏吗？struct 副本共享的引用字段写时复制了吗（QUERY-001/308）？

**错误流卡**：这个 catch(Exception) 的 OCE 过滤在哪（三种合规形态都查过了吗）？清理异常
挂 Data 还是覆盖了主异常？这个错误码判定在真驱动路径验证过吗——手工构造异常是假绿（403）？
超时与取消可区分吗（206）？

**AOT 流卡**：这个新 API 走反射/MakeGeneric/Expression.Compile 了吗？STJ 调用传 JsonTypeInfo 了吗？
抑制了 IL 警告吗？生成物在三平台 AOT 原生路径真跑过吗（E2）？

**生成语义流卡**：这个列集合改动，三序（SQL 列序/RowFactory 序号/Bind 参数序）同步了吗？
新特性组合进快照实体了吗（[Timestamp] 盲区教训 402）？Emitter 字符串拼接对特殊字符转义了吗（410/411）？
这个注解声称的行为，DDL/INSERT/物化三处一致吗（402 的 NOT NULL 无 DEFAULT 形态）？

## 核心原则

```
0. 质量为先——一切优化（探针/防线/档位/并行）都在保持最高质量前提下进行，不以牺牲覆盖换速度
1. 先发现，后判断——禁止在信息不完整时下结论
2. 证据驱动——每项发现标注可信度（✅⚠❓）+ 至少 1 个信息源
3. 地毯式逐行是默认——范围内逐文件逐行读完；抽样仅限声明的范围外区域且结论标 ⚠
4. 实现质量 ≥ 架构设计——不因"架构清晰"而忽略"配置缺失"
5. 有害度驱动优先级——危害 × 复杂度，不是"容不容易修"
6. 区分"没找到"和"不存在"——零发现必须附覆盖度证据
```

## 误判定稿门（v2.2 强化——三问齐备才定稿）

每条 P0-P2 候选定稿前过三问，任一不过即降级或转探针：

1. **误判库对照**：逐条对照模式 ID，报告段 3 记"已对照模式"列（如"已排除 1/3/P7"）。
2. **反证搜索**：花一次搜索找"这不是缺陷"的证据——前置 catch？幂等保护？ModuleInitializer 填充？
   文档声明的契约？调用方约束？（误判库 15 模式里 11 个的根因是没做这一步）
3. **可复现表述**：发现描述必须含触发路径（"调用 X 传 Y 则 Z"），写不出触发路径的降 P3 或标 ❓。

被探针证伪的候选计入 metrics"证伪数"列并评估转误判库新模式——证伪数下降才证明误判库在生效。

## 证据分级与验证要求（v2.2——每级配默认探针形态，降低达标成本）

| 发现级别 | 最低验证要求 | 默认探针形态（probe-template.sh 30 秒起步） |
|:--------:|-------------|------|
| P0/P1 | Read 源码 + 探针实证 | 按流选：DryRun SQL / 真库最小用例 / 编译探针 / AOT publish+run |
| P2 | Read 源码 + grep 交叉验证 | 允许 [推断] 定稿，行动项标"修复前先补探针" |
| P3 | 至少 1 个信息源（标注 ⚠） | — |

**[推断] 零容忍**（教训：ITM-317/318 挂账一轮才实测收口，ITM-301 当轮编译探针直接定 P0）：

1. P0/P1 发现禁止以 ⚠[推断] 状态定稿。定稿前必须转化为可执行探针之一：
   - **编译探针**：/tmp 最小工程复现目标 API → 编译通过/失败
   - **真库用例**：写入 Integration.Tests，CI 服务容器（postgres:17 + mysql:8.4 + 三平台 AOT）执行；本机不可达标注"待 CI 证实"
   - **生成物断言**：SourceGen 类推断写入 SourceGen.Tests 断言或快照
2. 探针结果（证实/证伪）写入报告信息源列；证伪项转误判知识库候选模式。
3. P2/P3 允许 [推断] 定稿，行动项标注"修复前先补探针证实"。

## 影响判定（危害 × 复杂度矩阵）

| | 高危害 | 中危害 | 低危害 |
|------|:------:|:------:|:------:|
| **易修复**（< 1h） | P0 紧急 | P1 近期 | P2 |
| **中等**（1-4h） | P1 近期 | P2 | P3 |
| **难修复**（> 4h） | P2 | P3 | 评估（产出 ADR） |

## 发现下沉审查（收口时强制）

> 原则：评审证明会反复出现的发现类别，逐一变成机械防线；评审收缩到机器构不着的语义判断。
> 阶梯：提示词 → 脚本门禁（gate-check/assertion-strength-check） → Roslyn 诊断（PALORM0xx） → 测试（快照/对称性/架构） → 类型系统。

每个 P0/P1 发现收口时必须回答：

| 问题 | 是 → 动作 |
|------|----------|
| 可被 grep/正则机械检测？ | 下沉为 gate-check.sh G 项或专项脚本 |
| 可在编译期由分析器捕获？ | 下沉为 PALORM0xx 诊断 + 负向测试 |
| 可被生成物断言/快照/对称性测试捕获？ | 下沉为 SourceGen.Tests 用例 |
| 属于"所有 X 必须经过 Y"的架构不变式？ | 下沉为架构测试（ArchitectureInvariantTests） |
| 都不是（需语义判断）？ | 保留为提示词检查项 + 误判库模式 |

P0/P1 收口的附加动作：该发现所属根因类若是新类，向对应**七流问题卡**追加一问——
问题卡是逐行的发现率杠杆，每个真缺陷都应让下一轮逐行多一双眼睛。

下沉结果记录在行动项账本的「下沉审查」段（模板见 templates/action-items.md）。

## 质量指标（替代主观评分）

> 三层加权综合分与十维度小数分已废止——评分不可复现且与实现质量脱节（误判模式 6 的系统性根源）。
> 每轮记录以下指标至 [`metrics.md`](metrics.md)：

| 指标 | 定义 | 数据源 |
|------|------|--------|
| 缺陷逃逸率 | 真库/CI/用户发现而深检未发现的缺陷数（每轮） | metrics.md 逃逸账本 |

## 历史教训速查卡

| 如果遇到… | 记住… |
|-----------------|--------|
| "grep 显示有 N 处 X" | grep 做定位，不做计数判断。逐行读后再下结论 |
| "这个分析器应该会在 X 时报错" | dotnet build 验证。不许猜分析器行为 |
| "代码看起来有并发竞态" | 读完整 lock 块。不许读半截下结论 |
| "这段代码缺异常过滤" | 检查上下文。可能有前置 catch(OCE){throw;} |
| "这个修复很简单，P2 吧" | 判断危害，不是复杂度。连接泄漏不是 P2 |
| "Core 层应该加个 Helper" | Core 只放接口+record+enum。Helper 放 Provider 或独立工具类 |
| "这个文件可以移到其他 Provider" | 检查是否破坏 Provider 独立性 |
| "架构分层很清晰" | 检查配置完整度和资源释放。观感不等于实现质量 |
| "Provider 间代码重复" | 检查是否是方言差异导致的刻意独立（误判模式 P2） |
| "*.g.cs 文件有问题" | 排除源生成器生成文件。只评手写代码 |
| "SQLite 测试过了" | SQLite-only 测试掩蔽 MySQL/PG 缺陷（BulkDelete 参数重名教训）——方言敏感变更必须三方言验证 |
| "测试里构造了这个异常" | 手工 `new XxxException(code)` 走不到驱动的真实错误码填充路径（ITM-403：扩展码恒 0，主码判定假绿）。断言驱动异常行为的探针必须真库触发 |
| "上一轮已经修过这类问题" | 区分补丁与根治：修复只覆盖已发现的触发形态（如逐子句前缀）= 补丁，同根因换个入口即复发（ITM-307→401 两轮）；根治 = 让该类形态在结构上不可表达（如 WHERE 统一括组）。评审补丁式修复时必答"还有哪些入口能触发同根因" |

## 子代理执行纪律（会话中断三次丢失全部子代理进度的教训）

1. **探针先行，委托靠后**：能被一个探针（DryRun SQL / 真库最小用例 / dotnet build）直接证实或证伪的疑点，主线程立即做——本轮最有价值的 P1（ITM-401）来自主线程 5 分钟探针，而三个后台评审子代理因会话中断全部丢失。
2. 子代理只委托**边界清晰的全量枚举面**（逐 catch 判定、逐文件逐行流），且提示词必须自包含（误判库摘要 + 判定规则内嵌），使其结论不依赖主线程上下文。
3. 主线程在等待子代理期间持续做增量探针，不空转；子代理丢失时按其范围重新派发，不尝试恢复半成品。
4. **催收优于苦等**（0937e7f 轮补充）：子代理有进展但迟迟不收口（如无上界的片外交叉阅读），
   与死循环不同——催收即可（"基于已读内容立即输出，未完成部分如实标注"），
   不必重派也不必等它自然结束。催收阈值与预算边界见「并行地毯协议」v2.3 段。
5. 中断后恢复的子代理，其交付物按"覆盖度自报 + 主线程抽查复核"处理（对其高危疑点
   至少一个探针验证），并在报告局限声明中标注——不强制整片重派（重派成本 > 抽查成本
   时抽查即可，0937e7f 轮片 2 的两个高危疑点探针复核均证实，交叉可信）。
