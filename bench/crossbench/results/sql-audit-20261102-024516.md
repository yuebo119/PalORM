# SQL 文本审计（2026-11-02 02:46:36）

> 审计对象：CrossBench 九组（ADO.NET 地板 + 八个 ORM）× 方言 SQLite / MySQL / PostgreSQL × 17 操作，行数档 2,000。
> 判据：测试对象是 ORM 的 SQL 生成能力。取「实际执行过的 SQL 文本」为证据——同方言内归一化后文本完全相同的组，要么共用同一 SQL 真源（手写模板或同一驱动路径），要么各自生成了同形 SQL；跨组同文本表把两者并列，判读见第三节。
> 本批不参与计时：每条操作只执行一次，与预热/计时/采样协议无关。

## 一、方法与边界

| 组 | 捕获通道 | 覆盖 |
|---|---|---|
| ADO_NET | 宿主连接包装层（`DbCommand.CommandText` 赋值即记录） | 除 MySQL/PostgreSQL 的批量插入外全部操作——该地板的批量走驱动级协议（`MySqlBulkCopy` / Npgsql binary COPY），按 provider 具体类型强转，包装层不可用，见第二节 |
| Dapper | 同左 | 全部操作（批量走 `BulkSql` 多值 INSERT，不经驱动批量协议） |
| Dapper.AOT | 同左 | 非事务操作为主；事务内走 `Command<T>` 的三条操作（TxSingleInsert / TxHundredInserts / EnumInserts）不可包装——Dapper.AOT 构造 `Command<T>` 时校验`transaction.Connection == connection`，包装层必然不等（上游约束，见第二节） |
| PalORM | 同左 | 除 PostgreSQL 批量插入（要求具体 `NpgsqlConnection`）外全部操作；MySQL 批量在服务端 `local_infile` 开启时走 `MySqlBulkCopy`，同样不可包装——本批该开关为关闭，产品回退多值 INSERT，已捕获 |
| RepoDB | 未接入 | 该组无可用通道：连接包装层被 provider 类型解析拒绝（MissingMappingException）；全局 `ITrace` 只覆盖同步路径——1.17.0 的 `Tracer.InvokeBeforeExecutionAsync` 在无 per-call trace 时对 null Task 执行 await，异步 API 必抛 NRE（2026-11-02 单操作探针复现，脚本未随批入库）。SQL 形态以源码审计为准，见第二节 |
| FreeSql | `fsql.Aop.CommandAfter` | 除批量插入外全部操作（批量插入走 provider 私有通道，AOP 不触发，见第二节） |
| SqlSugar | `db.Aop.OnLogExecuting`（每次操作前重装） | 全部操作；`Fastest`/BulkCopy 路径（BulkInsert / BulkUpdate）只留库自有日志（矩阵标「非 SQL 日志」） |
| EF Core | `DbContextOptionsBuilder.LogTo`（`CommandExecuted` 事件） | 全部操作 |
| linq2db | `DataConnection.LastQuery`（操作后读取） | 全部操作；只保留最后一条语句（分块批删/批改只呈现末块形态） |

归一化口径（只用于「是否同一文本」的比较；报告里的语句列展示归一化结果，原始语句见同名 JSON）：标识符引号剥离、字符串/数字字面量替换为 `?`、参数占位（`@x` / `$1` / `:x`）统一为 `?`、标识符整体保留（`perf_s1` / `INT8` 不被数字规则拆开）、注释与空白折叠、去尾分号。别名不剥离——各组的别名风格恰是生成特征。

剔除项：连接初始化 `PRAGMA`（SQLite 会话初始化）与 `SELECT @@local_infile`（MySQL 批量能力探测），两者属臂/会话初始化而非操作 SQL。

落盘口径：JSON 的 `Statements` 按原文去重（同文只留一条）、单条超 8000 字符截断，捕获次数另存 `CaptureCount`。报告里的「条数」是**捕获次数**（命令文本赋值 / 库回调的次数），不是执行次数——命令复用路径（ADO / PalORM 的复用槽）一次捕获对应多次执行，逐行新建命令的组（Dapper / EF）两者相同。

## 三、读法

- **手写三组（ADO_NET / Dapper / Dapper.AOT）同文本是设计如此**：单语句操作共用同一份字面 SQL，批量操作共用 `BulkSql` 模板。它们等于同一个「手写 SQL」样本的三次测量，横评里不构成三个独立的 SQL 生成能力样本——报告说明列应按此注明（既知口径偏差）。
- **ORM 组与地板同文本**（如 PalORM 的主键直查/更新与 ADO 同簇）说明该组生成的 SQL 与手写最优形态同形，属正面证据；判据是「它的别名风格与参数命名是否也与手写组一致」——若一致到连别名都相同，才说明疑似抄模板。
- **单组独有文本 + 形态符合该库惯用写法**（EF 的 `INSERT … VALUES … RETURNING`、linq2db 的 `MERGE`、FreeSql 的临时表 + UPDATE）是该组确实在用自身 API 生成 SQL 的直接证据。
- **「非 SQL 日志」格**（如 SqlSugar 的 `Begin BulkCopy name:…`）表示该路径不经 SQL 文本通道（驱动级批量协议），库只留下自有日志——这本身是该路径不走 SQL 生成的证据。
- **EF Core 的 `UpsertBatch` 只出现 SELECT**：本夹具的种子行值未变，EF 的「查出已存在行 → 改属性 → SaveChanges」路径判定无改动、不发写语句。该格不代表 EF 的写路径成本，横评时需注明——审计只呈现「实际执行了什么」，不为各组补 SQL。
- 各组的捕获通道（连接包装层 / AOP / 日志事件 / LastQuery）都只旁路读取，不回写 SQL：捕获到的文本即被测代码实际交给驱动的内容。
